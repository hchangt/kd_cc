§1 Node.js Architecture

Node.js is not just another runtime — it's an architectural decision. When Ryan Dahl introduced it in 2009, he was solving a concrete problem: traditional servers blocked on I/O. Every database query, every file read, every network call parked a thread. Threads are expensive — each one costs ~2MB of stack space. At 10,000 concurrent connections, you're already at 20GB of RAM just for stack space.

Node's answer: one thread, non-blocking everything. If you're coming from Python, this feels strange at first. But once you internalize it, it's elegant.

The Event Loop Deep Dive

The event loop is not a simple queue. It's a sequence of phases, each draining its own queue before moving to the next. Understanding this prevents entire classes of bugs.

ℹ️
Info — microtasks jump the queue

process.nextTick() and resolved Promise callbacks (microtasks) execute between every phase transition — even between callbacks within the same phase. This means: if you recursively call process.nextTick(), you can starve the I/O poll phase forever. Prefer setImmediate() for deferring work inside callbacks.

libuv Under the Hood

libuv is the C library that gives Node its superpowers. It provides:

  • The event loop itself — cross-platform abstraction over epoll (Linux), kqueue (macOS), IOCP (Windows)
  • A thread pool (default 4, max 1024 via UV_THREADPOOL_SIZE) for operations that don't have async kernel equivalents: DNS lookups, filesystem calls, some crypto ops
  • Async TCP/UDP sockets, timers, child process management, signal handling

The critical insight: not all async in Node is truly non-blocking at the OS level. When you call fs.readFile(), libuv dispatches it to its thread pool. The thread pool thread blocks — but your main thread doesn't. You get the illusion of non-blocking I/O even for operations the OS handles synchronously.

typescript libuv-threadpool.ts 
import { readFile } from 'fs/promises'

// This is NOT blocking the main thread:
// libuv pushes the disk read to its thread pool (UV_THREADPOOL_SIZE threads)
// When done, the callback is queued back to the event loop poll phase
const data = await readFile('/large-file.bin')

// But this DOES block:
import { readFileSync } from 'fs'
const blocking = readFileSync('/large-file.bin') // main thread frozen here

// Tune thread pool size for I/O-heavy workloads
// process.env.UV_THREADPOOL_SIZE = '16' (set before requiring any modules)

Worker Threads for CPU-Intensive Tasks

The event loop is single-threaded, which means CPU-bound code blocks everyone. Compressing an image, computing a hash over 1GB of data, running ML inference — these will freeze your server while they run. The solution: Worker Threads.

typescript worker-pool.ts 
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads'
import { cpus } from 'os'

// ── worker.ts (runs in separate thread) ──────────────────────────────
if (!isMainThread) {
  const { data }: { data: number[] } = workerData
  // CPU-intensive: this thread can block without affecting main thread
  const result = data.reduce((acc, n) => acc + Math.sqrt(n), 0)
  parentPort?.postMessage(result)
}

// ── main.ts ──────────────────────────────────────────────────────────
interface WorkerResult {
  value: number
}

function runWorker(data: number[]): Promise<number> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(__filename, { workerData: { data } })
    worker.on('message', (result: number) => resolve(result))
    worker.on('error', reject)
    worker.on('exit', (code) => {
      if (code !== 0) reject(new Error(`Worker exited with code ${code}`))
    })
  })
}

// Parallel CPU work across all cores
const numCores = cpus().length
const chunks = Array.from({ length: numCores }, (_, i) =>
  Array.from({ length: 1_000_000 }, (_, j) => i * 1_000_000 + j)
)

const results = await Promise.all(chunks.map(runWorker))
const total = results.reduce((a, b) => a + b, 0)
console.log('Total:', total)
🐍
Python Comparison — GIL vs Single Thread

Python's Global Interpreter Lock (GIL) allows only one thread to execute Python bytecode at a time — even on multi-core machines. threading.Thread gives you concurrency for I/O-bound work (while one thread waits for I/O, another runs) but no true parallelism for CPU-bound work.

Node's model is different: there is one thread and it never blocks (if written correctly). For CPU parallelism, worker_threads spawn true OS threads with separate V8 isolates — no shared heap, communication via structured clone. In Python you'd use multiprocessing for the same reason: escape the GIL with separate processes. Node 12+ worker threads are lighter than processes but still isolated.

The V8 Engine

V8 is the JavaScript engine written by Google, originally for Chrome. It compiles JavaScript (and TypeScript after stripping types) to native machine code via JIT compilation. Two key V8 concepts every Node developer should know:

  • Hidden classes: V8 creates hidden classes for objects. Adding properties in inconsistent order creates different hidden classes, deoptimizing the code. Always initialize objects with all properties, in the same order.
  • Garbage collection: V8 uses generational GC. Short-lived objects (young generation) are collected fast. Long-lived objects move to old generation and cause longer pauses. Watch for objects that escape their scope unintentionally.
💡
Tip — V8 optimization

Run Node with --trace-opt --trace-deopt in development to see which functions V8 is deoptimizing. The most common cause: polymorphic function calls (passing objects of different shapes to the same function). TypeScript helps here — if your types are correct, your shapes tend to be consistent.

Streams and Backpressure

Node streams solve a critical problem: processing data larger than available RAM. Instead of reading a 10GB log file into memory, you read it in chunks. Backpressure is the mechanism that prevents a fast producer from overwhelming a slow consumer.

typescript backpressure.ts 
import { createReadStream, createWriteStream } from 'fs'
import { Transform, pipeline } from 'stream'
import { promisify } from 'util'
import { createGzip } from 'zlib'

const pipelineAsync = promisify(pipeline)

// pipeline() handles backpressure automatically
// If the gzip output can't keep up, it signals the read stream to pause
await pipelineAsync(
  createReadStream('large-10gb-log.txt'),
  new Transform({
    transform(chunk: Buffer, _encoding: string, callback: () => void) {
      // Filter lines containing 'ERROR'
      const filtered = chunk
        .toString()
        .split('\n')
        .filter(line => line.includes('ERROR'))
        .join('\n')
      this.push(filtered)
      callback()
    }
  }),
  createGzip(),
  createWriteStream('errors.txt.gz')
)
// Memory usage: ~constant regardless of file size

§2 Core Node.js Modules (with TypeScript Types)

Node ships with a comprehensive standard library. All types come from @types/node. Here's the essential catalog — every backend TypeScript engineer should have these at their fingertips.

fs / fs/promises

File system: read, write, mkdir, watch, stat. Always prefer fs/promises over callback-based fs.

path

Cross-platform path manipulation. join, resolve, dirname, basename, extname, relative.

http / https

Raw HTTP server and client. Low-level but gives full control over request/response streams.

net

TCP/UDP sockets. Build custom protocols, proxies, anything HTTP doesn't cover.

crypto

Cryptography: hashing, HMAC, AES encryption, RSA, TLS. Wraps OpenSSL.

os

Operating system info: CPU count, total memory, platform, hostname, temp directory.

child_process

Spawn subprocesses: exec, spawn, fork. Run shell commands, call Python scripts.

worker_threads

True parallel threads with isolated V8 heaps. Share ArrayBuffers for zero-copy data transfer.

cluster

Fork the process per CPU core, sharing one port. Pre-worker_threads parallelism pattern.

stream

Readable, Writable, Transform, Duplex. The foundation of all I/O in Node.

events

EventEmitter base class. Most Node APIs extend it. Foundation for reactive patterns.

url / querystring

URL parsing and construction. Use the WHATWG URL class (no import needed in modern Node).

Let's look at the most important ones with real TypeScript examples.

http — Building a Raw HTTP Server

typescript raw-http-server.ts 
import http, { IncomingMessage, ServerResponse } from 'http'

interface ApiResponse<T> {
  data: T
  timestamp: string
}

function sendJson<T>(res: ServerResponse, statusCode: number, data: T): void {
  const body: ApiResponse<T> = { data, timestamp: new Date().toISOString() }
  res.writeHead(statusCode, { 'Content-Type': 'application/json' })
  res.end(JSON.stringify(body))
}

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {
  if (req.method === 'GET' && req.url === '/health') {
    sendJson(res, 200, { status: 'ok' })
    return
  }

  if (req.method === 'POST' && req.url === '/echo') {
    const chunks: Buffer[] = []
    req.on('data', (chunk: Buffer) => chunks.push(chunk))
    req.on('end', () => {
      const body = Buffer.concat(chunks).toString('utf-8')
      sendJson(res, 200, { echo: JSON.parse(body) })
    })
    return
  }

  sendJson(res, 404, { error: 'Not Found' })
})

server.listen(3000, () => console.log('Server on http://localhost:3000'))

crypto — Typed Cryptography

typescript crypto-utils.ts 
import {
  createHash,
  createHmac,
  randomBytes,
  scrypt,
  timingSafeEqual,
} from 'crypto'
import { promisify } from 'util'

const scryptAsync = promisify(scrypt)

// Hash a string
function sha256(input: string): string {
  return createHash('sha256').update(input).digest('hex')
}

// HMAC — tamper-evident signatures (used in JWTs, webhooks)
function hmacSHA256(message: string, secret: string): string {
  return createHmac('sha256', secret).update(message).digest('hex')
}

// Secure password hashing (use bcrypt/argon2 in production, but scrypt is built-in)
async function hashPassword(password: string): Promise<{ hash: string; salt: string }> {
  const salt = randomBytes(16).toString('hex')
  const derived = await scryptAsync(password, salt, 64) as Buffer
  return { hash: derived.toString('hex'), salt }
}

// Timing-safe comparison prevents timing attacks
async function verifyPassword(
  password: string,
  hash: string,
  salt: string
): Promise<boolean> {
  const derived = await scryptAsync(password, salt, 64) as Buffer
  const hashBuffer = Buffer.from(hash, 'hex')
  return timingSafeEqual(derived, hashBuffer)
}

// Secure random token — for session IDs, reset tokens
function generateToken(bytes = 32): string {
  return randomBytes(bytes).toString('base64url')
}

child_process — Spawning Subprocesses

typescript child-process.ts 
import { exec, spawn } from 'child_process'
import { promisify } from 'util'

const execAsync = promisify(exec)

// Simple command — typed output
async function getGitLog(): Promise<string[]> {
  const { stdout } = await execAsync('git log --oneline -10')
  return stdout.trim().split('\n')
}

// Streaming output — better for long-running commands
function runPython(scriptPath: string, args: string[]): Promise<number> {
  return new Promise((resolve, reject) => {
    const proc = spawn('python3', [scriptPath, ...args], {
      stdio: ['inherit', 'pipe', 'pipe']
    })

    proc.stdout?.on('data', (data: Buffer) => {
      process.stdout.write(`[python] ${data.toString()}`)
    })

    proc.stderr?.on('data', (data: Buffer) => {
      process.stderr.write(`[python:err] ${data.toString()}`)
    })

    proc.on('close', (code: number | null) => {
      if (code === 0) resolve(0)
      else reject(new Error(`Python exited with code ${code}`))
    })
  })
}
💡
Tip — use execa for better child process DX

The built-in child_process module has an awkward API. The execa library (npm i execa) wraps it with promise support, better error messages, and proper TypeScript types. In practice, use execa for everything except cases where you need full control over stdio streams.

Info — module: "NodeNext" explained

module: "NodeNext" tells TypeScript to respect Node's ESM resolution rules, which means .js extensions in imports are required (e.g., import { foo } from './utils.js') even when writing .ts files. This trips up many teams. The extension you write in the import corresponds to the compiled output, not the source file. It's counterintuitive but correct.

§4 Bun — The Fast Alternative

Bun is a JavaScript runtime built from scratch in Zig by Jarred Sumner, released 1.0 in September 2023. Its differentiator: speed. Bun uses JavaScriptCore (Safari's JS engine) instead of V8, which has significantly faster startup time. It runs TypeScript natively — no compilation step, no tsx, no ts-node.

Bun ships as a single binary that includes: a runtime, a package manager (bun install), a bundler (bun build), and a test runner (bun test). It's the all-in-one tool Node never was.

Speed Comparison: Node vs Bun

Bun's Built-in TypeScript Support

Create a file, run it. No config, no compilation, no tsconfig.json required for the basics.

bash 
# Install Bun
curl -fsSL https://bun.sh/install | bash

# Run TypeScript directly
bun run server.ts

# Development with hot reload
bun --hot run server.ts

# Test runner
bun test

# Package manager (much faster than npm)
bun install
bun add zod
bun add --dev @types/node

Bun.serve() — HTTP Server

Bun's HTTP server API is simpler and faster than Node's built-in http module. It uses the Fetch API paradigm — the same Request and Response objects you know from the browser.

typescript bun-server.ts 
import type { Server } from 'bun'

interface RouteHandler {
  (req: Request, params: Record<string, string>): Response | Promise<Response>
}

// Bun.serve uses the Web Fetch API — Response, Request, Headers
const server: Server = Bun.serve({
  port: 3000,
  hostname: '0.0.0.0',

  async fetch(req: Request): Promise<Response> {
    const url = new URL(req.url)

    if (url.pathname === '/health') {
      return Response.json({ status: 'ok', runtime: 'bun' })
    }

    if (req.method === 'POST' && url.pathname === '/echo') {
      const body = await req.json()
      return Response.json({ echo: body }, { status: 200 })
    }

    // Streaming response
    if (url.pathname === '/stream') {
      const stream = new ReadableStream({
        start(controller) {
          let i = 0
          const interval = setInterval(() => {
            controller.enqueue(`data: ${JSON.stringify({ tick: i++ })}\n\n`)
            if (i > 10) { clearInterval(interval); controller.close() }
          }, 100)
        }
      })

      return new Response(stream, {
        headers: {
          'Content-Type': 'text/event-stream',
          'Cache-Control': 'no-cache',
        }
      })
    }

    return new Response('Not Found', { status: 404 })
  },

  error(error: Error): Response {
    console.error(error)
    return Response.json({ error: error.message }, { status: 500 })
  }
})

console.log(`Listening on http://localhost:${server.port}`)

Bun APIs vs Node APIs — Compatibility

Bun implements most of Node's API surface, so existing Node code usually runs unchanged. But Bun also offers superior native alternatives.

Task Node.js Bun native
Read file fs.readFile() Bun.file().text()
Write file fs.writeFile() Bun.write(path, data)
HTTP server http.createServer() Bun.serve()
Hash crypto.createHash() Bun.CryptoHasher
SQLite Need better-sqlite3 bun:sqlite (built-in)
WebSocket Need ws package Bun.serve({ websocket })
Password hash Need bcrypt Bun.password.hash()
Environment process.env Bun.env (typed)

When to Choose Bun vs Node

💡
Tip — choosing your runtime

Choose Bun for: CLI tools (startup speed matters enormously), greenfield projects where you control the full stack, scripts that need to run fast, teams that want zero TypeScript build config friction.

Choose Node for: production systems requiring maximum ecosystem stability, projects with native addons (.node files), when deploying to environments that only support Node, or when team Node expertise is deep and Bun's production track record matters to you.

Bun's Node compatibility is ~95%+ for most application code. The gaps are mostly in native addons and some edge cases in streams.

§5 File System Operations

File I/O is the most common backend task. Always use fs/promises — the callback-based fs API is legacy. TypeScript's types give you full IntelliSense and catch mistakes at compile time.

Reading and Writing Files

typescript file-ops.ts 
import {
  readFile,
  writeFile,
  appendFile,
  mkdir,
  rm,
  readdir,
  stat,
  rename,
  copyFile,
} from 'fs/promises'
import { existsSync } from 'fs'
import { join, resolve, dirname, basename, extname } from 'path'

// Reading a text file — utf-8 encoding makes return type string
const content: string = await readFile('data.txt', 'utf-8')

// Reading binary — no encoding returns Buffer
const buffer: Buffer = await readFile('image.png')

// Writing files
await writeFile('output.txt', content, 'utf-8')
await writeFile('copy.png', buffer)

// Appending
await appendFile('log.txt', `${new Date().toISOString()} - Event\n`)

// Working with JSON — fully typed
interface Config {
  port: number
  database: { host: string; name: string }
}

async function readConfig(path: string): Promise<Config> {
  const raw = await readFile(path, 'utf-8')
  return JSON.parse(raw) as Config
}

async function writeConfig(path: string, config: Config): Promise<void> {
  await writeFile(path, JSON.stringify(config, null, 2), 'utf-8')
}

Directory Operations

typescript directory-ops.ts 
import { mkdir, readdir, rm, stat } from 'fs/promises'
import { join } from 'path'

// Create nested directories (like mkdir -p)
await mkdir('data/logs/2025', { recursive: true })

// List directory entries with types
const entries = await readdir('src', { withFileTypes: true })
const tsFiles = entries
  .filter(e => e.isFile() && e.name.endsWith('.ts'))
  .map(e => e.name)

// Recursive directory listing
async function* walk(dir: string): AsyncGenerator<string> {
  const entries = await readdir(dir, { withFileTypes: true })
  for (const entry of entries) {
    const path = join(dir, entry.name)
    if (entry.isDirectory()) {
      yield* walk(path)
    } else {
      yield path
    }
  }
}

// Usage
for await (const file of walk('./src')) {
  console.log(file)
}

// Delete recursively (like rm -rf)
await rm('temp', { recursive: true, force: true })

// File info
const info = await stat('package.json')
console.log(info.size, info.mtime, info.isDirectory())

File Watching

typescript file-watch.ts 
import { watch } from 'fs'
import { readFile } from 'fs/promises'

// Watch a file for changes — debounced
let debounceTimer: ReturnType<typeof setTimeout>

watch('./config.json', { persistent: true }, (event, filename) => {
  if (!filename) return
  clearTimeout(debounceTimer)
  debounceTimer = setTimeout(async () => {
    const content = await readFile('./config.json', 'utf-8')
    console.log('Config reloaded:', JSON.parse(content))
  }, 100)
})

// Watch a directory
const watcher = watch('./src', { recursive: true }, (event, filename) => {
  console.log(`${event}: ${filename}`)
})

// Clean up on exit
process.on('SIGINT', () => {
  watcher.close()
  process.exit(0)
})

Path Manipulation

typescript path-utils.ts 
import { join, resolve, dirname, basename, extname, relative, parse } from 'path'
import { fileURLToPath } from 'url'

// ESM equivalent of __dirname (Node ESM doesn't have __dirname)
const __filename = fileURLToPath(import.meta.url)
const __dirname = dirname(__filename)

// join: cross-platform path joining (uses \ on Windows, / on Unix)
const configPath = join(__dirname, '..', 'config', 'app.json')
// → /home/user/project/config/app.json

// resolve: makes absolute path
const abs = resolve('relative/path')

// Parse a path into parts
const parts = parse('/home/user/project/src/index.ts')
// → { root: '/', dir: '...', base: 'index.ts', ext: '.ts', name: 'index' }

// Get relative path between two absolutes
const rel = relative('/home/user/project', '/home/user/project/src/utils.ts')
// → 'src/utils.ts'

// Common patterns
function resolveFromRoot(...parts: string[]): string {
  return join(__dirname, ...parts)
}
🐍
Python Comparison — pathlib vs path

Python's pathlib.Path is an object-oriented API with method chaining: Path('src') / 'index.ts'. Node's path module is functional: join('src', 'index.ts'). Both handle cross-platform separators. In Python you rarely think about __file__ in ESM contexts — Node's switch to ESM removed __dirname and requires the fileURLToPath(import.meta.url) dance. Bun fixes this: import.meta.dir gives you the directory directly.

Streaming Large Files

typescript stream-large-file.ts 
import { createReadStream } from 'fs'
import { createInterface } from 'readline'
import { Transform, pipeline } from 'stream'
import { promisify } from 'util'
import { createWriteStream } from 'fs'

const pipelineAsync = promisify(pipeline)

// Line-by-line processing — constant memory regardless of file size
async function processLargeCSV(inputPath: string): Promise<void> {
  const stream = createReadStream(inputPath, { encoding: 'utf-8' })
  const rl = createInterface({ input: stream, crlfDelay: Infinity })

  let lineNum = 0
  for await (const line of rl) {
    lineNum++
    if (lineNum === 1) continue // skip header

    const [id, name, value] = line.split(',')
    // Process each row without loading entire file into memory
    await processRow({ id, name, value: parseFloat(value) })
  }
}

// Transform stream: uppercase all text
const uppercaser = new Transform({
  encoding: 'utf-8',
  transform(chunk: string, _enc: string, cb: () => void) {
    this.push(chunk.toUpperCase())
    cb()
  }
})

// Memory-efficient file transformation
await pipelineAsync(
  createReadStream('input.txt'),
  uppercaser,
  createWriteStream('output.txt')
)

async function processRow(_row: { id: string; name: string; value: number }) {
  // ... process row
}

§6 Environment Variables

process.env is typed as NodeJS.ProcessEnv — a Record<string, string | undefined>. Every access returns string | undefined, which TypeScript enforces. This is correct behavior: environment variables are not guaranteed to exist at runtime.

The Naive Approach (Avoid)

typescript 
// ❌ Bad — PORT is string | undefined, not number
const port = process.env.PORT  // string | undefined — not a number!
const db = process.env.DATABASE_URL  // could be undefined

// ❌ Non-null assertion — lies to TypeScript
const badPort = process.env.PORT!  // pretends it's defined — blows up in prod

The Right Way — Validate with Zod

typescript env.ts 
import { z } from 'zod'

const envSchema = z.object({
  // Strings
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  DATABASE_URL: z.string().url('DATABASE_URL must be a valid URL'),
  JWT_SECRET: z.string().min(32, 'JWT_SECRET must be at least 32 chars'),

  // Numbers — transform from string
  PORT: z.string().regex(/^\d+$/).transform(Number).default('3000'),
  MAX_CONNECTIONS: z.string().transform(Number).default('10'),

  // Booleans — "true"/"false" strings
  ENABLE_METRICS: z.string()
    .transform(v => v === 'true')
    .default('false'),

  // Optional
  REDIS_URL: z.string().url().optional(),
  SENTRY_DSN: z.string().optional(),
})

// Parse at startup — throws immediately if anything is wrong
export const env = envSchema.parse(process.env)

// Now everything is fully typed:
// env.PORT → number
// env.NODE_ENV → "development" | "production" | "test"
// env.DATABASE_URL → string
// env.REDIS_URL → string | undefined
⚠️
Warning — never commit .env to git

Add .env, .env.local, and .env.*.local to your .gitignore immediately. Commit a .env.example with all required keys but no real values. Use a secrets manager (AWS Secrets Manager, 1Password Secrets Automation, Doppler) in production — not .env files on servers.

function parseArgs(argv: string[]): Record<string, string | boolean> {
  const result: Record<string, string | boolean> = {}
  for (let i = 0; i < argv.length; i++) {
    const arg = argv[i]
    if (arg.startsWith('--')) {
      const key = arg.slice(2)
      const next = argv[i + 1]
      if (next && !next.startsWith('--')) {
        result[key] = next
        i++
      } else {
        result[key] = true
      }
    }
  }
  return result
}

Graceful Shutdown

Graceful shutdown is not optional in production. When Kubernetes sends SIGTERM, your server has ~30 seconds to stop accepting new requests, finish in-flight requests, close database connections, and exit. Getting this right prevents data corruption and dropped requests during deployments.

typescript graceful-shutdown.ts 
import http from 'http'

interface Closeable {
  close: () => Promise<void>
}

class GracefulShutdown {
  private readonly resources: Closeable[] = []
  private shuttingDown = false

  register(resource: Closeable): void {
    this.resources.push(resource)
  }

  install(server: http.Server): void {
    // SIGTERM: sent by Kubernetes, systemd, PM2 on restart
    process.on('SIGTERM', () => this.shutdown('SIGTERM'))
    // SIGINT: sent by Ctrl+C
    process.on('SIGINT', () => this.shutdown('SIGINT'))
    // Uncaught exceptions — last resort
    process.on('uncaughtException', (err) => {
      console.error('Uncaught exception:', err)
      this.shutdown('uncaughtException')
    })
    process.on('unhandledRejection', (reason) => {
      console.error('Unhandled rejection:', reason)
      this.shutdown('unhandledRejection')
    })
  }

  private async shutdown(signal: string): Promise<void> {
    if (this.shuttingDown) return
    this.shuttingDown = true

    console.log(`${signal} received — starting graceful shutdown`)

    // Timeout: force exit if graceful shutdown takes too long
    const timeout = setTimeout(() => {
      console.error('Graceful shutdown timed out — forcing exit')
      process.exit(1)
    }, 30_000)

    try {
      await Promise.all(this.resources.map(r => r.close()))
      console.log('Graceful shutdown complete')
      clearTimeout(timeout)
      process.exit(0)
    } catch (err) {
      console.error('Error during shutdown:', err)
      process.exit(1)
    }
  }
}

// Usage
const shutdown = new GracefulShutdown()
const server = http.createServer(/* ... */)

// Register everything that needs cleanup
shutdown.register({
  close: () => new Promise(resolve => server.close(resolve))
})
// shutdown.register({ close: () => db.disconnect() })
// shutdown.register({ close: () => redis.quit() })
shutdown.install(server)

§8 Streams in TypeScript

Streams are the backbone of efficient Node.js I/O. There are two stream APIs: Node.js streams (import { Readable } from 'stream') and the Web Streams API (ReadableStream, WritableStream) which is now available in Node 18+ and is Bun's native API.

Node.js Streams — the four types

typescript streams.ts 
import { Readable, Writable, Transform, Duplex, pipeline } from 'stream'
import { promisify } from 'util'

const pipelineAsync = promisify(pipeline)

// ── Readable: source of data ─────────────────────────────────────────
class NumberStream extends Readable {
  private current = 0
  private readonly max: number

  constructor(max: number) {
    super({ objectMode: true })
    this.max = max
  }

  _read(): void {
    if (this.current > this.max) {
      this.push(null)  // signals end of stream
    } else {
      this.push(this.current++)
    }
  }
}

// ── Transform: converts data ──────────────────────────────────────────
class SquareTransform extends Transform {
  constructor() {
    super({ objectMode: true })
  }

  _transform(chunk: number, _enc: string, cb: () => void): void {
    this.push(chunk * chunk)
    cb()
  }
}

// ── Writable: sink for data ───────────────────────────────────────────
class SumWriter extends Writable {
  sum = 0

  constructor() { super({ objectMode: true }) }

  _write(chunk: number, _enc: string, cb: () => void): void {
    this.sum += chunk
    cb()
  }
}

// Wire them together
const writer = new SumWriter()
await pipelineAsync(
  new NumberStream(100),
  new SquareTransform(),
  writer
)
console.log('Sum of squares:', writer.sum)  // 338350

Async Iteration — the modern stream API

typescript async-iteration.ts 
import { createReadStream } from 'fs'
import { createGunzip } from 'zlib'

// Async iteration is the cleanest way to consume streams
async function processCompressedLog(path: string): Promise<Map<string, number>> {
  const errorCounts = new Map<string, number>()

  const stream = createReadStream(path).pipe(createGunzip())

  let buffer = ''
  for await (const chunk of stream as AsyncIterable<Buffer>) {
    buffer += chunk.toString('utf-8')
    const lines = buffer.split('\n')
    buffer = lines.pop() ?? ''  // keep incomplete last line

    for (const line of lines) {
      if (line.includes('ERROR')) {
        const match = line.match(/ERROR\s+(\w+)/)
        if (match) {
          const key = match[1]
          errorCounts.set(key, (errorCounts.get(key) ?? 0) + 1)
        }
      }
    }
  }
  return errorCounts
}

// Streaming HTTP response with fetch (Web Streams API, works in Node 18+, Bun)
async function streamOpenAI(prompt: string): Promise<void> {
  const response = await fetch('https://api.openai.com/v1/completions', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${process.env.OPENAI_KEY}` },
    body: JSON.stringify({ model: 'gpt-4o', stream: true, messages: [{ role: 'user', content: prompt }] })
  })

  if (!response.body) throw new Error('No response body')

  const reader = response.body.getReader()
  const decoder = new TextDecoder()

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    process.stdout.write(decoder.decode(value, { stream: true }))
  }
}

§9 EventEmitter with TypeScript

Node's EventEmitter is the pub/sub backbone of the ecosystem — HTTP servers, streams, file watchers all extend it. The problem: it's not typed by default. Here's how to get full type safety.

typescript typed-emitter.ts 
import { EventEmitter } from 'events'

// ── Pattern 1: TypedEventEmitter utility type ─────────────────────────
type EventMap = Record<string, unknown[]>

interface TypedEventEmitter<Events extends EventMap> {
  on<K extends keyof Events & string>(event: K, listener: (...args: Events[K]) => void): this
  off<K extends keyof Events & string>(event: K, listener: (...args: Events[K]) => void): this
  emit<K extends keyof Events & string>(event: K, ...args: Events[K]): boolean
  once<K extends keyof Events & string>(event: K, listener: (...args: Events[K]) => void): this
}

// Define your event shape
interface JobEvents extends EventMap {
  started: [jobId: string, timestamp: Date]
  progress: [jobId: string, percent: number]
  completed: [jobId: string, result: unknown]
  failed: [jobId: string, error: Error]
}

// Extend EventEmitter with typed interface
class JobQueue extends (EventEmitter as new () => TypedEventEmitter<JobEvents>) {
  private jobs = new Map<string, AbortController>()

  async enqueue(jobId: string, task: () => Promise<unknown>): Promise<void> {
    const controller = new AbortController()
    this.jobs.set(jobId, controller)
    this.emit('started', jobId, new Date())

    try {
      const result = await task()
      this.emit('completed', jobId, result)
    } catch (err) {
      this.emit('failed', jobId, err instanceof Error ? err : new Error(String(err)))
    } finally {
      this.jobs.delete(jobId)
    }
  }
}

// Usage — fully typed, IntelliSense works perfectly
const queue = new JobQueue()
queue.on('progress', (jobId, percent) => {
  //              ↑ string    ↑ number  — TypeScript knows!
  console.log(`Job ${jobId}: ${percent}%`)
})
queue.on('failed', (jobId, error) => {
  //              ↑ string   ↑ Error — TypeScript knows!
  console.error(`Job ${jobId} failed:`, error.message)
})

  error: (err: Error) => void
  ready: () => void

class MetricsCollector extends EventEmitter<MetricsEvents> {
  private readonly timings: number[] = []

  record(duration: number, path: string, status: number): void {
    this.timings.push(duration)
    this.emit('request', duration, path, status)

typescript memory-monitor.ts 
import { memoryUsage } from 'process'

interface MemorySnapshot {
  heapUsed: number
  heapTotal: number
  external: number
  rss: number
  timestamp: Date
}

function captureMemory(): MemorySnapshot {
  const mem = memoryUsage()
  return {
    heapUsed: Math.round(mem.heapUsed / 1024 / 1024),
    heapTotal: Math.round(mem.heapTotal / 1024 / 1024),
    external: Math.round(mem.external / 1024 / 1024),
    rss: Math.round(mem.rss / 1024 / 1024),
    timestamp: new Date(),
  }
}

// Monitor heap every 30 seconds — alert if growing steadily
const snapshots: MemorySnapshot[] = []

setInterval(() => {
  const snap = captureMemory()
  snapshots.push(snap)
  if (snapshots.length > 10) snapshots.shift()

  // Linear trend: if consistently growing → likely leak
  const heapValues = snapshots.map(s => s.heapUsed)
  const isGrowing = heapValues.every((v, i) => i === 0 || v >= heapValues[i - 1])

  if (isGrowing && snap.heapUsed > 500) {  // >500MB and growing
    console.error('Possible memory leak detected', snap)
    // Alert to your observability platform
  }
}, 30_000)

Performance — the cluster module vs worker_threads

The cluster module forks the entire Node process N times, each listening on the same port — the OS distributes connections between them. This is simpler than worker_threads and still the standard approach for HTTP servers. Worker threads share memory (via SharedArrayBuffer) and are better for CPU-parallel computation. In practice: use cluster or PM2 cluster mode for HTTP servers, worker_threads for CPU-bound tasks within a server.

Python Comparison — asyncio vs the event loop

Python's asyncio is an explicit framework you opt into: you create an event loop, you await coroutines, you call asyncio.run(). Node's event loop is implicit — it's always running, and all async I/O flows through it automatically. This means Python lets you have both synchronous and asynchronous code patterns in the same codebase more easily; Node defaults to async everywhere and synchronous code is the explicit opt-in (the Sync suffix: readFileSync, execSync). In practice, write no synchronous Node code in server paths.
