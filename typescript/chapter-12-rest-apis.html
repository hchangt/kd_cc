1. REST API Design Principles

Before touching a framework, you need a shared vocabulary. REST (Representational State Transfer) is an architectural style, not a protocol. The constraints—statelessness, uniform interface, resource-based URLs—produce APIs that are predictable, cacheable, and evolvable.

ℹ
Info — "RESTful" vs REST

Most production "REST" APIs are actually REST-ish (Level 2 on Richardson Maturity Model: resources + HTTP verbs). True REST (Level 3) includes HATEOAS links in responses. For most teams, Level 2 is the sweet spot.

HTTP Methods

Use HTTP verbs semantically. The method communicates intent; the URL communicates the resource.

Method Semantics Idempotent Body Example
GET Fetch resource(s) Yes No GET /users/:id
POST Create new resource No Yes POST /users
PUT Replace full resource Yes Yes PUT /users/:id
PATCH Partial update Usually Yes PATCH /users/:id
DELETE Remove resource Yes Rarely DELETE /users/:id

Status Codes — The Ones That Matter

200 OK Success (GET, PUT, PATCH)
201 Created Resource created (POST)
204 No Content Success, no body (DELETE)
400 Bad Request Malformed syntax / body
401 Unauthorized Not authenticated
403 Forbidden Authenticated, not authorized
404 Not Found Resource doesn't exist
409 Conflict State conflict (duplicate email)
422 Unprocessable Valid syntax, invalid semantics
500 Server Error Unexpected server failure
⚠
Warning — 401 vs 403

This trips up every team. 401 means "I don't know who you are — authenticate." 403 means "I know who you are — you're not allowed." Returning 403 for unauthenticated requests leaks resource existence. Return 401.

URL Design

Good URL design makes an API self-documenting. Follow these conventions:

  • Use nouns, not verbs: /users not /getUsers
  • Version at the path prefix: /api/v1/users
  • Nested resources for containment: /users/:userId/posts
  • Query params for filtering/sorting/pagination: /users?role=admin&page=2
  • Path params for identity: /users/:id
  • Request body for complex write payloads (POST/PUT/PATCH)

2. Hono — The Modern TypeScript Web Framework

Hono (Japanese for "flame") was built by Yusuke Wada as a Web Standards-first framework. It runs on Cloudflare Workers, Node.js, Bun, Deno, AWS Lambda@Edge, and Fastly Compute — the same code, no changes. That portability is its killer feature in 2025.

⚡
AI Era — Why Hono?

AI workloads often live at the edge (low latency inference proxies, streaming completions, RAG endpoints). Hono's edge-native design means your API layer runs milliseconds from users globally. At Meta we moved several ML serving APIs to edge frameworks for exactly this reason.

Middleware with app.use()

src/app.ts typescript 
import { Hono } from 'hono'
import { cors } from 'hono/cors'
import { logger } from 'hono/logger'
import { bearerAuth } from 'hono/bearer-auth'
import { compress } from 'hono/compress'

const app = new Hono()

// Global middleware (runs on every request)
app.use('*', logger())
app.use('*', cors({
  origin: ['https://myapp.com', 'http://localhost:3000'],
  allowMethods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowHeaders: ['Content-Type', 'Authorization'],
}))
app.use('*', compress())

// Scoped middleware (only on /api/* routes)
app.use('/api/*', bearerAuth({ token: process.env.API_TOKEN! }))

// Custom middleware
app.use('*', async (c, next) => {
  const requestId = crypto.randomUUID()
  c.set('requestId', requestId)
  c.header('X-Request-ID', requestId)
  await next()
  // code here runs AFTER the handler (response phase)
})

3. Building a Complete REST API with Hono

Let's build a production-quality CRUD API for a Users resource. We'll use an in-memory store for simplicity — swapping in a real database is a one-function change.

Full CRUD Routes

src/routes/users.ts typescript 
import { Hono } from 'hono'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'
import { db, type User } from '../types.js'
import {
  CreateUserSchema,
  UpdateUserSchema,
} from '../schemas/user.schema.js'
import { AppError } from '../errors.js'

const users = new Hono()

// ── GET /users ── List with optional filtering
users.get('/', (c) => {
  const role = c.req.query('role')
  let result = [...db.values()]

  if (role) {
    result = result.filter((u) => u.role === role)
  }

  return c.json({
    data: result,
    total: result.length,
    page: 1,
  })
})

// ── GET /users/:id ── Get single user
users.get('/:id', (c) => {
  const id = c.req.param('id')
  const user = db.get(id)

  if (!user) {
    throw new AppError(404, `User ${id} not found`, 'USER_NOT_FOUND')
  }

  return c.json({ data: user })
})

// ── POST /users ── Create user
users.post(
  '/',
  zValidator('json', CreateUserSchema),
  async (c) => {
    const body = c.req.valid('json')  // fully typed, validated

    // Check duplicate email
    const existing = [...db.values()].find((u) => u.email === body.email)
    if (existing) {
      throw new AppError(409, 'Email already in use', 'EMAIL_CONFLICT')
    }

    const now = new Date().toISOString()
    const user: User = {
      id: crypto.randomUUID(),
      ...body,
      createdAt: now,
      updatedAt: now,
    }

    db.set(user.id, user)

    return c.json({ data: user }, 201)
  }
)

// ── PUT /users/:id ── Full replace
users.put(
  '/:id',
  zValidator('json', CreateUserSchema),
  async (c) => {
    const id = c.req.param('id')
    const body = c.req.valid('json')

    if (!db.has(id)) {
      throw new AppError(404, `User ${id} not found`, 'USER_NOT_FOUND')
    }

    const existing = db.get(id)!
    const updated: User = {
      ...existing,
      ...body,
      id,
      updatedAt: new Date().toISOString(),
    }

    db.set(id, updated)
    return c.json({ data: updated })
  }
)

// ── PATCH /users/:id ── Partial update
users.patch(
  '/:id',
  zValidator('json', UpdateUserSchema),
  async (c) => {
    const id = c.req.param('id')
    const body = c.req.valid('json')
    const existing = db.get(id)

    if (!existing) {
      throw new AppError(404, `User ${id} not found`, 'USER_NOT_FOUND')
    }

    const updated: User = {
      ...existing,
      ...body,
      id,
      updatedAt: new Date().toISOString(),
    }

    db.set(id, updated)
    return c.json({ data: updated })
  }
)

// ── DELETE /users/:id ── Remove user
users.delete('/:id', (c) => {
  const id = c.req.param('id')

  if (!db.has(id)) {
    throw new AppError(404, `User ${id} not found`, 'USER_NOT_FOUND')
  }

  db.delete(id)
  return new Response(null, { status: 204 })
})

export { users }

Best Practice — c.req.valid() vs c.req.json()

Always use c.req.valid('json') after a zValidator middleware — this gives you the parsed and typed value. c.req.json() returns unknown and bypasses validation. The former is safe; the latter is a footgun.

4. Fastify — The Battle-Tested Alternative

Fastify is the speed king of Node.js frameworks (consistently 2–3× faster than Express in benchmarks). It was designed from the ground up for TypeScript and schema-first validation — every route declares its shape upfront.

Installation & Basic Setup

terminal bash 
pnpm add fastify @fastify/cors @fastify/swagger
pnpm add -D @types/node
src/server.ts typescript 
import Fastify from 'fastify'
import cors from '@fastify/cors'

const fastify = Fastify({ logger: true })

await fastify.register(cors, { origin: '*' })

// Schema-based validation (JSON Schema)
const getUserSchema = {
  schema: {
    params: {
      type: 'object',
      properties: { id: { type: 'string' } },
      required: ['id'],
    },
    response: {
      200: {
        type: 'object',
        properties: {
          data: {
            type: 'object',
            properties: {
              id:    { type: 'string' },
              name:  { type: 'string' },
              email: { type: 'string' },
            },
          },
        },
      },
    },
  },
} as const

fastify.get('/users/:id', getUserSchema, async (request, reply) => {
  const { id } = request.params  // typed via JSON Schema inference
  return reply.send({ data: { id, name: 'Alice', email: 'alice@example.com' } })
})

await fastify.listen({ port: 3000 })

Plugins & Decorators

src/plugins/auth.ts typescript 
import fp from 'fastify-plugin'
import type { FastifyPluginAsync } from 'fastify'

// Extend FastifyRequest type
declare module 'fastify' {
  interface FastifyRequest {
    userId: string
  }
}

const authPlugin: FastifyPluginAsync = async (fastify) => {
  // Decorate request with userId
  fastify.decorateRequest('userId', '')

  fastify.addHook('preHandler', async (request, reply) => {
    const token = request.headers.authorization?.replace('Bearer ', '')
    if (!token) {
      return reply.status(401).send({ error: 'Unauthorized' })
    }
    // verify JWT...
    request.userId = 'extracted-from-token'
  })
}

// fp() wraps in fastify-plugin so decorations aren't scoped
export default fp(authPlugin)

5. Express (Legacy — Still Important)

Express powers roughly 60% of existing Node.js APIs. You will maintain Express codebases. Understanding its patterns — and its TypeScript limitations — lets you work with and migrate away from it confidently.

TypeScript Setup

terminal bash 
pnpm add express
pnpm add -D @types/express
src/express-app.ts typescript 
import express, {
  type Request,
  type Response,
  type NextFunction,
  type RequestHandler,
} from 'express'

const app = express()
app.use(express.json())

// Express router
const router = express.Router()

router.get('/users', (_req: Request, res: Response) => {
  res.json({ users: [] })
})

// Typed route params — requires manual assertion
router.get('/users/:id', (req: Request<{ id: string }>, res: Response) => {
  const { id } = req.params  // typed as string
  res.json({ id })
})

// Error handler (must have 4 params — Express detects by arity)
const errorHandler = (
  err: Error,
  _req: Request,
  res: Response,
  _next: NextFunction
): void => {
  res.status(500).json({ error: err.message })
}

app.use('/api/v1', router)
app.use(errorHandler)

app.listen(3000)

Why Express Has Poor TypeScript Support

  • req.body is typed as any — no schema inference
  • No built-in Zod/JSON Schema integration
  • Middleware types are loose — easy to break the chain silently
  • No native async error propagation (must wrap handlers or use express-async-errors)
  • Route types don't flow through to response — res.json() is untyped

Migrating Express to Hono

migration patterns typescript 
// BEFORE (Express)
router.get('/users/:id', async (req, res, next) => {
  try {
    const user = await db.findUser(req.params.id)
    if (!user) return res.status(404).json({ error: 'Not found' })
    res.json({ data: user })
  } catch (err) {
    next(err)
  }
})

// AFTER (Hono) — cleaner, typed, no try/catch boilerplate
users.get('/:id', async (c) => {
  const user = await db.findUser(c.req.param('id'))
  if (!user) throw new AppError(404, 'Not found', 'NOT_FOUND')
  return c.json({ data: user })
})
⚠
Warning — Express Async Errors

Express does not catch async errors by default. Either use express-async-errors package (add import 'express-async-errors' at the top), wrap every handler manually, or migrate to Hono/Fastify which handle async errors natively.

6. Input Validation with Zod

Zod is the standard for TypeScript-first schema validation. Its killer feature: schemas are the single source of truth for both runtime validation and compile-time types.

src/schemas/user.schema.ts typescript 
import { z } from 'zod'

// Basic schema with built-in validators
const CreateUserSchema = z.object({
  name:  z.string().min(2).max(100),
  email: z.string().email(),
  age:   z.number().int().min(0).max(150).optional(),
  role:  z.enum(['admin', 'user', 'moderator']).default('user'),
  tags:  z.array(z.string()).max(10).default([]),
})

// Derive TypeScript type — zero duplication
type CreateUser = z.infer<typeof CreateUserSchema>
// { name: string; email: string; age?: number; role: 'admin'|'user'|'moderator'; tags: string[] }

// Nested objects
const AddressSchema = z.object({
  street: z.string(),
  city:   z.string(),
  country: z.string().length(2), // ISO country code
})

const UserWithAddressSchema = CreateUserSchema.extend({
  address: AddressSchema.optional(),
})

// Partial (for PATCH)
const UpdateUserSchema = CreateUserSchema.partial()

// Transformations — normalize at parse time
const NormalizedEmailSchema = z
  .string()
  .email()
  .transform((email) => email.toLowerCase().trim())

// Discriminated unions
const EventSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('created'), userId: z.string() }),
  z.object({ type: z.literal('deleted'), userId: z.string(), reason: z.string() }),
])
type Event = z.infer<typeof EventSchema>  // fully typed union

parse vs safeParse

validation patterns typescript 
// parse() — throws ZodError on failure (use in middleware)
const user = CreateUserSchema.parse(rawBody)

// safeParse() — returns Result object (use when you want to handle errors yourself)
const result = CreateUserSchema.safeParse(rawBody)

if (!result.success) {
  const errors = result.error.issues.map((issue) => ({
    field: issue.path.join('.'),
    message: issue.message,
    code: issue.code,
  }))
  return c.json({ errors }, 422)
}

const user = result.data  // typed as CreateUser

Schema Composition Patterns

composition typescript 
// .extend() — add fields
const AdminUserSchema = CreateUserSchema.extend({
  permissions: z.array(z.string()),
})

// .pick() / .omit() — select/exclude fields
const PublicUserSchema = CreateUserSchema.omit({ role: true })
const LoginSchema = CreateUserSchema.pick({ email: true }).extend({
  password: z.string().min(8),
})

// .merge() — combine two schemas
const BaseSchema = z.object({ id: z.string(), createdAt: z.string() })
const FullUserSchema = CreateUserSchema.merge(BaseSchema)

// Reusable branded types
const UserId = z.string().uuid().brand<'UserId'>()
type UserId = z.infer<typeof UserId>
// UserId is structurally identical to string but nominal — prevents mixing IDs
🐍
Python Comparison — Zod vs Pydantic

Zod is the closest TypeScript equivalent to Pydantic. Both define schemas as code and derive types from them. Key differences:

  • Pydantic uses class inheritance; Zod uses function composition
  • z.infer<typeof Schema> ≈ using the Pydantic model class as a type annotation
  • Both support .parse() (throws) and .safeParse() (result object)
  • Zod transformations ≈ Pydantic @field_validator with mode='before'
  • Pydantic is faster (Rust core); Zod is pure JS but fast enough for HTTP handlers

7. Error Handling Patterns

Good error handling is invisible to users and invaluable to developers. The goals: consistent response shape, appropriate status codes, machine-readable error codes, and full stack traces in development.

Custom Error Class

src/errors.ts typescript 
export class AppError extends Error {
  constructor(
    public readonly statusCode: number,
    message: string,
    public readonly code: string,
    public readonly details?: unknown,
  ) {
    super(message)
    this.name = 'AppError'
    // Maintains proper stack trace in V8
    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, AppError)
    }
  }

  toJSON() {
    return {
      type: `https://errors.myapi.com/${this.code}`,
      title: this.message,
      status: this.statusCode,
      code: this.code,
      ...(this.details ? { details: this.details } : {}),
    }
  }
}

// Convenience factories
export const NotFound    = (msg: string) => new AppError(404, msg, 'NOT_FOUND')
export const Conflict    = (msg: string) => new AppError(409, msg, 'CONFLICT')
export const BadRequest  = (msg: string) => new AppError(400, msg, 'BAD_REQUEST')
export const Unauthorized = ()           => new AppError(401, 'Unauthorized', 'UNAUTHORIZED')

Global Error Handler (Hono)

src/middleware/error.ts typescript 
import { ZodError } from 'zod'
import type { Context } from 'hono'
import { AppError } from '../errors.js'

export function errorHandler(err: Error, c: Context) {
  // Zod validation error
  if (err instanceof ZodError) {
    return c.json(
      {
        type: 'https://errors.myapi.com/VALIDATION_ERROR',
        title: 'Validation failed',
        status: 422,
        code: 'VALIDATION_ERROR',
        issues: err.issues.map((i) => ({
          field: i.path.join('.'),
          message: i.message,
        })),
      },
      422
    )
  }

  // Known application error
  if (err instanceof AppError) {
    return c.json(err.toJSON(), err.statusCode as any)
  }

  // Unknown error — log and return generic 500
  console.error('[Unhandled Error]', err)
  return c.json(
    {
      type: 'https://errors.myapi.com/INTERNAL_ERROR',
      title: 'An unexpected error occurred',
      status: 500,
      code: 'INTERNAL_ERROR',
      ...(process.env.NODE_ENV !== 'production'
        ? { stack: err.stack }
        : {}),
    },
    500
  )
}
ℹ
Info — RFC 7807 Problem Details

The error shape above follows RFC 7807 "Problem Details for HTTP APIs." The type (URI), title, and status fields are standardized. Clients can reliably parse errors without guessing your schema. Use it — it's the industry standard.

8. Middleware Patterns

JWT Authentication Middleware

src/middleware/auth.ts typescript 
import type { Context, Next } from 'hono'
import { verify } from 'hono/jwt'
import { AppError } from '../errors.js'

type JwtPayload = { sub: string; role: string; iat: number; exp: number }

export async function authMiddleware(c: Context, next: Next) {
  const authHeader = c.req.header('Authorization')
  if (!authHeader?.startsWith('Bearer ')) {
    throw new AppError(401, 'Missing or invalid Authorization header', 'UNAUTHORIZED')
  }

  const token = authHeader.slice(7)
  try {
    const payload = await verify(token, process.env.JWT_SECRET!) as JwtPayload
    c.set('userId', payload.sub)
    c.set('userRole', payload.role)
  } catch {
    throw new AppError(401, 'Invalid or expired token', 'INVALID_TOKEN')
  }

  await next()
}

// Role guard — compose with authMiddleware
export function requireRole(...roles: string[]) {
  return async (c: Context, next: Next) => {
    const role = c.get('userRole') as string
    if (!roles.includes(role)) {
      throw new AppError(403, 'Insufficient permissions', 'FORBIDDEN')
    }
    await next()
  }
}

Request ID & Logging

src/middleware/request-id.ts typescript 
import type { Context, Next } from 'hono'

export async function requestIdMiddleware(c: Context, next: Next) {
  // Accept upstream request ID (e.g., from load balancer) or generate one
  const requestId =
    c.req.header('X-Request-ID') ?? crypto.randomUUID()

  c.set('requestId', requestId)
  c.header('X-Request-ID', requestId)

  const start = performance.now()
  await next()
  const duration = (performance.now() - start).toFixed(2)

  // Structured log — ships to your observability stack
  console.log(
    JSON.stringify({
      requestId,
      method: c.req.method,
      path: new URL(c.req.url).pathname,
      status: c.res.status,
      durationMs: Number(duration),
    })
  )
}

Rate Limiting

src/middleware/rate-limit.ts typescript 
// Simple in-memory rate limiter (use Redis in production)
const requests = new Map<string, { count: number; resetAt: number }>()

type RateLimitOptions = { limit: number; windowMs: number }

export function rateLimit({ limit, windowMs }: RateLimitOptions) {
  return async (c: Context, next: Next) => {
    const key = c.req.header('x-forwarded-for') ?? 'unknown'
    const now = Date.now()
    const entry = requests.get(key)

    if (!entry || now > entry.resetAt) {
      requests.set(key, { count: 1, resetAt: now + windowMs })
    } else if (entry.count >= limit) {
      c.header('Retry-After', String(Math.ceil((entry.resetAt - now) / 1000)))
      throw new AppError(429, 'Too many requests', 'RATE_LIMITED')
    } else {
      entry.count++
    }

    c.header('X-RateLimit-Limit', String(limit))
    c.header('X-RateLimit-Remaining', String(limit - (requests.get(key)?.count ?? 1)))
    await next()
  }
}

// Usage
app.use('/api/*', rateLimit({ limit: 100, windowMs: 60_000 }))

10. Type-Safe API Client Pattern

Your API types shouldn't live only on the server. A shared client wrapper propagates types across the stack — catch mismatches at compile time, not in production.

src/client/api.ts typescript 
// Generic fetch wrappers with typed responses
const BASE_URL = process.env.API_URL ?? 'http://localhost:3000/api/v1'

async function apiGet<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE_URL}${url}`, {
    headers: { 'Content-Type': 'application/json', ...init?.headers },
    ...init,
  })
  if (!res.ok) {
    const err = await res.json().catch(() => ({ title: 'Unknown error' }))
    throw new Error(`HTTP ${res.status}: ${err.title}`)
  }
  return res.json() as Promise<T>
}

async function apiPost<TBody, TResponse>(
  url: string,
  body: TBody,
  init?: RequestInit
): Promise<TResponse> {
  return apiGet<TResponse>(url, {
    method: 'POST',
    body: JSON.stringify(body),
    ...init,
  })
}

// Typed API surface — mirrors server routes
import type { User } from '../types.js'
import type { CreateUserInput } from '../schemas/user.schema.js'

export const usersApi = {
  list: ()                    => apiGet<{ data: User[]; total: number }>('/users'),
  get:  (id: string)          => apiGet<{ data: User }>(`/users/${id}`),
  create: (input: CreateUserInput) =>
    apiPost<CreateUserInput, { data: User }>('/users', input),
}

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, EmailStr
from typing import Optional

app = FastAPI()

class CreateUser(BaseModel):
    name: str
    email: EmailStr
    age: Optional[int] = None

class User(CreateUser):
    id: str

db: dict[str, User] = {}

@app.post("/users", response_model=User, status_code=201)
async def create_user(user: CreateUser):
    existing = next((u for u in db.values() if u.email == user.email), None)
    if existing:
        raise HTTPException(status_code=409, detail="Email already in use")
    new_user = User(id=str(uuid4()), **user.model_dump())
    db[new_user.id] = new_user
    return new_user
TypeScript Hono — equivalent typescript 
import { Hono } from 'hono'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'

const app = new Hono()

const CreateUserSchema = z.object({
  name:  z.string(),
  email: z.string().email(),
  age:   z.number().int().optional(),
})

type User = z.infer<typeof CreateUserSchema> & { id: string }

const db = new Map<string, User>()

app.post('/users', zValidator('json', CreateUserSchema), async (c) => {
  const body = c.req.valid('json')
  const existing = [...db.values()].find((u) => u.email === body.email)
  if (existing) {
    return c.json({ detail: 'Email already in use' }, 409)
  }
  const user: User = { id: crypto.randomUUID(), ...body }
  db.set(user.id, user)
  return c.json(user, 201)
})

  • FastAPI's Depends() DI is more powerful for complex graphs; Hono uses middleware + context variables

  • Both achieve the same result — validated input, typed output, auto-docs — with different ergonomics
  • Hono wins on edge deployment and multi-runtime portability; FastAPI wins on DI and ecosystem maturity
