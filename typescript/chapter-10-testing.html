1. Testing Philosophy for TypeScript

Coming from Python, you probably have a healthy respect for automated tests. In TypeScript, the relationship between the type system and your test suite is different from anything you've experienced with pytest or unittest. The type system does work your tests used to do — and that changes what you need to test.

What the Type System Replaces

In Python, you might write a test to verify that add(1, "two") raises a TypeError. In TypeScript, that test is pointless: the compiler refuses to compile the call in the first place. Types give you a whole category of bugs for free — the entire class of "wrong-type argument" errors.

typescript math.ts 
// TypeScript — you don't need to test this at runtime
function add(a: number, b: number): number {
  return a + b;
}

// This is a compile error, not a test case:
add(1, "two"); // Error: Argument of type 'string' is not assignable to parameter of type 'number'

// What you DO need to test: runtime behaviour types can't see
add(0.1, 0.2); // → 0.30000000000000004 (floating point!)
add(Infinity, -Infinity); // → NaN
🍎

Python Comparison

In pytest, you commonly write with pytest.raises(TypeError) to guard against wrong types. TypeScript eliminates that entire category. Your test suite gets smaller — in a good way. Focus the tests you do write on behaviour, not type safety.

What Types Cannot Test

  • Runtime values: A string could be an empty string, a million-character blob, or a SQL injection attempt.
  • External systems: APIs fail, databases go down, file permissions change.
  • Business logic edge cases: What happens when a user has exactly 0 balance?
  • Integration: Two correctly-typed modules can still interact badly.
  • Performance: Types don't tell you a function is O(n²).
  • Async timing: Race conditions, ordering bugs, timeout edge cases.

The Testing Pyramid

The testing pyramid is as applicable to TypeScript as to any language. Types shift where you invest:

TypeScript Shifts the Pyramid

Because the type checker catches shape errors, your unit test layer is smaller than in Python. You need fewer defensive tests. But the integration and E2E layers stay equally important — types don't run in production, your code does.

2. Vitest — The Modern Test Runner

If you're starting a new TypeScript project today, use Vitest. It's built on Vite, understands TypeScript and ESM natively (no transpilation step needed), and its API is intentionally compatible with Jest. If you know pytest, the mental model maps cleanly: a test runner that collects and runs functions.

Why Vitest Over Jest?

  • Native ESM & TypeScript: No Babel, no ts-jest, no config gymnastics.
  • Speed: Vitest shares the Vite transform pipeline — tests typically start 5–10× faster on cold runs.
  • Same API: Migrating from Jest is usually just a config change.
  • Built-in type testing: expectTypeOf is a first-class citizen.
  • UI mode: A browser-based test explorer out of the box.

Writing Your First Test

typescript src/math.ts 
export function add(a: number, b: number): number {
  return a + b
}

export function divide(a: number, b: number): number {
  if (b === 0) throw new Error('Division by zero')

import { describe, it, expect } from 'vitest'
import { add, divide } from './math'

describe('add', () => {
  it('adds two positive numbers', () => {
    expect(add(1, 2)).toBe(3)
  })

  it('handles negative numbers', () => {
    expect(add(-1, -2)).toBe(-3)
  })

  it('handles zero', () => {
    expect(add(0, 5)).toBe(5)

  it('divides correctly', () => {
    expect(divide(10, 2)).toBe(5)
  })

  it('throws on division by zero', () => {
    expect(() => divide(10, 0)).toThrow('Division by zero')
  })
})

Global Test Functions

With globals: true in the config, you get these available everywhere without imports:

describe(name, fn)
Groups related tests. Nest freely. Equivalent to class Test* or a module in pytest.
it(name, fn) / test()
Defines a single test case. it and test are identical — choose for readability.
expect(value)
Creates an assertion chain. All assertions hang off this.
beforeEach(fn)
Runs before every test in the current describe. Like pytest's function-scoped fixture.
afterEach(fn)
Cleanup after each test. Reset state, close connections.
beforeAll / afterAll
Run once before/after the entire describe block. Expensive setup (DB connections).
✍

Watch Mode for TDD

Run pnpm vitest (no arguments) for watch mode. Vitest reruns only the tests affected by your changes. This is the TDD loop: write a failing test, watch it go red, make it pass, watch it go green. Extremely fast feedback.

#    jest.fn()     → vi.fn()

ℹ

When to Keep Jest

If your project uses Next.js with the App Router, the Next.js team ships an official Jest preset. If you have a large team with established Jest tooling (custom reporters, CI integrations), migration risk may outweigh the speed gain. New projects: always Vitest.

4. Matchers Deep Dive

Both Vitest and Jest use the same matcher API. These are the methods you chain after expect(value). Coming from pytest, think of matchers as the right side of your assert value == expected.

Equality

typescript matchers/equality.test.ts 
// toBe — strict equality (Object.is). Use for primitives.
expect(1 + 1).toBe(2)
expect('hello').toBe('hello')
expect(null).toBe(null)

// toEqual — deep structural equality. Use for objects and arrays.
expect({ a: 1, b: [2, 3] }).toEqual({ a: 1, b: [2, 3] })
expect([1, 2, 3]).toEqual([1, 2, 3])

// toBe fails for objects (reference equality):
const obj = { x: 1 }
expect(obj).toBe(obj)         // ✓ same reference
expect({ x: 1 }).toBe({ x: 1 }) // ✗ different references!
expect({ x: 1 }).toEqual({ x: 1 }) // ✓ deep equal

// toMatchObject — partial matching (extra keys allowed)
const user = { id: 1, name: 'Alice', createdAt: new Date() }
expect(user).toMatchObject({ id: 1, name: 'Alice' }) // ✓ ignores createdAt

// toStrictEqual — like toEqual but also checks undefined properties and class instances
expect({ a: 1, b: undefined }).toEqual({ a: 1 })       // ✓ (ignores undefined)
expect({ a: 1, b: undefined }).toStrictEqual({ a: 1 })  // ✗ (undefined key matters)

Truthiness & Existence

typescript matchers/existence.test.ts 
expect(null).toBeNull()
expect(undefined).toBeUndefined()
expect('defined').toBeDefined()
expect(true).toBeTruthy()
expect(0).toBeFalsy()
expect('').toBeFalsy()

// Negation with .not
expect(1).not.toBeNull()
expect('hello').not.toBeUndefined()

Numbers & Collections

typescript matchers/collections.test.ts 
// Numbers
expect(10).toBeGreaterThan(5)
expect(5).toBeLessThan(10)
expect(10).toBeGreaterThanOrEqual(10)
expect(0.1 + 0.2).toBeCloseTo(0.3, 5) // floating point!

// Arrays and strings
expect([1, 2, 3]).toContain(2)
expect([1, 2, 3]).toHaveLength(3)
expect('hello world').toContain('world')
expect('hello').toHaveLength(5)

// Object property
expect({ name: 'Alice' }).toHaveProperty('name')
expect({ user: { id: 1 } }).toHaveProperty('user.id', 1)

Errors

typescript matchers/errors.test.ts 
function riskyOp(): never {
  throw new Error('Something went wrong')
}

// toThrow — wrap in arrow function!
expect(() => riskyOp()).toThrow()
expect(() => riskyOp()).toThrow('Something went wrong') // message match
expect(() => riskyOp()).toThrow(Error)                  // type match
expect(() => riskyOp()).toThrow(/went wrong/i)           // regex match

// Custom error classes
class ValidationError extends Error {
  constructor(public field: string, message: string) {
    super(message)
    this.name = 'ValidationError'
  }
}

function validateAge(age: number) {
  if (age < 0) throw new ValidationError('age', 'Age must be non-negative')
}

expect(() => validateAge(-1)).toThrow(ValidationError)
expect(() => validateAge(-1)).toThrow('Age must be non-negative')

Async Matchers

typescript matchers/async.test.ts 
async function fetchUser(id: number): Promise<{ id: number; name: string }> {
  if (id <= 0) throw new Error('Invalid ID')
  return { id, name: 'Alice' }
}

// resolves — unwrap the resolved value
it('fetches a user', async () => {
  await expect(fetchUser(1)).resolves.toEqual({ id: 1, name: 'Alice' })
  await expect(fetchUser(1)).resolves.toMatchObject({ name: 'Alice' })
})

// rejects — assert rejection
it('rejects invalid IDs', async () => {
  await expect(fetchUser(0)).rejects.toThrow('Invalid ID')
  await expect(fetchUser(-1)).rejects.toThrow(Error)
})

5. Mocking in TypeScript

Mocking replaces real dependencies with controlled fakes. TypeScript makes mocking safer because your mocks must match the type of the thing being mocked.

vi.fn() — Mock Functions

typescript mocking/fn.test.ts 
import { vi, it, expect } from 'vitest'

// Create a typed mock function
const mockGreet = vi.fn((name: string): string => `Hello, ${name}!`)

it('calls and returns correctly', () => {
  const result = mockGreet('Alice')

  expect(result).toBe('Hello, Alice!')
  expect(mockGreet).toHaveBeenCalledOnce()
  expect(mockGreet).toHaveBeenCalledWith('Alice')
})

it('can override the implementation', () => {
  mockGreet.mockReturnValue('Howdy!')
  expect(mockGreet('Bob')).toBe('Howdy!')

  mockGreet.mockImplementation((name) => `Yo ${name}`)
  expect(mockGreet('Bob')).toBe('Yo Bob')
})

it('resets between tests', () => {
  mockGreet.mockReset() // clear calls and implementation
  expect(mockGreet).not.toHaveBeenCalled()
})

vi.spyOn() — Spy on Existing Methods

typescript mocking/spy.test.ts 
import { vi, it, expect, afterEach } from 'vitest'

const emailService = {
  send(to: string, subject: string, body: string): boolean {
    // Real implementation would call SMTP...
    return true
  }
}

afterEach(() => {
  vi.restoreAllMocks() // ← critical: restore originals after each test
})

it('sends a welcome email on signup', () => {
  const sendSpy = vi.spyOn(emailService, 'send')
  sendSpy.mockReturnValue(true)

  // Run the code that should send an email
  signupUser('alice@example.com', emailService)

  expect(sendSpy).toHaveBeenCalledWith(
    'alice@example.com',
    'Welcome!',
    expect.stringContaining('Alice')
  )
})

vi.mock() — Module Mocking

typescript mocking/module.test.ts 
import { vi, describe, it, expect, beforeEach } from 'vitest'

// Mock an entire module — vi.mock() is hoisted to the top automatically
vi.mock('./database', () => ({
  db: {
    query: vi.fn(),
    insert: vi.fn(),
  }
}))

import { db } from './database'  // now gets the mock
import { createUser } from './user-service'

describe('createUser', () => {
  beforeEach(() => {
    vi.clearAllMocks()
  })

  it('inserts a user and returns the result', async () => {
    const mockUser = { id: '123', name: 'Alice', email: 'alice@example.com' }
    vi.mocked(db.insert).mockResolvedValue(mockUser)

    const result = await createUser({ name: 'Alice', email: 'alice@example.com' })

    expect(db.insert).toHaveBeenCalledWith(
      expect.objectContaining({ name: 'Alice' })
    )
    expect(result).toEqual(mockUser)
  })
})

Type-Safe Mocks with vi.mocked()

typescript mocking/typed.test.ts 
import { vi } from 'vitest'
import axios from 'axios'

vi.mock('axios')

// Without vi.mocked: TypeScript doesn't know axios.get is a mock
// axios.get.mockResolvedValue(...)  // ← Error: mockResolvedValue doesn't exist on typeof axios.get

// With vi.mocked: TypeScript knows this is a MockInstance, gets full autocomplete
const mockedGet = vi.mocked(axios.get)
mockedGet.mockResolvedValue({
  data: { users: [{ id: 1, name: 'Alice' }] },
  status: 200,
})

Mocking Timers

typescript mocking/timers.test.ts 
import { vi, it, expect, beforeEach, afterEach } from 'vitest'

function debounce<T extends unknown[]>(fn: (...args: T) => void, delay: number) {
  let timer: ReturnType<typeof setTimeout>
  return (...args: T) => {
    clearTimeout(timer)
    timer = setTimeout(() => fn(...args), delay)
  }
}

beforeEach(() => { vi.useFakeTimers() })
afterEach(() => { vi.useRealTimers() })

it('debounces the function call', () => {
  const handler = vi.fn()
  const debounced = debounce(handler, 300)

  debounced('a')
  debounced('b')
  debounced('c')

  // Handler not yet called
  expect(handler).not.toHaveBeenCalled()

  // Fast-forward time
  vi.advanceTimersByTime(300)

  expect(handler).toHaveBeenCalledOnce()
  expect(handler).toHaveBeenCalledWith('c')
})
⚠

When NOT to Mock

Mocking has a cost: your mock is only as accurate as your understanding of the real dependency. Over-mocking leads to tests that pass but code that breaks in production. Use mocks for: external APIs, email services, payment providers. Avoid mocking your own internal modules — test them directly.

6. Testing Async Code

Async is everywhere in TypeScript — HTTP calls, database queries, file I/O. Testing it correctly requires understanding how Vitest handles Promises.

The Golden Rule: Always Await or Return

✗ Incorrect — test always passes
it('fetches data', () => {
  // WRONG: Promise ignored,
  // test passes before fetch completes
  fetchUser(1).then(user => {
    expect(user.name).toBe('Alice')
  })
})
✓ Correct — awaited
it('fetches data', async () => {
  // RIGHT: await ensures assertion
  // runs before test exits
  const user = await fetchUser(1)
  expect(user.name).toBe('Alice')
})

Testing Error Handling

typescript async/error-handling.test.ts 
import { it, expect } from 'vitest'

async function getUser(id: number) {
  if (id <= 0) throw new Error(`Invalid user ID: ${id}`)
  const response = await fetch(`/api/users/${id}`)
  if (!response.ok) throw new Error(`HTTP error ${response.status}`)
  return response.json()
}

// Option 1: rejects matcher (cleanest)
it('rejects negative IDs', async () => {
  await expect(getUser(-1)).rejects.toThrow('Invalid user ID: -1')
})

// Option 2: try/catch (useful for additional assertions)
it('throws with the correct message', async () => {
  expect.assertions(2) // ← ensures assertions actually run
  try {
    await getUser(0)
  } catch (error) {
    expect(error).toBeInstanceOf(Error)
    expect((error as Error).message).toBe('Invalid user ID: 0')
  }
})
✓

expect.assertions(n)

When using try/catch in tests, call expect.assertions(n) at the top of the test. This causes the test to fail if the expected number of assertions didn't run — protecting you from a silent pass when the error is never thrown.

Timeout Configuration

7. Integration Testing

Integration tests verify that multiple parts of your system work together. In TypeScript/Node.js, the most common integration tests cover HTTP APIs and database interactions.

Testing HTTP APIs with Hono

typescript integration/api.test.ts 
import { describe, it, expect } from 'vitest'
import { Hono } from 'hono'
import { testClient } from 'hono/testing'

// The actual app (or a test version of it)
const app = new Hono()

app.get('/users/:id', (c) => {
  const id = c.req.param('id')
  return c.json({ id, name: 'Alice' })
})

app.post('/users', async (c) => {
  const body = await c.req.json()
  if (!body.name) return c.json({ error: 'name required' }, 400)
  return c.json({ id: '123', ...body }, 201)
})

// Hono's testClient: no network, direct function calls
const client = testClient(app)

describe('GET /users/:id', () => {
  it('returns a user', async () => {
    const res = await client.users[':id'].$get({ param: { id: '1' } })
    expect(res.status).toBe(200)

    const body = await res.json()
    expect(body).toMatchObject({ id: '1', name: 'Alice' })
  })
})

describe('POST /users', () => {
  it('creates a user', async () => {
    const res = await client.users.$post({ json: { name: 'Bob' } })
    expect(res.status).toBe(201)
  })

  it('rejects missing name', async () => {
    const res = await client.users.$post({ json: {} })
    expect(res.status).toBe(400)
  })
})

Database Integration Tests

typescript integration/db.test.ts 
import { describe, it, expect, beforeAll, afterAll, beforeEach } from 'vitest'
import { drizzle } from 'drizzle-orm/node-postgres'
import { Pool } from 'pg'

    expect(result).toHaveLength(1)
    expect(result[0]).toMatchObject({ name: 'Alice' })
  })
})

8. Testing Types Themselves

This is unique to TypeScript. Library authors — and increasingly, application developers — need to verify that their types behave correctly. A function might return the right runtime value but infer the wrong type. Type tests catch that.

expectTypeOf() — Vitest's Built-in

typescript types/inference.test.ts 
import { it, expectTypeOf } from 'vitest'

function identity<T>(value: T): T {
  return value
}

function getFirstItem<T>(arr: T[]): T | undefined {
  return arr[0]
}

it('identity returns the same type', () => {
  expectTypeOf(identity(42)).toBeNumber()
  expectTypeOf(identity('hello')).toBeString()
  expectTypeOf(identity({ x: 1 })).toEqualTypeOf<{ x: number }>()
})

it('getFirstItem returns T | undefined', () => {
  expectTypeOf(getFirstItem([1, 2, 3])).toEqualTypeOf<number | undefined>()
  expectTypeOf(getFirstItem(['a', 'b'])).toEqualTypeOf<string | undefined>()
})

it('checks function parameter types', () => {
  expectTypeOf(identity).parameter(0).toBeNumber()
  // ↑ This will fail because identity<T> is generic — good to know!
})

Testing Conditional Types

typescript types/conditional.test.ts 
import { it, expectTypeOf } from 'vitest'

// A utility type we want to verify
type NonNullable<T> = T extends null | undefined ? never : T
type Awaited<T> = T extends Promise<infer U> ? U : T

it('NonNullable strips null and undefined', () => {
  expectTypeOf<NonNullable<string | null>>().toEqualTypeOf<string>()
  expectTypeOf<NonNullable<number | undefined>>().toEqualTypeOf<number>()
})

it('Awaited unwraps Promises', () => {
  expectTypeOf<Awaited<Promise<string>>>().toEqualTypeOf<string>()
  expectTypeOf<Awaited<number>>().toEqualTypeOf<number>() // non-promise passthrough
})

@ts-expect-error Directive

typescript types/expect-error.test.ts 
// @ts-expect-error tells TypeScript: "the NEXT line MUST be a type error"
// If the next line is NOT an error, TypeScript itself fails.
// This is how you verify that invalid code is correctly rejected.

function add(a: number, b: number): number {
  return a + b
}

// Verify the type system rejects wrong inputs:
// @ts-expect-error — string argument to number parameter
add('hello', 2)

// @ts-expect-error — missing argument
add(1)

// @ts-expect-error — too many arguments
add(1, 2, 3)

// If you change add's signature to accept strings, the @ts-expect-error
// becomes an error itself — alerting you that your types loosened unexpectedly.
★

Best Practice: Library Authors

If you publish a TypeScript library, type tests are as important as runtime tests. A type regression — where your library suddenly infers any instead of a specific type — can silently break consumer code without any runtime error. The tsd package is an alternative to expectTypeOf that runs type checks as a separate compilation step.

9. Code Coverage

Coverage measures which lines, branches, and functions your tests exercise. It's a useful signal, not a target. A codebase with 100% coverage can still have terrible tests.

Setup

terminal 
pnpm add -D @vitest/coverage-v8
# Then run:
pnpm vitest run --coverage
typescript vitest.config.ts (coverage section) 
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',            // or 'istanbul'
      reporter: ['text', 'html', 'lcov'],
      include: ['src/**/*.ts'],  // only measure source files
      exclude: [                 // skip test files, generated code, types
        'src/**/*.test.ts',
        'src/**/*.d.ts',
        'src/generated/**',
      ],
      thresholds: {
        lines: 80,
        functions: 80,
        branches: 70,
        statements: 80,
      },
    },
  },

100% Coverage Theater

You can achieve 100% coverage with tests that make no assertions. Coverage tells you which code was executed, not whether it was tested correctly. Aim for meaningful coverage of critical paths. A thoughtful 75% is better than a hollow 100%. Don't let coverage thresholds drive you to write useless tests.

10. Testing Best Practices

Arrange-Act-Assert (AAA)

typescript patterns/aaa.test.ts 
it('calculates order total with discount', () => {
  // ARRANGE — set up the world
  const items = [
    { price: 10.00, quantity: 2 },
    { price: 5.00,  quantity: 1 },
  ]
  const discountPercent = 10

  // ACT — do the thing
  const total = calculateOrderTotal(items, discountPercent)

  // ASSERT — verify the result
  expect(total).toBeCloseTo(22.50) // (25.00 - 10%)
})

Test Naming Conventions

typescript patterns/naming.test.ts 
// Pattern: "it [verb]s [what] when [condition]"
it('returns null when user is not found')
it('throws ValidationError when email is invalid')
it('sends a welcome email when user registers')
it('calculates total including tax')

// Good describe grouping:
describe('UserService', () => {
  describe('createUser', () => {
    it('inserts the user into the database', ...)
    it('hashes the password before storing', ...)
    it('throws DuplicateEmailError when email exists', ...)
  })
  describe('deleteUser', () => {
    it('marks the user as deleted', ...)
    it('throws NotFoundError when user does not exist', ...)
  })
})

The TDD Red-Green-Refactor Cycle

1. Red — Write a failing test
it('validates email format', () => {
  expect(isValidEmail('notanemail'))
    .toBe(false)
  expect(isValidEmail('a@b.com'))
    .toBe(true)
})

// isValidEmail doesn't exist yet
// → Test fails: Cannot find name
2. Green — Make it pass (minimal)
export function isValidEmail(
  email: string
): boolean {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/
    .test(email)
}

// Run vitest — test passes
// 3. Refactor: improve implementation
//    without breaking the test

What NOT to Test

  • TypeScript types: Don't test that a string variable holds a string — the compiler ensures it.
  • Third-party library internals: Trust that axios sends HTTP requests correctly.
  • Simple getters: A one-line property accessor usually doesn't need its own test.
  • Implementation details: Test the contract, not that a specific private method was called.
  • Trivial code: return value * 2 is fine to leave uncovered.
★

Best Practice: Test Isolation

Each test must pass or fail independently of every other test. Never rely on execution order. Use beforeEach to reset state. Avoid global mutable variables in test files. If tests pass individually but fail when run together, you have a shared-state bug.

11. Python pytest → Vitest Comparison

If you've been writing pytest tests for years, here's everything you already know mapped to Vitest. The concepts are identical — only the syntax changes.

Concept pytest (Python) Vitest (TypeScript) Notes
Test file naming test_math.py math.test.ts Convention: colocate or use __tests__/
Test function def test_add(): ... it('adds numbers', () => {...}) test() is alias for it()
Test grouping class TestMath: describe('Math', () => {...}) describe nests freely
Assertion assert result == expected expect(result).toBe(expected) Vitest gives better failure messages
Deep equality assert obj == {'a': 1} expect(obj).toEqual({a: 1}) Use toEqual, not toBe, for objects
Function-scoped fixture @pytest.fixture beforeEach / afterEach Run before/after each test in block
Module-scoped fixture @pytest.fixture(scope='module') beforeAll / afterAll Run once per describe
Shared fixtures conftest.py vitest.setup.ts Configured via setupFiles in vitest.config
Parameterized tests @pytest.mark.parametrize('a,b', [(1,2)]) it.each([[1,2]])('adds %i+%i', ...) Also: test.each
Expected exception with pytest.raises(ValueError): expect(() => fn()).toThrow() Wrap in arrow function!
Skip a test @pytest.mark.skip it.skip('name', ...) Or prefix with x: xit()
Run only this test pytest -k "test_name" it.only('name', ...) Or: vitest -t "test name"
Mock a function mocker.patch('module.fn') vi.fn() / vi.spyOn() Vitest: explicit, type-safe
Mock a module mocker.patch('module') vi.mock('./module') Hoisted automatically by Vitest
Fake time freezegun library vi.useFakeTimers() Built-in, no extra dependency
Async test @pytest.mark.asyncio it('name', async () => {...}) Vitest handles async natively
Coverage pytest --cov vitest run --coverage Uses V8 or Istanbul
Watch mode pytest-watch (plugin) vitest (default mode) Watch is the default, not --watch

it.each — pytest.mark.parametrize Equivalent

typescript patterns/parametrize.test.ts 
import { it, expect, describe } from 'vitest'
import { add } from './math'

// Array of [a, b, expected] tuples — identical mental model to pytest.mark.parametrize
describe('add', () => {
  it.each([
    [1,  2,  3],
    [0,  0,  0],
    [-1, 1,  0],
    [-5, -3, -8],
  ])('add(%i, %i) === %i', (a, b, expected) => {
    expect(add(a, b)).toBe(expected)
  })
})

// Object form (more readable for many parameters):
it.each([
  { input: 'hello world', expected: 'HELLO WORLD' },
  { input: '',            expected: '' },
  { input: 'abc',         expected: 'ABC' },
])('toUpperCase($input) === $expected', ({ input, expected }) => {
  expect(input.toUpperCase()).toBe(expected)
})
🍎

The Biggest Mental Shift

In pytest, fixtures are injected by name as function parameters — a form of dependency injection built into the framework. In Vitest, you handle setup in beforeEach and share values through closure variables. It's less magical but equally powerful. Once you internalize the closure pattern, you'll find the Vitest approach actually easier to trace and debug.

conftest.py → vitest.setup.ts

typescript vitest.setup.ts 
import { beforeAll, afterAll, beforeEach, vi } from 'vitest'
import { db } from './src/database'

// Global setup — runs before ALL tests (like conftest.py at the root)
beforeAll(async () => {
  await db.connect()
})

afterAll(async () => {
  await db.disconnect()
})

// Reset fetch mocks between every test
beforeEach(() => {
  vi.restoreAllMocks()
})

// Extend expect with custom matchers
import { expect } from 'vitest'

expect.extend({
  toBeWithinRange(received: number, floor: number, ceiling: number) {
    const pass = received >= floor && received <= ceiling
    return {
      pass,
      message: () =>
        `expected ${received} to be within range [${floor}, ${ceiling}]`,
    }
  },
})
⚡

AI Era: LLMs and Test Generation

AI assistants are remarkably good at generating test boilerplate from function signatures. Feed Claude or GitHub Copilot a function and ask for tests — you'll get a solid starting point in seconds. But read every generated test carefully: LLMs hallucinate edge cases, sometimes write assertions that always pass, and rarely generate good integration tests. Use AI to skip the boring parts, then apply your judgment on what actually matters to test.
