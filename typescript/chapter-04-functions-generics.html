Chapter 4

Functions, Generics & Type Inference

This chapter is where TypeScript stops feeling like "annotated JavaScript" and starts feeling like a powerful type system in its own right. Generics are the single most important thing to master — they are how TypeScript remains expressive without losing safety. By the end of this chapter you will write generic functions that work across types without sacrificing a single bit of type information.

1. Functions in TypeScript

TypeScript builds directly on JavaScript's three function syntaxes and adds optional type annotations to parameters and return values. You never have to annotate return types — TypeScript infers them — but annotating them is a form of documentation and a safety net.

Three syntaxes, one type system

All three function syntaxes TypeScript 
// 1. Function declaration
function add(a: number, b: number): number {
  return a + b;
}

// 2. Function expression (assigned to a variable)
const subtract = function(a: number, b: number): number {
  return a - b;
};

// 3. Arrow function — most common in modern TypeScript
const multiply = (a: number, b: number): number => a * b;

// Return type is INFERRED — annotation optional
const divide = (a: number, b: number) => a / b; // inferred: number
Mental Model

Think of the colon after each parameter name as a "is of type" declaration: a: number reads as "a is of type number." The colon after the closing parenthesis ): number reads as "returns type number." Once you read it that way, the syntax becomes second nature.

Optional parameters

Append ? after a parameter name to make it optional. Inside the function, its type becomes T | undefined, so you must handle both cases.

Optional parameters TypeScript 
function greet(name: string, greeting?: string): string {
  // greeting is `string | undefined` here
  return `${greeting ?? "Hello"}, ${name}!`;
}

greet("Alice");           // "Hello, Alice!"
greet("Alice", "Hey");   // "Hey, Alice!"

Default parameters

Default parameters automatically infer their type from the default value. You rarely need an explicit annotation.

Default parameters — type is inferred from the default TypeScript 
// greeting inferred as `string`, not `string | undefined`
function greet(name: string, greeting = "Hello"): string {
  return `${greeting}, ${name}!`;
}

// TypeScript error: Argument of type 'number' is not assignable
// to parameter of type 'string'.
greet("Alice", 42);

Rest parameters

Rest parameters — typed as an array TypeScript 
function sum(...numbers: number[]): number {
  return numbers.reduce((acc, n) => acc + n, 0);
}

sum(1, 2, 3, 4); // 10

// You can also use tuple rest for strongly-typed variadic functions
function first(...args: [T, ...unknown[]]): T {
  return args[0];
}

2. Function Types

In TypeScript, functions are first-class values, and so they need types. A function type describes what a function accepts and returns — without saying how it does it.

Function type expressions

Function type expressions TypeScript 
// The type of "a function that takes a string and returns void"
type StringCallback = (s: string) => void;

// Use it as a parameter type
function forEach(arr: string[], callback: StringCallback): void {
  for (const item of arr) {
    callback(item);
  }
}

forEach(["a", "b", "c"], (item) => {
  //                       ^^^^ TypeScript knows item: string
  console.log(item.toUpperCase());
});

Call signatures in type aliases

When you want to describe a callable object (a function that also has properties), use a call signature inside an interface or object type.

Call signatures TypeScript 
type DescribableFunction = {
  description: string;
  // This is the call signature
  (someArg: number): boolean;
};

function doSomething(fn: DescribableFunction) {
  console.log(fn.description + " returned " + fn(6));
}

const myFn: DescribableFunction = (n: number) => n > 5;
myFn.description = "Checks if number is greater than 5";

doSomething(myFn);

Function overloads

Overloads let you declare multiple type signatures for a single function. TypeScript uses the overload signatures for type checking and the implementation signature (which must be compatible with all overloads) to do the actual work.

Warning

The implementation signature is not visible to callers. Only the overload signatures are. Do not put string | number in the overloads — put that only in the implementation.

Function overloads TypeScript 
// Overload signatures (visible to callers)
function format(value: string): string;
function format(value: number, decimals: number): string;

// Implementation signature (not directly callable by callers)
function format(value: string | number, decimals?: number): string {
  if (typeof value === "string") {
    return value.trim();
  }
  return value.toFixed(decimals ?? 2);
}

format("  hello  ");    // "hello"
format(3.14159, 2);     // "3.14"
format(3.14159);        // Error — no matching overload

The this parameter

Unlike Python's self, JavaScript's this is dynamic — its value depends on how the function is called. TypeScript lets you annotate a fake first parameter named this to document and enforce the expected this type. This parameter is erased at runtime.

The this parameter TypeScript 
interface User {
  name: string;
  greet(this: User): void;
}

const user: User = {
  name: "Alice",
  greet() {
    console.log(`Hello, I'm ${this.name}`);
  },
};

// Safe: called as a method
user.greet();

// Unsafe: TypeScript catches this
const { greet } = user;
greet(); // Error: The 'this' context of type 'void' is not assignable...
Python Comparison

In Python, self is always the first argument and always refers to the instance — there is no ambiguity. In JavaScript, this is set by the call site, not the definition site. This is a genuine source of bugs. Arrow functions capture this lexically (like a Python method would), which is why you see them so often in class bodies. TypeScript's this parameter lets the compiler catch the cases where you accidentally lose this binding.

3. Type Inference — TypeScript's Superpower

TypeScript's inference engine is sophisticated. In the majority of situations, you do not need to write type annotations because TypeScript can figure them out from context. Over-annotating is a sign of inexperience — it adds visual noise without adding safety.

Return type inference

Over-annotated (unnecessary)
// These annotations repeat information TypeScript
// already knows. Don't do this.
const double = (n: number): number => n * 2;
const isEven = (n: number): boolean => n % 2 === 0;
const toStr = (n: number): string => String(n);
Let TypeScript infer (preferred)
// TypeScript infers the return type from the body.
// Cleaner, same safety.
const double = (n: number) => n * 2;         // number
const isEven = (n: number) => n % 2 === 0;   // boolean
const toStr = (n: number) => String(n);       // string
Tip — When to annotate return types

Annotate return types on public API functions and exported functions. This acts as documentation and catches the case where you accidentally return the wrong type deep inside the function body. For internal, short functions, trust inference.

Contextual typing

TypeScript infers types from context — when you pass a function to .map(), TypeScript already knows the parameter type based on the array element type.

Contextual typing in action TypeScript 
const names = ["Alice", "Bob", "Charlie"];

// TypeScript knows `name` is `string` because names is `string[]`
const upper = names.map((name) => name.toUpperCase());
//                       ^^^^ string — inferred from context

const lengths = names.map((name) => name.length);
//                                  ^^^^^^^^^^^^ number[] inferred

const assertions and literal type inference

By default, TypeScript widens literal types. const x = "hello" infers x: string, not x: "hello". Use as const to lock the value to its narrowest literal type.

as const — freeze to literal types TypeScript 
// Without as const: widened types
const config = {
  endpoint: "/api/v1",
  method: "GET",
};
// config.method: string  ← too wide

// With as const: literal types, readonly deeply
const config2 = {
  endpoint: "/api/v1",
  method: "GET",
} as const;
// config2.method: "GET"  ← exact literal
// config2 is readonly — you can't mutate it

// Useful for discriminated unions and exhaustive checks
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
function request(url: string, method: HttpMethod) { /* ... */ }

request(config.endpoint, config.method);   // Error: string not assignable to HttpMethod
request(config2.endpoint, config2.method); // OK: "GET" matches

The satisfies operator (TypeScript 4.9+)

satisfies validates that a value conforms to a type without widening the inferred type of the value. It gives you the best of both worlds: type safety from the constraint and precise inference from the value.

Using type annotation — loses precision
type Palette = Record<string, string[]>;

// TypeScript enforces the constraint, but loses
// the specific key names in the inferred type.
const palette: Palette = {
  red: ["#ff0000", "#cc0000"],
  blue: ["#0000ff"],
};

// Error: palette.red is string[] | string
// TypeScript doesn't know "red" is a key
palette.purple; // No error — but "purple" doesn't exist!
Using satisfies — keeps precision
type Palette = Record<string, string[]>;

// satisfies validates the shape but keeps
// the exact keys in the inferred type.
const palette = {
  red: ["#ff0000", "#cc0000"],
  blue: ["#0000ff"],
} satisfies Palette;

palette.red;    // string[] ← TypeScript knows this key
palette.purple; // Error: Property 'purple' does not exist

4. Generics — The Heart of Reusable TypeScript

A generic function is a function that works over many types while preserving type information. Without generics, you either write a separate function for each type, or you use any and lose all safety. Generics are the third option — the correct option.

Python Comparison — TypeVar

Python's equivalent is TypeVar. In Python you write: T = TypeVar("T"); def identity(x: T) -> T: return x. TypeScript eliminates the separate declaration and puts the type parameter inline on the function: function identity<T>(x: T): T { return x; }. Python 3.12+ introduced def identity[T](x: T) -> T syntax that mirrors TypeScript more closely.

The identity function — simplest possible generic

Generic identity function TypeScript 
// T is a type parameter — a placeholder for a real type.
// TypeScript fills it in when the function is called.
function identity<T>(value: T): T {
  return value;
}

// TypeScript infers T = string from the argument
const str = identity("hello");   // string
const num = identity(42);        // number
const bool = identity(true);     // boolean

// You can also pass T explicitly (rare — prefer inference)
const explicit = identity<string>("world");
When you call identity("hello"), TypeScript binds T = string at the call site and propagates it through the function, so the return type is exactly string — not the wider unknown or any.

Multiple type parameters

Multiple type parameters TypeScript 
// Two independent type parameters A and B
function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

const result = pair("Alice", 30);
//    ^^^^^^  [string, number] — fully typed tuple

// Real-world example: Map-like transform
function mapValues<K extends string, V, R>(
  obj: Record<K, V>,
  fn: (value: V, key: K) => R
): Record<K, R> {
  const result = {} as Record<K, R>;
  for (const key in obj) {
    result[key] = fn(obj[key], key);
  }
  return result;
}

const doubled = mapValues({ a: 1, b: 2 }, (v) => v * 2);
// { a: number, b: number }

Default type parameters

Default type parameters TypeScript 
// T defaults to string if not specified
function createArray<T = string>(length: number, fill: T): T[] {
  return Array.from({ length }, () => fill);
}

// T inferred from argument — default not used
const nums = createArray(3, 0);       // number[]
const strs = createArray(3, "hello"); // string[]

// T = string (default) — you'd need to pass fill to use default

Real-world generic utilities

wrap, unwrap, first, last, pick, omit TypeScript 
// Wrap any value in a container
function wrap<T>(value: T): { value: T } {
  return { value };
}

function unwrap<T>(wrapped: { value: T }): T {
  return wrapped.value;
}

// Safely get first/last elements
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

function last<T>(arr: T[]): T | undefined {
  return arr[arr.length - 1];
}

// Pick specific keys from an object
function pick<T extends object, K extends keyof T>(
  obj: T,
  keys: K[]
): Pick<T, K> {
  return keys.reduce(
    (acc, key) => ({ ...acc, [key]: obj[key] }),
    {} as Pick<T, K>
  );
}

// Omit specific keys from an object
function omit<T extends object, K extends keyof T>(
  obj: T,
  keys: K[]
): Omit<T, K> {
  const result = { ...obj };
  for (const key of keys) delete result[key];
  return result;
}

const user = { id: "1", name: "Alice", age: 30, role: "admin" };

const publicInfo = pick(user, ["name", "role"]);
// { name: string; role: string }

const withoutRole = omit(user, ["role", "age"]);
// { id: string; name: string }

5. Generic Constraints in Depth

Unconstrained generics are maximally flexible but minimally useful — you can only do things that work on every possible type (i.e., almost nothing). Constraints narrow what T can be, unlocking more capabilities.

The extends keyword

Without constraint — TypeScript error
// ERROR: Property 'length' does not exist
// on type 'T' — T could be anything!
function getLength<T>(value: T): number {
  return value.length;
  //     ^^^^^^^^^^^^^ Error
}
With constraint — TypeScript happy
// T must have a .length property
function getLength<T extends { length: number }>(
  value: T
): number {
  return value.length; // safe: T has .length
}

getLength("hello");    // 5
getLength([1, 2, 3]);  // 3
getLength({ length: 7, name: "file" }); // 7
getLength(42); // Error: number has no .length

The keyof operator

keyof T produces a union of all the keys of type T. Combining keyof with generics gives you type-safe property access.

keyof — type-safe property lookup TypeScript 
// K must be a key of T — ensures obj[key] is valid
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: "u1", name: "Alice", age: 30 };

const name = getProperty(user, "name");  // string — inferred!
const age  = getProperty(user, "age");   // number — inferred!

// TypeScript error: "email" is not a key of user
getProperty(user, "email"); // Error
Mental Model — T[K] is "indexed access"

T[K] is TypeScript's way of saying "the type you get when you look up key K in type T." If T = { name: string; age: number } and K = "name", then T[K] = string. It is the type-level equivalent of obj[key] at runtime.

Type-safe fetch wrapper

Generic fetch wrapper TypeScript 
// Without this wrapper, fetch returns Promise<any> effectively
async function typedFetch<T>(
  url: string,
  options?: RequestInit
): Promise<T> {
  const response = await fetch(url, options);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }
  return response.json() as Promise<T>;
}

// Usage — T is specified at the call site
interface User {
  id: string;
  name: string;
  email: string;
}

const user = await typedFetch<User>("/api/users/1");
//    ^^^^ User — fully typed. No manual casting needed.
console.log(user.name); // TypeScript knows this is string

Type-safe event emitter

Generic event emitter — maps event names to payload types TypeScript 
type EventMap = Record<string, unknown>;

class TypedEventEmitter<Events extends EventMap> {
  private listeners = new Map<keyof Events, Set<Function>>();

  on<K extends keyof Events>(
    event: K,
    listener: (payload: Events[K]) => void
  ): this {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(listener);
    return this;
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    this.listeners.get(event)?.forEach((fn) => fn(payload));
  }
}

// Define your event shape in one place
interface AppEvents {
  "user:login": { userId: string; timestamp: Date };
  "user:logout": { userId: string };
  "message:sent": { content: string; channelId: string };
}

const emitter = new TypedEventEmitter<AppEvents>();

// TypeScript knows the shape of each event payload
emitter.on("user:login", ({ userId, timestamp }) => {
  //                        ^^^^^^  string, Date — inferred!
  console.log(`${userId} logged in at ${timestamp}`);
});

emitter.emit("user:login", { userId: "u1", timestamp: new Date() }); // OK
emitter.emit("user:login", { userId: "u1" }); // Error: missing timestamp
emitter.emit("unknown:event", {}); // Error: not in AppEvents

6. Higher-Order Functions

map, filter, reduce — typed correctly

Typed HOFs TypeScript 
// The built-in Array methods are generic — let's write our own
function map<T, U>(arr: T[], fn: (item: T, i: number) => U): U[] {
  return arr.map(fn);
}

function filter<T>(arr: T[], pred: (item: T) => boolean): T[] {
  return arr.filter(pred);
}

function reduce<T, Acc>(
  arr: T[],
  fn: (acc: Acc, item: T) => Acc,
  initial: Acc
): Acc {
  return arr.reduce(fn, initial);
}

const numbers = [1, 2, 3, 4, 5];

// TypeScript infers U = string in map
const strings = map(numbers, (n) => n.toString()); // string[]

// TypeScript keeps T = number in filter
const evens = filter(numbers, (n) => n % 2 === 0); // number[]

// TypeScript infers Acc = number from initial value
const total = reduce(numbers, (acc, n) => acc + n, 0); // number

Currying

Typed currying TypeScript 
// A curried function takes its arguments one at a time
function curry<A, B, C>(fn: (a: A, b: B) => C): (a: A) => (b: B) => C {
  return (a) => (b) => fn(a, b);
}

const add = (a: number, b: number) => a + b;
const curriedAdd = curry(add);
//    ^^^^^^^^^^  (a: number) => (b: number) => number

const add5 = curriedAdd(5);  // (b: number) => number
const ten = add5(5);          // 10

// Practical use: pre-configuring callbacks
const double = curry((factor: number, value: number) => factor * value)(2);
const tripled = [1, 2, 3].map(
  curry((factor: number, value: number) => factor * value)(3)
); // [3, 6, 9]

Utility types: ReturnType, Parameters, Awaited

TypeScript ships with several utility types that extract type information from functions. These are invaluable when working with third-party code you do not control.

ReturnType, Parameters, Awaited TypeScript 
async function fetchUser(id: string) {
  const res = await fetch(`/api/users/${id}`);
  return res.json() as Promise<{ id: string; name: string }>;
}

// Extract return type — useful for typing derived data
type FetchUserReturn = ReturnType<typeof fetchUser>;
// Promise<{ id: string; name: string }>

// Unwrap the Promise
type User = Awaited<ReturnType<typeof fetchUser>>;
// { id: string; name: string }

// Extract parameter types as a tuple
type FetchUserParams = Parameters<typeof fetchUser>;
// [id: string]

type FirstParam = FetchUserParams[0];
// string

// Real-world usage: mocking in tests
function mockFetch(
  ...args: Parameters<typeof fetchUser>
): ReturnType<typeof fetchUser> {
  return Promise.resolve({ id: args[0], name: "Mock User" });
}
AI Era Note

When building AI pipelines, you often chain async operations: fetch data, call an LLM API, parse the response, store results. Awaited<T> and ReturnType<T> let you derive types from your pipeline functions rather than re-declaring them, keeping your AI agent's type system in sync automatically as the pipeline evolves.

7. Async Functions

TypeScript's async/await mirrors JavaScript's exactly, adding one rule: an async function's return type is always Promise<T>, where T is whatever the function body resolves to.

async/await with typed Promise TypeScript 
interface User {
  id: string;
  name: string;
  email: string;
}

// Return type annotation is optional — TypeScript infers Promise<User>
async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`);

  if (!response.ok) {
    throw new Error(`Failed to fetch user ${id}`);
  }

  return response.json();
}

// Callers use await to get the User — no Promise handling needed
const user = await fetchUser("u1");
console.log(user.name); // TypeScript knows: string

Error handling with typed errors

Warning — catch gives you unknown, not Error

In TypeScript's strict mode, the catch variable is typed as unknown, not Error. This is correct — anything can be thrown. Always narrow before using.

Typed error handling TypeScript 
class ApiError extends Error {
  constructor(
    message: string,
    public readonly statusCode: number
  ) {
    super(message);
    this.name = "ApiError";
  }
}

async function fetchUserSafe(id: string): Promise<User | null> {
  try {
    return await fetchUser(id);
  } catch (error: unknown) {
    // Narrow the error type before using it
    if (error instanceof ApiError) {
      console.error(`API error ${error.statusCode}: ${error.message}`);
      return null;
    }
    if (error instanceof Error) {
      console.error(`Network error: ${error.message}`);
      return null;
    }
    // Unknown error — re-throw
    throw error;
  }
}

Promise combinators with generics

Promise.all, allSettled, race — inferred types TypeScript 
// Promise.all: tuple of types when given tuple input
const [user, posts] = await Promise.all([
  fetchUser("u1"),         // Promise<User>
  fetchPosts("u1"),        // Promise<Post[]>
]);
// user: User, posts: Post[] — exact types preserved

// Promise.allSettled: each result has status + value or reason
const results = await Promise.allSettled([
  fetchUser("u1"),
  fetchUser("nonexistent"),
]);

for (const result of results) {
  if (result.status === "fulfilled") {
    console.log(result.value.name); // TypeScript: User
  } else {
    console.error(result.reason);   // TypeScript: any (unknown failure)
  }
}

// Promise.race: returns the type of the fastest resolving promise
async function withTimeout<T>(
  promise: Promise<T>,
  ms: number
): Promise<T> {
  const timeout = new Promise<never>((_resolve, reject) =>
    setTimeout(() => reject(new Error(`Timed out after ${ms}ms`)), ms)
  );
  return Promise.race([promise, timeout]);
}

8. Type Narrowing with Functions

TypeScript narrows types inside if blocks based on checks like typeof and instanceof. But sometimes you want to put that narrowing logic inside a reusable function. That requires a special return type: a type predicate.

Type predicates

Type predicates — value is T TypeScript 
// Without a type predicate, the return is just boolean
// and TypeScript doesn't narrow after the call.
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function processInput(value: unknown) {
  if (isString(value)) {
    // value: string here — TypeScript narrowed it!
    console.log(value.toUpperCase());
  }
}

// A more complex type guard
interface Cat { meow(): void; }
interface Dog { bark(): void; }

function isCat(animal: Cat | Dog): animal is Cat {
  return "meow" in animal;
}

function handleAnimal(animal: Cat | Dog) {
  if (isCat(animal)) {
    animal.meow(); // TypeScript: Cat
  } else {
    animal.bark(); // TypeScript: Dog
  }
}

Assertion functions

Assertion functions — asserts condition TypeScript 
// When the function returns normally (doesn't throw),
// TypeScript knows the condition is true.
function assert(condition: boolean, message?: string): asserts condition {
  if (!condition) {
    throw new Error(message ?? "Assertion failed");
  }
}

function assertIsString(value: unknown): asserts value is string {
  if (typeof value !== "string") {
    throw new TypeError(`Expected string, got ${typeof value}`);
  }
}

// Usage
function processEnvVar(name: string) {
  const value = process.env[name];
  // value is `string | undefined` before the assertion
  assertIsString(value);
  // After the assertion, TypeScript knows value is string
  return value.trim();
}
Mental Model — Type predicates vs Assertion functions

A type predicate (value is string) is used in an if condition — "if this returns true, narrow the type inside the block." An assertion function (asserts condition) says "if this function returns at all (i.e., doesn't throw), then the condition is true from here on." Use predicates for conditional branching; use assertions for "must be valid or crash" scenarios.

9. Real-World Generic Patterns

Generic API response wrapper

ApiResponse<T> — standardize all API returns TypeScript 
// Define the wrapper once
type ApiResponse<T> =
  | { success: true; data: T; error: null }
  | { success: false; data: null; error: string };

// Helper constructors
function ok<T>(data: T): ApiResponse<T> {
  return { success: true, data, error: null };
}

function fail<T>(error: string): ApiResponse<T> {
  return { success: false, data: null, error };
}

// Usage in route handlers
async function getUserHandler(id: string): Promise<ApiResponse<User>> {

interface Repository<T extends Entity> {

  findAll(): Promise<T[]>;

  delete(id: string): Promise<boolean>;
}

  }

    return null;
  }

  async delete(id: string): Promise<boolean> {
    return true;
  }

// Generic service that works with ANY repository
async function paginate<T extends Entity>(
  repo: Repository<T>,
  page: number,
  size: number
): Promise<{ items: T[]; total: number }> {
  const all = await repo.findAll();
  const start = (page - 1) * size;
  return {
    items: all.slice(start, start + size),
    total: all.length,
  };
}

import { useState } from "react";

// A generic hook: the type follows what you put in
function useLocalStorage<T>(
  key: string,
  initialValue: T
): [T, (value: T) => void] {
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = window.localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;
    }
  });

  const setValue = (value: T) => {
    try {
      setStoredValue(value);
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch (error) {
      console.error(error);
    }
  };

  return [storedValue, setValue];
}

// Usage — T is inferred from initialValue
const [theme, setTheme] = useLocalStorage("theme", "light");
//     ^^^^^ string — inferred!

const [count, setCount] = useLocalStorage("count", 0);
//     ^^^^^ number — inferred!

setTheme(42); // Error: Argument of type 'number' is not assignable to 'string'

Generic Memoize
Intermediate

Implement a memoize higher-order function that caches the results of any function based on its first argument. The types of the input function must be fully preserved.

Hint: use Parameters<T> and ReturnType<T> utility types. The returned function should have the same type as the input function.

Open in TypeScript Playground
Show solution 
function memoize<T extends (arg: string) => unknown>(fn: T): T {
  const cache = new Map<string, ReturnType<T>>();
  return ((arg: string) => {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg) as ReturnType<T>;
    cache.set(arg, result);
    return result;
  }) as T;
}

// More general version using rest parameters
function memoizeGeneral<
  Args extends unknown[],
  R
>(fn: (...args: Args) => R): (...args: Args) => R {
  const cache = new Map<string, R>();
  return (...args: Args): R => {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key)!;
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

const expensiveCalc = (n: number): number => {
  console.log("Computing...");
  return n * n;
};

const memoCalc = memoizeGeneral(expensiveCalc);
memoCalc(5); // "Computing..." then 25
memoCalc(5); // 25 (from cache, no log)

Type-Safe Builder Pattern

Implement a generic QueryBuilder<T> class that accumulates filter conditions for an entity type T. The where method should only accept valid keys of T, and the value type must match the property type.

Signature: where<K extends keyof T>(key: K, value: T[K]): this

Bonus: add a build method that returns a Partial<T> representing all the accumulated filters.

Show solution 
class QueryBuilder<T extends object> {
  private filters: Partial<T> = {};

  where<K extends keyof T>(key: K, value: T[K]): this {
    this.filters[key] = value;
    return this; // enables chaining
  }

  build(): Partial<T> {
    return { ...this.filters };
  }
}

interface User {
  id: string;
  name: string;
  age: number;
  role: "admin" | "user";
}

const query = new QueryBuilder<User>()
  .where("name", "Alice")        // OK: string
  .where("role", "admin")        // OK: "admin" | "user"
  .where("age", 30)              // OK: number
  .build();
// Partial<User>

// These should error:
// .where("name", 42)            // Error: number not assignable to string
// .where("email", "a@b.com")    // Error: "email" not in User
// .where("role", "superuser")   // Error: not in union

console.log(query); // { name: "Alice", role: "admin", age: 30 }
