Type-Level Programming
& Template Literal Types

TypeScript's type system is not just an annotation layer — it's a full programming language that runs entirely at compile time. This chapter shows you how to exploit that power to build zero-cost abstractions that make the impossible type-safe.

Gabriel Vergnaud
Staff Engineer @ Stripe  ·  Creator of ts-pattern & HotScript

01 What Is Type-Level Programming?

Most TypeScript developers think of types as documentation: you write them, the compiler checks them, the runtime ignores them. That's true, but it's only half the picture. TypeScript's type system has computation built in — conditional branches, recursion, pattern matching on type structure, string manipulation. Every operation executes at compile time and produces zero bytes of JavaScript output.

The spectrum runs from trivial to mind-bending:

  • Level 0 — Simple annotations: const x: string = "hello"
  • Level 1 — Generic constraints: function head<T>(arr: T[]): T
  • Level 2 — Conditional types: T extends string ? "yes" : "no"
  • Level 3 — Recursive mapped types, template literal parsing
  • Level 4 — Turing-complete programs: type-level arithmetic, SQL parsers, regex engines
💡
TypeScript's type system is Turing-complete

This was proven empirically when community members implemented cellular automata, chess validators, and even a JSON query language entirely at the type level. The limit is not capability — it's the depth counter and your colleagues' patience.

Why does this matter?

The libraries that defined modern TypeScript — tRPC, Prisma, Zod, React Query — lean heavily on type-level computation. When you call z.object({ name: z.string() }), Zod derives the TypeScript type { name: string } from the schema value. When tRPC wraps your router, the entire procedure signature flows to the client with perfect type safety — no codegen step, no manual type duplication.

Understanding these techniques lets you build APIs with the same ergonomics — and lets you read and contribute to the libraries you depend on.

Famous examples in the wild

LibraryType-level trickUser benefit
tRPC Router inference threads through inferRouterInputs / inferRouterOutputs Client knows every procedure's exact input/output shape
Prisma Schema-to-type codegen + conditional select types Query result type matches exactly what you selected

02 Template Literal Types

Template literal types — introduced in TypeScript 4.1 — do to strings what mapped types do to objects. They let you construct and deconstruct string types at compile time, opening a class of APIs that were simply impossible before.

Basics

TypeScript Intermediate 
// Simplest form: embed a type into a string
type Greeting = `Hello, ${string}!`;
// → accepts any string that starts with "Hello, " and ends with "!"

const a: Greeting = "Hello, world!";   // ✓
const b: Greeting = "Hello, !";        // ✓ (string can be empty)
const c: Greeting = "Goodbye, world!"; // ✗ Type '"Goodbye..."' not assignable

// Embedding a literal union
type Size = "sm" | "md" | "lg";
type SizeClass = `text-${Size}`;
// → "text-sm" | "text-md" | "text-lg"

Union distribution in template literals

When you embed a union type in a template literal, TypeScript distributes over it automatically — producing the Cartesian product of all combinations.

TypeScript Intermediate 
type NS = "north" | "south";
type EW = "east"  | "west";

type Directions = `${NS}-${EW}`;
// → "north-east" | "north-west" | "south-east" | "south-west"

// This is the Cartesian product: |NS| × |EW| = 2 × 2 = 4 members
// Union size grows multiplicatively — be careful with large unions!

Built-in string manipulation types

TypeScript ships four intrinsic string utilities implemented in the compiler itself (not expressible in user-land):

UtilityInputOutput
Uppercase<S>"hello""HELLO"
Lowercase<S>"WORLD""world"
Capitalize<S>"foo""Foo"
Uncapitalize<S>"Foo""foo"

Real-world patterns

TypeScript — event handler derivation Advanced 
// Pattern: derive handler types from event name unions
type EventName = "click" | "focus" | "blur" | "keydown";

// From event names to handler prop names
type HandlerProps = {
  [K in EventName as `on${Capitalize}`]: (event: Event) => void;
};
// → { onClick: ..., onFocus: ..., onBlur: ..., onKeydown: ... }

// ── API routes ──────────────────────────────────────────────────
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE" | "PATCH";
type ResourceName = "users" | "posts" | "comments";

type APIEndpoint = `/${ResourceName}` | `/${ResourceName}/${string}`;
// → "/users" | "/users/${string}" | "/posts" | ...

// ── Database column conventions ────────────────────────────────
type ForeignKey = `${T}_id`;
type Timestamp = "created_at" | "updated_at";

// ── CSS properties ─────────────────────────────────────────────
type CSSDirection = "top" | "right" | "bottom" | "left";
type CSSSpacing = `${"margin" | "padding"}-${CSSDirection}`;
// → "margin-top" | "margin-right" | "padding-left" | ... (8 members)
▶ Type Playground — Try it mentally 
// What does this produce?
type Events = "mouseenter" | "mouseleave" | "mousedown";
type Handlers = `on${Capitalize}`;
//                ↑ hover here in your IDE to see:
// "onMouseenter" | "onMouseleave" | "onMousedown"

// Now flip it: given a handler prop name, extract the event name
type ExtractEvent =
  H extends `on${infer E}` ? Uncapitalize : never;

type E = ExtractEvent<"onClick">;  // → "click"
type F = ExtractEvent<"onFocus">;  // → "focus"
✓
Tip: Template literals check at assignment, not declaration

The type `${string}-${string}` matches any string containing a hyphen. TypeScript validates this at assignment sites, not when you define the type alias. Use this for "stringly-typed" APIs you can't enumerate exhaustively.

03 The infer Keyword Deep Dive

infer is the pattern-matching operator of TypeScript's type system. Inside a extends clause, it introduces a type variable that TypeScript fills in during structural matching. Think of it as destructuring, but for types.

TypeScript — core infer patterns Intermediate 
// Unwrap a Promise
type UnwrapPromise = T extends Promise ? U : T;

type A = UnwrapPromise>;  // → string
type B = UnwrapPromise>;// → number[]
type C = UnwrapPromise;          // → boolean (not a Promise, returned as-is)

// Extract array element type
type ArrayElement = T extends Array ? Item : never;

type D = ArrayElement;  // → string
type E = ArrayElement<[1, 2, 3]>; // → 1 | 2 | 3 (tuple → union of elements)

// Extract function return type (reimplementing the built-in)
type ReturnType = T extends (...args: any[]) => infer R ? R : never;

// Extract function parameters
type Parameters = T extends (...args: infer P) => any ? P : never;

// Multiple infer in one clause
type FirstAndRest =
  T extends [infer First, ...infer Rest] ? { first: First; rest: Rest } : never;

type X = FirstAndRest<[string, number, boolean]>;
// → { first: string; rest: [number, boolean] }

Inferring parts of strings

Combined with template literal types, infer lets you extract substrings by structure. This is where the real magic happens.

TypeScript — string pattern extraction Advanced 
// Extract the "namespace" from "namespace.property"
type Namespace =
  S extends `${infer N}.${string}` ? N : never;

type NS = Namespace<"config.timeout">; // → "config"

// Split on the LAST dot (recursive approach)
type BeforeLast =
  S extends `${infer H}${D}${infer T}`
    ? T extends `${string}${D}${string}`
      ? `${H}${D}${BeforeLast}`  // there's another delimiter, keep going
      : H                                // T has no more delimiters, H is the answer
    : never;

// Extract route params: "/users/:id/posts/:postId" → "id" | "postId"
type ExtractParams =
  S extends `${string}:${infer Param}/${infer Rest}`
    ? Param | ExtractParams<`/${Rest}`>
    : S extends `${string}:${infer LastParam}`
    ? LastParam
    : never;

type Params = ExtractParams<"/users/:id/posts/:postId">;
// → "id" | "postId"

// Type-safe route builder
declare function buildRoute(
  pattern: S,
  params: Record, string>
): string;

buildRoute("/users/:id/posts/:postId", { id: "42", postId: "7" }); // ✓
buildRoute("/users/:id/posts/:postId", { id: "42" });              // ✗ missing postId

Building ParseQueryString<S>

⚠
Advanced — this is genuinely hard

The following type parses a query string at the type level. It's a realistic example of recursive template literal inference and is close to what you'd find in a production routing library.

TypeScript — ParseQueryString Expert 
// Parse a single key=value pair
type ParsePair =
  S extends `${infer Key}=${infer Value}`
    ? { [K in Key]: Value }
    : Record;

// Parse the full query string recursively
type ParseQueryString =
  S extends `${infer Pair}&${infer Rest}`
    ? Merge, ParseQueryString>
    : ParsePair;

// Helper: merge two objects (shallow)
type Merge = {
  [K in keyof A | keyof B]:
    K extends keyof B ? B[K] :
    K extends keyof A ? A[K] : never
};

// Usage:
type Q = ParseQueryString<"name=Alice&age=30&role=admin">;
// → { name: "Alice"; age: "30"; role: "admin" }

// This is the foundation of type-safe URL routing libraries
declare function parseQuery(qs: S): ParseQueryString;
const result = parseQuery("name=Alice&age=30");
result.name; // type: "Alice"
result.age;  // type: "30"
result.foo;  // ✗ Property 'foo' does not exist

04 Recursive Types

TypeScript allows type aliases to reference themselves — a feature that unlocks the ability to describe data structures of arbitrary depth, parse strings of arbitrary length, and build type-level algorithms.

The canonical example: JSON

TypeScript Intermediate 
// The JSON type is naturally recursive — and TypeScript can express it:
type JSONValue =
  | string
  | number
  | boolean
  | null
  | JSONValue[]                    // arrays of JSON values
  | { [key: string]: JSONValue };  // objects with JSON values

// This correctly models:
const valid: JSONValue = {
  name: "Alice",
  scores: [10, 20, 30],
  meta: { active: true, data: null }
};

Deep utility types

TypeScript — DeepReadonly, DeepPartial, DeepRequired Advanced 
// DeepReadonly: recursively marks all properties readonly
type DeepReadonly =
  T extends (infer Item)[]
    ? ReadonlyArray>
    : T extends object
    ? { readonly [K in keyof T]: DeepReadonly }
    : T;

// DeepPartial: makes all nested properties optional
type DeepPartial =
  T extends object
    ? { [K in keyof T]?: DeepPartial }
    : T;

// DeepRequired: makes all nested properties required (removes ?)
type DeepRequired =
  T extends object
    ? { [K in keyof T]-?: DeepRequired }   // note: -? removes optionality
    : T;

// Usage
interface Config {
  server: {
    host: string;
    port?: number;
    tls?: {
      cert: string;
      key?: string;
    };
  };
}

type FrozenConfig = DeepReadonly;
// Every field at every depth is now readonly

type PartialConfig = DeepPartial;
// Every field at every depth is optional — great for patch payloads

Recursive template literals: Split and Join

TypeScript — Split and Join Expert 
// Split a string into a tuple at a delimiter
type Split =
  S extends `${infer Head}${D}${infer Tail}`
    ? [Head, ...Split]
    : [S];

type Parts = Split<"a.b.c.d", ".">;
// → ["a", "b", "c", "d"]

// Join a tuple of strings with a delimiter
type Join =
  T extends []
    ? ""
    : T extends [infer Only extends string]
    ? Only
    : T extends [infer First extends string, ...infer Rest extends string[]]
    ? `${First}${D}${Join}`
    : never;

type Path = Join<["users", "123", "posts"], "/">;
// → "users/123/posts"

// Practical: type-safe deep property access
type Get =
  P extends `${infer Key}.${infer Rest}`
    ? Key extends keyof T
      ? Get
      : never
    : P extends keyof T
    ? T[P]
    : never;

interface Data { user: { name: string; age: number } }
type Name = Get; // → string
type Age  = Get;  // → number
type Nope = Get;  // → never
⚠
Depth limit: TypeScript caps recursive instantiation

TypeScript enforces a recursion depth limit (currently ~100 levels for conditional types). For very deep recursion, use an "accumulator" tuple parameter to help the compiler short-circuit: type Split<S, D, Acc extends string[] = []>. This is the type-level equivalent of tail-call optimization.

05 Mapped Types: Advanced Patterns

Mapped types have been in TypeScript since 2.1, but the as key-remapping clause (4.1) turned them from a convenience into a full type-transformation language.

TypeScript — key remapping and filtering Advanced 
// ── Filter keys by value type ──────────────────────────────────
// Keep only string-valued properties
type StringKeys = {
  [K in keyof T as T[K] extends string ? K : never]: T[K]
};

interface Mixed { id: number; name: string; active: boolean; tag: string }
type StringProps = StringKeys;
// → { name: string; tag: string }

// ── Rename keys ────────────────────────────────────────────────
// Generate getter method signatures from a plain object type
type Getters = {
  [K in keyof T as `get${Capitalize}`]: () => T[K]
};

type PersonGetters = Getters<{ name: string; age: number }>;
// → { getName: () => string; getAge: () => number }

// ── Remove readonly (variance modifier) ───────────────────────
type Mutable = {
  -readonly [K in keyof T]: T[K]
};
// The minus prefix removes the readonly modifier

type RequiredAndMutable = {
  -readonly [K in keyof T]-?: T[K]  // remove both readonly and ?
};

// ── Variance annotations (TS 4.7) ─────────────────────────────
// Explicit covariance and contravariance annotations
type Provider = () => T;    // covariant: Producer ⊆ Producer
type Consumer = (x: T) => void; // contravariant
TypeScript — building an event emitter type Advanced 
// Combining everything: type-safe EventEmitter
type EventMap = {
  connect:    { userId: string };
  disconnect: { userId: string; reason: string };
  message:    { from: string; body: string };
};

type EventEmitter> = {
  on(
    event: K,
    listener: (payload: Events[K]) => void
  ): void;
  off(event: K, listener: (payload: Events[K]) => void): void;
  emit(event: K, payload: Events[K]): void;
};

declare const emitter: EventEmitter;

// Every call is precisely typed:
emitter.on("message", ({ from, body }) => { /* from: string, body: string */ });
emitter.emit("disconnect", { userId: "42", reason: "timeout" });
emitter.emit("connect", { userId: "42", extra: "x" }); // ✗ 'extra' unexpected

06 Conditional Types: Advanced Techniques

Distributive conditional types

When a bare type parameter appears on the left of extends inside a conditional type, TypeScript distributes the conditional over each member of a union. This is usually what you want — but occasionally you need to suppress it.

TypeScript — distribution vs non-distribution Advanced 
// Distributive (default):
type IsString = T extends string ? true : false;
type R1 = IsString;
// → boolean (= true | false) — distributed over each union member

// Non-distributive (wrap in tuple):
type IsStringND = [T] extends [string] ? true : false;
type R2 = IsStringND;
// → false — evaluated as one unit: (string | number) extends string?

// This technique enables precise utility types:
type IsNever  = [T] extends [never] ? true : false;
type IsAny    = 0 extends (1 & T)  ? true : false;

// IsUnion: true only when T is a union type
type IsUnion =
  T extends U
    ? [U] extends [T] ? false : true
    : never;
// IsUnion → true
// IsUnion          → false
// IsUnion           → false

Building complex utility types

TypeScript — Flatten, TupleToUnion, UnionToTuple Expert 
// Flatten a nested array type one level
type Flatten = T extends Array ? Item : T;
type F1 = Flatten; // → number[]
type F2 = Flatten;   // → string
type F3 = Flatten;    // → boolean

// Tuple to union (easy direction)
type TupleToUnion = T[number];
type U = TupleToUnion<[string, number, boolean]>; // → string | number | boolean

// UnionToTuple (hard direction — requires variance trick)
// This exploits the fact that function parameter position is contravariant
type UnionToIntersection =
  (U extends any ? (x: U) => void : never) extends (x: infer I) => void ? I : never;

type LastOf =
  UnionToIntersection U : never> extends () => infer Last
    ? Last : never;

type UnionToTuple> =
  [U] extends [never]
    ? []
    : [...UnionToTuple>, Last];

type T = UnionToTuple<"a" | "b" | "c">;
// → ["a", "b", "c"] — order is an implementation detail, not guaranteed
🧠
Mental Model: Union → Tuple is fundamentally hard

Converting a union to a tuple requires imposing an order on something that has none. The contravariance hack works because function intersection creates a call signature that TypeScript resolves by returning the last overload — which gives us a consistent (if arbitrary) ordering. This is why UnionToTuple is considered a compiler exploit rather than a feature.

07 Type-Level Algorithms

Type-level arithmetic

TypeScript has no number literal arithmetic built in (1 + 1 is not 2 at the type level). The community workaround uses tuple lengths as numbers.

TypeScript — type-level addition via tuples Expert 
// Build a tuple of length N
type BuildTuple =
  T["length"] extends N ? T : BuildTuple;

// Add two numbers via tuple concatenation
type Add =
  [...BuildTuple, ...BuildTuple]["length"];

type Sum = Add<3, 4>; // → 7

// Subtract: remove B elements from a tuple of length A
type Subtract =
  BuildTuple extends [...BuildTuple, ...infer Rest]
    ? Rest["length"]
    : never;

type Diff = Subtract<10, 3>; // → 7

// Type-level comparison
type IsGreater =
  BuildTuple extends [...BuildTuple, ...infer _Rest extends [unknown, ...unknown[]]]
    ? true : false;

type CMP = IsGreater<5, 3>; // → true
⚠
Practical limit: ~999

Tuple tricks for arithmetic break down around 999 due to TypeScript's tuple size limit. For large-number arithmetic use a different encoding (e.g., decimal digit tuples). In practice, type-level math is most useful for small, bounded values like array indices.

Reimplementing Pick and Omit from scratch

TypeScript — from first principles Intermediate 
// Pick: keep only specified keys
type MyPick = {
  [P in K]: T[P]
};
// Equivalent to the built-in Pick

// Omit: remove specified keys
type MyOmit = {
  [P in keyof T as P extends K ? never : P]: T[P]
};
// The "as" clause remaps K-keys to never, effectively removing them

// Strict: Omit that catches misspelled keys
type StrictOmit = MyOmit;

// NonNullable from scratch
type MyNonNullable = T extends null | undefined ? never : T;

// Required from scratch (remove optionality modifier)
type MyRequired = { [K in keyof T]-?: T[K] };

// Readonly from scratch
type MyReadonly = { +readonly [K in keyof T]: T[K] };

A type-safe query builder

▶ Type Playground — QueryBuilder

08 Pattern Matching with ts-pattern


      

        ts-pattern brings ML-style pattern matching to TypeScript. Where a switch statement
        narrows by equality, ts-pattern narrows by structure — and enforces exhaustiveness at
        compile time, not runtime.
      


      

        ✨
        

          AI Era: LLM responses are perfect candidates for pattern matching
          

            LLM tool-call responses, streaming events, and structured outputs arrive as discriminated
            unions. ts-pattern's exhaustive matching ensures you handle every case — a critical property
            when model behavior can evolve.
          

        

      


      

        

          

            TypeScript — ts-pattern basics
            Intermediate
          

        

        
import { match, P } from "ts-pattern";

type Shape =
  | { kind: "circle";    radius: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle";  base: number;  height: number };

const area = (shape: Shape): number =>
  match(shape)
    .with({ kind: "circle" },    ({ radius }) => Math.PI * radius ** 2)
    .with({ kind: "rectangle" }, ({ width, height }) => width * height)
    .with({ kind: "triangle" },  ({ base, height }) => 0.5 * base * height)
    .exhaustive();
// If you remove one .with() branch, TypeScript errors:
// "NonExhaustiveError<{ kind: 'triangle'; ... }>"

// ── Wildcards and guards ────────────────────────────────────────
const describe = (value: unknown): string =>
  match(value)
    .with(P.string,               (s) => `string: "${s}"`)
    .with(P.number.positive(),    (n) => `positive number: ${n}`)
    .with(P.number.negative(),    (n) => `negative number: ${n}`)
    .with({ kind: P.string },     (o) => `object with kind: ${o.kind}`)
    .with(P.array(P.number),      (a) => `number array of length ${a.length}`)
    .otherwise(() => "something else");

      


      

        

          

            TypeScript — handling AI tool responses
            Advanced
          

        

        
// Modeling Claude tool call responses as a discriminated union
type ToolResult =
  | { type: "text";       text: string }
  | { type: "tool_use";   id: string; name: string; input: unknown }
  | { type: "tool_result"; tool_use_id: string; content: string }
  | { type: "error";      error: { type: string; message: string } };

const handleContent = (block: ToolResult): string =>
  match(block)
    .with({ type: "text" }, ({ text }) =>
      `Response: ${text}`)
    .with({ type: "tool_use" }, ({ name, input }) =>
      `Calling tool "${name}" with ${JSON.stringify(input)}`)
    .with({ type: "tool_result" }, ({ tool_use_id, content }) =>
      `Tool ${tool_use_id} returned: ${content}`)
    .with({ type: "error", error: { type: "rate_limit_error" } }, () =>
      "Rate limited — retry after delay")
    .with({ type: "error" }, ({ error }) =>
      `Error: ${error.message}`)
    .exhaustive();

      


      

        ✓
        

          Tip: .exhaustive() vs .otherwise()
          

            Use .exhaustive() when you want a compile-time guarantee that all cases
            are covered — the compiler will error if you add a new union member and forget to handle it.
            Use .otherwise(fallback) when the input type is wider than you can enumerate
            (e.g., unknown from external JSON).
          

        

      

    

      
09 Real-World Type Tricks


      
How tRPC's type inference works

      

        tRPC's magic is that procedure types flow from server to client without a codegen step.
        The key insight is that the router type itself is the API contract.
      


      

        

          

            TypeScript — tRPC-style type inference sketch
            Advanced
          

        

        
// Simplified: how tRPC threads types from router → client
type Procedure = {
  _input: Input;
  _output: Output;
};

type Router>> = {
  _procedures: Procedures;
};

// Extract input/output from a router type
type RouterInputs> = {
  [K in keyof R["_procedures"]]: R["_procedures"][K]["_input"]
};
type RouterOutputs> = {
  [K in keyof R["_procedures"]]: R["_procedures"][K]["_output"]
};

// On the server:
declare const appRouter: Router<{
  getUser:  Procedure<{ id: string }, { name: string; email: string }>;
  listPosts: Procedure<{ page: number }, { posts: string[]; total: number }>;
}>;

// On the client — derived entirely from the server type, zero duplication:
type Inputs  = RouterInputs;
// → { getUser: { id: string }; listPosts: { page: number } }

type Outputs = RouterOutputs;
// → { getUser: { name: string; email: string }; ... }

Express request augmentation


      

        

          

            TypeScript — declaration merging for middleware
            Intermediate
          

        

        
// Express middleware often attaches data to req — type it safely
// via declaration merging with Express's namespace

declare global {
  namespace Express {
    interface Request {
      user?: {
        id: string;
        role: "admin" | "user";
        permissions: string[];
      };
      requestId: string;
    }
  }
}

// Now req.user is typed throughout your entire codebase:
app.get("/profile", (req, res) => {
  if (!req.user) return res.status(401).json({ error: "Unauthorized" });
  // req.user is now { id: string; role: ...; permissions: string[] }
  res.json({ profile: req.user });
});

      


      

        🧠
        

          Mental Model: TypeScript namespaces as "open interfaces"
          

            Declaration merging lets library consumers extend third-party types without modifying
            source code. This is TypeScript's answer to monkey-patching — but done at the type level,
            with no runtime cost and full type safety.
          

        

      

    

      
10 Performance of Type Computation


      

        Complex recursive types come with a real cost: slower IDE response times, longer
        tsc runs, and occasionally hitting compiler limits. Understanding the performance
        model lets you make informed tradeoffs.
      


      
Where types get slow

      
    
        
  • Deep recursion: Each recursive instantiation adds to the depth counter. Types that recurse per-character of a string are the worst offenders.
    • 
        
  • Large unions: Union distribution multiplies instantiation count. A 20-member union conditional type can trigger 20× as many checks as expected.
    • 
        
  • Uncached instantiations: TypeScript caches type instantiations, but only when arguments are structurally identical. Variance in type parameters kills caching.
    •

Patterns for faster types


      

        

          

            TypeScript — optimization patterns
            Advanced
          

        

        
// ── 1. Use interface instead of type alias for object shapes ────
// Interfaces are lazily evaluated; type aliases are eager.
// Prefer interface for large object types that are used many times.

// SLOWER:
type User = { id: string; name: string; /* 50 more fields */ };

// FASTER (deferred evaluation):
interface User { id: string; name: string; /* 50 more fields */ }

// ── 2. Avoid distributive conditionals on large unions ──────────
// If T has 30 members, "T extends string ? ..." runs 30 times.
// Wrap to prevent distribution when you don't need it:
type NonDistributive = [T] extends [string] ? true : false;

// ── 3. Use early termination in recursion ───────────────────────
// Check the base case FIRST to short-circuit:
type SafeSplit =
  S extends ""                           // base case first
    ? Acc
    : S extends `${infer H}${D}${infer T}`
    ? SafeSplit
    : [...Acc, S];

// ── 4. Extract hot paths to interface declarations ──────────────
// TypeScript resolves interfaces lazily — use this for large intermediates
interface ExtractedResult {
  value: T extends { data: infer D } ? D : never;
}
// Reference ExtractedResult instead of inlining the conditional

      


      

        💡
        

          The real-world guidance
          

            Most applications never need to worry about type performance. The types that get slow are
            the ones parsing unbounded strings character-by-character, or doing arithmetic on large numbers.
            If you're building a library for other developers, run tsc --diagnostics
            on your test suite and watch the instantiation count. Above ~500,000 instantiations,
            your users will feel it.
