Design Patterns & Architecture in TypeScript

Fifteen years of production codebases taught me one thing: the language you write in matters far less than the architecture you build with it. TypeScript's type system — interfaces, generics, discriminated unions — makes many classical patterns better than in the languages they were invented for. This chapter shows you how.

1. SOLID Principles in TypeScript

SOLID is a set of five design principles that make software easier to maintain and extend. TypeScript's structural typing makes several of them feel natural — almost inevitable.

S
Single Responsibility
A class should have one reason to change.
O
Open/Closed
Open for extension, closed for modification.
L
Liskov Substitution
Subtypes must be substitutable for their base types.
I
Interface Segregation
Clients shouldn't depend on methods they don't use.
D
Dependency Inversion — most important for TypeScript
High-level modules should not depend on low-level modules. Both should depend on abstractions.

Single Responsibility Principle (SRP)

A common violation: the "God class" that handles HTTP parsing, business logic, and database writes all at once. Split it.

Anti-Pattern — God Class
class UserService {
  // HTTP concern
  parseRequest(req: Request): UserDTO { ... }
  // Business logic concern
  validateAge(age: number): boolean { ... }
  hashPassword(pw: string): string { ... }
  // Database concern
  saveToDatabase(user: User): void { ... }
  sendWelcomeEmail(email: string): void { ... }
  generatePDFReport(): Buffer { ... }
}
SRP — One Reason to Change
class UserParser {
  parse(req: Request): UserDTO { ... }
}

class UserDomainService {
  validate(dto: UserDTO): Result<User, string> { ... }
}

class UserRepository {
  save(user: User): Promise<void> { ... }
}

class EmailService {
  sendWelcome(email: string): Promise<void> { ... }
}

Open/Closed Principle (OCP)

Add new behavior by adding new code, not by modifying existing code. TypeScript interfaces make this clean.

Anti-Pattern — Open/Closed Violation
function calculateDiscount(
  user: User,
  type: 'premium' | 'student' | 'employee'
): number {
  if (type === 'premium') return 0.20
  if (type === 'student') return 0.15
  if (type === 'employee') return 0.30
  // Adding VIP requires modifying this function
  return 0
}
OCP — Extend via Interface
interface DiscountStrategy {
  calculate(user: User): number
}

class PremiumDiscount implements DiscountStrategy {
  calculate(user: User) { return 0.20 }
}

class StudentDiscount implements DiscountStrategy {
  calculate(user: User) { return 0.15 }
}

// Adding VIP: new class, zero modification
class VIPDiscount implements DiscountStrategy {
  calculate(user: User) { return 0.40 }
}

Liskov Substitution Principle (LSP)

If S extends T, anywhere you use T you should be able to use S without breaking the program. TypeScript's structural typing catches many LSP violations at compile time.

Anti-Pattern — LSP Violation
class Rectangle {
  setWidth(w: number): void { this.width = w }
  setHeight(h: number): void { this.height = h }
  area(): number { return this.width * this.height }
}

class Square extends Rectangle {
  // Violates LSP: setWidth changes both dimensions
  setWidth(w: number): void {
    this.width = w
    this.height = w  // ← breaks callers of Rectangle
  }
}
LSP — Prefer Composition
interface Shape {
  area(): number
}

class Rectangle implements Shape {
  constructor(
    private readonly width: number,
    private readonly height: number
  ) {}
  area() { return this.width * this.height }
}

class Square implements Shape {
  constructor(private readonly side: number) {}
  area() { return this.side ** 2 }
}

Interface Segregation Principle (ISP)

Split fat interfaces into small, focused ones. Clients only implement what they actually need.

Anti-Pattern — Fat Interface
interface Worker {
  work(): void
  eat(): void
  sleep(): void
  attendMeeting(): void
}

// Robot must implement eat() and sleep()
// even though it never eats or sleeps
class Robot implements Worker {
  work(): void { ... }
  eat(): void { throw new Error('Robots do not eat') }
  sleep(): void { throw new Error('Robots do not sleep') }
  attendMeeting(): void { ... }
}
ISP — Segregated Interfaces
interface Workable { work(): void }
interface Feedable { eat(): void }
interface Restable { sleep(): void }
interface Meetable { attendMeeting(): void }

class Human implements
  Workable, Feedable, Restable, Meetable { ... }

// Robot only implements what it needs
class Robot implements Workable, Meetable {
  work(): void { ... }
  attendMeeting(): void { ... }
}

Dependency Inversion Principle (DIP)

This is the most powerful principle in TypeScript. High-level policy should not know about low-level details. Both depend on an interface. TypeScript interfaces are zero-cost at runtime — they exist purely to enforce the contract at compile time.

Anti-Pattern — Depends on Concrete
import { PrismaClient } from '@prisma/client'

class OrderService {
  private db = new PrismaClient()  // ← concrete!

  async getOrder(id: string) {
    return this.db.order.findUnique({ where: { id } })
  }
}
// Cannot test without a real database
// Cannot swap to DynamoDB without editing this class
DIP — Depends on Abstraction
interface OrderRepository {
  findById(id: string): Promise<Order | null>
}

class OrderService {
  constructor(private readonly repo: OrderRepository) {}

  async getOrder(id: string) {
    return this.repo.findById(id)
  }
}

// Swap freely: Prisma, DynamoDB, in-memory...
const svc = new OrderService(new PrismaOrderRepository())
const testSvc = new OrderService(new InMemoryOrderRepo())
SOLID Principle — The DI Insight

TypeScript interfaces are erased at runtime — they compile to nothing. This means your abstractions are purely a TypeScript construct with zero overhead. There is no better language for Dependency Inversion.

2. Design Patterns in TypeScript

The Gang of Four patterns were written for statically-typed OO languages. TypeScript inherits all of them — and improves several with generics and discriminated unions.

Creational Patterns

Creational Factory Pattern

Problem: Callers shouldn't need to know which concrete class to instantiate — they should ask a factory for the right object based on a key or config.

Factory pattern: concrete types implement a shared interface; the factory returns the right one.
Factory PatternTypeScript
interface Notifier {
  send(message: string): Promise<void>
}

class EmailNotifier implements Notifier {
  async send(message: string) { /* smtp */ }
}

class SlackNotifier implements Notifier {
  async send(message: string) { /* webhook */ }
}

// Simple factory function (preferred over factory class)
type Channel = 'email' | 'slack' | 'sms'

function createNotifier(channel: Channel): Notifier {
  switch (channel) {
    case 'email': return new EmailNotifier()
    case 'slack': return new SlackNotifier()
    case 'sms':   return new SMSNotifier()
    default:      channel satisfies never  // exhaustiveness check!
  }
}

// Abstract Factory: family of related objects
interface UIFactory {
  createButton(): Button
  createInput(): Input
  createModal(): Modal
}

class WebUIFactory implements UIFactory { ... }
class MobileUIFactory implements UIFactory { ... }
Creational Builder Pattern

Problem: Constructing complex objects step by step without a constructor with 12 parameters. TypeScript generics make the builder type-safe — incomplete builders can be typed to prevent premature use.

Builder Pattern with Method ChainingTypeScript
class QueryBuilder<T> {
  private table = ''
  private conditions: string[] = []
  private limitVal?: number
  private orderByCol?: string

  from(table: string): this {
    this.table = table
    return this
  }

  where(condition: string): this {
    this.conditions.push(condition)
    return this
  }

  limit(n: number): this {
    this.limitVal = n
    return this
  }

  orderBy(col: string): this {
    this.orderByCol = col
    return this
  }

  build(): string {
    let sql = `SELECT * FROM ${this.table}`
    if (this.conditions.length)
      sql += ` WHERE ${this.conditions.join(' AND ')}`
    if (this.orderByCol)
      sql += ` ORDER BY ${this.orderByCol}`
    if (this.limitVal !== undefined)
      sql += ` LIMIT ${this.limitVal}`
    return sql
  }
}

const query = new QueryBuilder<User>()
  .from('users')
  .where('age > 18')
  .where('active = true')
  .orderBy('created_at')
  .limit(50)
  .build()
// → SELECT * FROM users WHERE age > 18 AND active = true ORDER BY created_at LIMIT 50
Creational Singleton — and Why to Avoid It
Anti-Pattern — Singleton

Singletons are global mutable state with a fancy name. They make testing hard (you can't swap the instance), create hidden dependencies, and cause subtle bugs in serverless/multi-thread environments. Use Dependency Injection instead. The only legitimate use: a module-level const.

Avoid — Classic Singleton
class DatabaseConnection {
  private static instance: DatabaseConnection

  static getInstance(): DatabaseConnection {
    if (!this.instance)
      this.instance = new DatabaseConnection()
    return this.instance
  }
  // Impossible to mock in tests
  query(sql: string) { ... }
}
Prefer — Module Singleton
// db.ts — module is naturally a singleton
import { Pool } from 'pg'

export const db = new Pool({
  connectionString: process.env.DATABASE_URL,
})

// In tests, mock the module:
// jest.mock('./db', () => ({ db: mockPool }))
// Or better: use DI and pass db as a parameter
Creational Dependency Injection (Manual vs Container)
Manual DI — Simple and ExplicitTypeScript
// Define interfaces
interface Logger { info(msg: string): void }
interface Cache { get(key: string): Promise<string | null> }

// Concrete implementations
class PinoLogger implements Logger {
  info(msg: string) { console.log(JSON.stringify({ msg, time: Date.now() })) }
}

class RedisCache implements Cache {
  async get(key: string) { /* redis.get(key) */ return null }
}

// High-level service receives dependencies via constructor
class UserService {
  constructor(
    private readonly repo: UserRepository,
    private readonly cache: Cache,
    private readonly logger: Logger
  ) {}

  async findUser(id: string): Promise<User | null> {
    const cached = await this.cache.get(`user:${id}`)
    if (cached) return JSON.parse(cached)
    this.logger.info(`Cache miss for user ${id}`)
    return this.repo.findById(id)
  }
}

// Composition root (one place wires everything)
const userService = new UserService(
  new PrismaUserRepository(db),
  new RedisCache(redis),
  new PinoLogger()
)

// Tests become trivial
const testService = new UserService(
  new InMemoryUserRepository(),
  new NoopCache(),
  new NoopLogger()
)
Tip — When to Use a DI Container

Manual DI works for apps with fewer than ~30 services. Beyond that, wiring becomes tedious. Use inversify, tsyringe, or awilix when you need automatic wiring, scoped lifetimes (singleton vs request-scoped), or lazy instantiation.

Structural Patterns

Structural Adapter Pattern — Wrapping Third-Party Libraries

Problem: You're depending on a third-party SDK directly. When the SDK changes or you want to swap it, you touch every caller. Wrap it in an interface you own.

Adapter insulates your code from third-party SDKs. Swap SendGrid for SES by swapping one class.
Adapter PatternTypeScript
// Interface YOU own
interface EmailSender {
  send(to: string, subject: string, body: string): Promise<void>
}

// Adapter wraps the third-party SDK
class SendGridAdapter implements EmailSender {
  private client: SendGridClient

  constructor(apiKey: string) {
    this.client = new SendGridClient(apiKey)
  }

  async send(to: string, subject: string, body: string) {
    await this.client.sendEmail({
      to,
      from: 'noreply@myapp.com',
      subject,
      html: body,
    })
  }
}

// Swap to SES: zero changes to callers
class SESAdapter implements EmailSender {
  async send(to: string, subject: string, body: string) {
    /* AWS SES implementation */
  }
}

// Test double
class NoopEmailSender implements EmailSender {
  readonly sent: Array<{to: string; subject: string}> = []
  async send(to: string, subject: string) {
    this.sent.push({ to, subject })
  }
}
Structural Decorator Pattern

Problem: Add behavior to an object without subclassing. TypeScript has built-in decorator syntax (Stage 3), but the pattern also works without it using class wrapping.

Decorator Pattern — Both StylesTypeScript
// ─── Pattern-based Decorator (no @decorator syntax) ───────────
interface Service {
  execute(input: string): Promise<string>
}

class LoggingDecorator implements Service {
  constructor(
    private readonly inner: Service,
    private readonly logger: Logger
  ) {}

  async execute(input: string): Promise<string> {
    this.logger.info(`Calling execute with: ${input}`)
    const start = Date.now()
    const result = await this.inner.execute(input)
    this.logger.info(`execute took ${Date.now() - start}ms`)
    return result
  }
}

class CachingDecorator implements Service {
  private cache = new Map<string, string>()
  constructor(private readonly inner: Service) {}

  async execute(input: string): Promise<string> {
    if (this.cache.has(input)) return this.cache.get(input)!
    const result = await this.inner.execute(input)
    this.cache.set(input, result)
    return result
  }
}

// Stack decorators: Logging → Caching → RealService
const service = new LoggingDecorator(
  new CachingDecorator(new RealService()),
  logger
)

// ─── TypeScript @decorator syntax (tsconfig: experimentalDecorators) ─
function Log(target: any, key: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value
  descriptor.value = async function (...args: any[]) {
    console.log(`${key} called with`, args)
    return original.apply(this, args)
  }
  return descriptor
}

class PaymentService {
  @Log
  async charge(amount: number, card: string): Promise<void> { ... }
}
Structural Proxy Pattern
Proxy Pattern — Lazy Loading & Access ControlTypeScript
interface ImageLoader {
  display(): void
}

// Real object (expensive to create)
class RealImage implements ImageLoader {
  constructor(private readonly filename: string) {
    this.loadFromDisk()  // expensive!
  }
  private loadFromDisk() { console.log(`Loading ${this.filename}`) }
  display() { console.log(`Displaying ${this.filename}`) }
}

// Proxy: lazy-loads only when display() is called
class ImageProxy implements ImageLoader {
  private real?: RealImage
  constructor(private readonly filename: string) {}

  display() {
    if (!this.real) this.real = new RealImage(this.filename)
    this.real.display()
  }
}

// TypeScript Proxy (ES6) for meta-programming
const handler: ProxyHandler<Record<string, any>> = {
  get(target, key) {
    console.log(`Getting property: ${String(key)}`)
    return Reflect.get(target, key)
  },
  set(target, key, value) {
    console.log(`Setting ${String(key)} = ${value}`)
    return Reflect.set(target, key, value)
  },
}

const observed = new Proxy<Record<string, any>>({}, handler)
Structural Facade Pattern

Problem: A complex subsystem (video encoding, payment processing, shipping) has many moving parts. A facade provides a simple interface.

Facade PatternTypeScript
// Complex subsystems
class InventoryService { reserve(productId: string, qty: number) {} }
class PaymentGateway  { charge(card: Card, amount: number) {} }
class ShippingService { createLabel(order: Order) {} }
class EmailService    { sendConfirmation(email: string) {} }

// Facade hides all the complexity
class CheckoutFacade {
  constructor(
    private inventory: InventoryService,
    private payment: PaymentGateway,
    private shipping: ShippingService,
    private email: EmailService,
  ) {}

  async checkout(cart: Cart, card: Card, user: User): Promise<OrderResult> {
    await this.inventory.reserve(cart.productId, cart.qty)
    const charge = await this.payment.charge(card, cart.total)
    const order = new Order(cart, charge)
    await this.shipping.createLabel(order)
    await this.email.sendConfirmation(user.email)
    return { orderId: order.id, status: 'success' }
  }
}

// Callers only see one method
const facade = new CheckoutFacade(inv, pay, ship, mail)
await facade.checkout(cart, card, user)

Behavioral Patterns

Behavioral Observer / EventEmitter Pattern
Observer: one event, many handlers — all decoupled from each other.
Type-safe EventEmitterTypeScript
// Typed event map
type AppEvents = {
  'user.created': { userId: string; email: string }
  'order.placed': { orderId: string; total: number }
  'payment.failed': { orderId: string; reason: string }
}

class TypedEventEmitter<Events extends Record<string, any>> {
  private listeners = new Map<string, Array<(data: any) => void>>()

  on<K extends keyof Events>(
    event: K,
    listener: (data: Events[K]) => void
  ): void {
    const key = String(event)
    const existing = this.listeners.get(key) ?? []
    this.listeners.set(key, [...existing, listener])
  }

  emit<K extends keyof Events>(event: K, data: Events[K]): void {
    this.listeners.get(String(event))?.forEach(fn => fn(data))
  }

  off<K extends keyof Events>(event: K, listener: Function): void {
    const key = String(event)
    this.listeners.set(
      key,
      (this.listeners.get(key) ?? []).filter(fn => fn !== listener)
    )
  }
}

const emitter = new TypedEventEmitter<AppEvents>()

emitter.on('user.created', ({ userId, email }) => {
  // TypeScript knows the shape — fully typed!
  sendWelcomeEmail(email)
})

emitter.emit('user.created', { userId: '123', email: 'a@b.com' })
Behavioral Strategy Pattern

Problem: You need to switch algorithms at runtime. TypeScript interfaces make strategy objects naturally composable.

Strategy: swap algorithms at runtime by swapping the strategy object.
Strategy PatternTypeScript
interface PricingStrategy {
  calculate(basePrice: number, user: User): number
}

class RegularPricing implements PricingStrategy {
  calculate(basePrice: number, _user: User) { return basePrice }
}

class MemberPricing implements PricingStrategy {
  calculate(basePrice: number, _user: User) { return basePrice * 0.85 }
}

class PeakHourPricing implements PricingStrategy {
  calculate(basePrice: number, _user: User) {
    const hour = new Date().getHours()
    return hour >= 17 && hour <= 20 ? basePrice * 1.3 : basePrice
  }
}

class PriceCalculator {
  constructor(private strategy: PricingStrategy) {}

  setStrategy(strategy: PricingStrategy) { this.strategy = strategy }

  getPrice(basePrice: number, user: User): number {
    return this.strategy.calculate(basePrice, user)
  }
}

// Switch at runtime
const calc = new PriceCalculator(new RegularPricing())
calc.getPrice(100, user)  // 100

if (user.isMember) calc.setStrategy(new MemberPricing())
calc.getPrice(100, user)  // 85
Behavioral Command Pattern — with Discriminated Unions!

Problem: Encapsulate requests as objects for undo/redo, queuing, logging. TypeScript discriminated unions make command types exhaustive and self-documenting.

Command Pattern with Discriminated UnionsTypeScript
// Commands as discriminated union — exhaustive by nature
type EditorCommand =
  | { type: 'INSERT_TEXT'; position: number; text: string }
  | { type: 'DELETE_TEXT'; start: number; end: number }
  | { type: 'BOLD'; start: number; end: number }
  | { type: 'SET_FONT'; size: number; family: string }

interface CommandHandler {
  execute(cmd: EditorCommand): void
  undo(): void
}

class EditorCommandProcessor {
  private history: EditorCommand[] = []

  execute(cmd: EditorCommand, doc: Document): void {
    switch (cmd.type) {
      case 'INSERT_TEXT':
        doc.insert(cmd.position, cmd.text)
        break
      case 'DELETE_TEXT':
        doc.delete(cmd.start, cmd.end)
        break
      case 'BOLD':
        doc.setBold(cmd.start, cmd.end)
        break
      case 'SET_FONT':
        doc.setFont(cmd.size, cmd.family)
        break
      default:
        cmd satisfies never  // TypeScript ensures exhaustiveness
    }
    this.history.push(cmd)
  }

  undo(doc: Document): void {
    const last = this.history.pop()
    if (!last) return
    // Reverse the command
    if (last.type === 'INSERT_TEXT')
      doc.delete(last.position, last.position + last.text.length)
  }
}
Behavioral Iterator Pattern — Generators in TypeScript
Iterator with GeneratorsTypeScript
// TypeScript generators implement the iterator protocol natively
function* range(start: number, end: number, step = 1): Generator<number> {
  for (let i = start; i < end; i += step) yield i
}

function* take<T>(n: number, iter: Iterable<T>): Generator<T> {
  let count = 0
  for (const item of iter) {
    if (count++ >= n) return
    yield item
  }
}

// Paginated DB cursor as async generator
async function* paginateUsers(pageSize = 100): AsyncGenerator<User> {
  let cursor: string | undefined
  while (true) {
    const { users, nextCursor } = await fetchUsers({ cursor, pageSize })
    for (const user of users) yield user
    if (!nextCursor) return
    cursor = nextCursor
  }
}

// Consumer — lazy, memory-efficient
for await (const user of paginateUsers()) {
  await processUser(user)
  // Only one page in memory at a time
}
Behavioral State Machine Pattern
Finite State Machine with Discriminated UnionsTypeScript
type OrderStatus = 'pending' | 'confirmed' | 'shipped' | 'delivered' | 'cancelled'

type OrderState =
  | { status: 'pending' }
  | { status: 'confirmed'; confirmedAt: Date }
  | { status: 'shipped'; trackingId: string; shippedAt: Date }
  | { status: 'delivered'; deliveredAt: Date }
  | { status: 'cancelled'; reason: string }

type OrderEvent =
  | { type: 'CONFIRM' }
  | { type: 'SHIP'; trackingId: string }
  | { type: 'DELIVER' }
  | { type: 'CANCEL'; reason: string }

function transition(state: OrderState, event: OrderEvent): OrderState {
  switch (state.status) {
    case 'pending':
      if (event.type === 'CONFIRM')
        return { status: 'confirmed', confirmedAt: new Date() }
      if (event.type === 'CANCEL')
        return { status: 'cancelled', reason: event.reason }
      break
    case 'confirmed':
      if (event.type === 'SHIP')
        return { status: 'shipped', trackingId: event.trackingId, shippedAt: new Date() }
      if (event.type === 'CANCEL')
        return { status: 'cancelled', reason: event.reason }
      break
    case 'shipped':
      if (event.type === 'DELIVER')
        return { status: 'delivered', deliveredAt: new Date() }
      break
  }
  return state  // Invalid transitions are no-ops
}

// Usage
let order: OrderState = { status: 'pending' }
order = transition(order, { type: 'CONFIRM' })
order = transition(order, { type: 'SHIP', trackingId: 'UPS-123' })
// TypeScript knows order.trackingId exists here

Functional Result Type — Railway-Oriented Programming

The Result type (also called Either) is the single most valuable pattern from FP for production TypeScript. It makes error handling composable and forces callers to handle failure cases.

Railway-oriented programming: success flows on the top rail, errors fall to the bottom — no exceptions thrown.
Complete Result<T, E> ImplementationTypeScript
// ─── Core Result Type ──────────────────────────────────────────
type Result<T, E = string> =
  | { success: true;  data: T }
  | { success: false; error: E }

// Constructors
const Ok  = <T, E = never>(data: T): Result<T, E> => ({ success: true, data })
const Err = <T = never, E = string>(error: E): Result<T, E> => ({ success: false, error })

// Combinators
function map<T, U, E>(result: Result<T, E>, fn: (v: T) => U): Result<U, E> {
  return result.success ? Ok(fn(result.data)) : result
}

function flatMap<T, U, E>(
  result: Result<T, E>,
  fn: (v: T) => Result<U, E>
): Result<U, E> {
  return result.success ? fn(result.data) : result
}

function mapError<T, E, F>(result: Result<T, E>, fn: (e: E) => F): Result<T, F> {
  return result.success ? result : Err(fn(result.error))
}

// ─── Real Usage ────────────────────────────────────────────────
function divide(a: number, b: number): Result<number, string> {
  if (b === 0) return Err('Division by zero')
  return Ok(a / b)
}

function sqrt(n: number): Result<number, string> {
  if (n < 0) return Err('Cannot sqrt negative number')
  return Ok(Math.sqrt(n))
}

// Chain operations on the happy path
const result = flatMap(divide(100, 4), sqrt)
if (result.success) {
  console.log(result.data)  // 5
} else {
  console.error(result.error)
}

// ─── Validation with Result ────────────────────────────────────
interface SignupData { email: string; age: number; password: string }
type ValidationError = { field: string; message: string }

function validateEmail(email: string): Result<string, ValidationError> {
  if (!email.includes('@'))
    return Err({ field: 'email', message: 'Invalid email format' })
  return Ok(email.toLowerCase())
}

function validateAge(age: number): Result<number, ValidationError> {
  if (age < 18)
    return Err({ field: 'age', message: 'Must be 18 or older' })
  return Ok(age)
}

function validateSignup(data: SignupData): Result<SignupData, ValidationError> {
  const emailResult = validateEmail(data.email)
  if (!emailResult.success) return emailResult

  const ageResult = validateAge(data.age)
  if (!ageResult.success) return ageResult

  return Ok({ ...data, email: emailResult.data })
}
Functional Option/Maybe Type
Option<T> — Safe Null HandlingTypeScript
type Option<T> = { some: true; value: T } | { some: false }

const Some = <T>(value: T): Option<T> => ({ some: true, value })
const None = <T = never>(): Option<T> => ({ some: false })

function mapOption<T, U>(opt: Option<T>, fn: (v: T) => U): Option<U> {
  return opt.some ? Some(fn(opt.value)) : None()
}

function getOrElse<T>(opt: Option<T>, defaultVal: T): T {
  return opt.some ? opt.value : defaultVal
}

// Usage: replaces nullable types
function findUser(id: string): Option<User> {
  const user = db.get(id)
  return user ? Some(user) : None()
}

const username = getOrElse(
  mapOption(findUser('123'), u => u.name),
  'Anonymous'
)

4. Domain-Driven Design (DDD) in TypeScript

DDD is not a pattern — it's a philosophy. Model your code around the business domain, not around the database schema or HTTP API. TypeScript is uniquely well-suited for DDD because interfaces and classes map directly to DDD building blocks.

Bounded Contexts

Bounded contexts: each context owns its model. "Product" in Orders means something different than "Product" in Inventory. They communicate via domain events.

Value Objects

Value objects are immutable, equality is by value not identity. TypeScript's private constructors enforce the invariant that invalid value objects cannot be constructed.

Value Object PatternTypeScript
// Value Object: equality by value, immutable, self-validating
class EmailAddress {
  private constructor(readonly value: string) {}

  static create(email: string): Result<EmailAddress, string> {
    if (!email.includes('@'))
      return { success: false, error: 'Invalid email address' }
    if (email.length > 254)
      return { success: false, error: 'Email too long' }
    return { success: true, data: new EmailAddress(email.toLowerCase()) }
  }

  equals(other: EmailAddress): boolean {
    return this.value === other.value
  }

  toString(): string { return this.value }
}

class Money {
  private constructor(
    readonly amount: number,   // in cents to avoid float issues
    readonly currency: string
  ) {}

  static of(amount: number, currency: string): Result<Money, string> {
    if (amount < 0) return { success: false, error: 'Amount cannot be negative' }
    if (!['USD', 'EUR', 'GBP'].includes(currency))
      return { success: false, error: `Unknown currency: ${currency}` }
    return { success: true, data: new Money(amount, currency) }
  }

  add(other: Money): Result<Money, string> {
    if (this.currency !== other.currency)
      return { success: false, error: 'Currency mismatch' }
    return Money.of(this.amount + other.amount, this.currency)
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency
  }
}

Entities & Aggregates

Entity and Aggregate RootTypeScript
// Entity: identity-based equality
abstract class Entity<TId> {
  constructor(readonly id: TId) {}
  equals(other: Entity<TId>): boolean { return this.id === other.id }
}

// Domain event
interface DomainEvent {
  readonly occurredAt: Date
  readonly eventType: string
}

interface OrderPlacedEvent extends DomainEvent {
  readonly eventType: 'ORDER_PLACED'
  readonly orderId: string
  readonly totalAmount: number
}

// Aggregate Root: consistency boundary
class Order extends Entity<string> {
  private _items: OrderItem[] = []
  private _status: 'draft' | 'placed' | 'cancelled' = 'draft'
  private _events: DomainEvent[] = []

  private constructor(id: string, readonly customerId: string) {
    super(id)
  }

  static create(customerId: string): Order {
    return new Order(crypto.randomUUID(), customerId)
  }

  addItem(productId: string, qty: number, price: Money): Result<void, string> {
    if (this._status !== 'draft')
      return { success: false, error: 'Cannot modify a placed order' }
    this._items.push(new OrderItem(productId, qty, price))
    return { success: true, data: undefined }
  }

  place(): Result<void, string> {
    if (this._items.length === 0)
      return { success: false, error: 'Order has no items' }
    this._status = 'placed'
    this._events.push({
      eventType: 'ORDER_PLACED',
      occurredAt: new Date(),
      orderId: this.id,
      totalAmount: this.total().amount,
    } as OrderPlacedEvent)
    return { success: true, data: undefined }
  }

  total(): Money {
    // reduce all item prices
    return this._items.reduce(
      (sum, item) => sum.add(item.lineTotal()).data ?? sum,
      Money.of(0, 'USD').data!
    )
  }

  // Repository pulls events out and publishes them
  pullEvents(): DomainEvent[] {
    const events = [...this._events]
    this._events = []
    return events
  }
}

Application Services

Application Service — Orchestration LayerTypeScript
// Application service: orchestrates domain objects, no business logic here
class PlaceOrderCommand {
  constructor(
    readonly customerId: string,
    readonly items: Array<{ productId: string; qty: number }>
  ) {}
}

class PlaceOrderHandler {
  constructor(
    private readonly orders: OrderRepository,
    private readonly products: ProductRepository,
    private readonly events: EventPublisher,
  ) {}

  async handle(cmd: PlaceOrderCommand): Promise<Result<string, string>> {
    const order = Order.create(cmd.customerId)

    for (const item of cmd.items) {
      const product = await this.products.findById(item.productId)
      if (!product)
        return { success: false, error: `Product ${item.productId} not found` }

      const addResult = order.addItem(item.productId, item.qty, product.price)
      if (!addResult.success) return addResult
    }

    const placeResult = order.place()
    if (!placeResult.success) return placeResult

    await this.orders.save(order)

    // Publish domain events
    const domainEvents = order.pullEvents()
    await this.events.publishAll(domainEvents)

    return { success: true, data: order.id }
  }
}

5. Repository Pattern

The Repository pattern abstracts the data layer so that your domain code never sees SQL, Prisma, or DynamoDB. You work with domain objects; the repository handles persistence.

Repository pattern: the domain owns the interface, infrastructure provides implementations.
Repository Interface & ImplementationsTypeScript
// ─── Interface (lives in domain layer) ────────────────────────
interface UserRepository {
  findById(id: string): Promise<User | null>
  findByEmail(email: string): Promise<User | null>
  save(user: User): Promise<void>
  delete(id: string): Promise<void>
}

// ─── Prisma Implementation (infrastructure layer) ─────────────
class PrismaUserRepository implements UserRepository {
  constructor(private readonly prisma: PrismaClient) {}

  async findById(id: string): Promise<User | null> {
    const row = await this.prisma.user.findUnique({ where: { id } })
    return row ? this.toDomain(row) : null
  }

  async findByEmail(email: string): Promise<User | null> {
    const row = await this.prisma.user.findUnique({ where: { email } })
    return row ? this.toDomain(row) : null
  }

  async save(user: User): Promise<void> {
    await this.prisma.user.upsert({
      where: { id: user.id },
      create: this.toRow(user),
      update: this.toRow(user),
    })
  }

  async delete(id: string): Promise<void> {
    await this.prisma.user.delete({ where: { id } })
  }

  private toDomain(row: PrismaUser): User {
    // Map from DB shape to domain shape
    return new User(row.id, EmailAddress.create(row.email).data!)
  }

  private toRow(user: User): PrismaUser {
    return { id: user.id, email: user.email.value, createdAt: new Date() }
  }
}

// ─── In-Memory Implementation (for tests) ─────────────────────
class InMemoryUserRepository implements UserRepository {
  private store = new Map<string, User>()

  async findById(id: string): Promise<User | null> {
    return this.store.get(id) ?? null
  }

  async findByEmail(email: string): Promise<User | null> {
    return [...this.store.values()].find(u => u.email.value === email) ?? null
  }

  async save(user: User): Promise<void> {
    this.store.set(user.id, user)
  }

  async delete(id: string): Promise<void> {
    this.store.delete(id)
  }

  // Test helper
  all(): User[] { return [...this.store.values()] }
}

// ─── Test ──────────────────────────────────────────────────────
describe('UserService', () => {
  it('finds user by email', async () => {
    const repo = new InMemoryUserRepository()
    await repo.save(testUser)

    const svc = new UserService(repo)
    const found = await svc.findByEmail(testUser.email.value)
    expect(found?.id).toBe(testUser.id)
  })
})

7. Event-Driven Architecture

Events decouple producers from consumers. When an order is placed, the Orders service publishes an event — it doesn't know or care that Inventory, Payments, and Email are listening.

CQRS — Command Query Responsibility Segregation

CQRS: write path (Commands) and read path (Queries) are separated. Read models can be optimized independently.
CQRS ImplementationTypeScript
// Commands — intent to change state
type Command =
  | { type: 'CREATE_USER'; email: string; name: string }
  | { type: 'DELETE_USER'; userId: string }
  | { type: 'UPDATE_EMAIL'; userId: string; email: string }

// Queries — read only
type Query =
  | { type: 'GET_USER'; userId: string }
  | { type: 'LIST_USERS'; page: number; pageSize: number }
  | { type: 'SEARCH_USERS'; query: string }

// Command bus
class CommandBus {
  private handlers = new Map<string, (cmd: any) => Promise<Result<any, any>>>()

  register<T extends Command>(
    type: T['type'],
    handler: (cmd: T) => Promise<Result<any, any>>
  ): void {
    this.handlers.set(type, handler as any)
  }

  async dispatch<T extends Command>(cmd: T): Promise<Result<any, any>> {
    const handler = this.handlers.get(cmd.type)
    if (!handler) return Err(`No handler for command: ${cmd.type}`)
    return handler(cmd)
  }
}

// Registration
const bus = new CommandBus()
bus.register('CREATE_USER', async (cmd) => {
  const user = await createUser(cmd.email, cmd.name)
  return Ok(user.id)
})

// Usage
const result = await bus.dispatch({ type: 'CREATE_USER', email: 'a@b.com', name: 'Alice' })

Event Sourcing Basics

Event Sourcing — State from EventsTypeScript
// Events are the source of truth — never update records, only append events
type BankAccountEvent =
  | { type: 'ACCOUNT_OPENED'; accountId: string; initialBalance: number; at: Date }
  | { type: 'DEPOSIT';        accountId: string; amount: number; at: Date }
  | { type: 'WITHDRAWAL';     accountId: string; amount: number; at: Date }
  | { type: 'ACCOUNT_CLOSED'; accountId: string; at: Date }

interface BankAccountState {
  accountId: string
  balance: number
  isOpen: boolean
}

// Reconstruct state by replaying events (reduce is perfect here)
function reconstruct(events: BankAccountEvent[]): BankAccountState {
  return events.reduce<BankAccountState>((state, event) => {
    switch (event.type) {
      case 'ACCOUNT_OPENED':
        return { accountId: event.accountId, balance: event.initialBalance, isOpen: true }
      case 'DEPOSIT':
        return { ...state, balance: state.balance + event.amount }
      case 'WITHDRAWAL':
        return { ...state, balance: state.balance - event.amount }
      case 'ACCOUNT_CLOSED':
        return { ...state, isOpen: false }
      default:
        return state
    }
  }, { accountId: '', balance: 0, isOpen: false })
}

8. Layered Architecture

Clean Architecture — Concentric Circles

Clean Architecture: dependencies only flow inward. The domain layer has zero imports from infrastructure.

Hexagonal Architecture (Ports & Adapters)

Hexagonal is similar to Clean Architecture but uses the metaphor of ports (interfaces) and adapters (implementations). Your application core defines the ports; adapters implement them. This maps perfectly to TypeScript interfaces.

Ports and AdaptersTypeScript
// ─── Ports (application core defines these) ───────────────────
// Driving port (called BY external actors → app core)
interface PlaceOrderUseCase {
  execute(cmd: PlaceOrderCommand): Promise<Result<string, string>>
}

// Driven ports (called BY app core → external systems)
interface OrderRepository {
  save(order: Order): Promise<void>
  findById(id: string): Promise<Order | null>
}

interface PaymentGateway {
  charge(amount: Money, card: Card): Promise<Result<string, string>>
}

interface EmailPort {
  sendOrderConfirmation(order: Order): Promise<void>
}

// ─── Core Application (no infrastructure imports!) ────────────
class PlaceOrderService implements PlaceOrderUseCase {
  constructor(
    private readonly orders: OrderRepository,    // driven port
    private readonly payments: PaymentGateway,   // driven port
    private readonly email: EmailPort,           // driven port
  ) {}

  async execute(cmd: PlaceOrderCommand): Promise<Result<string, string>> {
    // Pure business logic — no Prisma, no Stripe, no SendGrid
    const order = Order.create(cmd.customerId)
    // ...
    return Ok(order.id)
  }
}

// ─── Adapters (infrastructure implements the ports) ───────────
class StripePaymentAdapter implements PaymentGateway {
  async charge(amount: Money, card: Card) { /* Stripe API */ }
}

class SendGridEmailAdapter implements EmailPort {
  async sendOrderConfirmation(order: Order) { /* SendGrid */ }
}

// ─── Adapter for HTTP (driving side) ─────────────────────────
class ExpressOrderAdapter {
  constructor(private readonly useCase: PlaceOrderUseCase) {}

  async handleRequest(req: Request, res: Response) {
    const result = await this.useCase.execute(req.body)
    result.success ? res.json({ id: result.data }) : res.status(400).json({ error: result.error })
  }
}

10. Error Handling Architecture

Error handling is an architectural concern. Most teams treat it as an afterthought — handling errors at the point they occur, throwing raw Error objects, and hoping something catches them. This scales poorly.

Typed Error Hierarchy

Typed Errors — Never Throw Raw ErrorTypeScript
// ─── Base domain error ────────────────────────────────────────
abstract class DomainError extends Error {
  abstract readonly code: string
  abstract readonly httpStatus: number

  constructor(
    message: string,
    readonly context?: Record<string, unknown>
  ) {
    super(message)
    this.name = this.constructor.name
  }
}

// ─── Specific error types ─────────────────────────────────────
class NotFoundError extends DomainError {
  readonly code = 'NOT_FOUND'
  readonly httpStatus = 404
}

class ValidationError extends DomainError {
  readonly code = 'VALIDATION_ERROR'
  readonly httpStatus = 400
  constructor(message: string, readonly field: string) {
    super(message, { field })
  }
}

class UnauthorizedError extends DomainError {
  readonly code = 'UNAUTHORIZED'
  readonly httpStatus = 401
}

class ConflictError extends DomainError {
  readonly code = 'CONFLICT'
  readonly httpStatus = 409
}

// ─── Infrastructure error wrapping ────────────────────────────
class DatabaseError extends DomainError {
  readonly code = 'DATABASE_ERROR'
  readonly httpStatus = 500
}

// ─── Result-typed service methods ────────────────────────────
type AppError = NotFoundError | ValidationError | UnauthorizedError | ConflictError | DatabaseError

async function getUser(id: string): Promise<Result<User, AppError>> {
  try {
    const user = await userRepo.findById(id)
    if (!user) return Err(new NotFoundError(`User ${id} not found`))
    return Ok(user)
  } catch (e) {
    return Err(new DatabaseError('DB read failed', { cause: String(e) }))
  }
}

Centralized Error Handling in APIs

Express Error Handler MiddlewareTypeScript
import pino from 'pino'
const logger = pino()

// Express error handler (4 args = error handler)
function errorHandler(
  err: unknown,
  req: Request,
  res: Response,
  next: NextFunction
): void {
  // Typed domain errors
  if (err instanceof DomainError) {
    logger.warn({
      code: err.code,
      message: err.message,
      context: err.context,
      path: req.path,
    })
    res.status(err.httpStatus).json({
      error: { code: err.code, message: err.message }
    })
    return
  }

  // Zod validation errors
  if (err instanceof ZodError) {
    logger.warn({ issues: err.issues, path: req.path })
    res.status(400).json({
      error: { code: 'VALIDATION_ERROR', issues: err.issues }
    })
    return
  }

  // Unexpected errors — log full details, hide from client
  logger.error({ err, path: req.path }, 'Unhandled error')
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'An unexpected error occurred' }
  })
}

// ─── Route handler pattern ────────────────────────────────────
// Wrap async handlers to catch promise rejections
function asyncHandler(fn: (req: Request, res: Response, next: NextFunction) => Promise<void>) {
  return (req: Request, res: Response, next: NextFunction) => {
    fn(req, res, next).catch(next)
  }
}

router.get('/users/:id', asyncHandler(async (req, res) => {
  const result = await userService.getUser(req.params.id)
  if (!result.success) throw result.error  // will be caught by errorHandler
  res.json(result.data)
}))

Logging Architecture with Pino

Structured Logging with pinoTypeScript
import pino, { Logger } from 'pino'

// Logger interface (port) — testable
interface AppLogger {
  info(obj: object, msg?: string): void
  warn(obj: object, msg?: string): void
  error(obj: object, msg?: string): void
  child(bindings: object): AppLogger
}

// Production: pino with structured JSON output
const rootLogger: AppLogger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  // Pretty print in development only
  transport: process.env.NODE_ENV === 'development'
    ? { target: 'pino-pretty' }
    : undefined,
})

// Per-request logger with correlation ID
function createRequestLogger(requestId: string): AppLogger {
  return rootLogger.child({ requestId })
}

// Usage in middleware
app.use((req, res, next) => {
  const requestId = req.headers['x-request-id'] ?? crypto.randomUUID()
  req.logger = createRequestLogger(String(requestId))
  req.logger.info({ method: req.method, path: req.path }, 'Request started')
  next()
})

// Inject logger into services via DI
class UserService {
  constructor(
    private readonly repo: UserRepository,
    private readonly logger: AppLogger
  ) {}

    if (!user) {
      this.logger.warn({ userId: id }, 'User not found')

  • Design Patterns — Factory, Builder, Adapter, Decorator, Observer, Strategy, Command (discriminated unions!), State Machine.
  • Functional Patterns — Result<T, E> for railway-oriented programming; Option<T> for safe nulls; compose/pipe for transformation pipelines.
  • DDD — Value Objects with private constructors and Result-returning factories; Aggregates as consistency boundaries; domain events for loose coupling.
  • Repository Pattern — interface in domain, implementation in infrastructure; in-memory implementation for free testability.
  • DI — start with manual; add a container only when the composition root grows beyond 50 services.
  • Clean/Hexagonal Architecture — dependencies point inward; interfaces belong to the layer that consumes them.
  • Error Handling — typed error hierarchy, Result types, centralized middleware, structured logging with pino.
