1 Authentication vs Authorization

These two words are often conflated, but they answer fundamentally different questions. Getting the distinction right is the first step to building a secure system.

  • Authentication (AuthN) — Who are you? Verifying identity: "I am user #42, proven by this signed token."
  • Authorization (AuthZ) — What can you do? Verifying permissions: "User #42 may read posts but not delete them."

Both must be correct. Authentication without authorization means anyone who logs in can do anything. Authorization without authentication means anyone can claim to be an authorized user.

The Auth Flow

Auth Flow — Login to Resource Access

Common Auth Patterns

Pattern How it works Best for Caveats
Session-based Server stores session, sends session ID in cookie Traditional web apps Requires server-side storage (Redis)
JWT Signed token, self-contained, stateless APIs, microservices, SPAs Cannot revoke before expiry
OAuth2 Delegate auth to provider, get access token Third-party integrations, social login Complex flows; use a library
API Keys Opaque secret sent in header Server-to-server, machine clients No expiry by default; rotate manually

2 JWT (JSON Web Tokens)

A JWT is a compact, URL-safe token that proves a claim was signed by someone who holds a secret key. The server can verify the token without storing state — it just checks the signature.

Structure: Header.Payload.Signature

JWT Structure
🔒 Security

The payload is Base64URL-encoded, not encrypted. Anyone who holds the token can decode and read the payload. Never store sensitive data (passwords, PII, secrets) in JWT claims. Only store the minimum needed: userId, email, role.

Signing JWTs with TypeScript

TypeScript auth/jwt.ts 
import jwt from 'jsonwebtoken'
import { z } from 'zod'

// Strongly type your payload — never use 'any'
const JWTPayloadSchema = z.object({
  userId: z.string().uuid(),
  email: z.string().email(),
  role: z.enum(['admin', 'editor', 'viewer']),
  iat: z.number().optional(),
  exp: z.number().optional(),
})

export type JWTPayload = z.infer<typeof JWTPayloadSchema>

const SECRET = process.env.JWT_SECRET
if (!SECRET) throw new Error('JWT_SECRET environment variable is required')

export function signToken(payload: Omit<JWTPayload, 'iat' | 'exp'>): string {
  return jwt.sign(payload, SECRET, {
    expiresIn: '15m',      // access tokens: short-lived
    algorithm: 'HS256',   // explicitly specify — never trust defaults
    issuer: 'myapp.com',
    audience: 'myapp-api',
  })
}

export function signRefreshToken(userId: string): string {
  return jwt.sign({ userId, type: 'refresh' }, SECRET, {
    expiresIn: '7d',
    algorithm: 'HS256',
  })
}

export function verifyToken(token: string): JWTPayload {
  // jwt.verify throws if invalid, expired, or tampered
  const raw = jwt.verify(token, SECRET, {
    algorithms: ['HS256'],  // whitelist — prevents alg confusion attacks
    issuer: 'myapp.com',
    audience: 'myapp-api',
  })

  // Parse and validate with Zod — do not cast with 'as'
  return JWTPayloadSchema.parse(raw)
}
💡 Tip

Always validate the JWT payload with Zod after verification. jwt.verify() only checks the signature — it won't catch missing fields or wrong types. Using as JWTPayload skips runtime validation and creates a false sense of security.

Access Tokens vs Refresh Tokens

Use a two-token strategy in production:

  • Access token — Short-lived (15 minutes). Sent on every API request in the Authorization: Bearer ... header. If stolen, it expires quickly.
  • Refresh token — Long-lived (7–30 days). Stored securely (httpOnly cookie). Used only to obtain a new access token. Can be revoked server-side.
TypeScript auth/refresh.ts 
// Refresh endpoint — issues new access token
app.post('/auth/refresh', async (c) => {
  const refreshToken = getCookie(c, 'refresh_token')
  if (!refreshToken) return c.json({ error: 'No refresh token' }, 401)

  let payload: { userId: string; type: string }
  try {
    payload = jwt.verify(refreshToken, SECRET, {
      algorithms: ['HS256'],
    }) as { userId: string; type: string }
  } catch {
    return c.json({ error: 'Invalid refresh token' }, 401)
  }

  if (payload.type !== 'refresh') {
    return c.json({ error: 'Wrong token type' }, 401)
  }

  // Check refresh token hasn't been revoked in Redis
  const isRevoked = await redis.get(`revoked:${refreshToken}`)
  if (isRevoked) return c.json({ error: 'Token revoked' }, 401)

  const user = await db.users.findUnique({ where: { id: payload.userId } })
  if (!user) return c.json({ error: 'User not found' }, 401)

  const newAccessToken = signToken({
    userId: user.id,
    email: user.email,
    role: user.role,
  })

  return c.json({ accessToken: newAccessToken })
})

JWT Pitfalls and Attacks

🔒 Security — alg:none Attack

The "alg": "none" attack: an attacker crafts a JWT with "alg": "none" in the header and no signature. Naive libraries accept it. Always pass an explicit algorithms whitelist to jwt.verify() — never let the token header dictate the algorithm.

🔒 Security — Weak Secrets

HS256 secrets must be at least 256 bits (32 bytes) of cryptographically random data. Never use a password or short string. Generate with: openssl rand -base64 32. For production, use RS256 (asymmetric) so you can distribute the public key to multiple services without sharing the private key.

3 Sessions

Session-based auth stores the session state server-side. The client holds only an opaque session ID (in a cookie). This allows instant revocation — just delete the session from the store.

Secure Cookie Attributes

TypeScript auth/session.ts 
import { Hono } from 'hono'
import { getCookie, setCookie, deleteCookie } from 'hono/cookie'
import { randomBytes } from 'crypto'
import { redis } from './redis'

const SESSION_TTL = 60 * 60 * 24 * 7 // 7 days in seconds

interface Session {
  userId: string
  email: string
  role: string
  createdAt: number
}

export async function createSession(userId: string, data: Session): Promise<string> {
  const sessionId = randomBytes(32).toString('hex') // 256-bit random ID
  await redis.setex(`session:${sessionId}`, SESSION_TTL, JSON.stringify(data))
  return sessionId
}

export async function getSession(sessionId: string): Promise<Session | null> {
  const raw = await redis.get(`session:${sessionId}`)
  if (!raw) return null
  return JSON.parse(raw) as Session
}

export async function destroySession(sessionId: string): Promise<void> {
  await redis.del(`session:${sessionId}`)
}

// Hono login route
app.post('/auth/login', async (c) => {
  const { email, password } = await c.req.json()
  const user = await verifyCredentials(email, password)
  if (!user) return c.json({ error: 'Invalid credentials' }, 401)

  // Session fixation: always create a NEW session ID on login
  const sessionId = await createSession(user.id, {
    userId: user.id,
    email: user.email,
    role: user.role,
    createdAt: Date.now(),
  })

  setCookie(c, 'session_id', sessionId, {
    httpOnly: true,   // JS cannot read — prevents XSS token theft
    secure: true,     // HTTPS only — never sent over plain HTTP
    sameSite: 'Lax',  // Protects against CSRF on navigations
    maxAge: SESSION_TTL,
    path: '/',
  })

  return c.json({ success: true })
})
⚠️ Warning — Session Fixation

Always generate a new session ID after a successful login, even if the user already had an anonymous session. If you reuse the pre-login session ID, an attacker who knows it (e.g., from a shared computer) can hijack the authenticated session.

SameSite Explained

  • SameSite=Strict — Cookie never sent on cross-site requests. Breaks OAuth callbacks and external links. Too strict for most apps.
  • SameSite=Lax — Cookie sent on top-level navigations (clicking a link) but not on cross-origin sub-requests (AJAX, forms). Good default.
  • SameSite=None; Secure — Cookie sent everywhere. Required for cross-site embeds. Must pair with Secure.

4 OAuth2 and OpenID Connect

OAuth2 is an authorization framework that lets users grant your app access to their data at another service (GitHub, Google, etc.) without sharing their password. OpenID Connect (OIDC) is a thin identity layer on top of OAuth2 — it adds a signed ID token that proves who the user is.

Authorization Code Flow with PKCE

PKCE (Proof Key for Code Exchange) is mandatory for public clients (SPAs, mobile apps) where a client secret cannot be kept secret. Use it for all new OAuth integrations — even for server-side apps as a defense in depth.

Auth.js (NextAuth) for TypeScript

Auth.js is the standard for Next.js + TypeScript OAuth integrations. It handles the entire OAuth flow, session management, and database adapters.

TypeScript auth.ts (Next.js App Router) 
import NextAuth from 'next-auth'
import Google from 'next-auth/providers/google'
import GitHub from 'next-auth/providers/github'
import { PrismaAdapter } from '@auth/prisma-adapter'
import { prisma } from '@/lib/prisma'
import type { Role } from '@prisma/client'

// Extend the session type to include our custom fields
declare module 'next-auth' {
  interface Session {
    user: {
      id: string
      email: string
      name: string | null
      image: string | null
      role: Role
    }
  }
}

export const { auth, handlers, signIn, signOut } = NextAuth({
  adapter: PrismaAdapter(prisma),
  providers: [
    Google({
      clientId: process.env.GOOGLE_CLIENT_ID!,
      clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
    }),
    GitHub({
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
    }),
  ],
  callbacks: {
    // Attach role and id to the session token
    async jwt({ token, user }) {
      if (user) {
        token.role = (user as { role: Role }).role
        token.userId = user.id
      }
      return token
    },
    async session({ session, token }) {
      return {
        ...session,
        user: {
          ...session.user,
          id: token.userId as string,
          role: token.role as Role,
        },
      }
    },
  },
  session: { strategy: 'jwt' },
})

Clerk — Managed Auth

Clerk is a hosted auth solution that handles registration, login, MFA, social login, and user management via a dashboard. The TypeScript SDK is excellent:

import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server'

  '/sign-up(.*)',
  '/api/webhook(.*)',
  '/',

import { auth } from '@clerk/nextjs/server'

export async function deletePost(postId: string) {
  const { userId } = await auth()
  if (!userId) throw new Error('Unauthorized')
  // ... delete logic
}

Managed Auth vs Roll Your Own

ℹ️ When to use managed auth (Clerk, Auth0, Supabase Auth)
  • You need MFA, magic links, passkeys, or social login quickly
  • Your team is small and security expertise is limited
  • You don't want to maintain the attack surface of an auth system
  • Compliance requirements (SOC2, HIPAA) benefit from a certified provider

Roll your own when: strict data residency, complex custom claims, or you need full control over the auth flow (e.g., AI-era agent identity).

5 Password Hashing

🔒 Security — Never Store Plain Text Passwords

Never store passwords in plain text, never store them with reversible encryption (AES, base64), and never use fast hashing algorithms (MD5, SHA-1, SHA-256). Fast hashes can be brute-forced at billions of attempts per second with a GPU.

Use a slow, purpose-built password hashing function. The leading options in 2025:

  • Argon2id — Winner of the Password Hashing Competition. Resistant to GPU and side-channel attacks. The modern first choice.
  • bcrypt — Battle-tested, widely supported. Fine for most applications. Max password length of 72 bytes.
  • scrypt — Memory-hard like Argon2. Use when Argon2 is unavailable.
TypeScript auth/passwords.ts 
import { hash, verify } from '@node-rs/argon2'
import { timingSafeEqual, randomBytes } from 'crypto'

// Argon2id is the recommended variant (combines Argon2i + Argon2d)
const ARGON2_OPTIONS = {
  memoryCost: 65536,      // 64 MB — tune to ~500ms on your hardware
  timeCost: 3,            // iterations
  parallelism: 4,
  outputLen: 32,
}

export async function hashPassword(password: string): Promise<string> {
  // Validate length before hashing
  if (password.length < 8) throw new Error('Password too short')
  if (password.length > 256) throw new Error('Password too long')

  return hash(password, ARGON2_OPTIONS)
  // Returns: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
  // Salt is automatically generated and embedded in the output
}

export async function verifyPassword(
  password: string,
  storedHash: string
): Promise<boolean> {
  try {
    // verify() is timing-safe — no early return on mismatch
    return await verify(storedHash, password, ARGON2_OPTIONS)
  } catch {
    // Hash format mismatch — treat as invalid
    return false
  }
}

// ── bcrypt example (if you prefer the battle-tested option) ──
import bcrypt from 'bcrypt'

const BCRYPT_ROUNDS = 12  // ~300ms on modern hardware

export async function hashPasswordBcrypt(password: string): Promise<string> {
  // bcrypt truncates at 72 bytes — pre-hash if needed for long passwords
  return bcrypt.hash(password, BCRYPT_ROUNDS)
}

export async function verifyPasswordBcrypt(
  password: string,
  hash: string
): Promise<boolean> {
  return bcrypt.compare(password, hash)  // timing-safe
}
💡 Timing-Safe Comparison

Never use hash1 === hash2 to compare hashes. JavaScript string comparison short-circuits on the first mismatch, creating a timing oracle. Both bcrypt.compare() and argon2.verify() are timing-safe. For other secrets (API keys, HMAC values), use Node's crypto.timingSafeEqual().

6 Role-Based Access Control (RBAC)

RBAC assigns permissions to roles, and roles to users. It is simpler to reason about than per-user permissions and scales well to most applications.

Permission Matrix

Resource / Action admin editor author viewer
Read posts YES YES YES YES
Create posts YES YES YES NO
Edit own posts YES YES OWN ONLY NO
Edit any post YES YES NO NO
Delete posts YES OWN ONLY NO NO
Manage users YES NO NO NO
View audit logs YES NO NO NO

Role-Checking Middleware (Hono)

TypeScript middleware/rbac.ts 
import type { Context, Next } from 'hono'
import { HTTPException } from 'hono/http-exception'

type Role = 'admin' | 'editor' | 'author' | 'viewer'

// Role hierarchy: each role includes all permissions of roles below it
const ROLE_HIERARCHY: Record<Role, number> = {
  viewer: 0,
  author: 1,
  editor: 2,
  admin: 3,
}

// requireRole: user must have this role or higher
export const requireRole = (minRole: Role) =>
  async (c: Context, next: Next) => {
    const user = c.get('user')  // set by auth middleware upstream

    if (!user) {
      throw new HTTPException(401, { message: 'Authentication required' })
    }

    if (ROLE_HIERARCHY[user.role as Role] < ROLE_HIERARCHY[minRole]) {
      throw new HTTPException(403, {
        message: `Requires ${minRole} role or higher`,
      })
    }

    await next()
  }

// requireOwnerOrRole: user owns the resource OR has the required role
export const requireOwnerOrRole = (
  minRole: Role,
  getOwnerId: (c: Context) => Promise<string>
) =>
  async (c: Context, next: Next) => {
    const user = c.get('user')
    if (!user) throw new HTTPException(401, { message: 'Authentication required' })

    const hasRole = ROLE_HIERARCHY[user.role as Role] >= ROLE_HIERARCHY[minRole]
    if (hasRole) return next()

    const ownerId = await getOwnerId(c)
    if (ownerId !== user.id) {
      throw new HTTPException(403, { message: 'Forbidden' })
    }

    await next()
  }

// Usage:
app.delete('/posts/:id',
  authMiddleware,                     // sets c.get('user')
  requireOwnerOrRole('editor', async (c) => {
    const post = await db.post.findUnique({ where: { id: c.req.param('id') } })
    return post?.authorId ?? ''
  }),
  async (c) => {
    await db.post.delete({ where: { id: c.req.param('id') } })
    return c.json({ success: true })
  }
)

Attribute-Based Access Control with CASL

When RBAC becomes complex — "editor can edit posts but only in their department, and only before they're published" — switch to ABAC with the CASL library:

TypeScript auth/abilities.ts 
import { AbilityBuilder, createMongoAbility } from '@casl/ability'

type Action = 'create' | 'read' | 'update' | 'delete' | 'manage'
type Subject = 'Post' | 'User' | 'Comment' | 'all'

interface User { id: string; role: Role; departmentId: string }
interface Post { authorId: string; departmentId: string; published: boolean }

export function defineAbilitiesFor(user: User) {
  const { can, cannot, build } = new AbilityBuilder(createMongoAbility)

  if (user.role === 'admin') {
    can('manage', 'all')  // admin can do everything
  } else if (user.role === 'editor') {
    can('read', 'Post')
    can('update', 'Post', { departmentId: user.departmentId })
    can('delete', 'Post', { departmentId: user.departmentId, published: false })
    cannot('delete', 'Post', { published: true }).because('Cannot delete published posts')
  } else if (user.role === 'author') {
    can('create', 'Post')
    can('read', 'Post')
    can('update', 'Post', { authorId: user.id })
    can('delete', 'Post', { authorId: user.id, published: false })
  } else {
    can('read', 'Post', { published: true })
  }

  return build()
}

// Usage in a route handler:
const ability = defineAbilitiesFor(user)
if (!ability.can('delete', post)) {
  throw new HTTPException(403, { message: ability.relevantRules[0]?.reason })
}
🐍 Python Comparison

Python's Django has a built-in permission system (user.has_perm('app.delete_post')) and the django-guardian package for object-level permissions. CASL is the TypeScript equivalent of django-guardian: fine-grained, attribute-based, and expressive. The difference is TypeScript gives you compile-time type safety on the action and subject types.

7 API Security

CORS

CORS (Cross-Origin Resource Sharing) is enforced by browsers to prevent malicious sites from making authenticated requests to your API using the visitor's credentials. CORS is a browser mechanism — it does not protect your API from server-to-server requests or curl.

TypeScript middleware/cors.ts 
import { cors } from 'hono/cors'

const ALLOWED_ORIGINS = new Set([
  'https://myapp.com',
  'https://www.myapp.com',
  // Add staging origins only in non-production
  ...(process.env.NODE_ENV !== 'production' ? ['http://localhost:3000'] : []),
])

app.use(cors({
  origin: (origin) => {
    // origin is undefined for same-origin requests
    if (!origin || ALLOWED_ORIGINS.has(origin)) return origin
    return null  // null = rejected
  },
  allowMethods: ['GET', 'POST', 'PUT', 'DELETE', 'OPTIONS'],
  allowHeaders: ['Content-Type', 'Authorization'],
  credentials: true,       // required if you send cookies cross-origin
  maxAge: 86400,            // cache preflight 24h
}))
🔒 Security — Never use origin: '*' with credentials

Setting origin: '*' (wildcard) and credentials: true is invalid per the CORS spec and browsers will reject it — but more importantly, never use a wildcard origin for authenticated APIs. Always allowlist specific origins. Also avoid dynamically reflecting the request origin without validation.

Rate Limiting

TypeScript middleware/ratelimit.ts 
import { rateLimiter } from 'hono-rate-limiter'
import { redis } from './redis'

// General API rate limit: 100 req/min per IP
export const apiRateLimit = rateLimiter({
  windowMs: 60_000,
  limit: 100,
  standardHeaders: 'draft-7',
  keyGenerator: (c) => c.req.header('cf-connecting-ip') ?? c.req.raw.headers.get('x-forwarded-for') ?? 'unknown',
})

// Auth endpoint rate limit: 5 attempts/15 min per IP (brute-force prevention)
export const authRateLimit = rateLimiter({
  windowMs: 15 * 60_000,
  limit: 5,
  standardHeaders: 'draft-7',
  keyGenerator: (c) => `auth:${c.req.header('cf-connecting-ip') ?? 'unknown'}`,
  handler: (c) =>
    c.json({ error: 'Too many attempts. Try again in 15 minutes.' }, 429),
})

// Usage:
app.use('/auth/*', authRateLimit)
app.use('/api/*', apiRateLimit)

SQL Injection Prevention

🔒 Security — Parameterized Queries Only

Never concatenate user input into SQL strings. SQL injection remains the #1 web vulnerability. Use parameterized queries (Prisma, Drizzle, pg's $1 syntax, Kysely). If you must write raw SQL, use tagged template literals that enforce parameterization.

TypeScript — SQL injection: safe vs unsafe 
// ❌ NEVER DO THIS — SQL injection vulnerability
const users = await db.query(
  `SELECT * FROM users WHERE email = '${email}'`  // attacker input: ' OR '1'='1
)

// ✅ Parameterized query (pg driver)
const users = await db.query(
  'SELECT * FROM users WHERE email = $1',
  [email]
)

// ✅ Prisma — always parameterized
const user = await prisma.user.findUnique({ where: { email } })

// ✅ Prisma raw — use Prisma.sql template tag
const users = await prisma.$queryRaw`
  SELECT * FROM users WHERE email = ${email}
`
// Prisma.sql automatically parameterizes — safe

// ❌ Prisma raw string — bypasses parameterization
const users = await prisma.$queryRawUnsafe(
  `SELECT * FROM users WHERE email = '${email}'`  // vulnerable!
)

CSRF Protection

CSRF (Cross-Site Request Forgery) tricks a user's browser into making authenticated requests to your site from a malicious page. With SameSite=Lax/Strict cookies, CSRF is largely mitigated for modern browsers. For older browsers or APIs that accept cookies with SameSite=None, use a CSRF token:

TypeScript middleware/csrf.ts 
import { csrf } from 'hono/csrf'

// Hono CSRF middleware — validates Origin/Referer header
app.use(csrf({
  origin: ['https://myapp.com', 'https://www.myapp.com'],
}))

// For APIs that use a CSRF token pattern:
// 1. GET /csrf-token → returns a token (also stored in session)
// 2. Client sends token in X-CSRF-Token header on mutations
// 3. Server validates header token matches session token

8 HTTPS and TLS

🔒 Security — HTTPS Everywhere

Never serve auth endpoints over plain HTTP in production. Not even for internal services. TLS prevents credential interception, session hijacking, and man-in-the-middle attacks. Modern deployment platforms (Railway, Fly.io, Vercel, AWS ALB) provide TLS termination for free. There is no valid excuse to skip HTTPS in 2025.

HTTP → HTTPS Redirect + HSTS

TypeScript middleware/https-redirect.ts 
// Force HTTPS redirect
app.use(async (c, next) => {
  const proto = c.req.header('x-forwarded-proto')
  if (proto === 'http') {
    const url = new URL(c.req.url)
    url.protocol = 'https:'
    return c.redirect(url.toString(), 301)
  }
  await next()
})

// HSTS: instruct browsers to always use HTTPS for 2 years
// (included in secureHeaders above, but shown explicitly)
// Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
//
// ⚠️  Do not set preload until you're certain your entire domain
//    can serve HTTPS — it's very hard to undo.

TLS Certificates with Let's Encrypt

Let's Encrypt provides free, auto-renewing TLS certificates. Use Caddy as a reverse proxy for automatic certificate management — it handles ACME challenges, renewal, and HTTPS redirect out of the box:

9 Secrets and Environment Security

🔒 Security — Never Commit Secrets

Never commit secrets to version control — not even in a private repo. Assume any secret that touches git is compromised. Git history is permanent. Use .gitignore for .env files and pre-commit hooks (e.g., detect-secrets, gitleaks) to catch accidents.

Type-Safe Environment Variables with Zod

TypeScript config/secrets.ts (AWS Secrets Manager) 
import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager'

const client = new SecretsManagerClient({ region: env.AWS_REGION })

interface AppSecrets {
  jwtSecret: string
  databaseUrl: string
  stripeApiKey: string
}

let cachedSecrets: AppSecrets | null = null

export async function getSecrets(): Promise<AppSecrets> {
  if (cachedSecrets) return cachedSecrets

  const { SecretString } = await client.send(
    new GetSecretValueCommand({ SecretId: env.AWS_SECRET_ARN })
  )

  if (!SecretString) throw new Error('Secret is empty')

  // Validate shape with Zod — don't trust the secrets store blindly
  const SecretsSchema = z.object({
    jwtSecret: z.string().min(32),
    databaseUrl: z.string().url(),
    stripeApiKey: z.string().startsWith('sk_'),
  })

  cachedSecrets = SecretsSchema.parse(JSON.parse(SecretString))
  return cachedSecrets
}
🔒 Security — Never Log Secrets

Structured logging libraries like pino log entire objects. Never log objects that might contain secrets: request bodies, environment variables, or JWT payloads. Use a redact config to strip known sensitive fields, and audit your logs regularly.

10 Audit Logging

Audit logs are your security camera footage. They tell you what happened, when, and by whom — essential for incident response, compliance, and detecting intrusions.

What to Log

  • Auth events — successful login, failed login, logout, password change, MFA enable/disable
  • Permission denials — every 403 response, with user ID and resource attempted
  • Data mutations — create, update, delete operations on sensitive resources
  • Admin actions — role changes, user creation/deletion, configuration changes
  • Anomalies — login from new IP/device, bulk data export, rate limit hits
TypeScript audit/logger.ts 
import { z } from 'zod'

const AuditEventSchema = z.object({
  eventType: z.enum([
    'auth.login.success',
    'auth.login.failure',
    'auth.logout',
    'auth.password_change',
    'authz.denied',
    'data.create',
    'data.update',
    'data.delete',
    'admin.role_change',
    'admin.user_delete',
  ]),
  timestamp: z.string().datetime(),
  userId: z.string().uuid().nullable(),
  sessionId: z.string().nullable(),
  ipAddress: z.string(),
  userAgent: z.string().optional(),
  resource: z.string().optional(),
  resourceId: z.string().optional(),
  outcome: z.enum(['success', 'failure', 'denied']),
  metadata: z.record(z.unknown()).optional(),
})

type AuditEvent = z.infer<typeof AuditEventSchema>

export async function logAuditEvent(event: AuditEvent): Promise<void> {
  const validated = AuditEventSchema.parse(event)

  // Write to immutable audit log (append-only table or log service)
  await db.auditLog.create({ data: validated })

  // Also stream to SIEM (Splunk, Datadog, CloudWatch)
  logger.info({ audit: validated }, 'audit_event')
}

// Middleware that auto-logs all auth events:
app.use(async (c, next) => {
  await next()

  const status = c.res.status
  if (status === 401 || status === 403) {
    await logAuditEvent({
      eventType: status === 401 ? 'auth.login.failure' : 'authz.denied',
      timestamp: new Date().toISOString(),
      userId: c.get('user')?.id ?? null,
      sessionId: c.get('sessionId') ?? null,
      ipAddress: c.req.header('cf-connecting-ip') ?? 'unknown',
      resource: c.req.path,
      outcome: 'denied',
    })
  }
})
ℹ️ Log Retention

Retain auth audit logs for at least 90 days (hot) and 1 year (cold archive). Many compliance frameworks (SOC2, PCI-DSS, HIPAA) mandate this. Use append-only storage — audit logs must be tamper-evident. AWS CloudWatch Logs with log group protection or WORM-compliant S3 are good options.

Never Use any for User Input

TypeScript — Input validation patterns 
// ❌ Dangerous — any bypasses all type checking
app.post('/users', async (c) => {
  const body: any = await c.req.json()  // untrusted user data, no validation
  await db.user.create({ data: body })  // mass assignment vulnerability!
})

// ✅ Always validate external data with Zod at the boundary
const CreateUserSchema = z.object({
  email: z.string().email().max(255),
  name: z.string().min(1).max(100).trim(),
  // role is NOT in the schema — users cannot self-assign roles
})

app.post('/users', async (c) => {
  const raw = await c.req.json()
  const body = CreateUserSchema.parse(raw)  // throws ZodError if invalid
  await db.user.create({
    data: { ...body, role: 'viewer' },  // role is server-controlled
  })
})
🔒 Security — Mass Assignment

Mass assignment is a critical vulnerability: if you pass the entire request body to your database layer, an attacker can include fields like "role": "admin" or "balance": 999999. Always define explicit Zod schemas that only allow the fields users are permitted to set. Never use spread on unvalidated input.

🤖 AI Era — LLM Agent Identity

AI agents make API calls on behalf of users. Apply the same auth principles: each agent should have its own API key or scoped JWT with the minimum required permissions (principle of least privilege). Log all agent API calls with the agent ID and the user it acted on behalf of. Implement agent-specific rate limits to prevent runaway loops from causing damage. Never give an agent admin-level credentials.

Common Mistakes — Auth Antipatterns

Storing JWT in localStorage

Any XSS vulnerability — including from a compromised npm package — can read localStorage and steal all tokens. Store access tokens in memory and refresh tokens in httpOnly cookies.

Using alg: none or not whitelisting algorithms

Not passing algorithms: ['HS256'] to jwt.verify() allows attackers to craft unsigned tokens with "alg": "none". Always explicitly whitelist the expected algorithm.

Storing passwords with MD5 / SHA-256

These are fast hashes, trivially brute-forced with GPUs. A 7-character password hashed with MD5 cracks in seconds. Always use bcrypt, Argon2id, or scrypt.

Sending the JWT secret in client-side code

NEXT_PUBLIC_ variables in Next.js, Vite's VITE_ prefix — anything that starts with these prefixes gets bundled into the client. Never prefix a secret with these patterns.

Logging the request body

Request bodies often contain passwords (login endpoint), tokens (refresh endpoint), or PII. Log only sanitized summaries of auth-related endpoints, never the raw body.

Not revoking sessions on logout

Deleting a cookie on the client doesn't invalidate the session server-side. If the attacker captured the cookie, they can still use it. Always delete the session from the server store (Redis) on logout.

Trusting user-supplied roles or permissions

Never accept role or permission flags from the client. Always look them up server-side from the database. Mass assignment of "role": "admin" is trivial if you trust the request body.

Missing rate limiting on auth endpoints

Without rate limiting, login and password-reset endpoints are open to brute-force attacks. Apply strict rate limits (5 attempts per 15 minutes per IP) and implement account lockout policies.

Verbose error messages on auth failure

Returning "User not found" vs "Wrong password" reveals whether an email is registered. Always return the same generic message: "Invalid email or password." This prevents user enumeration attacks.

Chapter Summary

  • AuthN vs AuthZ — identity and permissions are separate concerns; enforce both
  • JWT — use short-lived access tokens + long-lived httpOnly refresh tokens; always whitelist algorithms
  • Sessions — Redis-backed sessions with HttpOnly, Secure, SameSite cookies; regenerate ID on login
  • OAuth2 + PKCE — never implement the OAuth flow yourself in a SPA; use PKCE; verify the ID token
  • Passwords — Argon2id or bcrypt; never MD5/SHA; always timing-safe comparison
  • RBAC — roles in the database, not in the token; enforce with middleware; use CASL for complex rules
  • API Security — allowlist CORS origins, rate-limit auth endpoints, parameterize SQL, set CSP headers
  • Secrets — validate with Zod at startup; use a secrets manager in production; never log them
  • Audit logs — log auth events, permission denials, and data mutations; retain for compliance
  • TypeScript — strict mode, Zod at boundaries, no any for user input, npm audit in CI
