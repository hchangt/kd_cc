Chapter 21

Developer Experience in the AI Era

By Senior Staff Engineer @ Anthropic (previously Google)

The tools around TypeScript have always mattered — but the arrival of AI coding assistants changed everything. Type annotations are no longer just for humans and compilers: they are structured context that AI understands. This chapter covers the complete modern DX stack: Copilot, Cursor, Claude Code, ESLint, Prettier, Biome, strict mode, pre-commit hooks, and CI — everything you need to build a productive, AI-augmented TypeScript project in 2025.

1. The AI-Augmented Developer

How Development Has Changed

The developer's job description has quietly changed. A year ago you wrote nearly every line. Today, a well-configured AI coding environment writes a majority of boilerplate, fills in function bodies from signatures, suggests tests, and proposes refactors — while you navigate, review, reject, guide, and judge.

This shift is not subtle. GitHub's research found that developers using AI tools complete tasks 55% faster and report higher job satisfaction. The productivity compound is real.

TypeScript's Unique Advantage: Types as Context for AI

Python developers using Copilot get reasonable suggestions. TypeScript developers get remarkably good ones. The difference is types.

When you write a function signature like:

async function fetchUserOrders(
  userId: UserId,
  options: { limit: number; cursor?: string; status?: OrderStatus }
): Promise<PaginatedResult<Order>>

Copilot and Cursor now know: the argument is a branded UserId, not a raw string. It returns a generic paginated result. The status filter is optional and constrained to a specific enum. The function is async. Every one of those constraints narrows the space of valid implementations. The AI produces better code because the types act as a specification.

AI Era — Types Are a Prompt

Think of your TypeScript interfaces and type aliases as implicit prompts to every AI tool in your pipeline. The more precisely you type your domain, the fewer hallucinated implementations the AI suggests. Invest in types not just for type safety — invest in them because they make every AI touchpoint smarter.

The AI Pair-Programming Workflow

The highest-leverage workflow I've found after years of using these tools:

  1. Write the type signature first. Define the function name, parameters, return type, and any relevant JSDoc. This is the spec.
  2. Let AI fill the implementation. Accept if it looks correct. If not, guide with a comment like // use Array.reduce, not a for loop and re-trigger.
  3. Write the test skeleton. AI suggests test cases from the signature and implementation — review each.
  4. Run the linter and type-checker. Errors become feedback to AI in Cursor's Composer or Claude Code's agentic loop.
  5. Human review for correctness and architecture. AI is wrong about business logic, edge cases, and system design more than it is wrong about syntax.
Warning — Where Human Judgment Wins

AI excels at: boilerplate, CRUD operations, test generation, documentation, refactoring patterns, and well-known algorithms. AI struggles with: domain-specific business rules, security-sensitive code, distributed system edge cases, and anything that requires understanding organizational context. Always own the review.

2. GitHub Copilot with TypeScript

How Copilot Uses TypeScript Types to Generate Better Code

Copilot's context window includes the current file, nearby open files, and recently edited files. TypeScript's type information flows through all of it. The pattern that unlocks the best suggestions: write the type signature first, then position your cursor in the function body and wait.

// 1. Write this first — Copilot reads it as specification
interface CartItem {
  productId: ProductId
  quantity: number
  unitPrice: Money
}

type Money = { amount: number; currency: 'USD' | 'EUR' | 'GBP' }
type CartTotal = { subtotal: Money; tax: Money; total: Money }

// 2. Type signature is the prompt
function calculateCartTotal(
  items: CartItem[],
  taxRate: number,
  currency: Money['currency']
): CartTotal {
  // 3. Copilot fills this — and it's correct because the types constrain it
}

Copilot Chat takes this further. With Ctrl+I (inline) or the chat sidebar, you can ask architectural questions grounded in your actual codebase types:

// @workspace What's the best way to add caching to all functions
// that return Promise<Product> without changing their signatures?

Project-Specific Context: .github/copilot-instructions.md

Copilot reads this file and applies it as system context for all suggestions in your repo. Use it to encode project conventions the model wouldn't otherwise know:

.github/copilot-instructions.md
# Copilot Instructions

## Project conventions
- This is a TypeScript monorepo using pnpm workspaces.
- All monetary values use the `Money` branded type — never raw numbers.
- Use `Result<T, E>` from `~/lib/result` for fallible operations — never throw.
- Prefer `zod` for runtime validation at system boundaries.
- All async functions must be typed with explicit return types.
- Use `pino` for logging — never `console.log` in library code.

## Architecture
- Domain layer in `packages/domain` — pure functions, no I/O.
- Application layer in `packages/app` — orchestrates domain + infrastructure.
- Infrastructure in `packages/infra` — database, HTTP, queues.

## Testing
- Use vitest. All tests co-located with source in `*.test.ts` files.
- Mock at the boundary: infrastructure mocked, domain tested directly.

Best Practices: Accept, Reject, Guide

Pro Tip — The Three-Speed Copilot Workflow
  • Accept (Tab): When the suggestion is clearly correct and you'd write the same thing.
  • Accept word (Ctrl+Right): When the suggestion starts right but drifts — take the first few tokens.
  • Reject and guide: Add a comment stating your intent more precisely, or rename a variable to something more expressive, then re-trigger. Better input = better output.
  • Reject and write: For security-sensitive code, complex business rules, or anything where you have strong opinions. Don't fight the AI — own the keyboard.

TypeScript tricks that supercharge Copilot suggestions:

  • Use branded types — type UserId = string & { readonly _brand: 'UserId' } — so Copilot won't confuse IDs.
  • Use discriminated unions for state — Copilot correctly handles each variant when generating switch statements.
  • Add JSDoc with examples — Copilot treats example code as additional context.
  • Keep interface names semantic — OrderRepository beats IOrderRepo for AI comprehension.

3. Cursor — The AI-Native Editor

Tool Spotlight — Cursor

Cursor is a fork of VS Code with deep AI integration baked into the editor itself rather than added as an extension. It ships its own model routing, inline editing, multi-file Composer, and codebase-aware chat — all out of the box. Your VS Code extensions, keybindings, and settings import automatically.

Composer: AI That Edits Multiple Files at Once

Composer (Cmd+I) is the feature that separates Cursor from Copilot. Instead of single-location completions, Composer can plan and execute changes across an entire feature: creating files, modifying interfaces, updating imports, and adjusting tests — all in a single session.

A real Composer prompt for a TypeScript project:

# In Cursor Composer:

Add a `discountCode` optional field to the `Order` type. Propagate it:
- Update the `Order` interface in src/domain/order.ts
- Update the `CreateOrderInput` zod schema in src/validation/order.schema.ts
- Update the `OrderRepository.create()` method signature
- Add a migration in src/db/migrations/
- Update the `OrderMapper` to/from DB in src/infra/order.mapper.ts
- Update relevant tests

Cursor reads the TypeScript type graph to understand what "propagate" means. It follows imports, understands which interfaces depend on Order, and generates a diff you review before applying.

@codebase Context

In Cursor chat, prefix your question with @codebase to ground the answer in your actual repository:

@codebase Where does error handling happen for failed payments?
Show me the types involved and whether they propagate up to the HTTP layer.

Cursor indexes your repo (including TypeScript types) and performs semantic search to answer. This is where TypeScript pays dividends: the type graph is a navigable map of your architecture that Cursor's index understands.

`.cursorrules`: Project-Specific AI Instructions

.cursorrules
You are working on a TypeScript e-commerce API.

Tech stack: Node.js 22, TypeScript 5.6, Hono, Drizzle ORM, Zod, Vitest, pnpm.

Architecture: Domain-Driven Design. Bounded contexts: orders, catalog, fulfillment.
Never put business logic in route handlers. Always go through the application layer.

Type conventions:
- Branded primitives for all IDs: UserId, OrderId, ProductId
- Money type for all monetary values — never raw numbers
- Result<T, E> for fallible operations — never throw from domain code
- All external inputs validated with Zod at the HTTP boundary

Code style:
- No `any`. Use `unknown` and narrow.
- No non-null assertions `!` unless inside a test file.
- Explicit return types on all exported functions.
- Prefer `const` over `let`. Never `var`.

When writing tests: co-locate with source, use vitest, mock infrastructure not domain.

AI Era — The TypeScript Advantage in Cursor

When Cursor's Composer generates code that has TypeScript errors, the editor shows them inline. The agent can read those errors and iterate — without you doing anything. Type errors become automatic feedback in the agentic loop. This is why TypeScript projects get more out of Cursor than JavaScript ones: the compiler is a critic the AI can hear.

4. Claude Code (CLI)

Tool Spotlight — Claude Code

Claude Code is Anthropic's official CLI for Claude. Run claude from your terminal inside any project directory. It can read files, write files, execute shell commands, run your test suite, and iterate — autonomously, with your approval at each step. It is not a chatbot you describe code to. It is an agent that operates on your actual codebase.

Running Claude Code in Your TypeScript Project

# Install
npm install -g @anthropic-ai/claude-code

# Launch in your project root
cd my-typescript-project
claude

From there, you interact in natural language. Claude Code reads your tsconfig.json, understands your package structure, and operates within your actual file tree. It's not working from a description — it reads the real files.

Using Claude Code for Code Review and Refactoring

# In the claude session:

"Review src/services/order.service.ts for:
- any implicit `any` types
- missing error handling on async calls
- business logic that should be in the domain layer
- functions over 30 lines that should be extracted"

Claude Code reads the file, analyzes it against the criteria, and proposes specific edits — which it can apply directly with your permission.

Complex Multi-File Edits

For large refactors, Claude Code's approach is methodical:

  1. Read the relevant files to understand the current state.
  2. Propose a plan (which you can modify).
  3. Execute edits file by file, running pnpm typecheck after each batch to verify.
  4. Run the test suite. Fix failures. Repeat.

The feedback loop between TypeScript's compiler and Claude Code's edit-verify cycle is tight. A change that introduces a type error gets caught in the next tsc run, and the agent iterates.

The Agentic Loop: Claude Uses Tools Autonomously

TypeScript Types as Communication with Claude

When you ask Claude Code to implement something, the most effective prompt is often just a type signature:

// Add this to src/domain/inventory.ts and implement it.
// No external calls — pure domain logic only.
function reserveStock(
  inventory: Inventory,
  productId: ProductId,
  quantity: number
): Result<Inventory, 'INSUFFICIENT_STOCK' | 'PRODUCT_NOT_FOUND'>

This signature encodes: the function is pure, it operates on an Inventory value object, it returns a discriminated result (not throws), and the failure modes are finite and named. Claude produces a correct implementation on the first try because the types eliminate most of the ambiguity.

5. ESLint — Automated Code Quality

Installation

pnpm add -D eslint @eslint/js typescript-eslint

eslint.config.ts with typescript-eslint

eslint.config.ts
import eslint from '@eslint/js'
import tseslint from 'typescript-eslint'

export default tseslint.config(
  eslint.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: {
      parserOptions: {
        project: true,
        tsconfigRootDir: import.meta.dirname,
      }
    },
    rules: {
      '@typescript-eslint/no-explicit-any': 'error',
      '@typescript-eslint/explicit-function-return-type': 'warn',
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/strict-boolean-expressions': 'error',
      '@typescript-eslint/no-unnecessary-condition': 'warn',
    }
  }
)
Info — Flat Config Format

ESLint v9+ uses the new "flat config" format (eslint.config.ts or eslint.config.js). If you're on ESLint 8, use .eslintrc.js with @typescript-eslint/parser as the parser. The flat format is now the default and supports import.meta.dirname for finding your tsconfig.

Key Rules

Rule What it catches Recommended setting
no-explicit-any Stops any from spreading through your codebase 'error'
no-floating-promises Catches async calls whose Promise is never awaited or handled 'error'
strict-boolean-expressions Prevents if (user) when user could be 0 or "" 'error'
no-unnecessary-condition Flags conditions that are always true/false (types prove it) 'warn'
explicit-function-return-type Forces explicit return types — AI-generated code often omits these 'warn'
await-thenable Catches await nonPromise which silently works but is wrong 'error'

Type-Aware Linting

The rules marked with a lightning bolt in the typescript-eslint docs are type-aware: they invoke TypeScript's compiler API to check rules that require type information. They're slower but catch bugs that non-type-aware rules miss entirely. The project: true in parserOptions is what enables them.

AI Era — ESLint as AI Output Reviewer

no-explicit-any and explicit-function-return-type are especially valuable in AI-assisted projects. AI-generated code often uses any to sidestep type complexity and omits return types because they're inferred. ESLint catches both, forcing every AI-generated function through the same quality bar as hand-written code.

Auto-fix on Save in VS Code

.vscode/settings.json
{
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "eslint.validate": ["typescript", "typescriptreact"]
}

ESLint in CI

package.json
{
  "scripts": {
    "lint": "eslint . --ext .ts,.tsx",
    "lint:fix": "eslint . --ext .ts,.tsx --fix"
  }
}

6. Prettier — Code Formatting

Automated formatting is not about style preferences — it's about eliminating entire categories of code review comments and merge conflicts. When every file is formatted by the same tool, diffs are meaningful: every change is a logic change, not a whitespace change.

pnpm add -D prettier
.prettierrc
{
  "semi": false,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "es5",
  "printWidth": 100
}

Integrating Prettier with ESLint

Without coordination, ESLint and Prettier conflict on formatting rules. The fix:

pnpm add -D eslint-config-prettier
eslint.config.ts — add at the end
import eslint from '@eslint/js'
import tseslint from 'typescript-eslint'
import prettier from 'eslint-config-prettier'   // ← add this

export default tseslint.config(
  eslint.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  { /* your rules */ },
  prettier   // ← must be last; disables formatting rules
)

Format on Save in VS Code

.vscode/settings.json
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  }
}
Info — Prettier vs Biome

Prettier is the established standard with the widest plugin ecosystem. Biome (next section) is a Rust-based replacement that formats and lints in a single tool, running 10-20x faster. For new projects with no legacy tooling, Biome is worth evaluating. For existing projects with extensive ESLint rules, Prettier + ESLint remains the practical choice.

7. Biome — The All-in-One Tool

It formats and lints in one pass, with a unified configuration file, no plugin system complexity, and speeds that make it feel instant even on large codebases. 8. TypeScript Strict Mode — Your AI Safety Net

Strict mode is a single tsconfig flag that activates a suite of checks TypeScript omits by default for backwards compatibility. In 2025, there is no good reason to ship a new TypeScript project without it.

tsconfig.json
{
  "compilerOptions": {
    "strict": true
  }
}

strict: true is shorthand for all of these:

Flag What it enforces
strictNullChecks null and undefined are separate types. Accessing user.name when user might be null is a compile error.
noImplicitAny Every value must have an explicit type or a type that can be inferred. No silent any.
strictFunctionTypes Function parameter types are checked contravariantly. Prevents subtle callback type bugs.
strictBindCallApply Checks .bind(), .call(), and .apply() for correct argument types.
strictPropertyInitialization Class properties must be initialized in the constructor or declared !.
noImplicitThis Catches this in contexts where its type can't be determined.
useUnknownInCatchVariables Catch clause variables are typed unknown rather than any. Forces safe error handling.
AI Era — Strict Mode as Protection Against AI-Generated Bugs

AI coding tools are optimistic. They generate code that looks right and compiles — but may silently mishandle null, skip error handling, or use any to avoid figuring out the real type. Strict mode catches all three categories. It's not just a best practice for human code: it's the most effective automated reviewer you can apply to AI-generated code in your repo.

Enabling Strict Mode on an Existing Project (Incremental Approach)

Turning on strict: true in a large existing codebase often reveals hundreds of errors. The pragmatic approach:

  1. Enable one flag at a time, starting with noImplicitAny.
  2. Fix errors in one directory, commit, repeat.
  3. Use // @ts-expect-error with a comment for errors you're deferring — not // @ts-ignore, which hides errors silently.
  4. Use Claude Code: "Enable strictNullChecks in tsconfig.json, then fix all resulting errors in src/domain/. Do not touch src/infra/."
Pro Tip — ts-reset

After enabling strict mode, install @total-typescript/ts-reset. It tightens TypeScript's built-in lib types — for example, Array.filter(Boolean) correctly narrows to non-nullable values, and JSON.parse() returns unknown instead of any. One import, zero configuration.

10. Pre-commit Hooks

Pre-commit hooks catch errors before they reach CI — faster feedback, fewer red builds. lefthook is faster than husky (written in Go) and has first-class support for running hooks only on changed files.

pnpm add -D lefthook
pnpm lefthook install
lefthook.yml
pre-commit:
  parallel: false
  commands:
    typecheck:
      run: pnpm typecheck
    lint:
      glob: "*.{ts,tsx}"
      run: pnpm lint --fix
      stage_fixed: true
    format:
      glob: "*.{ts,tsx,json,md}"
      run: pnpm format
      stage_fixed: true

The stage_fixed: true option automatically re-stages files that were auto-fixed by ESLint or Prettier — so the commit includes the fixes without you doing anything.

Pre-commit Flow Diagram

lint-staged Alternative

If you prefer husky + lint-staged:

pnpm add -D husky lint-staged
pnpm husky init
package.json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,md,yml}": ["prettier --write"]
  }
}
.husky/pre-commit
pnpm typecheck
pnpm lint-staged
Tip — Run Only on Changed Files

lint-staged runs linting only on staged files, making hooks fast even in large repos. lefthook's glob option does the same. Never run tsc on a subset of files though — type checking requires the full project graph. Run tsc --noEmit on every commit regardless of which files changed.

11. CI/CD for TypeScript

GitHub Actions Workflow

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  check:
    name: Type Check, Lint, Test, Build
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v3
        with:
          version: 9

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Type check
        run: pnpm typecheck

      - name: Lint
        run: pnpm lint

      - name: Test
        run: pnpm test --run

      - name: Build
        run: pnpm build

Caching node_modules and .pnpm-store

The cache: 'pnpm' option in setup-node handles pnpm store caching automatically when used with pnpm/action-setup. For more control:

      - name: Get pnpm store directory
        id: pnpm-cache
        run: echo "STORE_PATH=$(pnpm store path)" >> $GITHUB_OUTPUT

      - name: Cache pnpm store
        uses: actions/cache@v4
        with:
          path: ${{ steps.pnpm-cache.outputs.STORE_PATH }}
          key: ${{ runner.os }}-pnpm-${{ hashFiles('**/pnpm-lock.yaml') }}
          restore-keys: |
            ${{ runner.os }}-pnpm-
Info — Type Checking vs Building Separately in CI

Run pnpm typecheck (which is tsc --noEmit) and pnpm build (which is tsc or tsup) as separate steps. This way, if the build fails due to a tool configuration issue rather than a type error, the error messages are distinct. It also allows you to fail fast on type errors before spending time on the full build.

AI Era — CI as the Final AI Code Reviewer

In AI-assisted projects, CI is not optional — it's mandatory. When Copilot, Cursor, or Claude Code generates code that passes your local checks but fails a rule you forgot to configure locally, CI catches it. Think of CI as the safety net below the AI safety net. Every AI-generated PR goes through the same pipeline as hand-written code.

}

# Start with debugger, pause at first line

The debugger Statement

Drop debugger anywhere in TypeScript — it works identically to JavaScript. When the debugger is attached, execution pauses there:

function processOrder(order: Order): ProcessedOrder {
  debugger  // ← execution stops here when debugger attached
  const validated = validateOrder(order)
  return applyBusinessRules(validated)
}
Warning — Remove debugger Before Commit

Add a lint rule to catch forgotten debugger statements: "no-debugger": "error" in ESLint. ESLint's base recommended config already includes this. Pre-commit hooks + CI will catch any that slip through.

Structured Logging in Production

For production code, replace console.log with pino — the fastest structured logger for Node.js, with TypeScript support built in:

pnpm add pino
pnpm add -D pino-pretty @types/pino
src/lib/logger.ts
import pino from 'pino'

export const logger = pino({
  level: process.env['LOG_LEVEL'] ?? 'info',
  transport:
    process.env['NODE_ENV'] !== 'production'
      ? { target: 'pino-pretty', options: { colorize: true } }
      : undefined,
})

// Usage — fully typed
logger.info({ orderId, userId }, 'Order created')
logger.error({ err, orderId }, 'Payment failed')
logger.debug({ query, params }, 'DB query executed')
Tip — TypeScript + Pino for AI-Generated Logging

Pino's structured logging works beautifully with TypeScript types. When you log { orderId }, the type of orderId is preserved. This makes logs machine-parseable and searchable in tools like Datadog or Grafana Loki — essential when debugging production issues in AI-generated code where you didn't write every path yourself.
