Advanced Types: Unions, Intersections & Utility Types

This is where TypeScript stops being a "JavaScript with types" add-on and becomes a full-blown type-level programming language. Master these tools and you'll write APIs that are impossible to misuse.

By Matt Pocock, Total TypeScript ~8,400 words 30+ code examples 3 SVG diagrams

1. Union Types In Depth

A union type says: "this value is one of these types." The | operator reads almost like English — string | number means string or number. But unions go far deeper than that surface reading.

Basic union types TypeScript 
// Primitive unions
type StringOrNumber = string | number;
type Primitive = string | number | boolean | null | undefined;

// Literal unions — the most useful kind
type Direction = "north" | "south" | "east" | "west";
type Status = "idle" | "loading" | "success" | "error";
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE" | "PATCH";

// Unions with object types
type Response =
  | { kind: "ok"; data: unknown }
  | { kind: "error"; message: string };

// Union with arrays
type StringOrArray = string | string[];

function ensureArray(val: StringOrArray): string[] {
  return Array.isArray(val) ? val : [val];
}
Mental Model

Think of a union type as a set containing all values that belong to any of the constituent types. string | number is the union of the set of all strings and the set of all numbers. TypeScript's type system is set-theoretic at its core — this insight unlocks everything.

Discriminated Unions

The most powerful pattern in TypeScript. A discriminated union is a union of object types that all share a common discriminant property — a literal type that uniquely identifies which variant you're dealing with.

Discriminated union — fetch state machine TypeScript 
type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error; retryCount: number };

// TypeScript knows EXACTLY which properties are available in each branch
function renderFetchState<T>(state: FetchState<T>, render: (data: T) => string): string {
  switch (state.status) {
    case "idle":    return "Ready.";
    case "loading": return "Loading...";
    case "success": return render(state.data);   // state.data is T here
    case "error":   return `Error: ${state.error.message} (retry #${state.retryCount})`;
  }
}
Discriminated union — Redux-style actions TypeScript 
type Action =
  | { type: "INCREMENT"; by: number }
  | { type: "DECREMENT"; by: number }
  | { type: "RESET" }
  | { type: "SET_VALUE"; value: number };

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case "INCREMENT": return state + action.by;   // action.by: number
    case "DECREMENT": return state - action.by;
    case "RESET":     return 0;                   // no extra properties here
    case "SET_VALUE": return action.value;
  }
}
Tip — Discriminants don't have to be strings

Any literal type works as a discriminant: number literals, boolean, even null. But string literals give the best error messages and are conventional. Avoid using kind and type interchangeably in a single codebase — pick one convention and stick to it.

Narrowing Techniques

TypeScript's control flow analysis tracks the type of a variable through branches. Every narrowing check is an opportunity for TypeScript to reduce the set of possible types.

typeof narrowing TypeScript 
function stringify(val: string | number | boolean): string {
  if (typeof val === "string") {
    return val.toUpperCase();  // val: string
  }
  if (typeof val === "number") {
    return val.toFixed(2);     // val: number
  }
  return String(val);          // val: boolean
}
instanceof narrowing TypeScript 
function handleError(error: Error | string): string {
  if (error instanceof TypeError) {
    return `Type error: ${error.message}`;  // error: TypeError
  }
  if (error instanceof Error) {
    return `Error: ${error.message}`;        // error: Error
  }
  return error;                              // error: string
}
in operator narrowing TypeScript 
type Cat = { meow(): void };
type Dog = { bark(): void; fetch(): void };
type Pet = Cat | Dog;

function makeNoise(pet: Pet) {
  if ("meow" in pet) {
    pet.meow();  // pet: Cat
  } else {
    pet.bark();  // pet: Dog
    pet.fetch();
  }
}

// Works great for discriminating ad-hoc object unions
type Admin = { role: "admin"; permissions: string[] };
type User  = { role: "user"; email: string };
type Account = Admin | User;

function getInfo(account: Account) {
  if ("permissions" in account) {
    console.log(account.permissions);  // account: Admin
  } else {
    console.log(account.email);        // account: User
  }
}
Custom type predicates TypeScript 
// Type predicate: paramName is Type
function isString(val: unknown): val is string {
  return typeof val === "string";
}

function isError(val: unknown): val is Error {
  return val instanceof Error;
}

// More complex predicates
interface Circle { kind: "circle"; radius: number }
interface Square { kind: "square"; side: number }
type Shape = Circle | Square;

function isCircle(shape: Shape): shape is Circle {
  return shape.kind === "circle";
}

const shapes: Shape[] = [
  { kind: "circle", radius: 5 },
  { kind: "square", side: 3 },
];

const circles = shapes.filter(isCircle);
//    ^? Circle[]  — not Shape[]!
Warning — Type predicates are a lie TypeScript believes

TypeScript trusts your type predicate completely. If you write val is string but return true for non-strings, TypeScript won't catch it. Use predicates carefully and prefer discriminated unions when possible — they're verified by the compiler.

Exhaustive Union Handling with never

The never type represents the empty set — a value that can never exist. It's the type you get when TypeScript has narrowed away all possibilities. We can exploit this to enforce exhaustive handling.

Exhaustive check with never TypeScript 
type Shape = "circle" | "square" | "triangle";

function getArea(shape: Shape, size: number): number {
  switch (shape) {
    case "circle":   return Math.PI * size ** 2;
    case "square":   return size ** 2;
    case "triangle": return (Math.sqrt(3) / 4) * size ** 2;
    default:
      // If you add "hexagon" to Shape, this line throws a compile error!
      const _exhaustiveCheck: never = shape;
      throw new Error(`Unhandled shape: ${_exhaustiveCheck}`);
  }
}

// Utility function — reusable exhaustive check
function assertNever(x: never): never {
  throw new Error(`Unexpected value: ${x}`);
}

// Usage
function describeShape(shape: Shape): string {
  switch (shape) {
    case "circle":   return "round";
    case "square":   return "boxy";
    case "triangle": return "pointy";
    default:         return assertNever(shape); // compile error if Shape grows
  }
}
AI Era — LLMs extending your unions

When AI tools generate code that adds new variants to your union types (e.g., new action types, new API response shapes), exhaustive never checks immediately flag every switch statement that needs updating. This makes AI-generated extensions to your codebase safe by default.

Distributive Behavior of Unions with Generics

Distributive union behavior TypeScript 
// When a generic type is used in a conditional, it distributes over unions
type ToArray<T> = T extends unknown ? T[] : never;

type Result = ToArray<string | number>;
//   ^? string[] | number[]
// NOT: (string | number)[]

// Compare: wrapping in [] prevents distribution
type ToArrayNonDistrib<T> = [T] extends [unknown] ? T[] : never;

type Result2 = ToArrayNonDistrib<string | number>;
//   ^? (string | number)[]

// Practical use: get nullable counterparts
type Nullable<T> = T extends unknown ? T | null : never;
type NullableStrNum = Nullable<string | number>;
// ^? string | null | number | null → string | number | null

2. Intersection Types In Depth

If a union says "A or B," an intersection says "A and B." A value of type A & B must satisfy both A and B simultaneously. The resulting type has all the properties of both.

Basic intersection types TypeScript 
type HasTimestamps = {
  createdAt: Date;
  updatedAt: Date;
};

type HasId = {
  id: string;
};

type BaseEntity = HasId & HasTimestamps;
// Equivalent to:
// { id: string; createdAt: Date; updatedAt: Date }

type User = BaseEntity & {
  name: string;
  email: string;
};

// Must satisfy ALL three constituent types:
const user: User = {
  id: "u_123",
  createdAt: new Date(),
  updatedAt: new Date(),
  name: "Alice",
  email: "alice@example.com",
};

Mixin Patterns Using Intersection

Composable behavior via intersection + generics TypeScript 
// Capability mixins
type Serializable = {
  serialize(): string;
  deserialize(data: string): void;
};

type Loggable = {
  log(message: string): void;
};

type Cacheable = {
  cache(): void;
  invalidate(): void;
};

// Compose capabilities for a specific service
type UserService = Serializable & Loggable & {
  getUser(id: string): Promise<User>;
  createUser(data: Omit<User, "id">): Promise<User>;
};

// Function-level mixin with generics
function withLogging<T extends object>(obj: T): T & Loggable {
  return {
    ...obj,
    log(message: string) {
      console.log(`[${new Date().toISOString()}] ${message}`);
    },
  };
}

Conflict Resolution in Intersections

What happens when both sides of an intersection define the same property with different types? The answer is often surprising.

Conflicting properties → never TypeScript 
type A = { id: string };
type B = { id: number };

type AB = A & B;
// id: string & number → never
// No value can be both string AND number simultaneously

const ab: AB = {
  id: "hello",  // Error: Type 'string' is not assignable to type 'never'
};

// Primitive intersections:
type StringAndNumber = string & number;  // → never
type NeverType = string & string;         // → string (same type is fine)

// Functions in intersections — overloads!
type StringFn = (x: string) => void;
type NumberFn = (x: number) => void;
type OverloadedFn = StringFn & NumberFn;
// Now callable as both f("hi") and f(42)
Common Mistake — Using intersection for "merging" objects at runtime

Intersection types are a compile-time concept only. Writing type Result = A & B doesn't merge objects at runtime — you still need Object.assign() or spread syntax for that. The type just describes what the merged result would look like.

When to use intersection vs interface extends TypeScript 
// Interface extends — use for named, reusable entities in OOP hierarchies
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): void;
}

// Intersection — use for ad-hoc type composition, utilities, generics
type WithMetadata<T> = T & { _meta: { version: number; author: string } };

type UserWithMeta = WithMetadata<User>;
// Works for any T — generics love intersections

// Intersection wins for:
// 1. Generic utilities (WithMetadata<T>, Loggable & T)
// 2. Composing multiple interfaces at once
// 3. Anonymous structural composition
//
// Interface extends wins for:
// 1. Declaration merging (open interface augmentation)
// 2. Self-referential / recursive types (interfaces show better in errors)
// 3. Class implements

3. TypeScript Utility Types (All of Them)

TypeScript ships with a standard library of generic utility types. These are not magic — every single one is implementable using the mapped types and conditional types you'll learn in sections 4 and 5. But you should know them cold because they appear everywhere.

Partial<T> and Required<T>

Without Partial Before 
interface Config {
  host: string;
  port: number;
  debug: boolean;
}

// Force all fields on every update
function updateConfig(
  current: Config,
  next: Config,
): Config {
  return { ...current, ...next };
}
// But we want partial updates!
With Partial After 
interface Config {
  host: string;
  port: number;
  debug: boolean;
}

function updateConfig(
  current: Config,
  next: Partial<Config>,
): Config {
  return { ...current, ...next };
}

// Now valid:
updateConfig(config, { debug: true });
updateConfig(config, { port: 8080 });
Required<T> — enforce all fields TypeScript 
interface DraftPost {
  title?: string;
  body?: string;
  tags?: string[];
  publishedAt?: Date;
}

type PublishedPost = Required<DraftPost>;
// { title: string; body: string; tags: string[]; publishedAt: Date }

function publish(draft: DraftPost): PublishedPost {
  if (!draft.title || !draft.body) {
    throw new Error("Missing required fields");
  }
  return draft as PublishedPost; // safe after runtime guard
}

Readonly<T> and Record<K, V>

Readonly — immutable configuration TypeScript 
interface AppConfig {
  apiUrl: string;
  timeout: number;
  retries: number;
}

const CONFIG: Readonly<AppConfig> = {
  apiUrl: "https://api.example.com",
  timeout: 5000,
  retries: 3,
};

CONFIG.apiUrl = "other";  // Error: Cannot assign to 'apiUrl' because it is a read-only property

// Readonly is shallow — nested objects are still mutable:
interface NestedConfig {
  server: { host: string };
}
const cfg: Readonly<NestedConfig> = { server: { host: "localhost" } };
cfg.server = { host: "other" };  // Error
cfg.server.host = "other";       // OK! (not deep readonly)
Record — typed dictionaries TypeScript 
// Record<Keys, Value>
type CountryCode = "US" | "UK" | "DE" | "JP";
type CurrencyMap = Record<CountryCode, string>;

const currencies: CurrencyMap = {
  US: "USD",
  UK: "GBP",
  DE: "EUR",
  JP: "JPY",
  // Adding "AU" here is a type error — not in CountryCode
};

// Record vs index signature:
type WithRecord = Record<string, number>;    // all string keys → number
type WithIndex = { [key: string]: number };   // same, but Record is more composable

// Useful pattern — categorised lookup tables
type StatusConfig = Record<"idle" | "loading" | "error", {
  label: string;
  color: string;
  icon: string;
}>;

const STATUS: StatusConfig = {
  idle:    { label: "Ready",   color: "#6B7280", icon: "circle" },
  loading: { label: "Loading", color: "#2563EB", icon: "spinner" },
  error:   { label: "Error",   color: "#DC2626", icon: "x" },
};

Pick<T, K> and Omit<T, K>

Pick and Omit — view projections TypeScript 
interface User {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  role: "admin" | "user";
  createdAt: Date;
}

// Pick only the fields you need
type UserPublicProfile = Pick<User, "id" | "name" | "role">;
// { id: string; name: string; role: "admin" | "user" }

// Omit sensitive/internal fields
type UserDTO = Omit<User, "passwordHash">;
// All fields except passwordHash

// Pattern: API payloads
type CreateUserInput = Omit<User, "id" | "createdAt">;
// Client provides everything except server-generated fields

type UpdateUserInput = Partial<Omit<User, "id" | "createdAt">>;
// Partial update — all optional, minus server-managed fields

function getPublicProfile(user: User): UserPublicProfile {
  const { id, name, role } = user;
  return { id, name, role };
}
Common Mistake — Omit with union types

Omit<T, K> does not distribute over unions. Omit<Cat | Dog, "age"> gives you a single merged type with age removed — not Omit<Cat, "age"> | Omit<Dog, "age">. Use a distributive helper instead:

type DistributiveOmit<T, K extends PropertyKey> =
  T extends unknown ? Omit<T, K> : never;

Exclude<T, U>, Extract<T, U>, NonNullable<T>

Exclude and Extract — union surgery TypeScript 
type AllEvents = "click" | "focus" | "blur" | "change" | "submit" | "keydown";

// Remove specific members from a union
type WithoutKeyboard = Exclude<AllEvents, "keydown">;
// "click" | "focus" | "blur" | "change" | "submit"

// Extract only matching members
type FocusEvents = Extract<AllEvents, "focus" | "blur">;
// "focus" | "blur"

// Works with broader types too
type Strings = Extract<string | number | boolean | null, string>;
// string

type NoFunctions = Exclude<string | number | (() => void), Function>;
// string | number

// NonNullable
type MaybeString = string | null | undefined;
type DefiniteString = NonNullable<MaybeString>;
// string

// Real-world: cleaning up API response types
type ApiValue = string | number | boolean | null | undefined;
type CleanApiValue = NonNullable<ApiValue>;
// string | number | boolean

ReturnType, Parameters, ConstructorParameters, InstanceType, Awaited

ReturnType and Parameters TypeScript 
function createUser(name: string, email: string, role: "admin" | "user") {
  return { id: Math.random().toString(), name, email, role, createdAt: new Date() };
}

type UserShape = ReturnType<typeof createUser>;
// { id: string; name: string; email: string; role: "admin"|"user"; createdAt: Date }

type CreateUserParams = Parameters<typeof createUser>;
// [name: string, email: string, role: "admin" | "user"]

// Spread parameters for wrapping functions
function logAndCreateUser(...args: Parameters<typeof createUser>): ReturnType<typeof createUser> {
  console.log("Creating user:", args[0]);
  return createUser(...args);
}

// Useful for higher-order functions without duplicating types
type AnyFn = (...args: any[]) => any;

function memoize<T extends AnyFn>(fn: T): T {
  const cache = new Map<string, ReturnType<T>>();
  return ((...args: Parameters<T>) => {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key)!;
  }) as T;
}
ConstructorParameters and InstanceType TypeScript 
class ApiClient {
  constructor(
    private baseUrl: string,
    private timeout: number,
    private headers: Record<string, string>,
  ) {}

  get<T>(path: string): Promise<T> {
    return fetch(`${this.baseUrl}${path}`).then(r => r.json());
  }
}

type ClientConfig = ConstructorParameters<typeof ApiClient>;
// [baseUrl: string, timeout: number, headers: Record<string, string>]

type ClientInstance = InstanceType<typeof ApiClient>;
// ApiClient

// Practical: factory functions that mirror constructor signatures
function createClient(...args: ConstructorParameters<typeof ApiClient>): ApiClient {
  return new ApiClient(...args);
}

// Useful for dependency injection containers
type Constructor<T> = new (...args: any[]) => T;

function inject<T>(ctor: Constructor<T>): InstanceType<typeof ctor> {
  // DI container resolves this
  return container.resolve(ctor);
}
Awaited — unwrapping nested Promises TypeScript 
// Awaited unwraps Promise types recursively
type A = Awaited<Promise<string>>;
// string

type B = Awaited<Promise<Promise<number>>>;
// number (unwrapped twice!)

type C = Awaited<string>;
// string (non-Promise passthrough)

// Practical: extracting the resolved value type of an async function
async function fetchUsers(): Promise<User[]> {
  return fetch("/api/users").then(r => r.json());
}

type UsersResult = Awaited<ReturnType<typeof fetchUsers>>;
// User[]  — not Promise<User[]>

String manipulation utility types TypeScript 
type Greeting = "hello world";

type Shout  = Uppercase<Greeting>;      // "HELLO WORLD"

// "getName" | "getEmail" | "getAge"

4. Mapped Types

Mapped types iterate over the keys of another type, transforming each property. They're the engine behind every utility type in section 3. Understanding mapped types means you can build your own utilities instead of just consuming them.

Mapped type fundamentals TypeScript 
// The base syntax: [K in keyof T]: ...
// K is the key variable, T is the source type

// Recreating Partial<T> from scratch:
type MyPartial<T> = {
  [K in keyof T]?: T[K];
  //           ^ optional modifier
  //                 ^ T[K] = lookup the type of key K in T
};

// Recreating Readonly<T>:
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
  // ^-- readonly modifier
};

// Recreating Required<T> — remove optional with -?:
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
  //           ^-- minus removes the optional modifier
};

// Mutable<T> — remove readonly with -readonly:
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];
};

// Nullable<T> — add null to every property
type Nullable<T> = {
  [K in keyof T]: T[K] | null;
};

Remapping Keys with as

Key remapping with as clause TypeScript 
// Rename every key using as + template literals
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

interface User {
  name: string;
  age: number;
}

type UserGetters = Getters<User>;
// { getName: () => string; getAge: () => number }

// Filter properties using as + conditional type (returning never drops the key)
type OnlyStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};

interface Mixed {
  id: string;
  name: string;
  age: number;
  active: boolean;
}

type StringOnly = OnlyStrings<Mixed>;
// { id: string; name: string }

// Flip object — swap keys and values
type Invert<T extends Record<string, string>> = {
  [K in keyof T as T[K]]: K;
};

type Codes = { US: "USD"; UK: "GBP"; DE: "EUR" };
type Inverted = Invert<Codes>;
// { USD: "US"; GBP: "UK"; EUR: "DE" }

Real Examples: DeepReadonly, Nullable, Mutable

DeepReadonly<T> — recursive mapped type TypeScript 
// DeepReadonly: recursively mark all nested properties as readonly
type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

interface AppState {
  user: {
    profile: { name: string; email: string };
    preferences: { theme: "light" | "dark" };
  };
  posts: Array<{ id: string; title: string }>;
}

type FrozenState = DeepReadonly<AppState>;
// Every nested property is readonly — great for Redux/Zustand state

const state: FrozenState = {
  user: {
    profile: { name: "Alice", email: "alice@example.com" },
    preferences: { theme: "light" },
  },
  posts: [{ id: "1", title: "Hello" }],
};

state.user.profile.name = "Bob";    // Error: readonly
state.posts.push({ id: "2", title: "World" }); // Error: ReadonlyArray
Practical mapped type patterns TypeScript 
// EventMap: from event names to handler signatures
type EventMap = {
  click: MouseEvent;
  keydown: KeyboardEvent;
  resize: UIEvent;
};

type HandlerMap = {
  [K in keyof EventMap]: (event: EventMap[K]) => void;
};
// { click: (event: MouseEvent) => void; ... }

// Flags type: all boolean properties
type Flags<T> = {
  [K in keyof T]: boolean;
};

type UserFlags = Flags<User>;
// { id: boolean; name: boolean; email: boolean; ... }

// Validated type: wrap each value in a validation result
type Validated<T> = {
  [K in keyof T]: { value: T[K]; error: string | null };
};

5. Conditional Types

Conditional types bring if-else logic to the type level. The syntax T extends U ? X : Y reads: "if T is assignable to U, resolve to X, otherwise resolve to Y."

Conditional type basics TypeScript 
// Basic conditional
type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<string>;  // "yes"
type B = IsString<number>;  // "no"
type C = IsString<"hello">; // "yes" — "hello" extends string

// Nesting conditionals
type TypeName<T> =
  T extends string   ? "string" :
  T extends number   ? "number" :
  T extends boolean  ? "boolean" :
  T extends null     ? "null" :
  T extends undefined? "undefined" :
  T extends Function ? "function" :
  "object";

type D = TypeName<string[]>;   // "object"
type E = TypeName<() => void>; // "function"

The infer Keyword

Inside a conditional type's "true" branch, you can use infer to capture a sub-type from the type being tested. This is how you extract types from within other types.

infer — building utility types from scratch TypeScript 
// Implement ReturnType ourselves
type MyReturnType<T extends (...args: any[]) => any> =
  T extends (...args: any[]) => infer R ? R : never;
  //                                      ^ R is inferred from return position

type Fn = (x: string) => number[];
type FnReturn = MyReturnType<Fn>; // number[]

// Implement Parameters ourselves
type MyParameters<T extends (...args: any[]) => any> =
  T extends (...args: infer P) => any ? P : never;

type FnParams = MyParameters<Fn>; // [x: string]

// Implement NonNullable ourselves
type MyNonNullable<T> = T extends null | undefined ? never : T;

// UnwrapPromise
type UnwrapPromise<T> =
  T extends Promise<infer U> ? UnwrapPromise<U> : T;
  // Recursively unwrap nested Promises

type P1 = UnwrapPromise<Promise<string>>;              // string
type P2 = UnwrapPromise<Promise<Promise<number>>>;     // number

// Extract array element type
type ElementOf<T> = T extends (infer U)[] ? U : never;

type StrElem = ElementOf<string[]>; // string
type NumElem = ElementOf<number[]>; // number

// Extract Promise from function return
type AsyncReturnType<T extends (...args: any[]) => Promise<any>> =
  T extends (...args: any[]) => Promise<infer R> ? R : never;

async function fetchUser(): Promise<User> { /* ... */ return {} as User; }
type FetchedUser = AsyncReturnType<typeof fetchUser>; // User

Distributive Conditional Types

Distributive conditional types in action TypeScript 
// When T is a bare type parameter in a conditional type,
// it distributes over union members

type IsArray<T> = T extends any[] ? "array" : "not array";

type R1 = IsArray<string[]>;         // "array"
type R2 = IsArray<string | number[]>; // "not array" | "array"
//        ^-- distributed: IsArray<string> | IsArray<number[]>

// NonNullable as distributive conditional:
type NonNull<T> = T extends null | undefined ? never : T;
type R3 = NonNull<string | null | undefined | number>;
// string | number
// (null → never, undefined → never, both dropped from union)

// Prevent distribution by wrapping in tuple:
type IsArrayExact<T> = [T] extends [any[]] ? "array" : "not array";
type R4 = IsArrayExact<string | number[]>; // "not array" (union is not an array)

6. Type Narrowing Patterns (Comprehensive)

TypeScript's control flow analysis is one of its most powerful — and underappreciated — features. Every check you write is an opportunity to narrow types.

All narrowing techniques in one place TypeScript 
declare const val: string | number | null | undefined | string[];

// 1. typeof narrowing
if (typeof val === "string") { val; /* string */ }
if (typeof val === "number") { val; /* number */ }

// 2. Truthiness narrowing
if (val) { val; /* string | number | string[] — null/undefined/0/"" excluded */ }
if (!val) { val; /* "" | 0 | null | undefined */ }

// 3. Equality narrowing
if (val === null) { val; /* null */ }
if (val !== null && val !== undefined) { val; /* string | number | string[] */ }

// 4. instanceof narrowing
class HttpError extends Error { constructor(public status: number, message: string) { super(message); } }
declare const err: Error | HttpError | string;
if (err instanceof HttpError) { err.status; /* number — HttpError */ }
if (err instanceof Error) { err.message; /* Error or HttpError */ }

// 5. in narrowing
type Cat = { purr: () => void };
type Dog = { bark: () => void };
declare const pet: Cat | Dog;
if ("purr" in pet) { pet.purr(); /* Cat */ }

// 6. Array.isArray narrowing
declare const strOrArr: string | string[];
if (Array.isArray(strOrArr)) { strOrArr[0]; /* string[] */ }

// 7. Discriminant property narrowing
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rect"; width: number; height: number };
declare const shape: Shape;
if (shape.kind === "circle") { shape.radius; /* number — circle */ }

// 8. Assertion functions
function assertDefined<T>(val: T | null | undefined): asserts val is T {
  if (val == null) throw new Error("Expected defined value");
}
declare let maybeUser: User | null;
assertDefined(maybeUser);
maybeUser; // User — null has been ruled out
Assertion functions — the modern way TypeScript 
// Assertion functions narrow in the calling scope (unlike type predicates)
function assertIsString(val: unknown): asserts val is string {
  if (typeof val !== "string") {
    throw new TypeError(`Expected string, got ${typeof val}`);
  }
}

function assertIsUser(val: unknown): asserts val is User {
  if (!val || typeof val !== "object") throw new TypeError("Not an object");
  if (!("id" in val) || !("name" in val)) throw new TypeError("Not a User");
}

// Usage — the type narrows after the assertion call
function processInput(input: unknown) {
  assertIsString(input);
  input; // string here — TypeScript knows
  console.log(input.toUpperCase());
}

// Combine with Zod schemas for validated narrowing
import { z } from "zod";
const UserSchema = z.object({ id: z.string(), name: z.string() });
function assertUser(val: unknown): asserts val is z.infer<typeof UserSchema> {
  UserSchema.parse(val); // throws if invalid
}
Tip — Control flow analysis crosses function calls... sometimes

TypeScript's control flow analysis does not follow into arbitrary function calls (it can't — functions might have side effects). That's why asserts functions and type predicates exist: they're the explicit contract that says "after calling this, TypeScript should update its knowledge."

Truthiness narrowing edge cases TypeScript 
// Be careful with truthiness + numbers
function double(x: number | null): number {
  if (x) {
    return x * 2; // Problem: 0 is falsy!
  }
  return 0; // This branch runs for x=0 too
}

// Better: explicit null check
function doubleSafe(x: number | null): number {
  if (x !== null) {
    return x * 2; // x: number — includes 0
  }
  return 0;
}

// Truthiness narrowing is great for strings:
function greet(name: string | null | undefined) {
  if (name) {
    // name: string (empty string "" is excluded — OK here)
    console.log(`Hello, ${name}!`);
  } else {
    console.log("Hello, stranger!");
  }
}

7. Template Literal Types (Preview)

Template literal types bring JavaScript's template string syntax to the type level. You can construct new string literal types by combining other string types — and combined with mapped types, this creates incredibly expressive APIs.

Template literal types — fundamentals TypeScript 
// Basic template literal type
type Greeting = `Hello, ${string}!`;
const g1: Greeting = "Hello, world!";  // OK
const g2: Greeting = "Hi, world!";     // Error

// Combining literal unions — creates cartesian product
type Color = "red" | "green" | "blue";
type Shade = "light" | "dark";
type ColorVariant = `${Shade}-${Color}`;
// "light-red" | "light-green" | "light-blue" | "dark-red" | ...

// Event names
type DomEvent = "click" | "focus" | "blur" | "change";
type EventHandler = `on${Capitalize<DomEvent>}`;
// "onClick" | "onFocus" | "onBlur" | "onChange"

// CSS properties with direction
type Side = "top" | "right" | "bottom" | "left";
type MarginProp = `margin${Capitalize<Side>}`;
// "marginTop" | "marginRight" | "marginBottom" | "marginLeft"

// REST API endpoint pattern
type ResourceName = "users" | "posts" | "comments";
type ApiEndpoint =
  | `/${ResourceName}`
  | `/${ResourceName}/:id`
  | `/${ResourceName}/:id/${"likes" | "shares"}`;
// "/users" | "/users/:id" | "/users/:id/likes" | ...
Template literals + mapped types — powerful combination TypeScript 
// Auto-generate getter methods from data shape
type GettersFor<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type UserGetters = GettersFor<{ name: string; age: number; email: string }>;
// { getName: () => string; getAge: () => number; getEmail: () => string }

// Auto-generate event emitter types
type EventNames<T extends object> = {
  [K in keyof T as `on${Capitalize<string & K>}Change`]: (
    prev: T[K],
    next: T[K],
  ) => void;
};

type UserEvents = EventNames<{ name: string; status: "active" | "inactive" }>;
// {
//   onNameChange: (prev: string, next: string) => void;
//   onStatusChange: (prev: "active"|"inactive", next: ...) => void;
// }

// Extract prefix from string literal type
type ExtractPrefix<S extends string, Prefix extends string> =
  S extends `${Prefix}${infer Rest}` ? Rest : never;

type WithoutOn = ExtractPrefix<"onClick", "on">; // "Click"
type WithoutGet = ExtractPrefix<"getName", "get">; // "Name"
AI Era — Generating type-safe API clients

Template literal types let you build type-safe API clients where the endpoint URL, path parameters, query parameters, and response type are all connected at the type level. AI tools that generate API client code can lean on these types to produce zero-configuration, fully typed fetch wrappers — no OpenAPI codegen required.

8. Practical Patterns with Advanced Types

Making API Responses Type-Safe

Type-safe API response wrapper TypeScript 
// Discriminated union for API responses
type ApiResponse<T> =
  | { ok: true; data: T; status: number }
  | { ok: false; error: string; status: number };

// Typed fetch wrapper
async function apiFetch<T>(url: string): Promise<ApiResponse<T>> {
  try {
    const res = await fetch(url);
    if (!res.ok) {
      const error = await res.text();
      return { ok: false, error, status: res.status };
    }
    const data: T = await res.json();
    return { ok: true, data, status: res.status };
  } catch (err) {
    return { ok: false, error: String(err), status: 0 };
  }
}

// Usage — TypeScript knows data only exists when ok is true
const result = await apiFetch<User[]>("/api/users");
if (result.ok) {
  result.data;   // User[] — type safe
} else {
  result.error;  // string — type safe
}

Type-Safe Event System

Fully typed event emitter TypeScript 
// Define your event map
type AppEvents = {
  "user:login":  { userId: string; timestamp: Date };
  "user:logout": { userId: string };
  "post:create": { postId: string; title: string; authorId: string };
  "post:delete": { postId: string };
};

// Type-safe emitter using generic constraints
class TypedEventEmitter<Events extends Record<string, unknown>> {
  private listeners: {
    [K in keyof Events]?: Array<(payload: Events[K]) => void>;
  } = {};

  on<K extends keyof Events>(
    event: K,
    handler: (payload: Events[K]) => void,
  ): () => void {
    (this.listeners[event] ??= []).push(handler);
    return () => this.off(event, handler);
  }

  off<K extends keyof Events>(event: K, handler: (payload: Events[K]) => void) {
    this.listeners[event] = this.listeners[event]?.filter(h => h !== handler);
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    this.listeners[event]?.forEach(h => h(payload));
  }
}

const emitter = new TypedEventEmitter<AppEvents>();

// Fully typed — event name and payload are linked
emitter.on("user:login", ({ userId, timestamp }) => {
  console.log(`User ${userId} logged in at ${timestamp.toISOString()}`);
});

emitter.emit("user:login", { userId: "u_1", timestamp: new Date() }); // OK
emitter.emit("user:login", { userId: "u_1" });                        // Error — missing timestamp

Builder Pattern with Types

Type-safe builder with generics TypeScript 
// Builder that tracks which fields have been set at the type level
class QueryBuilder<
  T extends object,
  Required extends keyof T = never
> {
  private query: Partial<T> = {};

  set<K extends keyof T>(key: K, value: T[K]): QueryBuilder<T, Required | K> {
    this.query[key] = value;
    return this as any;
  }

  // Build is only callable when all required keys are set
  build(): Pick<T, Required> & Partial<T> {
    return this.query as any;
  }
}

interface SearchQuery {
  table: string;
  limit: number;
  offset?: number;
  filter?: string;
}

const query = new QueryBuilder<SearchQuery>()
  .set("table", "users")
  .set("limit", 10)
  .build();

// Type of query.table is string (we set it)
// Type of query.offset is number | undefined (optional)

Recursive Types (JSON, Trees)

Recursive types for JSON and tree structures TypeScript 
// JSON — the canonical recursive type example
type JsonPrimitive = string | number | boolean | null;
type JsonObject = { [key: string]: JsonValue };
type JsonArray = JsonValue[];
type JsonValue = JsonPrimitive | JsonObject | JsonArray;

const valid: JsonValue = {
  name: "Alice",
  age: 30,
  active: true,
  address: null,
  tags: ["ts", "react"],
  nested: { deep: { deeper: 42 } },
};

// Tree structure — mutual recursion with interface
interface TreeNode<T> {
  value: T;
  children: TreeNode<T>[];
}

function mapTree<A, B>(node: TreeNode<A>, fn: (a: A) => B): TreeNode<B> {
  return {
    value: fn(node.value),
    children: node.children.map(child => mapTree(child, fn)),
  };
}

// Recursive Readonly
type DeepPartial<T> =
  T extends (infer U)[]
    ? DeepPartial<U>[]
    : T extends object
      ? { [K in keyof T]?: DeepPartial<T[K]> }
      : T;

type NestedConfig = {
  server: { host: string; port: number };
  database: { url: string; pool: { min: number; max: number } };
};

type PartialConfig = DeepPartial<NestedConfig>;
// Every nested field is optional

  server: { host: "localhost" }, // port omitted — OK
  // database omitted entirely — OK
};
Python Comparison — TypedDict vs TypeScript Object Types

Python's TypedDict is a rough equivalent to TypeScript's object type literals, but it only scratches the surface. Python lacks equivalents to mapped types, conditional types, and template literal types. What takes 3 lines in TypeScript (type Partial<T> = { [K in keyof T]?: T[K] }) requires complex runtime metaclass machinery or external libraries in Python. TypeScript's type system is genuinely more expressive for these patterns.

The DeepPartial Pattern

DeepPartial — production-ready version TypeScript 
// Production DeepPartial handles arrays, Maps, Sets, Dates
type DeepPartial<T> =
  T extends Date        ? T :
  T extends Map<infer K, infer V> ? Map<K, DeepPartial<V>> :
  T extends Set<infer U>          ? Set<DeepPartial<U>> :
  T extends (infer U)[]           ? DeepPartial<U>[] :
  T extends object                ? { [K in keyof T]?: DeepPartial<T[K]> } :
  T;

// Use case: deep merging configuration objects
function deepMerge<T extends object>(base: T, override: DeepPartial<T>): T {
  const result = { ...base };
  for (const key in override) {
    const overVal = override[key as keyof typeof override];
    const baseVal = base[key as keyof T];
    if (overVal && typeof overVal === "object" && !Array.isArray(overVal)) {
      (result as any)[key] = deepMerge(baseVal as any, overVal as any);
    } else if (overVal !== undefined) {
      (result as any)[key] = overVal;
    }
  }
  return result;
}

const defaultConfig: NestedConfig = {
  server: { host: "localhost", port: 3000 },
  database: { url: "postgres://localhost/dev", pool: { min: 2, max: 10 } },
};

const userConfig: DeepPartial<NestedConfig> = {
  database: { pool: { max: 20 } },
};

const merged = deepMerge(defaultConfig, userConfig);
// { server: { host: "localhost", port: 3000 }, database: { url: "...", pool: { min: 2, max: 20 } } }

Mental Model — The Type-Level / Value-Level Split

TypeScript has two parallel worlds that coexist in your source files:

  • Value level: variables, functions, classes, objects — what exists at runtime
  • Type level: types, interfaces, mapped types, conditional types — erased at compile time

Mapped types, conditional types, and template literal types are the programming constructs of the type level. They let you write programs that run during type-checking, producing types as their "output." Once you internalize this model, advanced TypeScript becomes intuitive instead of mysterious.
