1. Infrastructure as Code (IaC) Overview

When I was on the GCP team at Google, we managed thousands of cloud resources: Kubernetes clusters, Cloud SQL instances, load balancers, IAM bindings, service accounts, VPCs. The only way to keep that sane — reproducible, reviewable, auditable — was to define every resource in code. Not through the console. Not through one-off CLI commands. In code, checked into version control, reviewed like any other change.

That discipline is called Infrastructure as Code (IaC). The idea is simple: instead of clicking through the AWS console to create an S3 bucket, you write a declaration that says "I want a bucket with these properties," commit it, and a tool reads that declaration and makes it real. When the declaration changes, the tool figures out the minimal set of changes to apply.

💡
Info — Why IaC Matters

IaC gives you reproducibility (same code = same infra), version history (git blame your outage), peer review (PRs for infrastructure changes), and disaster recovery (rebuild from scratch in minutes, not weeks).

The IaC Landscape

Several tools compete in this space. Each makes a different tradeoff between simplicity and power:

Tool Language Company Type Safety Real Loops Real Functions Unit Tests IDE Support
Terraform HCL (custom DSL) HashiCorp ✗ ~ ~ ✗ ~
CloudFormation YAML / JSON AWS ✗ ✗ ✗ ✗ ✗
AWS CDK TypeScript / Python / Java AWS ✓ ✓ ✓ ✓ ✓
Pulumi TypeScript / Python / Go / C# Pulumi Corp ✓ ✓ ✓ ✓ ✓
Ansible YAML Red Hat ✗ ~ ✗ ~ ✗

Why YAML and HCL Are Limiting

The fundamental problem with YAML- and HCL-based IaC is that they are data formats pretending to be programming languages. They can express what you want, but not how to compute what you want.

Terraform HCL — creating 3 subnets
HCL main.tf 
# No real loops — must use count or for_each
resource "aws_subnet" "subnet" {
  count      = 3
  vpc_id     = aws_vpc.main.id
  cidr_block = element(
    ["10.0.1.0/24","10.0.2.0/24","10.0.3.0/24"],
    count.index
  )
  # Can't call a function to compute CIDR
  # Can't use if/else for conditional logic
  # Error messages are cryptic
}
Pulumi TypeScript — same thing
TypeScript index.ts 
// Real loops with real logic
const subnets = [1, 2, 3].map(i =>
  new aws.ec2.Subnet(`subnet-${i}`, {
    vpcId: vpc.id,
    // Real function call — compute CIDR
    cidrBlock: computeCidr(i),
    availabilityZone: azs[i - 1],
    tags: { Name: `subnet-${i}` },
  })
)

function computeCidr(index: number): string {
  return `10.0.${index}.0/24`
}

Here is what you simply cannot do in Terraform HCL or raw CloudFormation YAML, but can do trivially in Pulumi TypeScript:

  • No type safety — misspell cidrBlock as cidr_block (or vice versa) and you find out at deploy time, not at your editor
  • No real loops — Terraform's count and for_each are limited hacks; you cannot loop over heterogeneous resource types
  • No abstraction — you cannot write a "function" that creates a standard web service with a load balancer, ECS task, and security group, then reuse it three times
  • No testing — you cannot write unit tests for HCL. You can run terraform plan and squint at the diff
  • No refactoring — rename a resource in HCL and your editor has no idea what other files reference it
🤖
AI Era — LLMs Write Better Pulumi than HCL

LLMs are dramatically better at writing Pulumi TypeScript than Terraform HCL. The reason is simple: TypeScript is in their training data by the gigabyte. HCL is not. When you ask Claude or GPT-4 to generate infrastructure, the TypeScript output is type-checked by your IDE immediately — the HCL output requires a full terraform plan cycle to catch mistakes.

2. Pulumi Concepts

Before writing any code, you need to understand the six core concepts in Pulumi's model. These map cleanly to TypeScript primitives, which is why the mental model clicks so fast.

🎒
Stack
An isolated deployment of your program. One codebase, multiple stacks: dev, staging, prod. Each stack has its own state and config.
🪟
Resource
A cloud primitive — S3 bucket, EC2 instance, RDS database, IAM role. Creating a resource object in TypeScript registers it in the deployment graph.
⏰
Output<T>
Like a Promise — a value that exists after deployment. The bucket ID is not known until AWS creates the bucket. Output<T> wraps that future value.
🔒
Config
Per-stack configuration. Public values in Pulumi.dev.yaml. Secrets are encrypted at rest and never appear in logs.
💾
State
Pulumi tracks every deployed resource in a state file. Stored in Pulumi Cloud (default), S3, or local. This is how Pulumi knows what to update vs. create.
⛈
Provider
The cloud plugin — AWS, GCP, Azure, Cloudflare, Vercel, Kubernetes, GitHub. Each provider generates typed TypeScript bindings from its schema.

The Resource Graph

The most important thing Pulumi does is build a directed acyclic graph (DAG) of your resources. When resource B depends on resource A (for example, an ECS service depends on an ECS cluster), Pulumi knows it must create A before B, and can parallelize everything else. You never write explicit ordering — it falls out of the dependency structure automatically, inferred from which Output<T> values you reference.

Pulumi's resource graph — dependency arrows determine deployment order. Pulumi parallelizes independent branches automatically.
🏗
Architecture Note — The Graph Is Implicit

You never draw this graph manually. It emerges from which Output<T> values you pass to which resources. If you pass vpc.id to a subnet, Pulumi infers "subnet depends on VPC" and orders the deployment accordingly. This is the core insight of Pulumi's design.

3. Getting Started with Pulumi + TypeScript

Installation

Shell 
# Install the Pulumi CLI
brew install pulumi

# Authenticate (uses Pulumi Cloud for free state management)
pulumi login

# Create a new AWS TypeScript project
mkdir my-infra && cd my-infra
pulumi new aws-typescript

# You'll be prompted for:
#   project name, description, stack name (e.g. "dev"), AWS region

Project Structure

my-infra/
  ├── index.ts         # Your infrastructure — this is where you write code
  ├── package.json     # @pulumi/pulumi, @pulumi/aws dependencies
  ├── tsconfig.json    # Strict TypeScript config
  ├── Pulumi.yaml      # Project metadata (name, runtime: nodejs)
  ├── Pulumi.dev.yaml  # Stack config for "dev" (committed)
  └── Pulumi.prod.yaml # Stack config for "prod" (committed, no secrets)

Core CLI Commands

Shell 
# Preview what will change (like terraform plan)
pulumi preview

# Deploy — creates/updates/deletes resources to match your code
pulumi up

# Tear everything down
pulumi destroy

# Manage stacks
pulumi stack ls                    # list stacks
pulumi stack select prod           # switch to prod
pulumi stack output serviceUrl     # read an exported value

# Set config values
pulumi config set region us-west-2
pulumi config set --secret dbPassword hunter2  # encrypted
✅
Tip — Always Run Preview First

Make pulumi preview part of your PR pipeline. It shows exactly what will be created, updated, or deleted — without touching any real infrastructure. Catching a destructive change in CI is infinitely better than noticing it after pulumi up.

4. The Output<T> Type — Pulumi's Core Innovation

Output<T> is the single most important concept in Pulumi. Everything else builds on top of it. Understanding it deeply — where it comes from, how it flows, and why it exists — is the key to writing fluent Pulumi code.

When you create a cloud resource, many of its properties are not known until the cloud provider actually creates it. An S3 bucket's ID, an EC2 instance's IP address, an RDS endpoint — these values exist only after deployment. But you need to reference them in other resources before deployment happens. Output<T> is Pulumi's solution: a typed wrapper around a value that will exist in the future.

TypeScript index.ts 
import * as aws from '@pulumi/aws'
import * as pulumi from '@pulumi/pulumi'

// Create an S3 bucket
// TypeScript knows the full shape of all inputs — no guessing
const bucket = new aws.s3.BucketV2('my-bucket', {
  tags: { Environment: 'production', Team: 'platform' },
})

// bucket.id is Output — the bucket name is not known yet
const bucketId: pulumi.Output = bucket.id

// bucket.tags is Output<{[key: string]: string} | undefined>
const bucketTags: pulumi.Output<{[key: string]: string} | undefined> = bucket.tags

// .apply() transforms an Output — like Promise.then()
// The callback runs only during deployment, with the real value
const bucketUrl: pulumi.Output = bucket.bucket.apply(
  (name: string) => `https://${name}.s3.amazonaws.com`
)

// pulumi.all() combines multiple Outputs — like Promise.all()
const db = new aws.rds.Instance('db', { /* ... */ })

const connectionString: pulumi.Output = pulumi.all([
  db.endpoint,
  db.port,
  db.dbName,
]).apply(([endpoint, port, name]) =>
  `postgresql://${endpoint}:${port}/${name}`
)

// pulumi.interpolate is a tagged template for Output
// Cleaner than .apply() for string construction
const lambdaEnv = {
  DATABASE_URL: pulumi.interpolate`postgresql://${db.endpoint}:${db.port}/${db.dbName}`,
  BUCKET_URL: pulumi.interpolate`https://${bucket.bucket}.s3.amazonaws.com`,
}

// Export outputs — these appear after `pulumi up`
export const url = bucketUrl
export const dbEndpoint = db.endpoint

Output<T> as a Monad

If you have a functional programming background, Output<T> is a monad (specifically a functor with applicative structure). .apply() is map. pulumi.all() is the applicative combinator. The values are "effectful" — they carry the additional context that the value is produced by a deployment, not immediately available.

Output<T> values compose via .apply() and pulumi.all(). The real values flow through only when Pulumi deploys.
⚠
Warning — Never Use Output<T> in Plain JavaScript

You cannot use console.log(bucket.id) and see the bucket name — it will print [object Object]. Output values are not resolved until Pulumi's deployment engine runs them. Always use .apply(), pulumi.interpolate, or pulumi.all() to work with Output values. If you need to conditionally create resources based on a value, pass the Output through to the resource that needs it — never try to extract the raw value.

5. Building Real Infrastructure

Let's put it together. Here is a complete, production-representative Pulumi TypeScript program that deploys a Next.js application to AWS: VPC, ECS Fargate, RDS Postgres, an Application Load Balancer, and all the wiring between them.

Deploying a Next.js App to AWS

TypeScript index.ts 
import * as aws from '@pulumi/aws'
import * as awsx from '@pulumi/awsx'
import * as pulumi from '@pulumi/pulumi'

const config = new pulumi.Config()
const stack = pulumi.getStack()          // "dev" | "staging" | "prod"
const isProd = stack === 'prod'

// ── VPC ────────────────────────────────────────────────────────────────
// awsx (Crosswalk) provides higher-level constructs built on top of aws.*
const vpc = new awsx.ec2.Vpc('app-vpc', {
  numberOfAvailabilityZones: isProd ? 3 : 2,
  natGateways: { strategy: isProd ? 'OnePerAz' : 'Single' },
  tags: { Project: 'myapp', Stack: stack },
})

// ── Security Groups ────────────────────────────────────────────────────
const albSg = new aws.ec2.SecurityGroup('alb-sg', {
  vpcId: vpc.vpcId,
  description: 'Allow HTTP/HTTPS from internet',
  ingress: [
    { protocol: 'tcp', fromPort: 80,  toPort: 80,  cidrBlocks: ['0.0.0.0/0'] },
    { protocol: 'tcp', fromPort: 443, toPort: 443, cidrBlocks: ['0.0.0.0/0'] },
  ],
  egress: [{ protocol: '-1', fromPort: 0, toPort: 0, cidrBlocks: ['0.0.0.0/0'] }],
})

const appSg = new aws.ec2.SecurityGroup('app-sg', {
  vpcId: vpc.vpcId,
  description: 'App containers — allow from ALB only',
  ingress: [{
    protocol: 'tcp', fromPort: 3000, toPort: 3000,
    securityGroups: [albSg.id],        // typed: Output
  }],
  egress: [{ protocol: '-1', fromPort: 0, toPort: 0, cidrBlocks: ['0.0.0.0/0'] }],
})

const dbSg = new aws.ec2.SecurityGroup('db-sg', {
  vpcId: vpc.vpcId,
  description: 'Postgres — allow from app only',
  ingress: [{
    protocol: 'tcp', fromPort: 5432, toPort: 5432,
    securityGroups: [appSg.id],
  }],
})

// ── ECS Cluster ────────────────────────────────────────────────────────
const cluster = new aws.ecs.Cluster('app-cluster', {
  settings: [{ name: 'containerInsights', value: 'enabled' }],
})

// ── RDS Database ───────────────────────────────────────────────────────
const dbSubnetGroup = new aws.rds.SubnetGroup('db-subnets', {
  subnetIds: vpc.privateSubnetIds,     // Output
})

const db = new aws.rds.Instance('app-db', {
  engine:           'postgres',
  engineVersion:    '15.4',
  instanceClass:    isProd ? 'db.t3.medium' : 'db.t3.micro',
  allocatedStorage: isProd ? 100 : 20,
  storageEncrypted: true,              // TypeScript ensures this is boolean
  dbName:           'appdb',
  username:         config.require('dbUsername'),
  password:         config.requireSecret('dbPassword'),  // Output
  vpcSecurityGroupIds: [dbSg.id],
  dbSubnetGroupName:   dbSubnetGroup.name,
  skipFinalSnapshot:   !isProd,
  backupRetentionPeriod: isProd ? 7 : 0,
  multiAz: isProd,
})

// Build the connection string from Output values
const dbUrl: pulumi.Output = pulumi.interpolate`postgresql://${
  config.require('dbUsername')
}:${config.requireSecret('dbPassword')}@${db.endpoint}/${db.dbName}`

// ── ECR Image ──────────────────────────────────────────────────────────
// In a real pipeline, imageUri comes from your CI/CD system
// For this example we read it from config
const imageUri = config.require('imageUri')

// ── ECS Fargate Service (with ALB) ────────────────────────────────────
const service = new awsx.ecs.FargateService('app-service', {
  cluster: cluster.arn,
  desiredCount: isProd ? 3 : 1,
  networkConfiguration: {
    subnets:        vpc.privateSubnetIds,
    securityGroups: [appSg.id],
    assignPublicIp: false,
  },
  taskDefinitionArgs: {
    cpu:    isProd ? '1024' : '256',
    memory: isProd ? '2048' : '512',
    container: {
      name:  'app',
      image: imageUri,
      portMappings: [{ containerPort: 3000, protocol: 'tcp' }],
      environment: [
        { name: 'NODE_ENV',      value: isProd ? 'production' : 'development' },
        { name: 'DATABASE_URL',  value: dbUrl },
        { name: 'STACK',         value: stack },
      ],
      logConfiguration: {
        logDriver: 'awslogs',
        options: {
          'awslogs-group':         pulumi.interpolate`/ecs/myapp-${stack}`,
          'awslogs-region':        aws.config.region ?? 'us-east-1',
          'awslogs-stream-prefix': 'app',
        },
      },
    },
  },
  loadBalancers: [{
    targetGroupArn: targetGroup.arn,
    containerName: 'app',
    containerPort: 3000,
  }],
})

// ── Application Load Balancer ──────────────────────────────────────────
const alb = new aws.lb.LoadBalancer('app-alb', {
  internal:        false,
  loadBalancerType: 'application',
  securityGroups:  [albSg.id],
  subnets:         vpc.publicSubnetIds,
})

const targetGroup = new aws.lb.TargetGroup('app-tg', {
  port:       3000,
  protocol:   'HTTP',
  targetType: 'ip',
  vpcId:      vpc.vpcId,
  healthCheck: { path: '/api/health', interval: 30, healthyThreshold: 2 },
})

new aws.lb.Listener('http-listener', {
  loadBalancerArn: alb.arn,
  port:            80,
  protocol:        'HTTP',
  defaultActions: [{
    type:           'forward',
    targetGroupArn: targetGroup.arn,
  }],
})

// ── Exports ────────────────────────────────────────────────────────────
// These appear after `pulumi up` and can be read by other stacks
export const serviceUrl  = pulumi.interpolate`http://${alb.dnsName}`
export const dbEndpoint  = db.endpoint
export const clusterName = cluster.name
export const vpcId       = vpc.vpcId
💰
Cloud Cost Warning — NAT Gateways Are Expensive

NAT Gateways cost ~$32/month each plus $0.045/GB of data processed. For dev stacks, set natGateways: { strategy: 'Single' }. For prod with 3 AZs, that's $96/month before any traffic. Always use isProd conditionals to right-size dev environments. This is trivial in TypeScript, impossible in YAML.

6. Component Resources — Reusable Infrastructure

The greatest power of Pulumi over Terraform modules or CloudFormation nested stacks is Component Resources: real TypeScript classes that encapsulate a group of cloud resources, expose typed public properties, and can be instantiated like any class. Think of them as React components — but for infrastructure.

💡
Key Insight — Components Are Just Classes

A Pulumi Component Resource is a class extends pulumi.ComponentResource. All child resources pass { parent: this } so Pulumi tracks ownership. Public outputs are typed properties. Callers get full IntelliSense on what the component exposes. This is the abstraction primitive that Terraform modules can only dream about.

The WebService Component

TypeScript components/web-service.ts 
import * as aws from '@pulumi/aws'
import * as awsx from '@pulumi/awsx'
import * as pulumi from '@pulumi/pulumi'

// Strongly typed inputs — TypeScript catches missing required fields
export interface WebServiceArgs {
  /** Docker image URI (e.g. "123456.dkr.ecr.us-east-1.amazonaws.com/myapp:latest") */
  image: string
  /** Container port the app listens on */
  port: number
  /** Environment variables injected into the container */
  environment: Record>
  /** VPC to deploy into */
  vpcId: pulumi.Input
  /** Subnets for the ECS tasks (private) */
  privateSubnetIds: pulumi.Input[]>
  /** Subnets for the ALB (public) */
  publicSubnetIds: pulumi.Input[]>
  /** CPU units — 256 = 0.25 vCPU */
  cpu?: string
  /** Memory in MB */
  memory?: string
  /** Number of running tasks */
  desiredCount?: number
}

export class WebService extends pulumi.ComponentResource {
  /** The ALB DNS name — use this to reach the service */
  public readonly url: pulumi.Output
  /** The ECS service ARN */
  public readonly serviceArn: pulumi.Output
  /** The target group ARN — attach to your own listener if needed */
  public readonly targetGroupArn: pulumi.Output

  constructor(
    name: string,
    args: WebServiceArgs,
    opts?: pulumi.ComponentResourceOptions,
  ) {
    // Register this component with Pulumi's engine
    super('myapp:index:WebService', name, {}, opts)

    // All child resources get { parent: this } so Pulumi tracks ownership
    const childOpts = { parent: this }

    // ALB Security Group
    const albSg = new aws.ec2.SecurityGroup(`${name}-alb-sg`, {
      vpcId: args.vpcId,
      ingress: [
        { protocol: 'tcp', fromPort: 80,  toPort: 80,  cidrBlocks: ['0.0.0.0/0'] },
        { protocol: 'tcp', fromPort: 443, toPort: 443, cidrBlocks: ['0.0.0.0/0'] },
      ],
      egress: [{ protocol: '-1', fromPort: 0, toPort: 0, cidrBlocks: ['0.0.0.0/0'] }],
    }, childOpts)

    // App Security Group
    const appSg = new aws.ec2.SecurityGroup(`${name}-app-sg`, {
      vpcId: args.vpcId,
      ingress: [{
        protocol: 'tcp',
        fromPort: args.port,
        toPort:   args.port,
        securityGroups: [albSg.id],
      }],
      egress: [{ protocol: '-1', fromPort: 0, toPort: 0, cidrBlocks: ['0.0.0.0/0'] }],
    }, childOpts)

    // Application Load Balancer
    const alb = new aws.lb.LoadBalancer(`${name}-alb`, {
      loadBalancerType: 'application',
      securityGroups:   [albSg.id],
      subnets:          args.publicSubnetIds,
    }, childOpts)

    // Target Group
    const targetGroup = new aws.lb.TargetGroup(`${name}-tg`, {
      port:       args.port,
      protocol:   'HTTP',
      targetType: 'ip',
      vpcId:      args.vpcId,
      healthCheck: { path: '/health', interval: 30 },
    }, childOpts)

    // Listener
    new aws.lb.Listener(`${name}-listener`, {
      loadBalancerArn: alb.arn,
      port:            80,
      protocol:        'HTTP',
      defaultActions: [{ type: 'forward', targetGroupArn: targetGroup.arn }],
    }, childOpts)

    // ECS Cluster
    const cluster = new aws.ecs.Cluster(`${name}-cluster`, {}, childOpts)

    // Convert environment map to ECS format
    const envVars = Object.entries(args.environment).map(([name, value]) => ({
      name,
      value: value as pulumi.Input,
    }))

    // Fargate Service
    const service = new awsx.ecs.FargateService(`${name}-svc`, {
      cluster:      cluster.arn,
      desiredCount: args.desiredCount ?? 1,
      networkConfiguration: {
        subnets:        args.privateSubnetIds,
        securityGroups: [appSg.id],
        assignPublicIp: false,
      },
      taskDefinitionArgs: {
        cpu:    args.cpu    ?? '256',
        memory: args.memory ?? '512',
        container: {
          name:         name,
          image:        args.image,
          portMappings: [{ containerPort: args.port, protocol: 'tcp' }],
          environment:  envVars,
        },
      },
      loadBalancers: [{
        targetGroupArn: targetGroup.arn,
        containerName:  name,
        containerPort:  args.port,
      }],
    }, childOpts)

    // Expose public outputs
    this.url            = pulumi.interpolate`http://${alb.dnsName}`
    this.serviceArn     = service.service.arn
    this.targetGroupArn = targetGroup.arn

    // Tell Pulumi what this component outputs
    this.registerOutputs({
      url:            this.url,
      serviceArn:     this.serviceArn,
      targetGroupArn: this.targetGroupArn,
    })
  }
}

Now using this component is as simple as instantiating a class. The component encapsulates ~80 lines of resource configuration behind a clean, typed interface:

TypeScript index.ts 
import { WebService } from './components/web-service'

// Deploy the API service
const api = new WebService('api', {
  image:            'my-api:v1.2.3',
  port:             3000,
  vpcId:            vpc.vpcId,
  privateSubnetIds: vpc.privateSubnetIds,
  publicSubnetIds:  vpc.publicSubnetIds,
  cpu:              '512',
  memory:           '1024',
  desiredCount:     2,
  environment: {
    NODE_ENV:     'production',
    DATABASE_URL: dbUrl,
    LOG_LEVEL:    'info',
  },
})

// Deploy the web frontend — references api.url (Output)
// TypeScript knows api.url is Output — no guessing
const web = new WebService('web', {
  image:            'my-nextjs:v2.0.0',
  port:             3000,
  vpcId:            vpc.vpcId,
  privateSubnetIds: vpc.privateSubnetIds,
  publicSubnetIds:  vpc.publicSubnetIds,
  environment: {
    NODE_ENV: 'production',
    API_URL:  api.url,          // Output flows through cleanly
  },
})

// Export both URLs
export const apiUrl = api.url
export const webUrl = web.url
Component Resources encapsulate child resources. api.url flows as an Output<string> into the web service's environment, establishing a deployment dependency automatically.

7. Configuration and Secrets

Pulumi's config system is per-stack, version-controlled, and has first-class support for secrets. Public config is stored in plain YAML. Secrets are encrypted with a per-stack key before being written to disk — they never appear in logs or state files in plaintext.

TypeScript index.ts — config patterns 
import * as pulumi from '@pulumi/pulumi'

const config = new pulumi.Config()

// ── Basic values ───────────────────────────────────────────────────────
// config.get() returns string | undefined
const region = config.get('region') ?? 'us-east-1'

// config.require() throws if missing — use for mandatory values
const imageUri = config.require('imageUri')

// config.getNumber() / config.requireNumber()
const minInstances = config.getNumber('minInstances') ?? 1

// config.getBoolean() / config.requireBoolean()
const enableXray = config.getBoolean('enableXray') ?? false

// ── Secrets ────────────────────────────────────────────────────────────
// config.requireSecret() returns Output — never a plain string
// The value is decrypted only during deployment, never logged
const dbPassword: pulumi.Output = config.requireSecret('dbPassword')
const apiKey:     pulumi.Output = config.requireSecret('stripeApiKey')

// ── Typed config object ────────────────────────────────────────────────
interface AppConfig {
  region:       string
  instanceType: string
  minInstances: number
  maxInstances: number
  enableXray:   boolean
}

function loadConfig(): AppConfig {
  return {
    region:       config.get('region')                ?? 'us-east-1',
    instanceType: config.get('instanceType')          ?? 't3.micro',
    minInstances: config.getNumber('minInstances')    ?? 1,
    maxInstances: config.getNumber('maxInstances')    ?? 10,
    enableXray:   config.getBoolean('enableXray')     ?? false,
  }
}

const appConfig = loadConfig()
// appConfig is fully typed — TypeScript knows all properties and their types

// ── Object config ──────────────────────────────────────────────────────
// config.getObject() for structured values
interface ScalingPolicy {
  minCount: number
  maxCount: number
  targetCpu: number

8. Testing Pulumi Programs

One of the biggest advantages of Pulumi over Terraform is that your infrastructure is just TypeScript — you can unit test it with Jest, exactly like any other TypeScript code. Pulumi provides a mocking system that intercepts resource creation during tests, so no real cloud resources are created.

TypeScript tests/infra.test.ts 
import * as pulumi from '@pulumi/pulumi'

// Set up mocks BEFORE importing your infrastructure code
// This intercepts all resource creation — no real AWS calls
pulumi.runtime.setMocks({
  newResource: (args: pulumi.runtime.MockResourceArgs) => {
    // Return a fake ID and echo the inputs back as state
    return {
      id:    `${args.name}_id`,
      state: {
        ...args.inputs,
        // Simulate values that AWS would set after creation
        endpoint: args.name.includes('db') ? 'db.cluster.us-east-1.rds.amazonaws.com' : undefined,
        dnsName:  args.name.includes('alb') ? 'myapp-alb-123.us-east-1.elb.amazonaws.com' : undefined,
      },
    }
  },
  call: (args: pulumi.runtime.MockCallArgs) => ({
    result: {},
  }),
})

describe('Infrastructure', () => {
  // Dynamically import after mocks are set
  let infra: typeof import('../index')

  beforeAll(async () => {
    infra = await import('../index')
  })

  // ── S3 / Storage ────────────────────────────────────────────────────
  it('S3 bucket has required tags', async () => {
    const tags = await infra.bucket.tags.promise()
    expect(tags).toMatchObject({
      Environment: 'production',
      Team:        'platform',
    })
  })

  // ── Database security ───────────────────────────────────────────────
  it('RDS database has encryption enabled', async () => {
    const encrypted = await infra.db.storageEncrypted.promise()
    expect(encrypted).toBe(true)
  })

  it('RDS database is not publicly accessible', async () => {
    const publiclyAccessible = await infra.db.publiclyAccessible.promise()
    expect(publiclyAccessible).toBe(false)
  })

  it('RDS has backup retention in prod', async () => {
    // In prod, backupRetentionPeriod should be > 0
    const retention = await infra.db.backupRetentionPeriod.promise()
    expect(retention).toBeGreaterThan(0)
  })

  // ── Network security ────────────────────────────────────────────────
  it('App security group does not allow SSH from internet', async () => {
    const ingress = await infra.appSg.ingress.promise()
    const sshRules = (ingress ?? []).filter(
      r => r.fromPort === 22 && r.cidrBlocks?.includes('0.0.0.0/0')
    )
    expect(sshRules).toHaveLength(0)
  })

  // ── Service configuration ───────────────────────────────────────────
  it('ECS service exports a URL', async () => {
    const url = await infra.serviceUrl.promise()
    expect(url).toMatch(/^http:\/\//)
  })

  it('environment variables contain DATABASE_URL', async () => {
    const env = await infra.taskEnv.promise()
    const names = env.map((e: { name: string }) => e.name)
    expect(names).toContain('DATABASE_URL')
  })
})

// ── Policy tests — enforce organization standards ──────────────────────
describe('Security policy enforcement', () => {
  it('all resources have a Team tag', async () => {
    // In a real suite, you'd enumerate all resource outputs
    // and verify each one has required tags
    const bucketTags = await infra.bucket.tags.promise()
    expect(bucketTags).toHaveProperty('Team')
  })
})

Tip — Use .promise() to Resolve Outputs in Tests

In test code, output.promise() resolves the Output<T> to its underlying value (since the mock provides it synchronously). This is only valid in test mode — never call .promise() in production infrastructure code. Use .apply() and pulumi.interpolate there instead.

9. How Pulumi Uses TypeScript's Type System

Pulumi's TypeScript SDK is arguably the best example in any ecosystem of using TypeScript's type system as an API design tool. Every resource's inputs and outputs are generated from the cloud provider's own schema — meaning the types are always up to date and complete.

Generated Types from Cloud Schemas

When AWS publishes a new resource type, Pulumi re-generates the TypeScript types from the CloudFormation resource provider schema. Every property — its name, type, whether it's required, what values it accepts — is captured in TypeScript. Your IDE knows everything the AWS SDK knows, at author time, not deploy time.

TypeScript Type safety in action 
import * as aws from '@pulumi/aws'

// ── TypeScript CATCHES these bugs before you deploy ────────────────────

// Error: 'instanceclass' does not exist — should be 'instanceClass'
new aws.rds.Instance('db', {
  instanceclass: 'db.t3.micro',  // TS2345 — caught immediately in IDE
})

// Error: Type '"POSTGRES"' is not assignable to type
// '"mysql" | "postgres" | "aurora" | ...'
new aws.rds.Instance('db', {
  engine: 'POSTGRES',            // TS2322 — must be lowercase 'postgres'
})

// Error: Property 'password' is missing — it's required
new aws.rds.Instance('db', {
  engine:   'postgres',
  username: 'admin',
  // password is required — TypeScript error right here
})

// ── Input vs Output ────────────────────────────────────────────
// Pulumi uses Input for resource inputs — accepts both T and Output
// This is how you can pass an Output as input to another resource

type Input = T | pulumi.Output

// This works — TypeScript accepts Output where Input is expected
const sg = new aws.ec2.SecurityGroup('sg', {
  vpcId: vpc.vpcId,  // vpc.vpcId is Output, vpcId wants Input
})

// ── Type narrowing ────────────────────────────────────────────────────
function getInstanceClass(env: 'dev' | 'prod'): aws.rds.InstanceType {
  // TypeScript knows aws.rds.InstanceType is a union of all valid instance class strings
  return env === 'prod' ? 'db.t3.medium' : 'db.t3.micro'
  // Return 'db.t99.huge' and TypeScript errors immediately
}
🏗
Architecture Note — Input<T> is the Dual of Output<T>

pulumi.Input<T> is defined as T | Promise<T> | pulumi.Output<T>. All resource inputs accept Input<T>, which means you can pass a raw value, a Promise, or an Output — and TypeScript validates it all at compile time. This is the glue that makes the resource graph type-safe.

11. Advanced Patterns

Stack References — Sharing Outputs Between Stacks

Large organizations split their infrastructure into multiple Pulumi stacks: a "network" stack creates the VPC, and application stacks reference it. Stack references let stacks consume each other's exported outputs with full type safety.

TypeScript app/index.ts — consuming network stack outputs 
import * as pulumi from '@pulumi/pulumi'

const stack = pulumi.getStack()  // 'dev' | 'prod'

// Reference the network stack for this environment
const networkStack = new pulumi.StackReference(`myorg/network/${stack}`)

// Get typed outputs from the other stack
const vpcId            = networkStack.getOutput('vpcId')            // Output
const privateSubnetIds = networkStack.getOutput('privateSubnetIds') // Output
const publicSubnetIds  = networkStack.getOutput('publicSubnetIds')  // Output

// For stronger typing, cast — the network team should document their outputs
const typedVpcId = vpcId.apply(v => v as string)
const typedPrivateSubnets = privateSubnetIds.apply(v => v as string[])

// Now use these in your resources exactly like local Outputs
const sg = new aws.ec2.SecurityGroup('app-sg', {
  vpcId: typedVpcId,
})

Policy as Code with CrossGuard

Pulumi CrossGuard lets you write infrastructure policies in TypeScript that run before any deployment. If a resource violates policy, pulumi up is blocked — preventing the misconfiguration from reaching production.

TypeScript policy/s3-policy.ts 
import { PolicyPack, validateResourceOfType } from '@pulumi/policy'
import * as aws from '@pulumi/aws'

new PolicyPack('aws-security-policies', {
  policies: [
    {
      name:        'no-public-s3-buckets',
      description: 'S3 buckets must not be publicly accessible',
      enforcementLevel: 'mandatory',  // blocks deployment
      validateResource: validateResourceOfType(
        aws.s3.BucketV2,
        (bucket, args, reportViolation) => {
          // bucket is fully typed — aws.s3.BucketV2
          if (bucket.acl === 'public-read' || bucket.acl === 'public-read-write') {
            reportViolation('S3 bucket must not have a public ACL')
          }
        }
      ),
    },
    {
      name:        'rds-encryption-required',
      description: 'All RDS instances must have storage encryption enabled',
      enforcementLevel: 'mandatory',
      validateResource: validateResourceOfType(
        aws.rds.Instance,
        (db, args, reportViolation) => {
          if (!db.storageEncrypted) {
            reportViolation('RDS instance must have storageEncrypted: true')
          }
          if (db.backupRetentionPeriod === 0) {
            reportViolation('RDS instance must have backups enabled')
          }
        }
      ),
    },
    {
      name:        'require-tags',
      description: 'All resources must have Team and Environment tags',
      enforcementLevel: 'advisory',  // warns but does not block
      validateResource: (args, reportViolation) => {
        const tags = (args.props['tags'] ?? {}) as Record
        if (!tags['Team']) {
          reportViolation('Resource is missing required tag: Team')
        }
        if (!tags['Environment']) {
          reportViolation('Resource is missing required tag: Environment')
        }
      },
    },
  ],
})

The Pulumi Automation API

The Automation API lets you drive Pulumi programmatically from TypeScript — not as a CLI tool, but as a library. This enables building internal deployment platforms, self-service infrastructure portals, and sophisticated CI/CD pipelines without shelling out to the CLI.

TypeScript deploy.ts — programmatic deployments 
import { LocalWorkspace, PulumiFn } from '@pulumi/pulumi/automation'

// Your Pulumi program as a function — not a file
const infraProgram: PulumiFn = async () => {
  const aws = await import('@pulumi/aws')

  const bucket = new aws.s3.BucketV2('auto-bucket', {
    tags: { CreatedBy: 'automation-api' },
  })

  return { bucketName: bucket.bucket }
}

async function deployTenant(tenantId: string): Promise {
  // Create (or select) a stack for this tenant
  const stack = await LocalWorkspace.createOrSelectStack({
    stackName:   tenantId,
    projectName: 'saas-infra',
    program:     infraProgram,
  })

  // Set config for this tenant's stack
  await stack.setConfig('aws:region', { value: 'us-east-1' })

  // Run pulumi up programmatically
  const result = await stack.up({ onOutput: console.log })

  if (result.summary.result !== 'succeeded') {
    throw new Error(`Deployment failed: ${result.summary.message}`)
  }

  // Read the exported output
  return result.outputs['bucketName'].value
}

// Create a per-tenant environment on signup
async function onNewTenantSignup(tenantId: string) {
  console.log(`Provisioning infrastructure for tenant ${tenantId}...`)
  const bucketName = await deployTenant(tenantId)
  console.log(`Tenant ${tenantId} storage: ${bucketName}`)
}

// Tear down when a tenant cancels
async function onTenantCancellation(tenantId: string) {
  const stack = await LocalWorkspace.selectStack({
    stackName:   tenantId,
    projectName: 'saas-infra',
    program:     infraProgram,
  })
  await stack.destroy({ onOutput: console.log })
  await stack.workspace.removeStack(tenantId)
}

12. Key Lessons from Pulumi's Architecture

Pulumi is one of the cleanest examples in any ecosystem of using TypeScript's type system to create a developer tool that is both more powerful and easier to use than its predecessors. Here is what Pulumi's architecture teaches us about TypeScript API design.

1. The Type System as the API

Pulumi generates its entire AWS SDK from a machine-readable schema. The types are not written by hand — they are computed. Every new AWS service or property update automatically produces correct TypeScript types. This is the right way to build typed wrappers around large external systems: generate, don't maintain.

2. Lazy Evaluation via Output<T>

Cloud values do not exist at program-authoring time — they exist after deployment. Output<T> is TypeScript's way of representing this: a value that will be computed later, with full type information about what that value will be. This is the same pattern as Promises in async code. Pulumi's insight was that the same monad that works for async operations works for deployment-time values.

3. The Resource Graph is a Typed DAG

Pulumi's deployment engine builds a dependency graph from the Output<T> references in your code. You never draw the graph manually — it falls out of the type relationships. TypeScript's type system ensures you can only pass an Output<string> where a string is expected (Input<string> accepts both). The correctness of the graph is enforced by types.

4. Component Resources as the Abstraction Primitive

Extending pulumi.ComponentResource is the right primitive for reuse: it groups child resources, gives them a parent for Pulumi's state tracking, and exposes a clean typed interface to callers. This is the equivalent of writing a well-typed React component — hide the implementation, expose a contract.

5. Testing Infrastructure is Not Optional

The ability to unit test infrastructure — to verify that your RDS instance has encryption enabled, that your security group does not expose SSH to the internet, that all resources have required tags — before anything is deployed is transformative. Teams that test their infrastructure find bugs in code review that Terraform teams find in production incidents.
