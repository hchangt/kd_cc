Section 01Node.js, Bun & the Runtime Landscape

Before you write a single line of TypeScript, you need a JavaScript runtime — the engine that actually executes your code. Unlike Python, which ships one canonical interpreter, the JavaScript/TypeScript world has several credible runtimes in 2024. Let's understand each one and pick the right one for your project.

Node.js — The Original and Still Dominant

Node.js has been the server-side JavaScript runtime since 2009. Built on V8 (Chrome's JS engine), it powers the vast majority of production TypeScript deployments today. When you read a library's documentation and it says "requires Node 18+", this is what they mean.

Node.js uses an LTS (Long-Term Support) release cycle. Even-numbered versions (18, 20, 22) are LTS — they receive security patches for ~30 months. Odd-numbered versions are short-lived current releases. Always use an LTS version for production work.

⚠️ Important: Node.js does NOT run TypeScript natively

Node.js executes JavaScript. You must compile your .ts files to .js first — or use a tool like ts-node, tsx, or switch to Bun/Deno which handle this for you. We'll cover all paths in Section 3.

Bun — The New Speed King

Bun (released stable in September 2023) is a brand-new runtime built from scratch in Zig, using JavaScriptCore (Safari's engine) instead of V8. Its headline claims are compelling: up to 3× faster package installs, runs TypeScript natively without a build step, and is often faster at I/O-bound tasks. Bun is also a bundler, test runner, and package manager all in one.

For new projects where you're not locked into the Node.js ecosystem, Bun is increasingly worth a serious look. I use it for all my personal TypeScript projects.

Deno — The Thoughtful Alternative

Deno (created by Node's original author, Ryan Dahl) runs TypeScript natively and has excellent built-in security (permissions model) and web-standard APIs. Deno 2.0 added npm compatibility. It's excellent but has a smaller ecosystem than Node. Worth knowing, but Node or Bun will serve most readers better.

Installing Node.js with nvm (The Right Way)

The worst way to install Node.js is to download the installer from the website. The right way is nvm (Node Version Manager), which lets you switch between Node versions per-project — just like pyenv for Python.

  1. 1

    Install nvm

    bash
    $ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
# Then restart your shell, or source your profile:
$ source ~/.zshrc   # or ~/.bashrc
  2. 2

    Install the latest LTS Node.js

    bash
    $ nvm install --lts
Now using node v22.x.x (npm v10.x.x)
$ nvm use --lts
$ nvm alias default 'lts/*'   # make it the default
  3. 3

    Verify the installation

    bash
    $ node -v
v22.11.0
$ npm -v
10.8.2
  4. 4

    Pin a version per project with .nvmrc

    bash
    $ echo "22" > .nvmrc
$ nvm use   # reads .nvmrc automatically

    Add nvm use auto-switching to your shell profile for a seamless experience — the nvm README has instructions.

Section 02Package Managers

The JavaScript ecosystem has more package managers than Python does — and they genuinely differ in meaningful ways. Understanding the tradeoffs will save you confusion when you encounter yarn.lock files in one project and pnpm-lock.yaml in another.

Package Manager Speed Disk Usage Lockfile Workspace Support Best For
npm built-in Baseline High (copies) package-lock.json Basic Simple projects, learning
pnpm recommended ~2× faster Low (hard-links, content-addressable store) pnpm-lock.yaml Excellent Monorepos, production teams
yarn classic/berry ~1.5× faster Medium yarn.lock Good Legacy codebases
bun all-in-one ~5× faster Low bun.lockb (binary) Good New projects using Bun runtime
ℹ️ Why pnpm's disk efficiency matters

npm copies packages into every project's node_modules. If you have 20 projects all using React 18, npm stores 20 copies. pnpm stores one copy in a global content-addressable store and hard-links it into each project. On a typical developer machine, this saves gigabytes.

Anatomy of package.json

package.json is the central manifest for your TypeScript project — equivalent to a combination of Python's setup.py, pyproject.toml, and requirements.txt.

JSON
{
  "name": "my-typescript-app",         // Package name (kebab-case convention)
  "version": "1.0.0",                  // Semantic versioning: major.minor.patch
  "description": "A TypeScript app",
  "main": "dist/index.js",             // Entry point after compilation
  "types": "dist/index.d.ts",          // TypeScript declarations for consumers
  "scripts": {
    "build":     "tsc",                // Compile TypeScript → JavaScript
    "dev":       "tsx watch src/index.ts", // Run in watch mode (re-run on changes)
    "start":     "node dist/index.js", // Run compiled output
    "test":      "vitest",             // Run tests
    "lint":      "eslint src/",        // Check for code issues
    "typecheck": "tsc --noEmit"        // Type-check without emitting files
  },
  "dependencies": {
    // Runtime dependencies — shipped with your app
    "express": "^4.18.2",
    "zod": "^3.22.4"
  },
  "devDependencies": {
    // Build/dev tools — NOT shipped with your app
    "typescript": "^5.5.0",
    "@types/express": "^4.17.21",
    "tsx": "^4.9.0",
    "vitest": "^2.0.0",
    "eslint": "^9.0.0"
  },
  "engines": {
    "node": ">=20"                     // Declare minimum Node.js version
  }
}
🐍 Python Comparison: dependencies vs devDependencies

In Python, there's one requirements.txt (or you have requirements-dev.txt by convention). Node.js formalizes this split: dependencies = what your app needs at runtime (like flask), devDependencies = what you need only during development (like pytest, mypy).

When you deploy to production, run npm install --omit=dev to skip devDependencies.

Lockfiles: Why They Matter

A lockfile pins the exact version of every package (including transitive dependencies) installed. This ensures every developer on your team and every CI build uses identical packages.

  • Always commit your lockfile to version control
  • Never commit node_modules/ — add it to .gitignore
  • Only use one package manager per project — mixing npm and pnpm breaks things

Section 03Installing TypeScript

Local vs Global Installation

You can install TypeScript globally (available everywhere on your machine) or locally (pinned to a project). Always prefer local installation — it ensures everyone working on the project uses the same TypeScript version and avoids "works on my machine" issues.

Local (Recommended)

# pnpm
$ pnpm add -D typescript

bash
# Only for quick experiments
$ npm install -g typescript

# Then tsc is available directly
$ tsc --version

Running TypeScript Without Compiling

Compiling TypeScript to JavaScript and then running the JavaScript is the production approach, but during development you want a faster feedback loop. Here are the main options:

ToolInstallRunHow it worksRecommended?
ts-node npm i -D ts-node npx ts-node file.ts JIT-compiles TS via the TypeScript compiler. Slower startup. Legacy
tsx npm i -D tsx npx tsx file.ts Uses esbuild (Go-based). Very fast. Supports watch mode. Yes (Node projects)
bun run (just install Bun) bun run file.ts Native TS support in the runtime. Fastest. Yes (Bun projects)
deno run (just install Deno) deno run file.ts Native TS support. Permissions required for I/O. For Deno projects

Installing tsx (My Recommended Dev Runner for Node)

bash
$ npm install -D tsx

# Run a file once
$ npx tsx src/index.ts

# Watch mode — re-runs on every file change (like nodemon but for TS)
$ npx tsx watch src/index.ts

Add this to your package.json scripts:

JSON
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc",
    "start": "node dist/index.js"
  }
}
ℹ️ tsx strips types, it doesn't check them

Tools like tsx and Bun strip TypeScript type annotations (transpile) without running the type checker. This makes them fast, but you won't get type errors at run time. Always run tsc --noEmit (or your CI pipeline should) to catch type errors separately.

🤖 AI Era Note: GitHub Copilot + TypeScript = Supercharged

TypeScript's type system gives AI code assistants dramatically better context. When Copilot can see your types, it writes more accurate completions. A well-typed codebase is also far easier for AI agents to navigate and refactor safely. This is one of the underappreciated reasons TypeScript has surged in the AI era — your types are machine-readable documentation.

Section 04tsconfig.json — Your First Configuration

tsconfig.json is the TypeScript compiler's configuration file. It lives at the root of your project and controls everything about how TypeScript compiles your code — what JavaScript version to target, how strict the type-checking should be, where to put compiled output, and more.

Creating Your tsconfig

bash
$ npx tsc --init
Created a new tsconfig.json with:
  target: es2016
  module: commonjs
  strict: true
  ...

This generates a file with every option commented out. It's great for exploration, but for real projects I prefer a lean, intentional config. Let's break down the options that actually matter.

Essential Options Explained

OptionValues / DefaultWhat it doesRecommendation
target ES2020, ES2022, ESNext Which JavaScript version to compile down to. Affects which syntax is kept vs polyfilled. ES2022 for Node 18+; ES2020 for broader browser support
module CommonJS, ESM, NodeNext How modules are imported/exported. Node traditionally used CommonJS (require()), modern Node and browsers use ESM (import). NodeNext for Node 20+; ESNext for bundler-based projects
strict true / false Enables a family of strict checks (noImplicitAny, strictNullChecks, etc.) Always true — see callout below
outDir Any path, e.g. "./dist" Where compiled .js files are written "./dist"
rootDir Any path, e.g. "./src" Where your TypeScript source files live "./src"
lib Array: ["ES2022", "DOM"] Which built-in APIs are available. DOM adds browser types like document. Omit DOM for Node; include it for browser/React code
paths Object mapping aliases Enables path aliases like @/components instead of ../../components Great for large projects. Requires bundler or tsconfig-paths at runtime.
moduleResolution NodeNext, Bundler How TypeScript resolves module paths NodeNext for Node; Bundler for Vite/webpack projects
declaration true / false Emit .d.ts type declaration files alongside compiled JS true if publishing a library
sourceMap true / false Emit source maps so debuggers show original TS lines true during development
noEmit true / false Run type-checking without writing any output files true when a bundler handles compilation
⚠️ Always set strict: true

"strict": true enables several checks that catch real bugs:

  • strictNullChecks: forces you to handle null and undefined explicitly — the #1 source of runtime crashes
  • noImplicitAny: prevents unintentionally untyped variables
  • strictFunctionTypes: catches subtle callback type mismatches

The only reason to turn this off is migrating an existing JavaScript codebase to TypeScript incrementally. For any new TypeScript project, strict: true is non-negotiable.

Recommended Config: Node.js Backend

tsconfig.json
{
  "compilerOptions": {
    // ── Compilation target ─────────────────────────
    "target": "ES2022",            // Node 18+ supports all ES2022 features natively
    "lib": ["ES2022"],             // No DOM — this is a backend project

    // ── Module system ──────────────────────────────
    "module": "NodeNext",          // Use ESM with Node.js module resolution
    "moduleResolution": "NodeNext",

    // ── File locations ─────────────────────────────
    "rootDir": "./src",            // Source TypeScript files live here
    "outDir": "./dist",            // Compiled JavaScript output goes here

    // ── Type checking ──────────────────────────────
    "strict": true,                // Enable ALL strict checks — always
    "noUncheckedIndexedAccess": true, // array[i] might be undefined — TypeScript should know
    "noImplicitOverride": true,    // Must use 'override' keyword when overriding class methods

    // ── Output settings ────────────────────────────
    "declaration": true,           // Emit .d.ts files (useful if publishing as a package)
    "declarationMap": true,        // Source maps for .d.ts files
    "sourceMap": true,             // Source maps for debugging

    // ── Code quality ───────────────────────────────
    "forceConsistentCasingInFileNames": true, // Prevents case-sensitivity bugs
    "esModuleInterop": true,       // Allows default imports from CommonJS modules
    "resolveJsonModule": true,     // Allows import of .json files
    "skipLibCheck": true           // Skip type-checking .d.ts files (faster builds)
  },
  "include": ["src/**/*"],         // Only compile files in src/
  "exclude": ["node_modules", "dist", "**/*.test.ts"] // Ignore these
}

Recommended Config: React / Frontend (Vite)

tsconfig.json
{
  "compilerOptions": {
    // ── Compilation target ─────────────────────────
    "target": "ES2020",            // Good browser support
    "lib": ["ES2020", "DOM", "DOM.Iterable"], // DOM APIs for browser code

    // ── Module system ──────────────────────────────
    "module": "ESNext",            // Vite/bundlers handle modules
    "moduleResolution": "Bundler", // Let Vite resolve modules
    "noEmit": true,                // Vite compiles — tsc just type-checks

    // ── React/JSX ─────────────────────────────────
    "jsx": "react-jsx",            // React 17+ transform (no import React needed)

    // ── Type checking ──────────────────────────────
    "strict": true,
    "noUnusedLocals": true,        // Error on unused variables
    "noUnusedParameters": true,    // Error on unused function parameters
    "noFallthroughCasesInSwitch": true,

    // ── Path aliases ───────────────────────────────
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]           // '@/components/Button' → 'src/components/Button'
    },

    // ── Quality ────────────────────────────────────
    "forceConsistentCasingInFileNames": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "skipLibCheck": true
  },
  "include": ["src"],
  "references": [{ "path": "./tsconfig.node.json" }] // Vite config file uses this
}

Section 05VS Code Setup — The #1 Editor for TypeScript

VS Code and TypeScript were both created at Microsoft, and that's not a coincidence — they share the same TypeScript language server. The IntelliSense you get in VS Code is powered by the same engine that runs the compiler. This means error highlighting, autocomplete, and refactoring tools that are best-in-class.

You can use TypeScript in any editor (WebStorm, Neovim, Zed) but for this tutorial series, VS Code is the reference editor. Download it here.

Section 06Your First TypeScript Program

Let's write and run actual TypeScript. We'll do it three different ways to understand the compilation pipeline.

hello.ts

TypeScript
// hello.ts

// TypeScript adds type annotations to JavaScript
const greet = (name: string): string => {
  return `Hello, ${name}! Welcome to TypeScript.`
}

// This is perfectly valid — TypeScript infers the type as string[]
const languages = ['Python', 'TypeScript', 'Rust']

// TypeScript knows 'lang' is a string because of the array's type
for (const lang of languages) {
  console.log(greet(lang))
}

// Try this — TypeScript catches it at compile time, not at runtime:
// greet(42)  // ❌ Error: Argument of type 'number' is not assignable to parameter of type 'string'

Three Ways to Run It

Option A — Bun (fastest, no setup)

bash
$ bun run hello.ts
Hello, Python! Welcome to TypeScript.
Hello, TypeScript! Welcome to TypeScript.
Hello, Rust! Welcome to TypeScript.

Option B — tsx (Node.js, no compile step)

bash
$ npx tsx hello.ts
Hello, Python! Welcome to TypeScript.
Hello, TypeScript! Welcome to TypeScript.
Hello, Rust! Welcome to TypeScript.

Option C — Compile then run (the full pipeline)

bash
# Step 1: Compile TypeScript → JavaScript
$ npx tsc hello.ts
# Creates hello.js in the same directory

# Step 2: Run the compiled JavaScript
$ node hello.js
Hello, Python! Welcome to TypeScript.
Hello, TypeScript! Welcome to TypeScript.
Hello, Rust! Welcome to TypeScript.

Let's see what hello.js looks like after compilation:

JavaScript (compiled output)
// hello.js — generated by tsc
"use strict";
// Notice: the ': string' type annotations are GONE
// TypeScript types are erased at compile time — they're only for development
const greet = (name) => {
    return `Hello, ${name}! Welcome to TypeScript.`;
};
const languages = ['Python', 'TypeScript', 'Rust'];
for (const lang of languages) {
    console.log(greet(lang));
}
🐍 Python Comparison: Type Erasure

Python type hints (via mypy) work similarly — they're checked at development time but ignored at runtime unless you explicitly use get_type_hints(). TypeScript is the same: types exist only in .ts source files. The compiled .js is plain JavaScript with zero type information.

Section 08Python → TypeScript Mental Model: Environment Comparison

You already know Python's tooling. The good news: TypeScript's ecosystem solves the same problems — just with different names and some different tradeoffs. Here's the mapping that will save you hours of confusion.

🐍 The Biggest Mental Shift: No Virtual Environment Activation

In Python, you activate a virtual environment (source .venv/bin/activate) and your shell prompt changes. Node.js doesn't work this way. When you run node, npm, or any npm script, Node automatically resolves dependencies from the nearest node_modules directory by walking up the directory tree.

The equivalent of "activating" a Node environment is just being in the project directory. That's it. When you run npm run dev, Node finds node_modules/ in your project automatically.

🐍 mypy vs tsc — A Critical Difference

In Python, type hints are optional additions to an existing dynamic language. mypy is a separate third-party tool that checks them. You can always ignore mypy warnings and the code runs fine.

TypeScript is a different language that compiles to JavaScript. The type checker is the compiler — if tsc reports errors, it refuses to compile (unless you force it). Types are not optional decorators in TypeScript; they are load-bearing parts of the language. This is a more powerful approach that catches more bugs, but it requires the mindset shift that type errors are real errors.

Side-by-Side: Setting Up a New Project

Python

bash (Python)
$ mkdir myproject && cd myproject
$ python3 -m venv .venv
$ source .venv/bin/activate
$ pip install flask mypy black
$ pip freeze > requirements.txt
$ python main.py

TypeScript (Node)

bash (TypeScript)
$ mkdir myproject && cd myproject
$ npm init -y
# no activation step needed
$ npm i express
$ npm i -D typescript tsx @types/express
# package.json tracks everything
$ npx tsx src/main.ts
🤖 AI Era Note: Why Python Developers Are Learning TypeScript Now

The AI tooling ecosystem — LangChain, Vercel AI SDK, OpenAI's official client, Anthropic's SDK — ships TypeScript as a first-class citizen alongside Python. Many AI-powered web apps (chatbots, copilots, agents) are built with TypeScript frontends calling Python ML backends. Understanding both languages makes you dramatically more effective in this landscape.

Additionally, frameworks like Mastra and LangChain.js are TypeScript-native, offering some capabilities before the Python versions even ship them. The TypeScript ecosystem is no longer second-class in AI development.
