& Structural Typing

BC
Boris Cherny
Staff Engineer @ Meta · Author, Programming TypeScript
· ~75 min read · Intermediate

TypeScript's object system is one of the most elegant designs in any mainstream language. At its core sits structural typing — a decision that shapes everything from API design to library interoperability. In this chapter you will master interfaces, classes, enums, and discriminated unions, and understand why TypeScript's shape-based philosophy produces code that is both expressive and robust at scale.

1. Structural Typing Deep Dive

The Fundamental Rule

TypeScript cares about the shape of a value — the names and types of its properties and methods — not about its declared type name. If two types have the same shape, they are compatible, full stop.

In most typed languages you have two philosophies:

  • Nominal typing (Java, C#, Python's type hints): compatibility is determined by the name of the type or an explicit declaration of relationship.
  • Structural typing (TypeScript, Go interfaces, OCaml): compatibility is determined by the structure — the actual members — of the type.

TypeScript chose structural typing deliberately. JavaScript is a dynamically typed language where duck typing is universal. TypeScript's type system had to model that reality without breaking existing JS code.

The Duck Test

If it looks like a duck, swims like a duck, and quacks like a duck — TypeScript calls it a duck. You do not have to declare it a duck anywhere.

TypeScript Structural compatibility in action 
interface Duck {
  name: string;
  quack(): void;
}

// This object was never declared to be a Duck.
// TypeScript doesn't care. It has the right shape.
const donald = {
  name: "Donald",
  quack() { console.log("Quack!"); },
  walksLikeDuck: true,          // extra property — fine in a variable
};

function makeItQuack(duck: Duck) {
  console.log(duck.name, "says:");
  duck.quack();
}

makeItQuack(donald); // OK — donald has at least all of Duck's shape
🐍
Python Comparison

Python's type hints use nominal typing through the type checker (mypy, pyright). If you declare def f(x: Animal): ... and pass a Dog that isn't declared to extend Animal, mypy will reject it even if Dog has all the right methods. TypeScript would accept it based on shape alone.

Python does have duck typing at runtime (no explicit interface declaration needed), but the static type checker adds nominal constraints on top. TypeScript's static type checker reflects the runtime duck-typing directly.

Structural typing: TypeScript checks shape (properties + methods), not declared type names. The donald object is assignable to Duck because it has at least the required shape.

Excess Property Checking: The One Exception

Here is the subtlety that trips up almost every TypeScript newcomer. When you pass an object literal directly to a typed location, TypeScript applies excess property checking — it errors on extra properties. But when you go through an intermediate variable, that strictness disappears.

TypeScript Excess property checking 
interface Point { x: number; y: number; }

// DIRECT LITERAL — excess property check fires
const p1: Point = { x: 1, y: 2, z: 3 }; // Error: 'z' does not exist in type 'Point'

// THROUGH VARIABLE — no excess property check
const temp = { x: 1, y: 2, z: 3 };
const p2: Point = temp;                   // OK — structural compatibility

// FUNCTION ARGUMENT (literal) — excess property check fires
function drawPoint(p: Point) {}
drawPoint({ x: 1, y: 2, z: 3 });         // Error

// FUNCTION ARGUMENT (variable) — OK
const myPoint = { x: 1, y: 2, z: 3 };
drawPoint(myPoint);                        // OK
ℹ
Why does excess property checking exist?

Passing extra properties in an object literal to a typed location almost always indicates a typo or a misunderstanding. { x: 1, y: 2, colour: "red" } passed where Point is expected almost certainly means the developer intended a different type. TypeScript catches this while still allowing the general structural flexibility that makes JavaScript interoperability work.

Practical Implications

Structural typing has profound consequences for how you design APIs:

  • Library interoperability: Two libraries that define their own Logger interface can be used interchangeably as long as their shapes match — no adapter needed.
  • Testing: You can pass minimal mock objects to functions without implementing every method of a heavy interface.
  • Composition: Types compose naturally. If a function needs a shape, any superset of that shape works.
  • Refactoring safety: Renaming or adding properties is safe — TypeScript will catch all callsites that no longer satisfy the required shape.
✦
AI Era Relevance

When you integrate AI APIs (OpenAI, Anthropic, Bedrock) into TypeScript applications, structural typing lets you define your own ChatModel interface that any provider can satisfy — without vendor lock-in at the type level. You can swap providers by making sure the new client matches your interface's shape.

2. Interfaces

An interface is TypeScript's primary way to name a shape. Think of it as a contract: any value that satisfies this shape is considered to implement the interface — no explicit declaration required.

TypeScript Basic interface 
interface User {
  id: string;
  name: string;
  age: number;
}

const alice: User = { id: "u1", name: "Alice", age: 30 }; // OK

Optional Properties

Mark a property with ? to make it optional. Its type becomes T | undefined.

TypeScript 
interface User {
  id: string;
  name: string;
  age?: number;       // number | undefined
  bio?: string;
}

const alice: User = { id: "u1", name: "Alice" };          // OK — age and bio omitted
const bob: User = { id: "u2", name: "Bob", age: 25 };    // OK

Readonly Properties

The readonly modifier prevents reassignment after the object is created. It's a compile-time check, not a runtime freeze.

TypeScript 
interface Config {
  readonly apiKey: string;
  readonly baseUrl: string;
  timeout: number;          // mutable
}

const config: Config = {
  apiKey: "sk-abc",
  baseUrl: "https://api.example.com",
  timeout: 5000,
};

config.timeout = 10000;    // OK — mutable
config.apiKey = "sk-xyz";  // Error: Cannot assign to 'apiKey' because it is a read-only property

Method Signatures

Two syntaxes for methods in interfaces behave slightly differently:

TypeScript Method syntax vs property syntax 
interface Animal {
  // Method syntax: can be overridden in subtypes more freely
  // (bivariant parameter checking applies — more permissive)
  speak(text: string): void;

  // Property syntax: function type — stricter (contravariant params)
  // Preferred in most modern TS code with strictFunctionTypes
  eat: (food: string) => boolean;
}

class Dog implements Animal {
  speak(text: string) { console.log(`Woof! ${text}`); }
  eat(food: string) { console.log(`Eating ${food}`); return true; }
}
✓
Recommendation

With strictFunctionTypes: true (included in strict), prefer the property syntax (eat: (food: string) => boolean) for callbacks and event handlers to get stricter variance checking. Use method syntax for methods you expect subclasses to override.

Index Signatures

Index signatures let you describe objects used as dictionaries with dynamic keys.

TypeScript 
interface StringMap {
  [key: string]: string;
}

const env: StringMap = {
  NODE_ENV: "production",
  PORT: "3000",
  // any string key is fine, but value must be string
};

// You can mix index signatures with known properties
// but known property types must be assignable to the index signature type
interface FlexConfig {
  version: string;            // string — compatible with index signature
  [key: string]: unknown;     // catch-all for other keys
}

const cfg: FlexConfig = {
  version: "1.0",
  debugMode: true,            // unknown — fine
  retries: 3,                 // unknown — fine
};

Extending Interfaces

Interfaces can extend one or more other interfaces. The result inherits all members from the parent(s) and adds its own.

TypeScript Single and multiple extension 
interface Entity {
  id: string;
  createdAt: Date;
}

interface User extends Entity {
  name: string;
  email: string;
}

interface Auditable {
  auditLog: string[];
  lastModifiedBy: string;
}

interface Admin extends User, Auditable {
  role: "admin" | "superadmin";
  permissions: string[];
}

// Admin now has: id, createdAt, name, email, auditLog, lastModifiedBy, role, permissions
const admin: Admin = {
  id: "a1",
  createdAt: new Date(),
  name: "Carol",
  email: "carol@example.com",
  auditLog: [],
  lastModifiedBy: "system",
  role: "admin",
  permissions: ["read", "write"],
};

Declaration Merging

This is one of TypeScript's most distinctive features. If you declare an interface with the same name twice, TypeScript merges the declarations into one. This is the mechanism that allows third-party library type declarations to be extended.

TypeScript Declaration merging — interface augmentation 
// In some library's type definition (lib.d.ts)
interface Window {
  requestAnimationFrame(callback: FrameRequestCallback): number;
}

// In your application code — you ADD to the interface
interface Window {
  myAnalyticsId: string;      // merged into Window
}

// Now window.myAnalyticsId is typed!
window.myAnalyticsId = "UA-12345";

// A common real-world pattern: Express Request augmentation
// In @types/express you get:
// declare global {
//   namespace Express {
//     interface Request {}
//   }
// }
// In your middleware type declarations:
declare global {
  namespace Express {
    interface Request {
      user?: AuthenticatedUser;  // now req.user is typed everywhere
    }
  }
}
⚠
Declaration Merging Caveats

Declaration merging only works with interface, not type. If you need to augment a third-party type or a global, you must use interface. Type aliases that conflict with an existing name produce a compile error instead of merging.

3. Type Aliases for Objects

A type alias gives a name to any type expression — not just object shapes. For objects, type and interface look almost identical, but they differ in capability and intent.

TypeScript Basic type alias for an object 
type User = {
  id: string;
  name: string;
  age: number;
};

const alice: User = { id: "u1", name: "Alice", age: 30 };

Intersection Types for Composition

With type, you compose using & (intersection). Intersections combine all properties of both types into one.

TypeScript Intersection composition 
type Entity = {
  id: string;
  createdAt: Date;
};

type Auditable = {
  auditLog: string[];
  lastModifiedBy: string;
};

// Intersection — Admin has ALL properties of Entity AND Auditable AND its own
type Admin = Entity & Auditable & {
  name: string;
  role: "admin" | "superadmin";
};

// Useful for layering concerns without re-declaring everything
type ApiResponse = {
  data: T;
  status: number;
  message: string;
} & { timestamp: string; requestId: string };
⚠
Conflicting intersections produce never

If two intersected types have the same property key with incompatible types, you get never: type Bad = { x: string } & { x: number } — x becomes string & number which is never. Nothing can satisfy that type. This is usually a design error.

Interface vs Type: The Definitive Comparison

Feature interface type Notes
Object shapes Yes Yes Both work equally well for plain object types
Declaration merging Yes No Critical for augmenting library types
Extends syntax extends & intersection extends is clearer for hierarchies
Union types No Yes type Foo = A | B — only type can do this
Computed / mapped types No Yes type Keys = keyof User, Partial<T>, etc.
Tuple types No Yes type Pair = [string, number]
Primitive aliases No Yes type ID = string
Class can implement Yes Yes class Foo implements Bar works with both
Error messages Better Sometimes verbose Interface names appear in errors; type aliases sometimes get expanded
Performance (large codebases) Slightly faster Can be slower Interfaces are cached by identity; complex type aliases expand on every use
Rule of Thumb

Use interface when you are defining the shape of an object that represents a domain entity, a class contract, or a public API surface — especially if consumers might need to extend it.

Use type for unions, computed/utility types, tuples, function signatures, or any type that isn't purely an object shape. When in doubt and either works, prefer interface for objects.

4. Classes in TypeScript

TypeScript classes are JavaScript ES2022 classes with a typed overlay. They compile down to plain JavaScript. Everything you know from Python classes applies — but the syntax and type system integration differ significantly.

Python vs TypeScript: Class Syntax Side by Side

Python Python class 
from dataclasses import dataclass

@dataclass
class User:
    name: str
    age: int
    _id: str = ""

    def greet(self) -> str:
        return f"Hi, I'm {self.name}"

    @classmethod
    def create(cls, name: str) -> "User":
        return cls(name=name, age=0)
TypeScript TypeScript class 
class User {
  name: string;
  age: number;
  private id: string;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
    this.id = crypto.randomUUID();
  }

  greet(): string {
    return `Hi, I'm ${this.name}`;
  }

  static create(name: string): User {
    return new User(name, 0);
  }
}

Access Modifiers

Modifier Accessible from Python equivalent Compiled JS
public Anywhere (default) No prefix (name) Regular property
private Only this class _name (convention only) Regular property (TS-only enforcement)
#name (JS private) Only this class __name True runtime private (#name)
protected This class + subclasses _name (convention) Regular property
readonly Anywhere (read-only) @property (getter only) Regular property
TypeScript Access modifiers in practice 
class BankAccount {
  public readonly id: string;
  public owner: string;
  private balance: number;
  protected interestRate: number;

  constructor(owner: string, initialBalance: number) {
    this.id = crypto.randomUUID();
    this.owner = owner;
    this.balance = initialBalance;
    this.interestRate = 0.03;
  }

  // Public method — accessible anywhere
  getBalance(): number {
    return this.balance;
  }

  // Protected — accessible in subclasses
  protected applyInterest(): void {
    this.balance *= (1 + this.interestRate);
  }

  // Private method — only within this class
  private audit(amount: number, op: "credit" | "debit"): void {
    console.log(`[AUDIT] ${op} ${amount} — balance: ${this.balance}`);
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    this.balance += amount;
    this.audit(amount, "credit");
  }
}

const account = new BankAccount("Alice", 1000);
console.log(account.getBalance()); // 1000
account.deposit(500);
// account.balance        // Error: 'balance' is private
// account.interestRate   // Error: 'interestRate' is protected
// account.id = "new"     // Error: 'id' is readonly

Constructor Shorthand

TypeScript's most popular class ergonomic: declare and assign properties directly in the constructor parameter list. This eliminates the repetitive this.x = x boilerplate.

Before — verbose
TypeScript
class Point {
  public x: number;
  public y: number;
  private label: string;

  constructor(
    x: number,
    y: number,
    label: string,
  ) {
    this.x = x;
    this.y = y;
    this.label = label;
  }
}
After — shorthand
TypeScript
class Point {
  constructor(
    public x: number,
    public y: number,
    private label: string,
  ) {
    // Nothing needed — TS does it automatically
  }
}

// Both produce identical behavior.
// Shorthand is idiomatic TypeScript.

Static Members

TypeScript 
class IdFactory {
  private static counter = 0;
  static readonly prefix = "ID";

  static generate(): string {
    return `${IdFactory.prefix}-${++IdFactory.counter}`;
  }
}

console.log(IdFactory.generate()); // "ID-1"
console.log(IdFactory.generate()); // "ID-2"

Abstract Classes

Abstract classes define a template. They can have concrete methods (with implementations) and abstract methods (which subclasses must implement). You cannot instantiate an abstract class directly.

TypeScript Abstract class — template pattern 
abstract class DataProcessor {
  // Concrete method — shared behavior
  async process(data: T): Promise {
    const validated = this.validate(data);  // hook
    const result = await this.transform(validated);
    return this.postProcess(result);
  }

  // Subclasses must implement these
  protected abstract validate(data: T): T;
  protected abstract transform(data: T): Promise;

  // Optional hook with default no-op
  protected postProcess(result: R): R {
    return result;
  }
}

class JsonProcessor extends DataProcessor {
  protected validate(data: string): string {
    if (!data.trim()) throw new Error("Empty input");
    return data;
  }

  protected async transform(data: string): Promise
