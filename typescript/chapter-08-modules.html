Chapter 8

Modules, Package Management & Monorepos

By Orta Therox, TypeScript Team @ Microsoft

JavaScript's module story is a slow-motion train wreck that eventually became one of the great success stories of the web platform. To work effectively with TypeScript — especially in 2024 and beyond — you need to understand why that history exists, how TypeScript maps onto it, and how modern teams structure large codebases using monorepos and careful package boundaries. This chapter covers all of it, from the ancient days of global scripts to shipping a dual CJS+ESM TypeScript package to npm.

1. JavaScript Module History

The Chaos: From Nothing to Everything

For most of JavaScript's early life, there were no modules. Scripts were concatenated by hand, loaded via multiple <script> tags, and shared state through global variables. The window object was the universal module registry, and name collisions were a fact of life.

As applications grew, the community improvised. Several competing standards emerged in the late 2000s and early 2010s:

Historical Note — The Module Format Wars
  • AMD (Asynchronous Module Definition) — RequireJS popularized this around 2010. Designed for browsers, it supported async loading. Verbose and largely abandoned today.
  • CommonJS (CJS) — Node.js adopted this in 2009. Synchronous require() calls, module.exports assignments. Still dominant in the Node.js ecosystem in 2024.
  • UMD (Universal Module Definition) — An unholy union of AMD and CJS with an IIFE wrapper. Intended to work everywhere, readable by no one.
  • SystemJS / ES Module Shims — Polyfill layers that appeared as ES Modules were being standardized.

ES Modules: The Standard That Won

ES Modules (ESM) were standardized in ES2015 (ES6). They introduced static import and export syntax that compilers and bundlers could analyze at build time. Browsers shipped native ESM support starting around 2017–2018. Node.js finalized stable ESM support in v12 (2020).

The trouble: Node's entire ecosystem was built on CommonJS. Hundreds of thousands of packages used require() and module.exports. ESM and CJS are not natively interoperable — CJS can require ESM (with caveats), but ESM cannot statically import CJS in all situations. This created the "great schism" that the Node.js community is still navigating.

Warning — The CJS/ESM Interop Problem

An ESM file (.mjs or .js with "type":"module" in package.json) cannot synchronously require() a CJS module — but it can import one. A CJS file cannot require() an ESM-only package at all. It must use dynamic import().

This asymmetry is why many popular packages still ship dual CJS+ESM builds. Tools like Vite, esbuild, and tsup make producing dual builds easy, but the underlying tension won't fully resolve until the CJS-only ecosystem finishes migrating.

AI Era Note

Modern AI coding assistants are well-trained on ESM patterns. However, they frequently generate incorrect interop code when mixing CJS and ESM — for example, defaulting to require() inside an ESM project. Always check the "type" field in your package.json and the module setting in your tsconfig before accepting AI-generated import statements.

2. ES Modules in TypeScript

Import and Export Syntax

TypeScript uses ES Module syntax natively. The compiler then transpiles it to whatever output format you configure.

Named exports (preferred)
// math.ts — named exports
export function add(a: number, b: number): number {
  return a + b;
}

export function subtract(a: number, b: number): number {
  return a - b;
}

export const PI = 3.14159265;

// Named imports at the call site
import { add, PI } from './math';
import { add as sum } from './math'; // rename during import
Default exports (use sparingly)
// logger.ts — default export
export default class Logger {
  log(msg: string): void {
    console.log(`[LOG] ${msg}`);
  }
}

// Default import — name is chosen by the importer
import Logger from './logger';
import MyLogger from './logger'; // also valid, same thing
Tip — Named vs Default Exports

The TypeScript and JavaScript communities have largely converged on preferring named exports. They are refactoring-friendly (rename tools work correctly), support better tree-shaking, and avoid the "what do I call this?" problem at import sites. Default exports are still fine for framework components (React components, Next.js pages) where the convention is established. For utility libraries, prefer named exports.

Re-exports and Barrel Files

Re-exporting from an index file
// src/utils/index.ts — re-export everything
export { formatDate, parseDate } from './date';
export { slugify, truncate } from './string';
export type { DateOptions } from './date'; // type-only re-export

// Wildcard re-export (use cautiously — defeats tree-shaking)
export * from './validators';

Namespace Imports

import * as — namespace import
import * as utils from './utils';

utils.formatDate(new Date());
utils.slugify('Hello World');
Warning — Namespace Imports and Tree-Shaking

Namespace imports (import * as X) prevent most bundlers from tree-shaking effectively because the bundler must assume any export might be used. Prefer named imports when bundle size matters. Namespace imports are useful for grouping related utilities when you use many of them, or when writing scripts that won't be bundled.

Dynamic Imports

Dynamic imports load a module at runtime, returning a Promise. They are essential for code-splitting — deferring heavy modules until they are needed.

Dynamic import with await
async function processMarkdown(input: string): Promise {
  // 'marked' is only loaded when this function is called
  const { marked } = await import('marked');
  return marked(input);
}

// Conditional dynamic import
async function loadChartLibrary(type: 'bar' | 'line') {
  if (type === 'bar') {
    const { BarChart } = await import('./charts/bar');
    return new BarChart();
  } else {
    const { LineChart } = await import('./charts/line');
    return new LineChart();
  }
}

// With error handling
let heavy: typeof import('./heavy-module') | null = null;
async function getHeavy() {
  heavy ??= await import('./heavy-module');
  return heavy;
}

import type and export type

Type-only imports and exports are one of TypeScript's most important features for correctness and performance. They are erased entirely at compile time — they never appear in the JavaScript output.

import type — type-only import
// These are erased at compile time — zero runtime cost
import type { User } from './models/user';
import type { RequestHandler } from 'express';

// Inline type modifier on named imports
import { createUser, type UserCreateOptions } from './user-service';

// When to use:
// - Importing interfaces and type aliases (always use import type)
// - Importing classes used only as type annotations, not as values
// - Any import that would cause circular dependency at runtime

function getUser(id: string): Promise {
  return fetch(`/api/users/${id}`).then(r => r.json());
}
Tip — verbatimModuleSyntax

TypeScript 5.0 introduced "verbatimModuleSyntax": true in tsconfig. When enabled, TypeScript requires you to use import type for any import that is type-only, and will error if you forget. This is the recommended setting for modern TypeScript projects — it prevents accidentally importing modules that have side effects when you only need the types.

Info — Why This Matters for Tree-Shaking

Many bundlers (Webpack, Rollup, esbuild) rely on module imports to determine what code to include. A regular import { Foo } from './foo' tells the bundler that foo.ts may have side effects and should be evaluated. An import type { Foo } from './foo' is eliminated before the bundler even sees it — no unnecessary module evaluation, smaller bundles.

Module Resolution Strategies

TypeScript resolves module specifiers according to a configurable algorithm. The important thing to understand: import './foo' means "find foo.ts, foo.tsx, foo/index.ts..." according to the active strategy. ESM-strict environments (Node ESM, Deno) require explicit file extensions in imports.

Extension requirements in Node ESM
// With moduleResolution: "NodeNext" or "bundler"
// TypeScript requires .js extensions in imports, even for .ts files
// (because the emitted JS will have .js extensions)

import { add } from './math.js'; // ✅ correct — TypeScript resolves this to math.ts
import { add } from './math';    // ❌ error with NodeNext — missing extension
import { add } from './math.ts'; // ❌ error — cannot use .ts extension

3. TypeScript Module Configuration

The module Setting

The module compiler option controls what module format TypeScript emits. This is separate from what syntax you write.

module value Output format When to use
CommonJS CJS require() Node.js apps, older toolchains, compatibility
ESNext ESM import/export Modern bundlers (Vite, Webpack 5, Rollup)
Node16 CJS or ESM depending on package.json "type" Node.js 16+ apps with mixed CJS/ESM
NodeNext Same as Node16 but tracks latest Node behavior Node.js apps targeting current/next LTS
Preserve Keeps input syntax unchanged TypeScript 5.4+; when a bundler handles transforms

The moduleResolution Setting

Module resolution is separate from module output format. It controls how TypeScript finds modules when type-checking.

moduleResolution Behavior Use with
node (legacy) Classic Node.js CJS algorithm — no exports field support Old projects only; avoid for new work
node16 Supports exports field, requires .js extensions in imports module: "Node16"
nodenext Latest Node algorithm, tracks spec changes module: "NodeNext"
bundler Supports exports field, allows extension-less imports, relaxed Vite, esbuild, Webpack — most common for apps
Tip — Default Recommendation

For most frontend apps built with Vite or similar bundlers: use module: "ESNext" and moduleResolution: "bundler". For Node.js services or CLI tools: use module: "NodeNext" and moduleResolution: "nodenext". Avoid the legacy node resolution unless maintaining old code.

tsconfig.json — recommended app config
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

Path Aliases

Path aliases let you write import { Button } from '@/components/Button' instead of import { Button } from '../../../components/Button'. They are configured in tsconfig and require matching configuration in your bundler.

tsconfig.json — path aliases
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"],
      "@components/*": ["./src/components/*"],
      "@lib/*": ["./src/lib/*"],
      "@types/*": ["./src/types/*"]
    }
  }
}
vite.config.ts — matching alias config
import { defineConfig } from 'vite';
import { resolve } from 'path';

export default defineConfig({
  resolve: {
    alias: {
      '@': resolve(__dirname, 'src'),
      '@components': resolve(__dirname, 'src/components'),
      '@lib': resolve(__dirname, 'src/lib'),
    }
  }
});
Warning — Paths Are TypeScript-Only

TypeScript's paths configuration is purely for type-checking. It does not affect the emitted JavaScript. You must configure the same aliases in your bundler (Vite, Webpack, esbuild) or use a tool like tsc-alias if you're running tsc directly without a bundler.

The exports Field in package.json

The exports field is the modern replacement for main. It gives packages full control over what is accessible and how, supporting conditional exports for different environments.

package.json — exports field
{
  "name": "@myapp/utils",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./string": {
      "types": "./dist/string.d.ts",
      "import": "./dist/string.js",
      "require": "./dist/string.cjs"
    }
  },
  "files": ["dist"]
}

4. Declaring Types for Third-Party Libraries

@types/ Packages and DefinitelyTyped

Not every npm package ships TypeScript type definitions. For those that don't, the DefinitelyTyped project maintains community-written type declarations published as @types/ scoped packages.

Installing type definitions
# @types packages are always devDependencies
npm install -D @types/node
npm install -D @types/lodash
npm install -D @types/express

# Check if a package has built-in types
# (look for "types" or "typings" field in its package.json)
npm info react types       # → undefined (before @types/react)
npm info zod types         # → ./dist/types/index.d.ts (built-in!)
Scenario Types location Action
Package ships .d.ts files Inside the package itself Nothing — types are automatic
Community types exist DefinitelyTyped npm install -D @types/package-name
No types anywhere You write them Create a .d.ts file or use declare module
Types are wrong/incomplete Anywhere Module augmentation (see below)

Writing Your Own Declaration Files

src/types/some-untyped-library.d.ts
// Quick stub for an untyped package
declare module 'some-untyped-library' {
  export function process(input: string): string;
  export function transform(data: unknown): Record;

  interface Options {
    verbose?: boolean;
    timeout?: number;
  }

  export function configure(options: Options): void;
}
Declaring a module for non-JS imports (e.g., CSS, SVG)
// src/types/assets.d.ts
declare module '*.svg' {
  const src: string;
  export default src;
}

declare module '*.css' {
  const styles: Record;
  export default styles;
}

declare module '*.png' {
  const src: string;
  export default src;
}

Module Augmentation

Module augmentation lets you extend existing types from third-party libraries — without forking them. This is the correct way to add custom properties to Express's Request type, extend the global Window interface, or add methods to a library's classes.

Augmenting Express Request with a custom user property
// src/types/express.d.ts
import 'express';

declare module 'express' {
  interface Request {
    // TypeScript now knows req.user exists
    user?: {
      id: string;
      email: string;
      roles: string[];
    };
    correlationId: string;
  }
}

// Usage in route handlers — fully typed
app.get('/profile', (req, res) => {
  if (!req.user) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  res.json({ email: req.user.email }); // ✅ typed
});
Augmenting Window for custom global properties
// src/types/global.d.ts
declare global {
  interface Window {
    analytics: {
      track(event: string, properties?: Record): void;
    };
    __APP_VERSION__: string;
  }
}

// This file must have at least one import or export
// to be a module (otherwise it's a script, not a module)
export {};
Info — Ambient Declarations

Ambient declarations use the declare keyword to tell TypeScript about something that exists at runtime but wasn't declared in TypeScript. declare const __DEV__: boolean tells TypeScript that a __DEV__ global exists (injected by your bundler). declare module '...' tells TypeScript about an entire module's API. These declarations have no runtime presence — they are purely for the type checker.

5. npm Package Ecosystem

Finding and Evaluating Packages

The npm registry hosts over 2 million packages. Three tools help you make informed choices:

  • npmjs.com — package search, README, version history, download stats
  • bundlephobia.com — install/bundle size, tree-shaking support, composition analysis
  • packagephobia.com — install size (including dependencies), useful for CLI tools

When evaluating a package for a TypeScript project, check:

  • Does it ship types? (look for "types" in package.json or check npmjs.com for the "DT" badge)
  • Is it actively maintained? (last publish date, open issues)
  • What is the bundle size? (use bundlephobia)
  • Are there known security vulnerabilities? (npm audit)

package.json Anatomy Deep Dive

package.json — complete field reference
{
  "name": "@myapp/utils",
  "version": "1.2.3",
  "description": "Shared utilities for myapp",

  // Entry points — legacy fields (still needed for old tools)
  "main": "./dist/index.cjs",        // CJS entry
  "module": "./dist/index.js",       // ESM entry (non-standard but widely supported)

  // Modern entry points — takes precedence over main/module in Node 12+
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",  // TypeScript types — must come FIRST
      "import": "./dist/index.js",   // ESM
      "require": "./dist/index.cjs"  // CJS
    }
  },

  // Types location (for older tools that don't read "exports")
  "types": "./dist/index.d.ts",

  // Tree-shaking hint — tells bundlers this package has no side effects
  // Set false only if ALL files are side-effect-free
  // Can be an array of files that DO have side effects
  "sideEffects": false,

  // Node.js version constraint
  "engines": {
    "node": ">=18.0.0"
  },

  // What gets included when published (keep it small)
  "files": ["dist", "README.md"],

  // Packages the consumer must install
  "peerDependencies": {
    "react": "^18.0.0"
  },
  "peerDependenciesMeta": {
    "react": { "optional": true }  // mark as optional
  },

  "dependencies": {},
  "devDependencies": {
    "typescript": "^5.4.0",
    "tsup": "^8.0.0"
  }
}
Warning — types Must Be First in exports

When listing conditions in the exports field, "types" must come before "import" and "require". TypeScript reads conditions in order and stops at the first match. If "import" comes before "types", TypeScript in older configurations may not find the type declarations.

Semantic Versioning and TypeScript: A Warning

Standard semver says patch releases (1.0.0 → 1.0.1) are backwards-compatible bug fixes. For JavaScript packages, this works. For TypeScript packages, it's not that simple.

A patch release that fixes a type error in the library's own types may expose previously hidden type errors in your code that were relying on incorrect types. A minor TypeScript compiler upgrade in the package's build can change inference in subtle ways. This is why:

  • Libraries often mark type improvements as minor or even patch
  • You should check changelogs before updating any package with TypeScript types
  • Lock files (package-lock.json, pnpm-lock.yaml) are essential for reproducible builds
Info — Lock Files Comparison
  • package-lock.json — npm's lock file. Committed to source control. Ensures everyone installs identical versions.
  • pnpm-lock.yaml — pnpm's lock file. Human-readable YAML. More detailed dependency graph.
  • bun.lockb — Bun's binary lock file. Fastest install, but binary format means no readable diffs.
  • yarn.lock — Yarn's lock file. Both Yarn 1 (Classic) and Yarn Berry use this format.

Commit your lock file. Always. The only exception is for libraries published to npm — they typically .gitignore the lock file so consumers get flexible version resolution.

6. Monorepos

A monorepo (monolithic repository) is a single git repository that contains multiple related packages or applications. Instead of having separate repos for your frontend, backend, shared UI library, and utilities — they all live together.

Why Use a Monorepo?

  • Atomic commits — change a shared utility and the apps that use it in a single commit
  • Single version of truth — no more "which version of @myapp/utils does this service use?"
  • Refactoring across boundaries — rename a function and update all call sites in one IDE operation
  • Shared tooling — one ESLint config, one TypeScript base config, one CI pipeline
  • Easier dependency management — internal packages are always at HEAD, not versioned

Monorepo Tools in 2024

Tool Role Notable feature
npm workspaces Package linking Built into npm 7+, minimal config
pnpm workspaces Package linking Fastest installs, strict by default, disk-efficient
Yarn workspaces Package linking Established; Yarn Berry adds PnP mode
Turborepo Build orchestration Incremental builds, remote caching, pipeline definition
Nx Full monorepo platform Code generation, affected-graph commands, plugins
Lerna Package publishing Versioning and publishing automation; often combined with Nx

pnpm Workspaces Setup

pnpm-workspace.yaml
packages:
  - 'packages/*'   # shared libraries: @myapp/ui, @myapp/utils
  - 'apps/*'       # applications: web, mobile, api

A typical monorepo structure looks like this:

my-monorepo/ ├── package.json # root package.json (private: true) ├── pnpm-workspace.yaml # workspace definition ├── turbo.json # Turborepo pipeline config ├── tsconfig.base.json # shared TypeScript config ├── apps/ │ ├── web/ # Next.js frontend │ │ ├── package.json │ │ └── tsconfig.json # extends ../../tsconfig.base.json │ └── api/ # Node.js backend │ ├── package.json │ └── tsconfig.json └── packages/ ├── ui/ # @myapp/ui — shared React components │ ├── package.json │ ├── tsconfig.json │ └── src/ └── utils/ # @myapp/utils — shared utilities ├── package.json ├── tsconfig.json └── src/

Internal Package References

With workspaces, internal packages reference each other like npm packages, but pnpm symlinks them to the local source:

apps/web/package.json — referencing internal packages
{
  "name": "web",
  "private": true,
  "dependencies": {
    "@myapp/ui": "workspace:*",
    "@myapp/utils": "workspace:*"
  }
}
Usage in the web app
import { Button, Card } from '@myapp/ui';
import { formatDate, slugify } from '@myapp/utils';

// These resolve to packages/ui/src and packages/utils/src
// fully typed, live code — no publish step needed during development

TypeScript Project References

Project references ("references" in tsconfig) tell TypeScript about inter-project dependencies. This enables:

  • Incremental builds — only rebuild what changed
  • Correct build ordering — TypeScript knows to build utils before web
  • Single tsc -b command builds the entire repo in the right order
apps/web/tsconfig.json — with project references
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "references": [
    { "path": "../../packages/ui" },
    { "path": "../../packages/utils" }
  ]
}
Root tsconfig.json — solution file
{
  "files": [],
  "references": [
    { "path": "packages/utils" },
    { "path": "packages/ui" },
    { "path": "apps/api" },
    { "path": "apps/web" }
  ]
}
Build the entire monorepo
# Build all projects in dependency order
tsc -b

# Or with Turborepo (parallelized, cached)
turbo run build

Build Orchestration with Turborepo

turbo.json — pipeline configuration
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],   // build dependencies first (^)
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "lint": {
      "outputs": []
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
Tip — Remote Caching

Turborepo's killer feature is remote caching. Once CI builds a package, the result is cached in the cloud. Subsequent CI runs for unrelated changes skip the build entirely and restore from cache. On large monorepos this can cut CI times from 20 minutes to under 2 minutes. Set it up with npx turbo login and npx turbo link.

7. Publishing TypeScript Packages

Compiled JS or TypeScript Source?

Always publish compiled JavaScript with declaration files (.d.ts). Reasons:

  • Consumers may use different TypeScript versions — shipping source requires them to compile with your settings
  • Faster installs — no compilation step for consumers
  • Works with JavaScript consumers who don't use TypeScript
  • You can ship optimized, minified output

The exception: monorepo-internal packages. For packages that are never published to npm, you can often skip the build step and have consumers import TypeScript directly (if your build tool supports it).

tsup — The Go-To Build Tool

tsup is purpose-built for publishing TypeScript packages. It wraps esbuild for speed and handles the dual CJS+ESM output that most consumers need.

Install tsup
npm install -D tsup
tsup.config.ts — dual CJS+ESM output
import { defineConfig } from 'tsup';

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['cjs', 'esm'],       // output both formats
  dts: true,                    // generate .d.ts files
  sourcemap: true,              // source maps for debugging
  clean: true,                  // clean dist/ before build
  splitting: false,             // disable code splitting for libraries
  treeshake: true,              // remove unused code

  // Multiple entry points (for selective imports)
  entry: {
    index: 'src/index.ts',
    string: 'src/string.ts',
    date: 'src/date.ts',
  },
});
Output structure after tsup build
dist/
├── index.js        # ESM output
├── index.cjs       # CJS output
├── index.d.ts      # Type declarations
├── index.d.ts.map  # Declaration source maps
├── index.js.map    # JS source maps
├── string.js
├── string.cjs
├── string.d.ts
├── date.js
├── date.cjs
└── date.d.ts

Info — Declaration Maps

Setting "declarationMap": true generates .d.ts.map files alongside your declaration files. These map from the .d.ts back to the original .ts source. When consumers "Go to Definition" in their IDE on something from your package, they land in the original TypeScript source rather than the generated declaration file. This is an excellent developer experience improvement that costs almost nothing.

Publishing to npm

Publishing workflow

# Check the package contents
npm pack --dry-run

# Publish with public access (required for scoped packages)
npm publish --access public

# Publish a beta version

npm publish --tag beta                # consumers: npm install pkg@beta

8. Python pip → npm Mental Model

If you're coming from Python, the Node.js ecosystem has clear parallels — but also important differences. The most significant: Node.js has no global "virtual environment." Each project installs its dependencies locally into node_modules.

Python Comparison — Dependency Management

Python's pip installs packages globally by default unless you activate a virtual environment. This mismatch between developers led to the venv workflow. Node.js avoided this problem from the start: npm install always installs into the local project's node_modules.

Python Comparison — Development vs Production Dependencies

Python's requirements.txt is typically a single flat file. Some projects split into requirements.txt and requirements-dev.txt. npm formalizes this split in package.json: dependencies are runtime requirements; devDependencies are only needed during development (TypeScript itself, test frameworks, linters, build tools). When you npm install --production, devDependencies are skipped — crucial for keeping Docker images small.

Python Comparison — The node_modules Folder

If you're used to Python virtual environments living in a .venv folder, node_modules will feel familiar — except it can be shockingly large. A fresh Next.js project might have 300+ MB in node_modules from transitive dependencies. This is a known pain point; tools like pnpm address it by using a global content-addressed store with symlinks, meaning packages are only stored once on disk regardless of how many projects use them.

AI Era Note — Package Research

Modern LLMs know the npm ecosystem well, but their training data has a cutoff. When asking an AI assistant to recommend packages, always verify the recommendation is still maintained and hasn't been deprecated or superseded. The JavaScript ecosystem moves fast — packages that were best-in-class 18 months ago may have been replaced by faster, lighter alternatives. Use bundlephobia and npmjs.com to verify current health.
