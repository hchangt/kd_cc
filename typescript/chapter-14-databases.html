1. Database Landscape for TypeScript

Every non-trivial TypeScript application needs persistent storage. In 2024 the options have multiplied — serverless-native NewSQL, edge-compatible SQLite derivatives, and an entirely new category of vector databases for AI workloads. Choosing the wrong database at the architecture phase is expensive to undo. Let's map the terrain.

ⓘ
PostgreSQL First

Unless you have a concrete reason not to, start with PostgreSQL. It covers relational, JSON, full-text search, time-series (via TimescaleDB), and now vector similarity (via pgvector) in a single engine. That's four database categories for the price of one operational burden.

SQL Databases

PostgreSQL is the default choice for new TypeScript projects. Battle-tested, open-source, feature-rich. Every managed cloud (AWS RDS/Aurora, GCP Cloud SQL, Azure Database, Neon, Supabase) supports it. MySQL remains dominant in legacy stacks and is the wire protocol behind PlanetScale. SQLite is gaining a second life in edge/embedded runtimes (Cloudflare D1, Turso, Bun's built-in).

NoSQL

MongoDB provides a document model with a strong TypeScript SDK. Reach for it when your schema is genuinely document-shaped and varies heavily between records. Redis is not a primary database — it's a caching and pub/sub layer (covered in Section 6). DynamoDB is AWS-native, scales infinitely at the cost of query flexibility; use it only when you have DynamoDB-shaped access patterns.

NewSQL & Edge Databases

PlanetScale offers MySQL-compatible serverless scaling with a developer-friendly branching workflow. Neon brings serverless PostgreSQL with branching — a perfect fit for preview environments. Turso distributes SQLite to the edge (powered by libSQL), delivering sub-millisecond reads near every user.

Vector Databases

The AI era demands storing and querying high-dimensional embeddings. pgvector extends PostgreSQL with vector types and similarity operators — the pragmatic choice if you're already on Postgres. Pinecone is a purpose-built fully managed vector store with a first-class TypeScript SDK. Weaviate offers hybrid search (vector + BM25) as open-source.

✨
AI Era: Vector Databases Are Now Mainstream

Every RAG (Retrieval-Augmented Generation) pipeline needs a vector store. In 2023 this was exotic infrastructure. By 2025 it's table stakes. pgvector handles the majority of use cases without adding another service. Section 7 covers the full picture.

2. ORM vs Query Builder vs Raw SQL

The data-access layer is where architectural decisions compound. A full ORM feels like magic until a complex query makes you fight it. Raw SQL gives full control but loses type safety. Query builders sit in the middle. Here's how to think about the trade-offs.

What is an ORM?

An Object-Relational Mapper converts between database rows and in-memory objects (or TypeScript types). A good ORM also handles migrations, relations, and transactions. The cost: an abstraction layer that can generate inefficient queries, hide the database's actual capabilities, and introduce surprising behavior under load.

Your Options

Tool Type Type Safety Bundle Size Edge-compatible Best When
Prisma ORM Excellent Large Partial Rapid development, teams, migrations first
TypeORM ORM Good Large No Decorator-heavy, NestJS projects
Sequelize ORM Fair Large No Legacy Node.js codebases
Drizzle Query Builder Excellent Tiny Yes Edge, performance-critical, SQL control
Kysely Query Builder Excellent Small Yes Pure SQL ergonomics with type safety
Knex Query Builder Fair Small Partial Legacy projects, multi-DB portability
postgres.js Raw SQL + tagged templates Manual Tiny No Maximum performance, full SQL control
pg Raw SQL driver None Tiny No Lowest-level, maximum control
⚠
The "ORM is Fine Until it Isn't" Rule

ORMs are excellent for 80% of database access: simple CRUD, standard relations, paginated lists. They break down for: complex aggregations, window functions, recursive CTEs, bulk operations, and query plans that require specific index hints. The pragmatic answer: use an ORM for application-layer queries, drop to raw SQL for analytics and bulk jobs.

3. Prisma — The Developer's ORM

Prisma is the most developer-friendly ORM in the TypeScript ecosystem. Its schema-first approach, auto-generated type-safe client, and excellent migrations tooling make it the default choice for teams that want to move fast without sacrificing type safety.

Installation

$ pnpm add prisma @prisma/client
$ pnpm prisma init

prisma init creates a prisma/schema.prisma file and adds DATABASE_URL to .env.

Transactions

TypeScript src/db/transactions.ts 
// Sequential transaction — if any step throws, all are rolled back
const [newUser, newPost] = await prisma.$transaction([
  prisma.user.create({ data: { email: 'carol@example.com', name: 'Carol' } }),
  prisma.post.create({ data: { title: 'First Post', authorId: '...' } }),
])

// Interactive transaction — for complex logic between steps
const result = await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({
    data: { email: 'dave@example.com', name: 'Dave' },
  })

  const post = await tx.post.create({
    data: { title: 'My First Post', authorId: user.id, published: true },
  })

  // Update an aggregate counter atomically
  await tx.user.update({
    where: { id: user.id },
    data: { updatedAt: new Date() },
  })

  return { user, post }
})

Migrations

$ pnpm prisma migrate dev --name add-user-model

Prisma compares your schema to the current database state, generates a SQL migration file in prisma/migrations/, applies it, and re-generates the client. In production use prisma migrate deploy — never migrate dev.

💡
Tip: Single Prisma Client Instance

Never create new PrismaClient() in each file. In development Next.js hot-reloads modules and creates connection leaks. The pattern:

  • Create a singleton in src/lib/prisma.ts
  • Export a single prisma instance
  • Use global as a container in dev to survive hot-reloads
TypeScript src/lib/prisma.ts 
import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient }

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    log: process.env.NODE_ENV === 'development' ? ['query', 'error'] : ['error'],
  })

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma
}

4. Prisma Advanced Features

Raw SQL Queries

When you need SQL that Prisma cannot express, drop down to $queryRaw or $executeRaw. Tagged template literals are safe against SQL injection.

TypeScript 
// Type-safe raw query
const result = await prisma.$queryRaw>`
  SELECT u.id, COUNT(p.id) AS count
  FROM "User" u
  LEFT JOIN "Post" p ON p."authorId" = u.id
  WHERE u."createdAt" > ${new Date('2024-01-01')}
  GROUP BY u.id
  ORDER BY count DESC
  LIMIT 10
`

// Execute DDL or statements with no return
await prisma.$executeRaw`
  CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_posts_author
  ON "Post" ("authorId")
`

Middleware (Query Extensions)

TypeScript src/lib/prisma.ts 
// Prisma v5+: use $extends instead of $use
export const prisma = new PrismaClient().$extends({
  query: {
    $allModels: {
      async findMany({ model, operation, args, query }) {
        const start = performance.now()
        const result = await query(args)
        const duration = performance.now() - start
        if (duration > 100) {
          console.warn(`Slow query [${model}.${operation}]: ${duration.toFixed(1)}ms`)
        }
        return result
      },
    },
  },
})

Connection Pooling

Prisma uses a single connection pool per PrismaClient instance. For serverless functions where each invocation may spawn a new instance, use Prisma Accelerate (managed connection pooler) or PgBouncer in transaction mode.

🟢
Database Tip: Serverless Connection Limits

PostgreSQL has a hard limit on concurrent connections (typically 100 for small instances). A serverless function that creates 1000 parallel invocations will exhaust the pool. Solutions: Prisma Accelerate, PgBouncer, or Neon's HTTP driver which multiplexes over HTTP.

5. Drizzle ORM — The Lightweight Alternative

Drizzle is a TypeScript-first query builder that feels like writing SQL — because you essentially are. It has no query plan surprises, works in edge runtimes (Cloudflare Workers, Bun), and ships in a tiny bundle. It's grown explosively because it gives you SQL semantics with full type safety.

Why Drizzle Over Prisma?

  • Edge-compatible — runs in Cloudflare Workers, Bun, and Deno without workarounds
  • SQL-like API — no magic, the query you write is the query that runs
  • Tiny footprint — ~30KB vs Prisma's several hundred KB
  • Schema as TypeScript — no separate DSL file, just code
  • Faster for reads — no object mapper overhead

Installation

$ pnpm add drizzle-orm pg
$ pnpm add -D drizzle-kit @types/pg

  pgTable, serial, text, varchar, boolean,
  timestamp, integer, primaryKey,
} from 'drizzle-orm/pg-core'
import { relations } from 'drizzle-orm'

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  name: text('name'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

export const posts = pgTable('posts', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  content: text('content'),
  published: boolean('published').default(false).notNull(),
  authorId: integer('author_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

export const postsTags = pgTable(
  'posts_tags',
  {
    postId: integer('post_id').notNull().references(() => posts.id),
    tagId: integer('tag_id').notNull().references(() => tags.id),
  },
  (t) => ({ pk: primaryKey({ columns: [t.postId, t.tagId] }) })
)

export const tags = pgTable('tags', {
  id: serial('id').primaryKey(),
  name: varchar('name', { length: 100 }).notNull().unique(),
})

// Relations
export const usersRelations = relations(users, ({ many }) => ({
  posts: many(posts),
}))

export const postsRelations = relations(posts, ({ one, many }) => ({
  author: one(users, { fields: [posts.authorId], references: [users.id] }),
  tags: many(postsTags),
}))

// Inferred types — zero boilerplate
export type User    = typeof users.$inferSelect
export type NewUser = typeof users.$inferInsert
export type Post    = typeof posts.$inferSelect
export type NewPost = typeof posts.$inferInsert

Caching Pattern

Cache-Aside Flow
TypeScript src/services/userCache.ts 
import { redis } from '../lib/redis'
import { prisma } from '../lib/prisma'
import type { User } from '@prisma/client'

const TTL_SECONDS = 3600

async function getCachedUser(id: string): Promise {
  const key = `user:${id}`

  // 1. Try cache first
  const cached = await redis.get(key)
  if (cached) return JSON.parse(cached) as User

  // 2. Cache miss — fetch from DB
  const user = await prisma.user.findUnique({ where: { id } })
  if (!user) return null

  // 3. Store in cache with TTL
  await redis.setex(key, TTL_SECONDS, JSON.stringify(user))
  return user
}

async function invalidateUser(id: string): Promise {
  await redis.del(`user:${id}`)
}

// Cache aside with typed helper
async function withCache(
  key: string,
  ttl: number,
  fetcher: () => Promise
): Promise {
  const cached = await redis.get(key)
  if (cached) return JSON.parse(cached) as T
  const value = await fetcher()
  await redis.setex(key, ttl, JSON.stringify(value))
  return value
}

Rate Limiting with Redis

TypeScript src/middleware/rateLimit.ts 
async function isRateLimited(
  identifier: string,
  limit: number = 100,
  windowSeconds: number = 60
): Promise<{ limited: boolean; remaining: number; resetAt: number }> {
  const key = `rate:${identifier}`
  const now = Date.now()

  const pipeline = redis.pipeline()
  pipeline.incr(key)
  pipeline.ttl(key)
  const [[, count], [, ttl]] = await pipeline.exec() as [[null, number], [null, number]]

  // Set expiry on first request
  if (count === 1) await redis.expire(key, windowSeconds)

  const remaining = Math.max(0, limit - count)
  const resetAt = ttl > 0 ? now + ttl * 1000 : now + windowSeconds * 1000

  return { limited: count > limit, remaining, resetAt }
}

7. Vector Databases for AI Applications

Vector databases store high-dimensional numerical representations (embeddings) of text, images, and other data. They enable semantic search — finding results by meaning rather than exact keyword match. This is the foundational infrastructure for RAG systems, semantic search APIs, and recommendation engines.

✨
AI Era: Embeddings Are the New Index

Traditional databases use B-tree indexes for exact lookups. Vector databases use HNSW (Hierarchical Navigable Small World) graphs for approximate nearest-neighbor search. When you embed a query with the same model used to embed your documents, you can find semantically similar content in milliseconds across millions of records.

pgvector — Vectors Inside PostgreSQL

Install the extension and you have vector similarity search inside your existing Postgres instance. No additional service to operate.

SQL Enable pgvector 
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id        SERIAL PRIMARY KEY,
  content   TEXT NOT NULL,
  embedding vector(1536) -- OpenAI text-embedding-3-small dimension
);

-- IVFFlat index for approximate nearest neighbor (faster for large datasets)
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);
TypeScript src/ai/vectorSearch.ts 
import { prisma } from '../lib/prisma'
import OpenAI from 'openai'

const openai = new OpenAI()

async function embedText(text: string): Promise {
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text,
  })
  return response.data[0].embedding
}

// Store a document with its embedding
async function indexDocument(id: number, content: string): Promise {
  const embedding = await embedText(content)

  await prisma.$executeRaw`
    UPDATE documents
    SET embedding = ${JSON.stringify(embedding)}::vector
    WHERE id = ${id}
  `
}

// Semantic similarity search
type SearchResult = {
  id: number
  content: string
  similarity: number
}

async function semanticSearch(
  query: string,
  limit: number = 5,
  minSimilarity: number = 0.7
): Promise {
  const queryEmbedding = await embedText(query)

  const results = await prisma.$queryRaw`
    SELECT
      id,
      content,
      1 - (embedding <=> ${JSON.stringify(queryEmbedding)}::vector) AS similarity
    FROM documents
    WHERE 1 - (embedding <=> ${JSON.stringify(queryEmbedding)}::vector) > ${minSimilarity}
    ORDER BY embedding <=> ${JSON.stringify(queryEmbedding)}::vector
    LIMIT ${limit}
  `

  return results
}

Building a Semantic Search System

TypeScript src/ai/rag.ts 
import OpenAI from 'openai'
import { semanticSearch } from './vectorSearch'

const openai = new OpenAI()

// RAG: Retrieval-Augmented Generation
async function answerWithContext(question: string): Promise {
  // 1. Retrieve relevant documents
  const docs = await semanticSearch(question, 5, 0.6)

  // 2. Build context from retrieved docs
  const context = docs
    .map((d, i) => `[${i + 1}] ${d.content}`)
    .join('\n\n')

  // 3. Generate answer grounded in context
  const completion = await openai.chat.completions.create({
    model: 'gpt-4o',
    messages: [
      {
        role: 'system',
        content: 'Answer based only on the provided context. Cite sources.',
      },
      {
        role: 'user',
        content: `Context:\n${context}\n\nQuestion: ${question}`,
      },
    ],
    temperature: 0.1,
  })

  return completion.choices[0].message.content ?? ''
}

8. Database Best Practices

Environment Variables

Never hardcode database credentials. Use environment variables and validate them at startup.

TypeScript src/env.ts 
import { z } from 'zod'

const envSchema = z.object({
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url().optional(),
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
})

export const env = envSchema.parse(process.env)

Indexes: When and Why

🟢
Database Tip: Index Rules of Thumb
  • Add indexes on foreign keys — Postgres does not do this automatically
  • Index columns used in WHERE, ORDER BY, and JOIN conditions for large tables
  • Use partial indexes for filtered queries (e.g., WHERE published = true)
  • Use EXPLAIN ANALYZE before and after adding indexes in production
  • More indexes = slower writes. Don't index everything
Prisma prisma/schema.prisma — index examples 
model Post {
  id        String   @id @default(cuid())
  title     String
  published Boolean  @default(false)
  authorId  String
  createdAt DateTime @default(now())

  author User @relation(fields: [authorId], references: [id])

  @@index([authorId])                        // FK index
  @@index([createdAt(sort: Desc)])           // ordered feed
  @@index([published, createdAt(sort: Desc)]) // compound: filter + sort
}

N+1 Queries

N+1 is the most common ORM performance bug: fetching a list of N records, then issuing one query per record to load a relation.

TypeScript Anti-pattern vs correct 
// ❌ N+1: 1 query for users + N queries for posts
const users = await prisma.user.findMany()
for (const user of users) {
  user.posts = await prisma.post.findMany({ where: { authorId: user.id } })
}

// ✅ 1 query with include (Prisma uses a JOIN or batched IN query)
const users = await prisma.user.findMany({
  include: { posts: true },
})

// ✅ Drizzle: explicit join
const result = await db
  .select()
  .from(users)
  .leftJoin(posts, eq(posts.authorId, users.id))

Migrations in Production

  • Always run migrations in a transaction when possible
  • Never DROP COLUMN or DROP TABLE in a single migration step alongside application deployment — columns can be removed after the code referencing them is gone
  • Use CREATE INDEX CONCURRENTLY to avoid locking in production
  • Test migrations on a replica before the primary
  • Use Prisma's migrate deploy in CI/CD pipelines — it applies pending migrations without prompting

Audit Logs

Prisma prisma/schema.prisma 
model AuditLog {
  id         String   @id @default(cuid())
  entityType String   // "User", "Post", etc.
  entityId   String
  action     String   // "create", "update", "delete"
  actorId    String?  // who made the change
  before     Json?    // snapshot before
  after      Json?    // snapshot after
  createdAt  DateTime @default(now())

  @@index([entityType, entityId])
  @@index([actorId])
  @@index([createdAt])
}

Read Replicas

Direct read-heavy queries (analytics, reports, search) to a read replica. Write queries go to the primary. This pattern is straightforward with Prisma:

TypeScript 
import { PrismaClient } from '@prisma/client'

export const writeDb = new PrismaClient({
  datasources: { db: { url: process.env.DATABASE_URL } },
})

export const readDb = new PrismaClient({
  datasources: { db: { url: process.env.DATABASE_READ_URL } },
})

9. Testing with Databases

Test Database Strategy

Run tests against a real database. Mocking the ORM gives false confidence and misses real query behavior. Use a separate test database that resets between test suites.

TypeScript tests/setup.ts 
import { execSync } from 'child_process'
import { prisma } from '../src/lib/prisma'

// Run before all tests in this suite
beforeAll(async () => {
  // Reset test DB and apply all migrations
  execSync('pnpm prisma migrate reset --force --skip-seed', {
    env: { ...process.env, DATABASE_URL: process.env.TEST_DATABASE_URL },
  })
})

afterAll(async () => {
  await prisma.$disconnect()
})

Transaction Rollback in Tests

The cleanest isolation strategy: wrap each test in a transaction and roll it back after the test.

TypeScript tests/helpers/txRollback.ts 
import { prisma } from '../../src/lib/prisma'
import type { PrismaClient } from '@prisma/client'

// Note: Prisma's interactive transactions don't expose raw connection,
// so the cleanest approach is truncating tables between tests in the test DB.
export async function cleanDatabase() {
  const tables = ['Post', 'Profile', 'User', 'Tag']
  for (const table of tables) {
    await prisma.$executeRawUnsafe(`TRUNCATE TABLE "${table}" CASCADE`)
  }
}

Mocking Prisma Client

For unit tests where you don't want a database at all — testing business logic, not queries — use jest-mock-extended:

TypeScript tests/unit/userService.test.ts 
import { mockDeep, mockReset } from 'jest-mock-extended'
import type { PrismaClient } from '@prisma/client'

  prisma: prismaMock,

💡
Tip: Two Test Categories

Separate your database tests into two categories: integration tests (real DB, test real queries) and unit tests (mocked Prisma, test business logic in isolation). Run unit tests on every commit. Run integration tests in CI against a test Postgres instance (use Docker or Neon's branch-per-PR).

10. Python SQLAlchemy Comparison

Coming from Python's SQLAlchemy and Alembic, the TypeScript ecosystem maps cleanly. Here's the mental model translation.

🐍
Python Comparison

SQLAlchemy is the battle-tested ORM of Python. It's more low-level than Prisma and closer in spirit to Drizzle. Prisma is more like Django ORM in terms of abstraction level — high-level, opinionated, developer-friendly.

Model Definition

Python SQLAlchemy 
from sqlalchemy import Column, String, Boolean, DateTime, ForeignKey
from sqlalchemy.orm import DeclarativeBase, relationship
from datetime import datetime

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"
    id        = Column(String, primary_key=True)
    email     = Column(String, unique=True, nullable=False)
    name      = Column(String)
    created_at = Column(DateTime, default=datetime.utcnow)
    posts     = relationship("Post", back_populates="author")

class Post(Base):
    __tablename__ = "posts"
    id        = Column(String, primary_key=True)
    title     = Column(String, nullable=False)
    published = Column(Boolean, default=False)
    author_id = Column(String, ForeignKey("users.id"))
    author    = relationship("User", back_populates="posts")
Prisma TypeScript equivalent 
model User {
  id        String   @id @default(cuid())
  email     String   @unique

Key Differences to Internalize

  • Session vs connection: SQLAlchemy uses an explicit Session with commit()/rollback(). Prisma auto-commits each operation. Explicit control requires $transaction.
  • Lazy loading: SQLAlchemy lazy-loads relations by default. Prisma never lazy-loads — you must explicitly include or select relations. This makes N+1 bugs more visible.
  • Schema source of truth: SQLAlchemy models are Python classes. Prisma uses a DSL file. Drizzle uses TypeScript directly — closest to SQLAlchemy's model approach.
  • Type inference: SQLAlchemy requires Pydantic or manual typing for serialization. Prisma generates TypeScript types automatically. Drizzle infers types from the schema via $inferSelect.
🐍
Python Comparison: Alembic vs Prisma Migrations

Alembic migrations are Python scripts with upgrade() and downgrade() functions — you write both directions explicitly. Prisma generates SQL migration files automatically by diffing your schema. Prisma is faster for greenfield. Alembic gives more control for complex migrations involving data transformations. Drizzle is closer to Alembic in philosophy — you have more control over the generated SQL.
