React + TypeScript Philosophy

React has won the frontend. Over 40% of all web applications use it — not because of performance, but because its component model maps cleanly onto how UIs actually work: isolated pieces of state and UI that compose into larger experiences. TypeScript makes this model dramatically safer.

Without TypeScript, prop mistakes are runtime errors discovered in production. With TypeScript, they're compile errors discovered in your editor. You get autocomplete on every prop, instant feedback when you rename a component, and zero guessing about what a component accepts.

JSX and TSX

TypeScript natively understands JSX through .tsx files. The compiler validates that JSX elements correspond to real component types, that intrinsic elements like <div> receive valid HTML attributes, and that children are the right type. This is all built-in — no extra configuration beyond setting "jsx": "react-jsx" in tsconfig.json.

Typing React Components

A React component is a function that accepts props and returns JSX. TypeScript's job is to ensure callers pass the right props and the component returns valid JSX.

Defining a props interface

Button.tsx tsx 
interface ButtonProps {
  label: string
  onClick: () => void
  variant?: 'primary' | 'secondary' | 'danger'
  disabled?: boolean
  children?: React.ReactNode
}

function Button({ label, onClick, variant = 'primary', disabled = false }: ButtonProps) {
  const baseClass = 'px-4 py-2 rounded font-medium transition-colors'
  const variantClass = {
    primary: 'bg-indigo-600 text-white hover:bg-indigo-700',
    secondary: 'bg-gray-100 text-gray-900 hover:bg-gray-200',
    danger: 'bg-red-600 text-white hover:bg-red-700',
  }[variant]

  return (
    <button
      onClick={onClick}
      disabled={disabled}
      className={`${baseClass} ${variantClass} ${disabled ? 'opacity-50 cursor-not-allowed' : ''}`}
    >
      {label}
    </button>
  )
}

// Usage — TypeScript catches all mistakes at compile time
<Button label="Save" onClick={() => save()} variant="primary" />
<Button label="Delete" onClick={handleDelete} variant="danger" />
// Error: 'giant' is not assignable to 'primary' | 'secondary' | 'danger'
<Button label="?" onClick={noop} variant="giant" />

React.FC vs direct props typing

⚠
The React.FC Debate

React.FC<ButtonProps> was popular but fell out of favour because it implicitly added children to every component (fixed in React 18 types), made generics awkward, and added noise without benefit. The community consensus today is to type props directly on the function parameter. That's what I recommend, and what you'll see throughout this chapter.

comparison.tsx tsx 
// ✗ Old style — React.FC
const Button: React.FC<ButtonProps> = ({ label }) => <button>{label}</button>

// ✓ Modern style — type props directly
function Button({ label }: ButtonProps) {
  return <button>{label}</button>
}

// ✓ Also fine with arrow functions
const Button = ({ label }: ButtonProps) => <button>{label}</button>

Extending HTML element props

One of the most powerful patterns: use React.ComponentProps<'button'> to inherit all native HTML attributes, then layer your own on top.

Button.tsx tsx 
// Extend native button props — gets all HTML attributes for free
interface ButtonProps extends React.ComponentProps<'button'> {
  variant?: 'primary' | 'secondary' | 'danger'
  isLoading?: boolean
}

function Button({ variant = 'primary', isLoading, children, ...rest }: ButtonProps) {
  return (
    <button
      {...rest}                             // passes through type, aria-*, data-* etc
      disabled={isLoading || rest.disabled}
      className={cn(variantClass[variant], rest.className)}
    >
      {isLoading ? <Spinner /> : children}
    </button>
  )
}

// Now callers get full native button API plus our custom props
<Button variant="primary" type="submit" aria-label="Save changes">
  Save
</Button>

  options: { label: string; value: T }[]
  value: T
  onChange: (value: T) => void
  placeholder?: string

Props typing cheat sheet

Pattern Type Notes
Any JSX content React.ReactNode strings, numbers, JSX, arrays, null — the catch-all
Only JSX elements React.ReactElement more restrictive — excludes strings/numbers
Click handler React.MouseEventHandler<HTMLButtonElement> shorthand for (e: React.MouseEvent<HTMLButtonElement>) => void
Change handler React.ChangeEventHandler<HTMLInputElement> shorthand pattern
Ref to DOM element React.RefObject<HTMLDivElement> from useRef
CSS class string string or ClassValue from clsx for conditional classes
Inline styles React.CSSProperties typed CSS-in-JS object
Extend a native element React.ComponentProps<'div'> or React.ComponentPropsWithRef<'input'>
Wrap another component's props React.ComponentProps<typeof MyComp> useful for composition
✔
Tip

Prefer React.ReactNode for children props — it's the most permissive type that still excludes functions and undefined patterns that won't render correctly. Use React.ReactElement only when you need to clone or inspect the child element.

Events and Event Handlers

React wraps native browser events in its own synthetic event system. TypeScript's @types/react provides precise types for every event, parameterized by the element type they originate from.

Core event types

events.tsx tsx 
// Mouse events — button, div, etc.
function handleClick(e: React.MouseEvent<HTMLButtonElement>) {
  e.preventDefault()
  console.log(e.currentTarget.tagName) // typed as HTMLButtonElement
}

// Change events — the most common
function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setValue(e.target.value)             // e.target.value is string
  setChecked(e.target.checked)        // for checkboxes
}

// For select elements
function handleSelect(e: React.ChangeEvent<HTMLSelectElement>) {
  setCategory(e.target.value)
}

// Keyboard events
function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
  if (e.key === 'Enter') {
    submitForm()
  }
  if (e.key === 'Escape') {
    closeModal()
  }
}

// Form submit
function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault()
  // process form...
}

// Drag events
function handleDrop(e: React.DragEvent<HTMLDivElement>) {
  const files = e.dataTransfer.files
  processFiles(Array.from(files))
}

// Focus events
function handleFocus(e: React.FocusEvent<HTMLInputElement>) {
  e.target.select() // selects input text on focus
}

Handler type shorthands

handlers.tsx tsx 
// React provides shorthand types for event handlers as props
interface InputProps {
  // Verbose form
  onChange: (e: React.ChangeEvent<HTMLInputElement>) => void
  // Shorthand form — exactly equivalent
  onClick: React.MouseEventHandler<HTMLButtonElement>
  onKeyDown: React.KeyboardEventHandler<HTMLInputElement>
  onSubmit: React.FormEventHandler<HTMLFormElement>
}

// Custom event handler type — useful for lifting state
interface SearchBarProps {
  onSearch: (query: string) => void   // not a DOM event — a processed value
}

function SearchBar({ onSearch }: SearchBarProps) {
  const [query, setQuery] = React.useState('')

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    setQuery(e.target.value)
  }

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault()
    onSearch(query)    // calls parent with clean string, not the DOM event
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={query} onChange={handleChange} />
    </form>
  )
}
✔
Tip

When lifting state up, prefer passing processed values (string, number, your domain types) rather than raw DOM events. This keeps parent components decoupled from the DOM structure of their children.

✗
Common Mistake

Don't type events as Event (the native DOM type) or any. Always use the React synthetic event types like React.ChangeEvent<HTMLInputElement>. The native Event type won't have e.target.value typed correctly and the TypeScript compiler will complain.

Hooks with TypeScript

React hooks were designed with type inference in mind. Most of the time, TypeScript infers the right types automatically. Occasionally you need to help it.

Hook Typing Decision Flow

useState

useState-examples.tsx tsx 
// TypeScript infers the type from initial value — no annotation needed
const [count, setCount] = React.useState(0)           // State<number>
const [name, setName] = React.useState('')            // State<string>
const [open, setOpen] = React.useState(false)         // State<boolean>

// When initial value is null/undefined, provide the generic
interface User {
  id: string
  name: string
  email: string
}

const [user, setUser] = React.useState<User | null>(null)
// user is User | null — TypeScript forces you to handle the null case

// Arrays: infer from initial value or provide generic
const [items, setItems] = React.useState<string[]>([])

// Union types: provide explicit generic
const [status, setStatus] = React.useState<'idle' | 'loading' | 'error' | 'success'>('idle')

useReducer

useReducer-example.tsx tsx 
// Discriminated union for actions — exhaustive and type-safe
type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'reset'; payload: number }
  | { type: 'set'; payload: number }

interface CounterState {
  count: number
  history: number[]
}

function reducer(state: CounterState, action: Action): CounterState {
  switch (action.type) {
    case 'increment':
      return { ...state, count: state.count + 1, history: [...state.history, state.count] }
    case 'decrement':
      return { ...state, count: state.count - 1, history: [...state.history, state.count] }
    case 'reset':
      return { count: action.payload, history: [] }  // payload typed as number
    case 'set':
      return { ...state, count: action.payload }
    // TypeScript enforces exhaustiveness — if a case is missing, it's a type error
  }
}

function Counter() {
  const [state, dispatch] = React.useReducer(reducer, { count: 0, history: [] })

  return (
    <div>
      <p>Count: {state.count}</p>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      <button onClick={() => dispatch({ type: 'reset', payload: 0 })}>Reset</button>
    </div>
  )
}

useRef

useRef-examples.tsx tsx 
// DOM refs — always provide the element type, always initialize with null
function FocusableInput() {
  const inputRef = React.useRef<HTMLInputElement>(null)

  const focusInput = () => {
    inputRef.current?.focus()  // nullable — could be null before mount
  }

  return <input ref={inputRef} />
}

// Mutable refs for values that shouldn't trigger re-renders
function Timer() {
  const intervalRef = React.useRef<ReturnType<typeof setInterval> | null>(null)

  const start = () => {
    intervalRef.current = setInterval(() => tick(), 1000)
  }

  const stop = () => {
    if (intervalRef.current !== null) {
      clearInterval(intervalRef.current)
      intervalRef.current = null
    }
  }

  // ...
}

Custom hooks

useLocalStorage.ts tsx 
// Generic custom hook — full type safety for any value
function useLocalStorage<T>(key: string, initialValue: T): [T, (value: T) => void] {
  const [storedValue, setStoredValue] = React.useState<T>(() => {
    try {
      const item = window.localStorage.getItem(key)
      return item ? (JSON.parse(item) as T) : initialValue
    } catch {
      return initialValue
    }
  })

  const setValue = (value: T) => {
    try {
      setStoredValue(value)
      window.localStorage.setItem(key, JSON.stringify(value))
    } catch (error) {
      console.error('localStorage error:', error)
    }
  }

  return [storedValue, setValue]
}

// Usage — T is inferred as 'light' | 'dark'
const [theme, setTheme] = useLocalStorage<'light' | 'dark'>('theme', 'light')

// Another custom hook with a typed return object
interface UseToggleReturn {
  isOn: boolean
  toggle: () => void
  turnOn: () => void
  turnOff: () => void
}

function useToggle(initial = false): UseToggleReturn {
  const [isOn, setIsOn] = React.useState(initial)
  return {
    isOn,
    toggle: () => setIsOn((prev) => !prev),
    turnOn: () => setIsOn(true),
    turnOff: () => setIsOn(false),
  }
}
🧠
Mental Model

Think of hooks as functions that return values — because that's exactly what they are. Typing a custom hook is just typing a function's return value. Use a named interface for the return type rather than an inline type — it makes the hook's API visible and gives you a label to reference in documentation and autocomplete.

Context API with TypeScript

React Context propagates values down the component tree without prop drilling. TypeScript makes context dramatically safer — you know exactly what the context contains, and you get autocomplete everywhere it's consumed.

Typed context pattern

ThemeContext.tsx tsx 
// 1. Define the shape of the context value
interface ThemeContextType {
  theme: 'light' | 'dark'
  toggleTheme: () => void
}

// 2. Create context with undefined default — forces correct usage through provider
const ThemeContext = React.createContext<ThemeContextType | undefined>(undefined)

// 3. Create a custom hook that enforces provider presence
function useTheme(): ThemeContextType {
  const ctx = React.useContext(ThemeContext)
  if (ctx === undefined) {
    throw new Error('useTheme must be used within ThemeProvider')
  }
  return ctx
}

// 4. Provider component
interface ThemeProviderProps {
  children: React.ReactNode
  defaultTheme?: 'light' | 'dark'
}

function ThemeProvider({ children, defaultTheme = 'light' }: ThemeProviderProps) {
  const [theme, setTheme] = React.useState<'light' | 'dark'>(defaultTheme)

  const value: ThemeContextType = {
    theme,
    toggleTheme: () => setTheme((prev) => (prev === 'light' ? 'dark' : 'light')),
  }

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>
}

// 5. Usage — fully typed, error if used outside provider
function ThemedButton() {
  const { theme, toggleTheme } = useTheme()
  return (
    <button
      onClick={toggleTheme}
      className={theme === 'dark' ? 'bg-gray-800 text-white' : 'bg-white text-gray-900'}
    >
      Current: {theme}
    </button>
  )
}

Multiple contexts pattern

providers.tsx tsx 
// Compose multiple providers into one — clean and maintainable
interface AppProvidersProps {
  children: React.ReactNode
}

function AppProviders({ children }: AppProvidersProps) {
  return (
    <ThemeProvider>
      <AuthProvider>
        <ToastProvider>
          {children}
        </ToastProvider>
      </AuthProvider>
    </ThemeProvider>
  )
}

// In main.tsx
// <AppProviders><App /></AppProviders>
ℹ
Info

Always initialize createContext with undefined and use a custom hook with a runtime check rather than providing a dummy default value. The dummy value approach makes silent failures possible — your component silently uses the wrong value with no error. The undefined approach fails loudly and clearly at the point of misuse.

Forms

Forms are where TypeScript's value is most visceral. Without types, form data is a bag of strings. With TypeScript and the right libraries, form data is a validated, typed object that can't be submitted unless it's correct.

react-hook-form + Zod

The industry standard combination: react-hook-form for performance (uncontrolled inputs, minimal re-renders), zod for schema validation, and @hookform/resolvers to connect them.

SignupForm.tsx tsx 
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'

// 1. Define the schema — single source of truth for validation AND types
const signupSchema = z.object({
  name: z.string().min(2, 'Name must be at least 2 characters'),
  email: z.string().email('Invalid email address'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
  role: z.enum(['admin', 'editor', 'viewer']),
  agreeToTerms: z.literal(true, {
    errorMap: () => ({ message: 'You must accept the terms' }),
  }),
})

// 2. Derive TypeScript type from schema — no duplication
type SignupFormData = z.infer<typeof signupSchema>
// Equivalent to:
// {
//   name: string
//   email: string
//   password: string
//   role: 'admin' | 'editor' | 'viewer'
//   agreeToTerms: true
// }

// 3. Build the form
function SignupForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
    watch,
    reset,
  } = useForm<SignupFormData>({
    resolver: zodResolver(signupSchema),
    defaultValues: {
      role: 'viewer',
    },
  })

  const onSubmit = async (data: SignupFormData) => {
    // data is fully typed — TypeScript knows every field is valid here
    await createUser(data)
    reset()
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)} className="flex flex-col gap-4">
      <div>
        <label>Name</label>
        <input {...register('name')} />
        {errors.name && <p className="text-red-600 text-sm">{errors.name.message}</p>}
      </div>

      <div>
        <label>Email</label>
        <input type="email" {...register('email')} />
        {errors.email && <p className="text-red-600 text-sm">{errors.email.message}</p>}
      </div>

      <div>
        <label>Password</label>
        <input type="password" {...register('password')} />
        {errors.password && <p className="text-red-600 text-sm">{errors.password.message}</p>}
      </div>

      <div>
        <label>Role</label>
        <select {...register('role')}>
          <option value="viewer">Viewer</option>
          <option value="editor">Editor</option>
          <option value="admin">Admin</option>
        </select>
      </div>

      <div>
        <label>
          <input type="checkbox" {...register('agreeToTerms')} />
          I agree to the terms
        </label>
        {errors.agreeToTerms && <p className="text-red-600 text-sm">{errors.agreeToTerms.message}</p>}
      </div>

      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? 'Creating account...' : 'Sign up'}
      </button>
    </form>
  )
}
✔
Tip

Define your Zod schema once. From it you get: runtime validation, TypeScript types via z.infer, error messages, and the shape for your API request. This is the highest-leverage pattern in frontend TypeScript — one definition drives everything.

Fetching Data

Data fetching in React has evolved dramatically. The naive useEffect + fetch pattern works but leaves you managing loading states, caching, deduplication, and error handling yourself. TanStack Query solves all of this — and TypeScript makes the whole pipeline type-safe.

The useEffect + fetch pattern (and its problems)

naive-fetch.tsx tsx 
// The naive pattern — works, but you're writing a lot of boilerplate
interface User {
  id: number
  name: string
  email: string
}

function UserList() {
  const [users, setUsers] = React.useState<User[]>([])
  const [isLoading, setIsLoading] = React.useState(true)
  const [error, setError] = React.useState<string | null>(null)

  React.useEffect(() => {
    let cancelled = false   // prevent state updates after unmount

    async function fetchUsers() {
      try {
        setIsLoading(true)
        const res = await fetch('/api/users')
        if (!res.ok) throw new Error(`HTTP ${res.status}`)
        const data: User[] = await res.json()
        if (!cancelled) setUsers(data)
      } catch (err) {
        if (!cancelled) setError(err instanceof Error ? err.message : 'Unknown error')
      } finally {
        if (!cancelled) setIsLoading(false)
      }
    }

    fetchUsers()
    return () => { cancelled = true }
  }, [])

  // No caching, no deduplication, no refetch on focus, no pagination...
}

TanStack Query (React Query)

TanStack Query handles caching, background refetching, deduplication, pagination, and mutations. Critically, it infers types from your query function.

UserList.tsx tsx 
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'

// Type your API functions separately — these drive type inference
async function fetchUsers(): Promise<User[]> {
  const res = await fetch('/api/users')
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
}

async function deleteUser(id: number): Promise<void> {
  const res = await fetch(`/api/users/${id}`, { method: 'DELETE' })
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
}

// useQuery infers: data: User[] | undefined, error: Error | null
function UserList() {
  const queryClient = useQueryClient()

  const { data: users, isLoading, error, isFetching } = useQuery({
    queryKey: ['users'],
    queryFn: fetchUsers,
    staleTime: 5 * 60 * 1000,   // 5 minutes
  })

  const deleteMutation = useMutation({
    mutationFn: deleteUser,
    onSuccess: () => {
      // Invalidate and refetch
      queryClient.invalidateQueries({ queryKey: ['users'] })
    },
  })

  if (isLoading) return <Skeleton />
  if (error) return <ErrorBanner message={error.message} />

  return (
    <ul>
      {users?.map((user) => (
        <li key={user.id}>
          {user.name}
          <button
            onClick={() => deleteMutation.mutate(user.id)}
            disabled={deleteMutation.isPending}
          >
            Delete
          </button>
        </li>
      ))}
    </ul>
  )
}

Optimistic updates

optimistic.tsx tsx 
const toggleFavouriteMutation = useMutation({
  mutationFn: (userId: number) => toggleFavourite(userId),

  // Optimistically update the cache before the server responds
  onMutate: async (userId: number) => {
    await queryClient.cancelQueries({ queryKey: ['users'] })

    const previous = queryClient.getQueryData<User[]>(['users'])

    queryClient.setQueryData<User[]>(['users'], (old) =>
      old?.map((u) => u.id === userId ? { ...u, isFavourite: !u.isFavourite } : u)
    )

    return { previous }   // return snapshot for rollback
  },

  // Rollback on error
  onError: (_err, _userId, context) => {
    if (context?.previous) {
      queryClient.setQueryData(['users'], context.previous)
    }
  },
})
ℹ
Info

TanStack Query infers the data type directly from the return type of your queryFn. This means if you correctly type your API functions, the entire data-fetching pipeline is type-safe with no extra work. The error type defaults to Error in TanStack Query v5.

Component Composition Patterns

TypeScript unlocks advanced React patterns that would be fragile without types. These patterns let you build highly flexible, reusable components without sacrificing safety.

Discriminated union props

Alert.tsx tsx 
// Discriminated union for conditional prop requirements
type AlertProps =
  | {
      variant: 'info' | 'success' | 'warning'
      message: string
      onDismiss?: () => void
    }
  | {
      variant: 'error'
      message: string
      error: Error         // required when variant is 'error'
      onRetry?: () => void // only makes sense for errors
      onDismiss?: () => void
    }

function Alert(props: AlertProps) {
  return (
    <div className={`alert alert-${props.variant}`}>
      <p>{props.message}</p>
      {props.variant === 'error' && (
        // TypeScript knows props.error and props.onRetry exist here
        <div>
          <code>{props.error.message}</code>
          {props.onRetry && <button onClick={props.onRetry}>Retry</button>}
        </div>
      )}
    </div>
  )
}

// TypeScript enforces the correct props for each variant
<Alert variant="success" message="Saved!" />
<Alert variant="error" message="Failed" error={new Error('Network error')} />
// Error: Property 'error' is missing for variant 'error'
<Alert variant="error" message="Failed" />

Polymorphic "as" prop

Text.tsx tsx 
// The polymorphic component — renders as any HTML element or React component
type PolymorphicProps<T extends React.ElementType> = {
  as?: T
  children: React.ReactNode
  className?: string
} & React.ComponentPropsWithoutRef<T>

function Text<T extends React.ElementType = 'span'>({
  as,
  children,
  className,
  ...rest
}: PolymorphicProps<T>) {
  const Component = as ?? 'span'
  return <Component className={className} {...rest}>{children}</Component>
}

// Usage — TypeScript validates props based on the 'as' element
<Text>Default span</Text>
<Text as="h1">Heading</Text>
<Text as="a" href="/home">Link</Text>       // href is valid because 'a' has href
// Error: 'href' doesn't exist on 'span'
<Text href="/home">Bad</Text>

Compound components

Card.tsx tsx 
// Compound components — namespace-style composition
interface CardProps {
  children: React.ReactNode
  className?: string
}

function CardRoot({ children, className }: CardProps) {
  return <div className={cn('rounded-xl border bg-white shadow-sm', className)}>{children}</div>
}

function CardHeader({ children, className }: CardProps) {
  return <div className={cn('border-b px-6 py-4', className)}>{children}</div>
}

function CardBody({ children, className }: CardProps) {
  return <div className={cn('px-6 py-4', className)}>{children}</div>
}

function CardFooter({ children, className }: CardProps) {
  return <div className={cn('border-t px-6 py-3', className)}>{children}</div>
}

// Attach sub-components as properties
const Card = Object.assign(CardRoot, {
  Header: CardHeader,
  Body: CardBody,
  Footer: CardFooter,
})

// Usage — discoverable via autocomplete
<Card>
  <Card.Header>
    <h2>Title</h2>
  </Card.Header>
  <Card.Body>
    Content here
  </Card.Body>
  <Card.Footer>
    <button>Action</button>
  </Card.Footer>
</Card>

Mental Model

Discriminated unions for props are the same technique you use for Redux actions or API response types. The discriminant (the variant field) narrows the type in a switch or if-statement, giving TypeScript complete knowledge of what's available in each branch. This is one of TypeScript's most powerful features — use it liberally in component design.

The cn() utility

Every serious TypeScript + Tailwind project uses this tiny utility to compose class names conditionally while avoiding conflicting Tailwind classes.

lib/utils.ts tsx 
import { type ClassValue, clsx } from 'clsx'
import { twMerge } from 'tailwind-merge'

// Merges class names, resolving Tailwind conflicts intelligently
export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs))
}

// Usage — conditional classes with conflict resolution
<button
  className={cn(
    'px-4 py-2 rounded font-medium',          // always applied
    variant === 'primary' && 'bg-indigo-600',  // conditional
    variant === 'danger' && 'bg-red-600',      // conditional
    disabled && 'opacity-50 cursor-not-allowed',
    className,                                  // allow override — conflicts resolved by twMerge
  )}
/>

Performance Optimization

TypeScript doesn't change React's rendering model, but it makes optimization patterns safer and more maintainable. TypeScript will catch you passing the wrong type to a memoized component or mistyping a dependency array element.

React.memo

MemoExample.tsx tsx 
interface UserCardProps {
  user: User
  onSelect: (id: string) => void
}

// React.memo wraps the component — TypeScript preserves prop types
const UserCard = React.memo(function UserCard({ user, onSelect }: UserCardProps) {
  return (
    <div onClick={() => onSelect(user.id)}>
      <h3>{user.name}</h3>
    </div>
  )
})

// Custom comparison function — TypeScript types both prev and next
const UserCard = React.memo(
  function UserCard({ user, onSelect }: UserCardProps) { /* ... */ },
  (prevProps, nextProps) => prevProps.user.id === nextProps.user.id
    && prevProps.onSelect === nextProps.onSelect
)

useMemo and useCallback

optimization.tsx tsx 
function UserDashboard({ users }: { users: User[] }) {
  const [filter, setFilter] = React.useState('')

  // useMemo — type inferred from the computation return type
  const filteredUsers = React.useMemo(
    () => users.filter((u) => u.name.toLowerCase().includes(filter.toLowerCase())),
    [users, filter]
  )
  // filteredUsers: User[]  ✓ inferred

  // useCallback — type inferred from the function signature
  const handleDelete = React.useCallback(
    async (userId: string) => {
      await deleteUser(userId)
    },
    []  // stable reference — safe to pass to memoized children
  )
  // handleDelete: (userId: string) => Promise<void>  ✓ inferred

  return <UserList users={filteredUsers} onDelete={handleDelete} />
}
⚠
Warning

Don't reach for useMemo and useCallback by default — they add memory and complexity. Profile first with React DevTools. Use them when: a computation is genuinely expensive (>1ms), you're passing callbacks to deeply memoized child components, or you're stabilizing a reference used in a useEffect dependency array.

Button.test.tsx tsx 
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { describe, it, expect, vi } from 'vitest'
import { Button } from './Button'

describe('Button', () => {
  it('renders with label', () => {
    render(<Button label="Click me" onClick={vi.fn()} />)
    expect(screen.getByText('Click me')).toBeInTheDocument()
  })

  it('calls onClick when clicked', async () => {
    const handleClick = vi.fn()
    render(<Button label="Click me" onClick={handleClick} />)

    await userEvent.click(screen.getByRole('button'))
    expect(handleClick).toHaveBeenCalledOnce()
  })

  it('is disabled when disabled prop is true', () => {
    render(<Button label="Disabled" onClick={vi.fn()} disabled />)
    expect(screen.getByRole('button')).toBeDisabled()
  })
})

// Testing custom hooks
import { renderHook, act } from '@testing-library/react'
import { useToggle } from './useToggle'

describe('useToggle', () => {
  it('starts with initial value', () => {
    const { result } = renderHook(() => useToggle(false))
    expect(result.current.isOn).toBe(false)
  })

  it('toggles state', () => {
    const { result } = renderHook(() => useToggle(false))

    act(() => result.current.toggle())
    expect(result.current.isOn).toBe(true)

    act(() => result.current.toggle())
    expect(result.current.isOn).toBe(false)
  })
})
✔
Tip

TypeScript in tests catches the same errors it catches in production code — passing the wrong prop type to a component in a test file is an immediate red squiggle. This means your test suite is also a type-checking exercise, not just a behaviour-checking one. Use vi.fn() instead of jest.fn() when working with Vitest.

Python Comparison

🐍
Python Comparison

Django/Flask + Jinja2 → React + TypeScript. In Django, templates are strings of HTML with variable interpolation — runtime errors, no type checking on context variables. In React + TypeScript, components are typed functions — compile-time errors, full IDE support, refactoring that actually works.

A Django template context dict ({"{'user': user, 'posts': posts}"}) maps to a React props interface. The difference: TypeScript enforces the interface on both the caller and the component. Python's template context is unchecked at the call site and in the template.

Server-side vs client-side rendering: Django renders HTML on the server and sends complete pages — great for SEO, simpler mental model, page reload on navigation. React renders on the client — instant navigation after initial load, rich interactivity, but requires hydration strategy for SEO (Next.js solves this — that's Chapter 17).
