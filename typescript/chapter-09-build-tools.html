Build Tools & tsconfig Deep Dive

Everything you need to go from TypeScript source to a production artifact — plus a complete reference for every tsconfig option that matters.

OT Orta Therox — TypeScript Team @ Microsoft  ·  2025

1 The Build Tool Landscape

TypeScript itself does not run in browsers or Node.js — the .ts source must be transformed into JavaScript first. Over the years, this seemingly simple step has grown into an entire ecosystem of tools competing on speed, features, and developer experience. Understanding the landscape helps you pick the right tool for the job instead of cargo-culting whatever the last project used.

The core jobs a build tool must perform for a TypeScript project are:

  • Compilation — strip types (and optionally downlevel syntax)
  • Bundling — combine many modules into one or a few output files
  • Minification — shrink code for production
  • Source maps — map back to original TypeScript lines for debugging
  • Tree-shaking — eliminate unused code
  • Dev server — instant feedback loop during development
ℹ️
Type Checking is Separate

None of the fast bundlers (esbuild, SWC, Bun) perform type checking. They treat TypeScript as "JavaScript with type annotations and strip them". Always run tsc --noEmit separately in CI to catch type errors.

The Players in 2024–2025

tsc — The TypeScript Compiler

The reference implementation. tsc is the only tool that performs full type checking. It can emit JavaScript, but its build speed doesn't scale well for large apps when used as the sole bundler. In modern setups it's used exclusively for type-checking (tsc --noEmit) while a faster tool handles emission.

🔧
Tool Spotlight — tsc

Best for: type checking in CI, generating .d.ts declaration files, small projects where build speed doesn't matter. Use --watch for incremental development, --build for project references.

esbuild — The Speed Demon

Written in Go, esbuild is 10–100x faster than JavaScript-based bundlers. It handles TypeScript by stripping types (no type checking). It is the engine underneath Vite's pre-bundling and tsup. It lacks some advanced features like decorator metadata rewriting and plugin APIs are simpler than webpack's.

Vite — The Modern Dev Server

Vite uses native ES modules in the browser during development — no bundling at all. It uses esbuild to pre-bundle dependencies and Rollup for production builds. The result is instant server start regardless of project size. Vite is the go-to choice for React, Vue, and Svelte frontends in 2024–2025.

Rollup — The Library Bundler

Rollup pioneered tree-shaking and produces the cleanest ESM output. It's used by Vite under the hood for production and by many library authors who need full control over output format. Config is verbose but powerful.

webpack — The Legacy King

webpack ruled bundling from 2014 to ~2021. Still widely used in large enterprise codebases and projects on React + Create React App (now in maintenance mode). Rich plugin ecosystem but slow cold starts and complex configuration.

Parcel — Zero-Config

Parcel requires zero configuration for most TypeScript projects. It auto-detects entry points and handles TypeScript, CSS, images, etc. Good for quick prototypes but less control for production tuning.

Bun — Native TypeScript Runtime

Bun is a JavaScript runtime written in Zig that executes TypeScript natively — no build step required for scripts and servers. It also ships a fast bundler. Gaining serious traction for backend services and CLI tools as of 2025.

tsup — Library Build Tool

tsup wraps esbuild and adds declaration file generation (--dts), dual CJS + ESM output, and sensible defaults for publishing npm packages. The opinionated sibling of esbuild for library authors.

SWC — Rust-Based Compiler

SWC (Speedy Web Compiler) is written in Rust and is used by Next.js, Nx, and Jest (via @swc/jest). It compiles TypeScript much faster than tsc and supports most decorators. Like esbuild, no type checking.

2 tsconfig.json — Complete Reference

The tsconfig.json file controls everything the TypeScript compiler does. Most developers use a copied config without understanding half the options. This section walks through every important option you'll encounter in real projects.

Compiler Options — Type Checking

Option Default Explanation
"strict" Always Enable false Master flag that enables all strict checks below. Setting this to true is the single most impactful thing you can do for a TypeScript project. It activates: strictNullChecks, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitAny, noImplicitThis, alwaysStrict.
"strictNullChecks" false (true with strict) Separates null and undefined from every other type. Without this, null is assignable to any type — the billion-dollar mistake TypeScript avoids when this is on. Enables the optional chaining (?.) and nullish coalescing (??) operators to be meaningful.
"strictFunctionTypes" false (true with strict) Enables contravariance checking for function parameter types. Prevents subtle bugs where a callback expecting a subtype can receive a supertype. Method signatures are excluded to preserve compatibility with common OO patterns.
"noImplicitAny" false (true with strict) Errors when TypeScript cannot infer a type and would silently fall back to any. If you have strict: true this is already covered, but you can set it independently for gradual migration.
"noImplicitThis" false (true with strict) Raises an error when this has an implicit any type. Forces you to annotate this parameters in functions that use it.
"alwaysStrict" false (true with strict) Parses all files in strict mode and emits "use strict" at the top of every output file. A good safety net even when targeting ESM (though redundant there).
"strictBindCallApply" false (true with strict) Makes bind, call, and apply type-safe. Without this, they all return any.
"strictPropertyInitialization" false (true with strict) Errors if a class property is declared but not assigned in the constructor. Prevents reading undefined from class fields. Use the definite assignment operator (!) to opt out per-property when needed (e.g., dependency injection).
"useUnknownInCatchVariables" TS 4.4+ false (true with strict) Typed catch clause variables as unknown instead of any. Forces you to narrow the error before using it. This is correct: anything can be thrown in JS.
"exactOptionalPropertyTypes" TS 4.4+ false Distinguishes between an optional property being absent (key not in object) vs. set to undefined (key: undefined). Not included in strict — opt in manually when you want this precision.
"noUncheckedIndexedAccess" false Adds | undefined to any array index or object key access. Highly recommended for safety. Also not in strict — enable separately.
"noImplicitOverride" false Requires the override keyword when overriding base class methods. Prevents accidentally breaking a derived class when renaming a base class method.
✅
Tip — Beyond strict

For maximum safety, also enable "noUncheckedIndexedAccess": true and "exactOptionalPropertyTypes": true. These are intentionally omitted from strict because they break many existing codebases, but new projects should use them.

Compiler Options — Output

Option Common Values Explanation
"target" ES2022, ESNext The ECMAScript version TypeScript downlevels syntax to. This affects which syntax transformations are applied (e.g., async/await, optional chaining, class fields). ES2022 is safe for modern Node.js (18+) and evergreen browsers. ESNext emits the latest syntax — only use if you're certain your runtime supports it.
"module" NodeNext, ESNext, CommonJS Controls the output module system. NodeNext is the correct choice for Node.js ≥18 and respects package.json "type" field. ESNext is used by bundlers like Vite. CommonJS for older Node.js or libraries that must support require().
"moduleResolution" bundler, node16 How TypeScript resolves import paths to files. bundler (TS 5.0+) matches how Vite/esbuild/webpack resolve modules — allows extension-less imports and exports map. node16 enforces explicit .js extensions in ESM. node (legacy) never use for new projects.
"outDir" "./dist" Directory where compiled JavaScript is emitted. Mirrors the rootDir structure inside this folder.
"rootDir" "./src" The root of the TypeScript source tree. TypeScript uses this to compute the output structure inside outDir. If omitted, TypeScript infers it from the input files — which can produce surprising output layouts.
"declaration" true (for libraries) Emit .d.ts declaration files alongside JavaScript output. Required when publishing a library so consumers get type information. No effect when building an application.
"declarationMap" true (for libraries) Emit .d.ts.map files alongside declarations. Enables IDE "Go to definition" to navigate to the original TypeScript source instead of the generated .d.ts. Highly recommended for libraries published with source included.
"sourceMap" true Emit .js.map source maps. Enables debuggers and error reporters to show original TypeScript line numbers. Always enable for development and production (you can restrict map serving via your CDN/server).
"removeComments" false Strip all comments from output JS. Your bundler/minifier will do this in production anyway — only useful if using tsc as the only build step and you want smaller output.
"noEmit" true (type-check only) Run the compiler for type-checking but produce no output files. Use in CI alongside your faster bundler: tsc --noEmit && esbuild ...
"incremental" true Save compilation state to a tsconfig.tsbuildinfo file and only recompile changed files on the next run. Dramatically speeds up repeated tsc calls in CI and watch mode.

Project Options

Option Explanation
"include" Array of glob patterns specifying which files TypeScript should include. Defaults to all .ts, .tsx, .d.ts in the project root. Be explicit: ["src/**/*"] prevents accidentally including test files in a library build.
"exclude" Glob patterns excluded from compilation. node_modules, dist, and outDir are excluded by default. Add "**/*.test.ts" to exclude tests from the library build.
"extends" Inherit another tsconfig. Useful in monorepos: a base config lives at the root, each package extends it and overrides only what differs. E.g., "extends": "../../tsconfig.base.json". Supports arrays since TS 5.0.
"references" Declare inter-package dependencies for TypeScript project references. Combined with composite: true, enables incremental builds across monorepo packages. tsc --build respects the dependency graph.
"composite" Required for project references. Enforces that declaration is true, rootDir is set, and enables build caching via .tsbuildinfo.

Commonly Missed Options

These options are frequently omitted but meaningfully affect correctness or interop:

Option Default Why it Matters
"resolveJsonModule" false Allows importing .json files as typed modules. Useful for config files, data files, or package.json version strings.
"esModuleInterop" false Adds helpers that allow import React from 'react' (default import) to work with CommonJS modules that use module.exports = .... Highly recommended. Without it you'd need import * as React from 'react'.
"allowSyntheticDefaultImports" false (true with esModuleInterop) Allows import X from 'module' even when the module has no default export, without requiring the interop helper emit. Included automatically with esModuleInterop.
"skipLibCheck" false Skip type-checking of all .d.ts files in node_modules. Often set to true in apps to avoid spurious errors from third-party type definitions that have bugs. Don't set in libraries — you want to catch declaration file issues.
"forceConsistentCasingInFileNames" false Errors if an import uses different casing than the actual filename. Critical for teams mixing macOS (case-insensitive) and Linux (case-sensitive) file systems — prevents bugs that only appear in CI or production.
"verbatimModuleSyntax" TS 5.0+ false Ensures imports/exports are written exactly as they'll be emitted. Forces you to use import type for type-only imports. Replaces the older importsNotUsedAsValues and preserveValueImports options. Use this for all new projects.
"moduleDetection" "auto" Controls whether files are treated as modules or scripts. "force" treats every file as a module (has an implicit export {}) — useful to prevent accidentally polluting the global scope in a file that doesn't have any imports/exports.
"allowImportingTsExtensions" TS 5.0+ false Allows importing .ts files directly with their extension — useful when using Bun, Deno, or other runtimes that natively handle TypeScript without a build step. Requires noEmit or emitDeclarationOnly.
⚠️
Warning — module / moduleResolution mismatch

The most common source of baffling TypeScript errors is a mismatch between module and moduleResolution. The correct pairings are: module: "NodeNext" with moduleResolution: "NodeNext", or module: "ESNext" with moduleResolution: "bundler". Never use module: "ESNext" with moduleResolution: "node" — it allows import syntax that won't actually work at runtime.

3 Vite — The Modern Dev Server

Vite (French for "fast") fundamentally changed frontend development. Its key insight: during development, don't bundle at all. Instead, serve source files as native ES modules directly to the browser. The browser's module resolution handles imports; Vite only transforms the file requested — on demand, in milliseconds.

Two distinct modes:

  • Dev mode — native ESM server, instant HMR, esbuild for JSX/TS transforms
  • Production build — Rollup under the hood, full bundling, tree-shaking, code splitting

Creating a Vite + TypeScript Project

Terminal 
# Create a new Vite project — pick React + TypeScript template
pnpm create vite my-app --template react-ts
cd my-app
pnpm install

# Start dev server (instant — no bundling needed)
pnpm dev

# Type-check (Vite does NOT type-check — run tsc separately)
pnpm exec tsc --noEmit

# Production build (Rollup under the hood)
pnpm build

# Preview production build locally
pnpm preview

Vite generates a minimal tsconfig.json and a vite.config.ts. The TypeScript config uses moduleResolution: "bundler" — a TS 5.0+ mode that exactly mirrors how Vite resolves modules (no mandatory .js extensions, supports exports maps).

vite.config.ts anatomy

import { defineConfig, loadEnv } from 'vite'
import react from '@vitejs/plugin-react'
import tsconfigPaths from 'vite-tsconfig-paths'
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig(({ mode }) => {
  // Load .env files relative to the project root
  const env = loadEnv(mode, process.cwd(), '')

  return {
    plugins: [
      react(),
      tsconfigPaths(),   // Respect tsconfig path aliases
      // Only include bundle visualizer in analyze mode
      mode === 'analyze' && visualizer({ open: true }),
    ],

    // Override esbuild target (default: browser-compatible)
    esbuild: {
      target: 'es2022',
    },

    build: {
      target: 'es2022',
      sourcemap: true,
      rollupOptions: {
        output: {
          // Split vendor chunks for better caching
          manualChunks: {
            vendor: ['react', 'react-dom'],
          },
        },
      },
    },

    server: {
      port: 3000,
      proxy: {
        // Proxy /api requests to your backend in development
        '/api': {
          target: env.VITE_API_URL ?? 'http://localhost:8080',
          changeOrigin: true,
        },
      },
    },

    resolve: {
      alias: {
        '@': '/src',   // Use @/components instead of ../../components
      },
    },
  }
})

Environment Variables

Vite loads .env, .env.local, .env.[mode], and .env.[mode].local files. Only variables prefixed with VITE_ are exposed to client-side code — all others are server-only (used in vite.config.ts plugins and SSR code). 

# .env.development
VITE_API_URL=http://localhost:8080
VITE_FEATURE_NEW_DASHBOARD=true

# .env.production
VITE_API_URL=https://api.myapp.com
VITE_FEATURE_NEW_DASHBOARD=false

Access in your TypeScript code with full type safety by extending ImportMetaEnv:

// src/vite-env.d.ts (Vite generates this)
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string
  readonly VITE_FEATURE_NEW_DASHBOARD: string
}

interface ImportMeta {
  readonly env: ImportMetaEnv
}

// Usage in your components:
const apiUrl = import.meta.env.VITE_API_URL  // string — type-safe
const isDev  = import.meta.env.DEV            // built-in boolean
✅
Tip — Hot Module Replacement

Vite's HMR is component-level, not page-level. When you save a React component, only that component re-renders — the rest of the app state is preserved. For custom modules, opt in with if (import.meta.hot) { import.meta.hot.accept() }.

4 esbuild — The Speed Demon

esbuild is written in Go and parallelizes work across all CPU cores. It avoids the overhead of a JavaScript-based plugin system during the hot path. The result: builds that used to take 30 seconds complete in under a second.

⚠️
No Type Checking

esbuild strips TypeScript annotations but performs zero type checking. Always pair it with tsc --noEmit in CI. This is a feature, not a bug — it keeps the build fast by not doing work that's already done by your editor's language server.

Direct CLI Usage

Terminal 
# Basic bundle
esbuild src/index.ts --bundle --outfile=dist/index.js

# Production: minify + sourcemaps + target
esbuild src/index.ts \
  --bundle \
  --minify \
  --sourcemap \
  --target=es2022 \
  --outfile=dist/index.js

# Watch mode for development
esbuild src/index.ts --bundle --outfile=dist/index.js --watch

# Multiple entry points with code splitting
esbuild src/index.ts src/worker.ts \
  --bundle \
  --splitting \
  --format=esm \
  --outdir=dist

Programmatic API

For complex build pipelines, the esbuild JavaScript API gives you full control. You write your build script in TypeScript and esbuild handles the rest. 

// build.ts
import * as esbuild from 'esbuild'

const result = await esbuild.build({
  entryPoints: ['src/index.ts'],
  bundle: true,
  minify: process.env.NODE_ENV === 'production',
  sourcemap: true,
  target: ['es2022'],
  platform: 'node',
  format: 'esm',
  outdir: 'dist',
  external: ['node:*'],  // Don't bundle Node.js built-ins

  // Plugins — esbuild plugin API
  plugins: [
    {
      name: 'env-replace',
      setup(build) {
        build.onResolve({ filter: /^#env$/ }, (args) => ({
          path: args.path,
          namespace: 'env-ns',
        }))
        build.onLoad({ filter: /.*/, namespace: 'env-ns' }, () => ({
          contents: JSON.stringify(process.env),
          loader: 'json',
        }))
      },
    },
  ],
})

// Access metafile for bundle analysis
const analysis = await esbuild.analyzeMetafile(result.metafile!)
console.log(analysis)
🤖
AI Era — esbuild in AI Toolchains

When building AI-powered applications, esbuild is increasingly the right choice for bundling server-side inference code — its speed matters when you're rebuilding frequently during prompt engineering iterations. LangChain.js, Vercel AI SDK, and similar libraries all ship esbuild-bundled outputs.

5 tsup — Library Build Tool

tsup is the "batteries included" version of esbuild for library authors. It handles the fiddly details of publishing: dual CJS + ESM output, declaration file generation, package.json exports field compatibility.

Terminal 
pnpm add -D tsup

# One-shot: build CJS + ESM + types
pnpm tsup src/index.ts --format cjs,esm --dts

# Watch mode for development
pnpm tsup src/index.ts --format cjs,esm --dts --watch

tsup.config.ts

import { defineConfig } from 'tsup'

export default defineConfig({
  entry: ['src/index.ts'],

  // Emit both CommonJS (.cjs) and ESM (.mjs)
  format: ['cjs', 'esm'],

  // Generate .d.ts declaration files
  dts: true,

  // Source maps for both formats
  sourcemap: true,

  // Remove dist before each build
  clean: true,

  // Minify in production
  minify: process.env.NODE_ENV === 'production',

  // Don't bundle peer dependencies
  external: ['react', 'react-dom'],

  // Split output — helps tree-shaking
  splitting: true,

  // Shim __dirname / __filename in ESM output
  shims: true,
})

The resulting package.json exports field for the published package:

{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.mts",
        "default": "./dist/index.mjs"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    }
  },
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts"
}
✅
tsup vs Rollup vs esbuild directly

Use tsup when publishing an npm library — it handles the dual-format boilerplate and declaration generation. Use esbuild directly when you need maximum control or are building an app (not a library). Use Rollup when you need advanced output control, custom plugins from the Rollup ecosystem, or are already using Vite's production build which runs Rollup under the hood.

6 Build Scripts and Automation

The package.json scripts field is the universal entry point for project automation. Every developer, CI system, and IDE knows to look there. A well-structured scripts section documents your workflow. 

{
  "scripts": {
    "build":     "tsup --clean",
    "dev":       "tsx watch src/index.ts",
    "typecheck": "tsc --noEmit",
    "lint":      "eslint src --max-warnings 0",
    "lint:fix":  "eslint src --fix",
    "format":    "prettier --write src",
    "test":      "vitest run",
    "test:watch":"vitest",
    "test:coverage": "vitest run --coverage",
    "ci":        "pnpm typecheck && pnpm lint && pnpm test"
  }
}

Key principle: separate type-checking from building. The build step should be fast (esbuild/tsup); type checking runs in parallel in CI and on save in your editor.

tsx and ts-node for Development

Running TypeScript files directly without a build step is essential for scripts, CLIs, and rapid development. Two tools dominate:

tsx (recommended)

Wraps esbuild, fast, supports ESM, works with modern Node.js without any flags. The watch sub-command re-runs on file change.

Terminal
pnpm add -D tsx

# Run once
tsx src/script.ts

# Watch mode
tsx watch src/server.ts

# In package.json
# "dev": "tsx watch src/index.ts"

ts-node

The original. Requires more configuration for ESM. Still useful for specific use cases or older projects.

Terminal
pnpm add -D ts-node

# CommonJS projects
ts-node src/script.ts

# ESM projects (needs flags)
node --loader ts-node/esm src/script.ts

# With SWC for speed
pnpm add -D @swc/core @swc/helpers
ts-node --swc src/script.ts

Incremental Builds

For large TypeScript projects using tsc directly, enable incremental compilation to avoid recompiling unchanged files:

{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": ".cache/tsconfig.tsbuildinfo"
  }
}
Terminal
# First run: compiles everything (~15s on large project)
tsc

# Subsequent runs: only recompiles changed files (~0.5s)
tsc

# Watch mode: stays alive, recompiles on save
tsc --watch

# Project references build (monorepo)
tsc --build --watch

7 CI/CD Considerations

TypeScript's build pipeline in CI should do three distinct things, ideally in parallel: type check, lint, and build. Merging them slows down feedback.

GitHub Actions Workflow

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  typecheck:
    name: Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      - run: corepack enable && pnpm install --frozen-lockfile
      - name: TypeScript type check
        run: pnpm typecheck

  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      - run: corepack enable && pnpm install --frozen-lockfile
      - run: pnpm lint

  test:
    name: Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      - run: corepack enable && pnpm install --frozen-lockfile
      - run: pnpm test:coverage

  build:
    name: Build
    runs-on: ubuntu-latest
    needs: [typecheck, lint, test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      - run: corepack enable && pnpm install --frozen-lockfile
      - run: pnpm build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
✅
Build Caching in CI

Cache node_modules by hashing the lockfile (actions/setup-node with cache: 'pnpm' does this automatically). For monorepos, also cache .cache/tsconfig.tsbuildinfo and .turbo (if using Turborepo) across runs to get incremental TypeScript builds in CI.

Docker with Node.js + TypeScript

The key pattern for TypeScript + Docker is a multi-stage build: compile in a builder stage that has dev dependencies, then copy only the compiled output into the slim production image. 

# Dockerfile
# ────── Stage 1: Install & Build ──────────────────────────────────
FROM node:20-alpine AS builder

# Enable pnpm via corepack
RUN corepack enable

WORKDIR /app

# Install dependencies first (layer caching — only re-runs if lockfile changes)
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

# Copy source and build
COPY . .
RUN pnpm typecheck   # Fail fast if types are broken
RUN pnpm build       # Emit JS to /app/dist

# ────── Stage 2: Production Image ─────────────────────────────────
FROM node:20-alpine AS production

RUN corepack enable

WORKDIR /app

# Only copy production dependencies
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile --prod

# Copy compiled output from builder
COPY --from=builder /app/dist ./dist

# Non-root user for security
USER node

EXPOSE 3000

CMD ["node", "dist/index.js"]
ℹ️
Docker Image Size

The multi-stage build ensures your production image contains only compiled JS and production node_modules — no TypeScript compiler, no dev dependencies, no source files. A typical Node.js TypeScript backend shrinks from ~400MB (builder) to ~80MB (production image) this way.

8 Python Build Tool Comparison

If you're coming from a Python background, the TypeScript/Node.js build ecosystem maps to Python concepts — though the conventions differ significantly.

🐍
Python Comparison

Python has a more unified build story (pyproject.toml → pip/poetry/uv) while the JavaScript ecosystem is more fragmented. The upside: JavaScript tooling has more specialization and typically much higher build performance.

pip / poetry / uv npm / pnpm / yarn pnpm is the modern choice (fastest, disk-efficient)

python setup.py bdist_wheel tsup / npm publish tsup builds the distributable; npm/pnpm publishes to registry

pytest vitest / jest vitest is the modern choice; faster, native TS support via Vite

TypeScript equivalent

Terminal — TypeScript
# Setup (node_modules = implicit venv)
pnpm install

# Type check
pnpm typecheck  # tsc --noEmit

# Lint + format
pnpm lint       # eslint src
pnpm format     # prettier --write src

# Test
pnpm test       # vitest run --coverage

# Build distribution
pnpm build      # tsup src/index.ts

# Publish
npm publish --access public
🐍
Key Difference — No Runtime Type Checking

Python's mypy and TypeScript's tsc --noEmit are both static analysis tools. But there is one crucial difference: in Python, you can use beartype or pydantic to enforce types at runtime. In TypeScript/JavaScript, all type information is erased at compile time — there is no runtime type enforcement built in. Use Zod or Valibot at your system boundaries (API responses, environment variables, user input) to get runtime validation.

🤖
AI Era — Build Tools for AI-Powered Apps

When building AI-powered TypeScript applications in 2025, the build tool choice matters more than ever. Streaming responses, edge runtimes, and large SDK bundles all create new constraints:

  • Edge runtimes (Cloudflare Workers, Vercel Edge) require small bundles without Node.js APIs — use esbuild with platform: "browser" and external for polyfills.
  • Server Components (Next.js App Router) split your bundle at the framework level — SWC handles the transform.
  • WASM modules for local AI inference (transformers.js, llama.cpp wasm) need Vite's assetsInclude or custom esbuild loaders.
  • tsc --noEmit is still essential — AI code generation produces plausible but sometimes incorrectly typed code that only tsc will catch.
