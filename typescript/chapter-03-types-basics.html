TypeScript Types:
A Python Developer's Rosetta Stone

Every Python type you know maps to a TypeScript equivalent. Some map cleanly. Some don't exist in Python at all. This chapter is the translation dictionary you'll reach for every day.

BC
Boris Cherny
Staff Engineer @ Meta  •  Author of Programming TypeScript (O'Reilly)

1 The Type System Philosophy

Before we map Python types to TypeScript, you need to understand that the two languages make fundamentally different bets about what a type means. This isn't an implementation detail — it changes how you model everything.

Structural Typing vs. Nominal Typing

Python (and Java, C#) use nominal typing: a type is identified by its name. If two classes have the same fields but different names, they are different types.

TypeScript uses structural typing: a type is defined by its shape — the names and types of its properties and methods. If two types have the same structure, they are compatible, regardless of their names.

Python (nominal)
class Dog:
    def __init__(self, name: str):
        self.name = name

class Cat:
    def __init__(self, name: str):
        self.name = name

def greet(animal: Dog) -> None:
    print(f"Hello, {animal.name}")

kitty = Cat("Kitty")
greet(kitty)
# mypy ERROR: Argument 1 to "greet"
# has incompatible type "Cat";
# expected "Dog"
# (same shape, different name = error)
TypeScript (structural)
type Dog = { name: string };
type Cat = { name: string };

function greet(animal: Dog): void {
  console.log(`Hello, ${animal.name}`);
}

const kitty: Cat = { name: "Kitty" };
greet(kitty);
// NO ERROR — Cat and Dog have the
// same shape, so they're compatible.
// TypeScript only cares about structure,
// not the name of the type.
Py
Python Comparison: Protocols

Python 3.8 added typing.Protocol which introduces structural typing to Python. If you've used Protocols, TypeScript will feel familiar — everything in TypeScript works like a Protocol.

Type Inference: The Compiler Reads Your Mind

TypeScript doesn't require you to annotate every variable. It infers types from the values you assign. You get the safety of static typing without the verbosity of Java.

// TypeScript infers: string
const greeting = "Hello, world";

// TypeScript infers: number
const answer = 42;

// TypeScript infers: boolean
const isDone = false;

// TypeScript infers: string[]
const names = ["Alice", "Bob", "Charlie"];

// TypeScript infers: { x: number; y: number }
const point = { x: 10, y: 20 };

// You can still annotate explicitly — useful for clarity
const pi: number = 3.14159;
✓
Tip: Let Inference Work

Annotate function parameters and return types. Let TypeScript infer everything else. Over-annotating produces noise without benefit — the compiler is better at inferring than humans at typing.

Types Are a Lie (A Useful One)

TypeScript types do not exist at runtime. The TypeScript compiler erases all type information before producing JavaScript. There is no instanceof check against a TypeScript interface at runtime; there is no reflection over type parameters. Types are purely a compile-time fiction that the compiler uses to catch your bugs.

// This TypeScript code...
const user: { name: string; age: number } = { name: "Alice", age: 30 };

// ...compiles to this JavaScript:
const user = { name: "Alice", age: 30 };
// The ": { name: string; age: number }" simply vanishes.
!
Runtime Caveat

Because types are erased, you cannot do if (value instanceof MyInterface) — interfaces don't exist at runtime. For runtime type checking, you need type guards, discriminated unions, or libraries like zod. We cover those in Chapter 8.

The TypeScript Type Hierarchy

TypeScript's types form a hierarchy from the most permissive (unknown, which accepts any value) to the least permissive (never, which accepts no values). Understanding this hierarchy is the key to mastering the type system.

Read the arrows as "is a subtype of." Every type is a subtype of unknown. never is a subtype of every type. any is special — it breaks in both directions, making it both a supertype and a subtype of everything.

Why One Number Type?

JavaScript (and therefore TypeScript) inherited one numeric type from the web: IEEE 754 double-precision float. Integers up to 253−1 (9,007,199,254,740,991) are represented exactly. Above that, use bigint. In practice this rarely matters — you'll use number for everything.

3 Type Annotations

TypeScript type annotations look like Python's, but with the colon after the variable name, and the type written differently. Here's the pattern: let variableName: Type = value.

Python
# Variable annotations
name: str = "Alice"
age: int = 30
is_active: bool = True
score: float = 9.5

# Function with typed params + return
def greet(name: str, times: int) -> str:
    return f"Hello {name}! " * times

# Optional (can be str or None)
from typing import Optional
nickname: Optional[str] = None
TypeScript
// Variable annotations
let name: string = "Alice";
let age: number = 30;
let isActive: boolean = true;
let score: number = 9.5;

// Function with typed params + return
function greet(name: string, times: number): string {
  return (name + "! ").repeat(times);
}

// Optional (can be string or undefined/null)
let nickname: string | null = null;

When to Annotate vs. When to Infer

The rule of thumb: annotate inputs, infer everything else.

// ANNOTATE function parameters — TypeScript cannot infer them from context
function processUser(id: number, role: string): void {
  // ...
}

// INFER local variables — annotation adds noise, no benefit
const doubled = [1, 2, 3].map(n => n * 2);  // inferred: number[]
const user = { name: "Alice", age: 30 };      // inferred: { name: string; age: number }

// ANNOTATE when inference is wrong or too wide
// Without annotation, TypeScript infers { status: string }
// With annotation, we get the literal type
const config: { status: "active" | "inactive" } = { status: "active" };

// ANNOTATE when you want to widen a type intentionally
let result: string | null = null;  // without annotation, inferred as: null
// Later we'll assign a string — the annotation lets us do that
result = "success";

const vs. let: Literal Types

This is one of the most important TypeScript behaviors to understand. const tells TypeScript the value can never change, so it infers the most specific (literal) type possible. let tells TypeScript the value might change, so it infers a widened type.

const direction = "left";
// TypeScript infers: "left"  (literal type!)
// Because it's const — value can never be anything else

let direction2 = "left";
// TypeScript infers: string  (widened type)
// Because it's let — value could be reassigned to any string

// This matters when you use literals in function calls:
function move(dir: "left" | "right" | "up" | "down"): void { /* ... */ }

move(direction);   // OK — "left" is assignable to the union
move(direction2);  // ERROR — string is not assignable to the union

// Fix: use const, or use an explicit annotation, or use "as const"
const direction3 = "left" as const;   // type: "left"
✓
Tip: Prefer const

Use const by default. Upgrade to let only when you genuinely need to reassign. This gives you better type inference and prevents accidental mutation — two wins for free.

Type Assertions and the Non-Null Assertion

Sometimes you know more about a type than TypeScript does. Type assertions let you override the inferred type. They're not casts — no runtime conversion happens.

// Type assertion: "I promise this is a string"
const input = document.getElementById("username") as HTMLInputElement;
// Without assertion, type is: HTMLElement | null
// We assert it's specifically HTMLInputElement so we can read .value

// The older angle-bracket syntax (not allowed in TSX/React files)
const input2 = <HTMLInputElement>document.getElementById("username");

// Double assertion — escaping to any first (danger zone)
const mystery = someValue as unknown as string;

// Non-null assertion operator: "I promise this is not null"
const el = document.getElementById("app")!;
// The ! tells TypeScript: trust me, this won't be null
// If you're wrong, you'll get a runtime crash
!
Warning: Don't Overuse Assertions

Type assertions and ! are TypeScript's "shut up, I know what I'm doing" operator. They silence the compiler but don't add runtime safety. If you're wrong, you get a crash with no warning. Use assertions only when you genuinely know more than the compiler — and when you use them, add a comment explaining why.

4 Arrays and Tuples

Python
from typing import Union

# List of strings
names: list[str] = ["Alice", "Bob"]

# List of mixed types
mixed: list[Union[str, int]] = ["a", 1]

# Tuple (fixed-length, typed)
point: tuple[str, int] = ("Alice", 30)

# Read-only sequence
from typing import Sequence
readonly_names: Sequence[str] = ["a", "b"]
TypeScript
// Array of strings (two equivalent syntaxes)
const names: string[] = ["Alice", "Bob"];
const names2: Array<string> = ["Alice", "Bob"];

// Array of mixed types
const mixed: (string | number)[] = ["a", 1];

// Tuple (fixed-length, typed)
const point: [string, number] = ["Alice", 30];

// Readonly array — no push/pop/splice
const readonlyNames: readonly string[] = ["a", "b"];
const readonlyNames2: ReadonlyArray<string> = ["a", "b"];

Tuples in Depth

TypeScript tuples are arrays where the type and position of each element is fixed. They're perfect for returning multiple values from a function — a pattern Python uses constantly.

// Basic tuple
const entry: [string, number] = ["Alice", 30];
const [name, age] = entry;  // destructuring works perfectly
// name: string, age: number

// Named tuples (TypeScript 4.0+) — same runtime, better docs
type UserEntry = [name: string, age: number, active: boolean];
const user: UserEntry = ["Alice", 30, true];

// Function returning a tuple — like Python's return a, b
function divide(a: number, b: number): [number, number] {
  return [Math.floor(a / b), a % b];  // [quotient, remainder]
}
const [quotient, remainder] = divide(17, 5);
// quotient: 3, remainder: 2

// Optional tuple elements (TypeScript 3.0+)
type HttpResponse = [status: number, body: string, headers?: Record<string, string>];

// Rest elements in tuples
type AtLeastOne = [string, ...string[]];
Py
Python Comparison: Return Tuples

In Python, returning multiple values from a function implicitly creates a tuple: return a, b. In TypeScript you must be explicit: return [a, b] with a return type of [TypeA, TypeB]. React hooks use this pattern constantly — const [count, setCount] = useState(0).

5 Objects and Type Aliases

In TypeScript, objects are the workhorse. Unlike Python's class-centric model, TypeScript encourages you to think in shapes — plain object types that describe the structure of data.

Python (TypedDict)
from typing import TypedDict, Optional

class User(TypedDict):
    name: str
    age: int

class UserOptional(TypedDict, total=False):
    name: str
    age: int  # optional

user: User = {"name": "Alice", "age": 30}
print(user["name"])  # "Alice"
TypeScript (type alias)
type User = {
  name: string;
  age: number;
};

type UserOptional = {
  name: string;
  age?: number;   // ? makes it optional
};

const user: User = { name: "Alice", age: 30 };
console.log(user.name);  // "Alice"

Optional and Readonly Properties

type Config = {
  readonly host: string;      // cannot be changed after creation
  readonly port: number;
  timeout?: number;           // optional — may be undefined
  retries?: number;           // optional
  debug: boolean;             // required
};

const config: Config = {
  host: "localhost",
  port: 3000,
  debug: false,
  // timeout and retries are optional — OK to omit
};

config.host = "example.com";  // ERROR: cannot assign to readonly property
config.debug = true;          // OK
config.timeout = 5000;        // OK — optional doesn't mean readonly

Excess Property Checking

One of TypeScript's most useful (and occasionally surprising) behaviors: when you assign an object literal directly to a typed variable, TypeScript checks for extra properties that don't exist in the type. This catches typos in config objects.

type Point = { x: number; y: number };

// DIRECT OBJECT LITERAL ASSIGNMENT — excess property check fires
const p: Point = { x: 1, y: 2, z: 3 };
// ERROR: Object literal may only specify known properties,
//        and 'z' does not exist in type 'Point'

// INDIRECT ASSIGNMENT — check does NOT fire (structural compat)
const raw = { x: 1, y: 2, z: 3 };
const p2: Point = raw;  // OK! raw has at least all the fields Point needs

// Why? Direct literals are likely bugs (typo "z" when you meant "y")
// Indirect assigns might be intentional subtyping
✓
Tip: Excess Property Checking in Practice

This is extremely useful for config objects and function options. If you pass { timeotu: 5000 } (typo!) to a function expecting { timeout: number }, TypeScript catches it at the call site. Python with TypedDict silently ignores the extra key.

Index Signatures

When you need a dictionary with arbitrary string keys (like Python's dict[str, int]), use an index signature:

// Index signature: any string key, number value
type ScoreMap = { [key: string]: number };

const scores: ScoreMap = {
  alice: 95,
  bob: 87,
  charlie: 92,
};

scores["diana"] = 88;     // OK
scores["eve"] = "great";  // ERROR: string not assignable to number

// Index signature + specific properties
type ApiResponse = {
  status: number;             // specific, required property
  message: string;            // specific, required property
  [key: string]: unknown;     // any other keys allowed (with unknown value)
};

// The built-in Record utility is cleaner for pure dictionaries
type ScoreMap2 = Record<string, number>;
type EnvVars = Record<string, string>;

6 Union and Intersection Types

Union and intersection types are where TypeScript's expressiveness really shines. They let you compose types in ways that are difficult or impossible in Python's type system.

Python
from typing import Union

# Python 3.9 style
def format_id(id: Union[str, int]) -> str:
    return str(id)

# Python 3.10+ style (pipe syntax)
def format_id2(id: str | int) -> str:
    return str(id)

# Literal types
from typing import Literal
Direction = Literal["left", "right", "up", "down"]

def move(dir: Direction) -> None:
    ...
TypeScript
// Union type: string OR number
function formatId(id: string | number): string {
  return String(id);
}

// Literal union — only these exact values
type Direction = "left" | "right" | "up" | "down";

function move(dir: Direction): void {
  // ...
}

move("left");    // OK
move("diagonal"); // ERROR: not in the union

Intersection Types

Intersection types combine multiple types into one. A value of an intersection type must satisfy all constituent types simultaneously. Python has no direct equivalent.

type Serializable = { serialize(): string };
type Loggable    = { log(): void };

// Intersection: must have BOTH serialize() AND log()
type SerializableLogger = Serializable & Loggable;

// Common pattern: merging object types
type BaseUser = { id: string; name: string };
type AdminFields = { permissions: string[]; role: "admin" };
type AdminUser = BaseUser & AdminFields;

const admin: AdminUser = {
  id: "u1",
  name: "Alice",
  permissions: ["read", "write", "delete"],
  role: "admin",
};

Type Narrowing

When you have a union type, TypeScript requires you to narrow it before accessing type-specific properties. This is the mechanism that makes union types safe.

function process(value: string | number): string {
  // value could be either type here — we must narrow
  if (typeof value === "string") {
    // Inside here, TypeScript knows: value is string
    return value.toUpperCase();
  } else {
    // Inside here, TypeScript knows: value is number
    return value.toFixed(2);
  }
}

// instanceof narrowing for classes
function logError(err: Error | string): void {
  if (err instanceof Error) {
    console.error(err.message);  // err is Error
  } else {
    console.error(err);          // err is string
  }
}

// Discriminated unions — the TypeScript superpower
type Shape =
  | { kind: "circle";    radius: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle";  base: number;  height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":    return Math.PI * shape.radius ** 2;
    case "rectangle": return shape.width * shape.height;
    case "triangle":  return 0.5 * shape.base * shape.height;
  }
}
AI
AI Era: Discriminated Unions for LLM Responses

When working with AI APIs, you often handle multiple response types: success, error, stream chunk, tool call. Discriminated unions are perfect here — model each variant with a type or kind field, then narrow in a switch. TypeScript will tell you if you forget to handle a new response variant.

7 The null and undefined Problem

TypeScript has two "nothing" values, and they mean different things. This confuses Python developers, who have only None.

ValueMeaningPython EquivalentCommon Source
null Intentional absence. Programmer says "there's nothing here." None Explicit assignments, database records with no value
undefined Uninitialized. Variable declared but never set. Missing key. no equivalent Unset variables, missing object properties, function params not passed 
let x: string | undefined;  // declared, not assigned
console.log(x);              // undefined

const obj = { a: 1 };
console.log(obj.b);          // undefined — key doesn't exist

// null must be explicitly assigned
let y: string | null = null;  // intentional: "no string right now"

// With strictNullChecks on, TypeScript tracks both
function getUser(id: string): User | null {
  // returns null if user not found — intentional absence
  return db.find(id) ?? null;
}

Always Enable strictNullChecks

With strictNullChecks: false (the old default), null and undefined are assignable to every type. You lose all protection. Always use strict: true in your tsconfig.json.

// With strict: true (strictNullChecks enabled)
let name: string = null;  // ERROR: null not assignable to string
let age: number = undefined;  // ERROR: undefined not assignable to number

// To allow null/undefined, you must say so explicitly
let name2: string | null = null;     // OK
let age2: number | undefined;        // OK
let value: string | null | undefined; // OK — both allowed

Optional Chaining and Nullish Coalescing

TypeScript (and modern JavaScript) ships two operators that obliterate null/undefined boilerplate.

Python
user = get_user(user_id)

# Verbose null checks
city = None
if user is not None:
    if user.address is not None:
        city = user.address.city

# Python 3.8 walrus + or for default
name = user.name if user else "Anonymous"
TypeScript
const user = getUser(userId);

// Optional chaining: ?. short-circuits on null/undefined
const city = user?.address?.city;
// If user is null/undefined, city = undefined
// No crash, no verbose if-chains

// Nullish coalescing: ?? returns right side if left is null/undefined
const name = user?.name ?? "Anonymous";
// user?.name is undefined? → "Anonymous"
// user?.name is "" (empty string)? → "" (not "Anonymous"!)
// ?? only short-circuits on null/undefined, not falsy values
i
?? vs ||

Don't confuse ?? (nullish coalescing) with || (logical OR). The || operator returns the right side for any falsy value: "", 0, false, null, undefined. The ?? operator only triggers for null and undefined. Use ?? when you want to allow empty strings or zero as valid values.

8 The any, unknown, and never Trinity

Three special types govern TypeScript's escape hatches and type system completeness. Understanding them deeply separates TypeScript beginners from engineers.

any: The Escape Hatch

// any turns off all type checking for that value
let x: any = "hello";
x = 42;           // OK
x = { a: 1 };    // OK
x.toUpperCase();  // OK (at compile time) — crashes at runtime if x is 42
x.nonExistent();  // OK (at compile time) — lies!

// any spreads like a virus
function parse(raw: any): any {
  return raw.data;  // any — TypeScript can't help you here
}
const result = parse(input);
result.user.name;  // any — you're on your own
!
Warning: any Is Contagious

Once a value is any, any operation on it produces any. The infection spreads through your codebase silently. Prefer unknown for values you don't know the type of — it forces you to narrow before use.

unknown: The Safe any

// unknown: you don't know what it is, and TypeScript won't let you
// pretend you do — you MUST check first
function processInput(input: unknown): string {
  // Can't call methods or access properties without narrowing
  input.toUpperCase();  // ERROR: Object is of type 'unknown'

  // Must narrow first
  if (typeof input === "string") {
    return input.toUpperCase();  // OK — narrowed to string
  }
  if (typeof input === "number") {
    return input.toFixed(2);     // OK — narrowed to number
  }
  return String(input);          // fallback
}

// unknown is perfect for:
// - API responses you haven't validated yet
// - User input
// - JSON.parse() results (which TypeScript types as any — use unknown instead)
function safeJsonParse(json: string): unknown {
  return JSON.parse(json);
}

never: The Bottom Type

// Functions that never return have return type never
function throwError(message: string): never {
  throw new Error(message);
  // TypeScript knows: code after this is unreachable
}

function infiniteLoop(): never {
  while (true) { /* ... */ }
}

// never is used for exhaustive checks — the TypeScript superpower
type Color = "red" | "green" | "blue";

function handleColor(color: Color): string {
  switch (color) {
    case "red":   return "#FF0000";
    case "green": return "#00FF00";
    case "blue":  return "#0000FF";
    default:
      // If you add "yellow" to Color but forget to handle it here,
      // TypeScript will error on this line — exhaustive check!
      const _exhaustive: never = color;
      throw new Error(`Unhandled color: ${color}`);
  }
}
AI
AI Era: Exhaustive Checks for Event Handling

When building AI agents or LLM pipelines, you often handle a finite set of event types (tool calls, messages, errors, completions). Using never for exhaustive checks means adding a new event type to your SDK will break compilation at every unhandled switch — catching bugs before they reach production.

When any Is Acceptable

// 1. Migrating a JavaScript codebase — temporary
//    (mark with a TODO to fix later)
const legacyData: any = getLegacyApiResponse();  // TODO: type this properly

// 2. Third-party library with broken/missing types
const result: any = badlyTypedLibrary.doSomething();

// 3. Prototype code you plan to type later
// (but actually: just use unknown — it's just as easy)

// BETTER: Use unknown instead of any in almost all cases
const apiResponse: unknown = await fetch(url).then(r => r.json());
// Force yourself to validate before using

9 Type Aliases vs. Interfaces (Preview)

TypeScript has two ways to name an object type: type aliases and interface declarations. Chapter 5 covers them exhaustively. Here's the 30-second version.

// type alias — works for any type, not just objects
type UserId = string;
type Status = "active" | "inactive" | "banned";
type User = {
  id: UserId;
  name: string;
  status: Status;
};

// interface — only for object shapes, but supports declaration merging
interface User {
  id: string;
  name: string;
}

// interface can be extended (opened) later — type alias cannot
interface User {
  status: string;  // merged into the existing User interface
}
Featuretypeinterface
Object shapesYesYes
Primitive aliases (type ID = string)YesNo
Union types (A | B)YesNo
Intersection types (A & B)YesVia extends
Declaration merging (add fields later)NoYes
Implements in classesYesYes
Recursive typesYes (with caveats)Yes
✓
The 30-Second Rule

Use type by default. Switch to interface when you need declaration merging (common when augmenting third-party library types) or when building a public library API where consumers might want to extend your types. For application code, type covers 90% of cases cleanly.

10 Exercises

Five exercises converting Python-typed code to TypeScript. Each exercise builds on the concepts from this chapter. Try each one before revealing the solution.

EX 01 Primitive Type Translation

Translate the following Python function signature and variables to TypeScript. The function takes a user's name (string), age (int), and score (float) and returns whether they qualify (bool). Include type annotations for all variables and the function.

def qualify(name: str, age: int, score: float) -> bool:
    return age >= 18 and score >= 7.5

player_name: str = "Alice"
player_age: int = 22
player_score: float = 8.3
result: bool = qualify(player_name, player_age, player_score)

function qualify(name: string, age: number, score: number): boolean {
  return age >= 18 && score >= 7.5;
}

const playerName: string = "Alice";
const playerAge: number = 22;
const playerScore: number = 8.3;
const result: boolean = qualify(playerName, playerAge, playerScore);

// Better: let TypeScript infer the variable types
const playerName2 = "Alice";    // inferred: string
const playerAge2 = 22;          // inferred: number
const playerScore2 = 8.3;       // inferred: number
