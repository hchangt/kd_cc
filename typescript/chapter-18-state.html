1 The State Management Landscape

State management is where frontend applications go to die — or thrive. Choose the wrong tool and you're drowning in boilerplate, fighting TypeScript, and debugging stale data. Choose correctly and your app practically writes itself.

The first rule: not all state is the same. Treating every piece of application state as equivalent is the original sin that leads to Redux stores full of API responses sitting next to UI toggle flags.

Start with useState

Before reaching for anything else: is this state truly needed beyond a single component? useState is underrated. It has zero overhead, perfect type inference, and the React team has been optimizing it for years. Use it for:

  • Toggle flags (isOpen, isEditing)
  • Form field values (ideally via react-hook-form)
  • Transient UI states (hover, focus, animation in progress)
  • Component-scoped counters or selections
💡
Tip

If you're reaching for global state because "I might need it somewhere else later," stop. Collocate state as close to where it's used as possible. Premature globalization is a real cost.

When You Actually Need Global State

Global state is justified when:

  • Multiple unrelated components need the same data
  • State needs to survive route navigation
  • You need shared user session / auth state
  • Feature flags, theme, locale preferences

The Problem with Redux (2016–2022)

Redux is not bad technology. It is expensive technology. Its verbosity was acceptable when the alternatives were worse. Today:

  • Actions, action creators, reducers, selectors — four files for one feature
  • TypeScript integration was bolted on, not designed in
  • No built-in solution for server state (RTK Query came late)
  • The connect() HOC pattern aged poorly
  • Bundle size overhead for simple apps
⚠️
Warning

Redux is still the right choice for very large teams (20+ engineers) who need strict conventions, time-travel debugging, and a long history of tooling. The ecosystem around Redux DevTools is unmatched. But most new projects should start elsewhere.

The Modern Alternatives

2 Client State vs. Server State

This distinction is the most important concept in this chapter. If you understand nothing else, understand this.

Figure 18-1 — Client State vs. Server State

Why Server State Is Different

Server state has unique properties that client state does not:

  • Remote ownership — the database owns the truth, not your app
  • Staleness — it can become outdated between fetches
  • Async by nature — always involves loading, error, and success states
  • Shared across tabs — invalidating a cache in one tab should propagate
  • Deduplication — 10 components requesting the same endpoint shouldn't fire 10 requests
  • Background refetching — data should refresh when the window regains focus
🚫
Anti-Pattern — Server State in Zustand

The classic mistake: fetching data in a useEffect, storing it in a Zustand store, and manually managing loading/error/stale states. You're reimplementing TanStack Query, badly.

This approach misses caching, deduplication, background refetching, stale-while-revalidate, and proper error retry logic. Every team that does this eventually rebuilds TanStack Query from scratch.

The Recommended Architecture

✅
Pattern — Separate Concerns
  • TanStack Query for all server state (API data)
  • Zustand or Jotai for client state (UI state, preferences)
  • useState for local/component-scoped state
  • URL state (nuqs) for shareable/bookmarkable state
  • react-hook-form for form state

3 Zustand — Simple Global State

Zustand is the result of asking: "What if Redux, but without all of Redux?" Created by the Pmndrs collective (same team behind Jotai, Valtio, and React Spring), it achieves remarkable simplicity without sacrificing power.
$ pnpm add zustand

Basic Store with TypeScript

Zustand stores are defined with create, which takes a callback receiving set (and optionally get) and returns the initial state + actions. TypeScript inference flows through the entire store if you define an interface first.

TypeScript store/user.store.ts 
import { create } from 'zustand'

interface User {
  id: string
  name: string
  email: string
  role: 'admin' | 'member' | 'guest'
}

interface UserStore {
  user: User | null
  isAuthenticated: boolean
  setUser: (user: User | null) => void
  updateRole: (role: User['role']) => void
  logout: () => void
}

export const useUserStore = create<UserStore>()((set, get) => ({
  user: null,
  isAuthenticated: false,

  setUser: (user) =>
    set({ user, isAuthenticated: user !== null }),

  updateRole: (role) => {
    const { user } = get()
    if (!user) return
    set({ user: { ...user, role } })
  },

  logout: () => set({ user: null, isAuthenticated: false }),
}))
ℹ️
Why create<UserStore>()() — Double Call?

The curried form create<T>()() is required to enable full TypeScript inference while also allowing middleware to be composed. Without it, TypeScript cannot infer the generic parameter correctly when middleware is in play. It's an intentional design decision by the Zustand team.

Using the Store in Components

TypeScript components/UserMenu.tsx 
import { useUserStore } from '@/store/user.store'

// ✅ Selector pattern — subscribe only to what you need
// Component only re-renders when `user` changes
function UserMenu() {
  const user = useUserStore((s) => s.user)
  const logout = useUserStore((s) => s.logout)

  if (!user) return <LoginButton />

  return (
    <div>
      <p>{user.name}</p>
      <button onClick={logout}>Logout</button>
    </div>
  )
}

// ❌ Avoid subscribing to the whole store
function BadUserMenu() {
  // This re-renders on ANY store change
  const store = useUserStore()
  return <div>{store.user?.name}</div>
}

Async Actions

Zustand actions are plain functions — there is no special middleware required for async. Just call set after your promise resolves.

TypeScript store/cart.store.ts 
interface CartStore {
  items: CartItem[]
  isLoading: boolean
  error: string | null
  addItem: (productId: string, qty: number) => Promise<void>
  removeItem: (itemId: string) => void
}

export const useCartStore = create<CartStore>()((set, get) => ({
  items: [],
  isLoading: false,
  error: null,

  addItem: async (productId, qty) => {
    set({ isLoading: true, error: null })
    try {
      const item = await cartApi.add({ productId, qty })
      set((state) => ({
        items: [...state.items, item],
        isLoading: false,
      }))
    } catch (err) {
      set({
        error: err instanceof Error ? err.message : 'Failed to add item',
        isLoading: false,
      })
    }
  },

  removeItem: (itemId) =>
    set((state) => ({
      items: state.items.filter((i) => i.id !== itemId),
    })),
}))
⚠️
Warning — Don't Put Server State Here

This addItem action manually manages isLoading and error. If cart data comes from an API, use TanStack Query's useMutation instead. Only keep items in Zustand if cart state is purely client-side (e.g., guest cart that hasn't been saved yet).

Slices for Large Stores

When stores grow, split them into slices — separate files that are composed into a single store.

TypeScript store/slices/ui.slice.ts 
import { StateCreator } from 'zustand'
import type { RootStore } from '../root.store'

export interface UISlice {
  sidebarOpen: boolean
  theme: 'light' | 'dark' | 'system'
  toggleSidebar: () => void
  setTheme: (theme: UISlice['theme']) => void
}

export const createUISlice: StateCreator<RootStore, [], [], UISlice> = (set) => ({
  sidebarOpen: false,
  theme: 'system',
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),
  setTheme: (theme) => set({ theme }),
})
TypeScript store/root.store.ts 
import { create } from 'zustand'
import { createUISlice, UISlice } from './slices/ui.slice'
import { createUserSlice, UserSlice } from './slices/user.slice'
import { createNotifSlice, NotifSlice } from './slices/notif.slice'

export type RootStore = UISlice & UserSlice & NotifSlice

export const useStore = create<RootStore>()((...args) => ({
  ...createUISlice(...args),
  ...createUserSlice(...args),
  ...createNotifSlice(...args),
}))

Middleware: devtools, persist, immer

TypeScript store/settings.store.ts 
import { create } from 'zustand'
import { devtools, persist } from 'zustand/middleware'
import { immer } from 'zustand/middleware/immer'

interface SettingsStore {
  language: string
  notifications: boolean
  dashboardLayout: 'grid' | 'list'
  setLanguage: (lang: string) => void
  toggleNotifications: () => void
}

export const useSettingsStore = create<SettingsStore>()(
  devtools(
    persist(
      immer((set) => ({
        language: 'en',
        notifications: true,
        dashboardLayout: 'grid',

        setLanguage: (lang) =>
          set((state) => { state.language = lang }),

        toggleNotifications: () =>
          set((state) => {
            state.notifications = !state.notifications
          }),
      })),
      {
        name: 'user-settings',           // localStorage key
        partialize: (state) => ({        // only persist these fields
          language: state.language,
          notifications: state.notifications,
          dashboardLayout: state.dashboardLayout,
        }),
      }
    ),
    { name: 'SettingsStore' }            // devtools label
  )
)

Middleware composition order matters — outermost to innermost, the standard order is devtools → persist → immer → your store creator.

4 Jotai — Atomic State

Jotai takes its name from the Japanese word for "state" (状態). It brings Recoil's atom-based model to production without the Facebook-scale bundle overhead. Every piece of state is an atom; atoms compose into derived atoms; derived atoms are fine-grained reactive computations.
$ pnpm add jotai

Basic Atoms and Derived State

TypeScript atoms/counter.ts 
import { atom, useAtom, useAtomValue, useSetAtom } from 'jotai'

// Primitive atom — like useState but global
const countAtom = atom(0)

// Derived (read-only) atom — recomputes when countAtom changes
const doubleCountAtom = atom((get) => get(countAtom) * 2)

// Derived writable atom — reads from one, writes to another
const clampedCountAtom = atom(
  (get) => Math.max(0, Math.min(100, get(countAtom))),
  (_get, set, value: number) => set(countAtom, value)
)

function Counter() {
  const [count, setCount] = useAtom(countAtom)
  const double = useAtomValue(doubleCountAtom) // read-only, no setter

  return (
    <div>
      <p>Count: {count} | Double: {double}</p>
      <button onClick={() => setCount((c) => c + 1)}>Increment</button>
    </div>
  )
}

// Component that only needs to write — zero re-renders on count change
function ResetButton() {
  const setCount = useSetAtom(countAtom) // no re-renders!
  return <button onClick={() => setCount(0)}>Reset</button>
}

Async Atoms

TypeScript atoms/user.ts 
import { atom } from 'jotai'
import { atomWithStorage } from 'jotai/utils'

// Persist to localStorage
export const tokenAtom = atomWithStorage<string | null>('auth-token', null)

// Async atom — Jotai handles loading/error state via Suspense
export const currentUserAtom = atom(async (get) => {
  const token = get(tokenAtom)
  if (!token) return null
  return fetchCurrentUser(token)   // returns Promise<User | null>
})

// Atom family — parameterized atoms (like a "store" per id)
import { atomFamily } from 'jotai/utils'

export const postAtomFamily = atomFamily((postId: string) =>
  atom(async () => fetchPost(postId))
)

// Usage — each postId gets its own cached atom
function PostCard({ postId }: { postId: string }) {
  const post = useAtomValue(postAtomFamily(postId)) // throws Promise → Suspense
  return <article>{post.title}</article>
}
ℹ️
Jotai + Suspense

Async atoms in Jotai integrate with React Suspense. The component suspends while the atom's promise is pending. Wrap it in <Suspense fallback={...}> and <ErrorBoundary>. This is the recommended pattern — no manual loading state needed.

Jotai vs. Zustand — When to Pick Which

Choose Zustand when...

  • You want a single, inspectable store
  • You have many actions / business logic
  • Team prefers Redux-like mental model
  • You need devtools with time-travel
  • Actions need to read from multiple slices

Choose Jotai when...

  • Fine-grained updates matter (large lists)
  • Heavy use of derived/computed state
  • You like the atomic mental model
  • You're building a data-heavy dashboard
  • You need Suspense-native async handling

5 TanStack Query — Server State Management

TanStack Query (formerly React Query) is, in my opinion, the single highest-leverage library in the React ecosystem. It solves an entire category of bugs — stale data, double-fetching, loading state spaghetti — with essentially zero effort once it's set up.
$ pnpm add @tanstack/react-query @tanstack/react-query-devtools

Setup

TypeScript app/providers.tsx 
'use client'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { ReactQueryDevtools } from '@tanstack/react-query-devtools'
import { useState } from 'react'

export function Providers({ children }: { children: React.ReactNode }) {
  // Create QueryClient inside component to avoid sharing between requests
  const [queryClient] = useState(
    () =>
      new QueryClient({
        defaultOptions: {
          queries: {
            staleTime: 60 * 1000,        // 1 minute — tune per app
            gcTime: 5 * 60 * 1000,       // 5 minutes (was cacheTime in v4)
            retry: 1,
            refetchOnWindowFocus: true,
          },
        },
      })
  )

  return (
    <QueryClientProvider client={queryClient}>
      {children}
      <ReactQueryDevtools initialIsOpen={false} />
    </QueryClientProvider>
  )
}

useQuery with Full TypeScript Typing

TypeScript hooks/useUsers.ts 
import { useQuery, keepPreviousData } from '@tanstack/react-query'

interface User { id: string; name: string; email: string }

interface UsersParams {
  page: number
  search: string
  role?: 'admin' | 'member'
}

// ✅ Separate query fn — testable, reusable, typed
async function fetchUsers(params: UsersParams): Promise<{ users: User[]; total: number }> {
  const url = new URL('/api/users', window.location.origin)
  url.searchParams.set('page', String(params.page))
  url.searchParams.set('search', params.search)
  if (params.role) url.searchParams.set('role', params.role)

  const res = await fetch(url)
  if (!res.ok) throw new Error(`Failed to fetch users: ${res.statusText}`)
  return res.json()
}

export function useUsers(params: UsersParams) {
  return useQuery({
    // Query key — array identifies this data. Any change causes a re-fetch.
    queryKey: ['users', params],
    queryFn: () => fetchUsers(params),
    staleTime: 5 * 60 * 1000,           // data fresh for 5 minutes
    placeholderData: keepPreviousData,  // keeps old data while fetching new page
  })
}

// In component:
function UserList({ page, search }: { page: number; search: string }) {
  const { data, isLoading, isError, error, isFetching } = useUsers({ page, search })

  if (isLoading) return <Skeleton />
  if (isError) return <Error message={error.message} />

  return (
    <div>
      {isFetching && <RefreshIndicator />}
      {data.users.map((u) => <UserRow key={u.id} user={u} />)}
    </div>
  )
}

useMutation for Writes

TypeScript hooks/useCreateUser.ts 
import { useMutation, useQueryClient } from '@tanstack/react-query'

interface CreateUser {
  name: string
  email: string
  role: 'admin' | 'member'
}

interface User extends CreateUser {
  id: string
  createdAt: string
}

async function createUser(data: CreateUser): Promise<User> {
  const res = await fetch('/api/users', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data),
  })
  if (!res.ok) throw new Error(await res.text())
  return res.json()
}

export function useCreateUser() {
  const queryClient = useQueryClient()

  return useMutation({
    mutationFn: createUser,

    // Optimistic update — update cache before server responds
    onMutate: async (newUser) => {
      await queryClient.cancelQueries({ queryKey: ['users'] })
      const previous = queryClient.getQueryData(['users'])

      queryClient.setQueryData(['users'], (old: any) => ({
        ...old,
        users: [...(old?.users ?? []), { ...newUser, id: 'temp-' + Date.now() }],
      }))

      return { previous }    // context for rollback
    },

    // On success: invalidate so real data is fetched
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['users'] })
    },

    // On error: roll back optimistic update
    onError: (_err, _vars, context) => {
      if (context?.previous) {
        queryClient.setQueryData(['users'], context.previous)
      }
    },
  })
}

// Usage
function CreateUserForm() {
  const { mutate, isPending, isError, error } = useCreateUser()

  function handleSubmit(data: CreateUser) {
    mutate(data, {
      onSuccess: () => toast.success('User created!'),
    })
  }

  return (
    <form onSubmit={handleSubmit}>
      {isError && <Alert>{error.message}</Alert>}
      <button disabled={isPending}>
        {isPending ? 'Creating...' : 'Create User'}
      </button>
    </form>
  )
}

Infinite Queries (Pagination / Infinite Scroll)

TypeScript hooks/useInfinitePosts.ts 
import { useInfiniteQuery } from '@tanstack/react-query'

export function useInfinitePosts() {
  return useInfiniteQuery({
    queryKey: ['posts', 'infinite'],
    queryFn: ({ pageParam }) => fetchPosts({ cursor: pageParam as string | undefined }),
    initialPageParam: undefined as string | undefined,
    getNextPageParam: (lastPage) => lastPage.nextCursor,

}

function PostFeed() {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfinitePosts()

  return (
    <div>
      {data?.pages.flatMap((p) => p.posts).map((post) => (
        <PostCard key={post.id} post={post} />
      ))}
      {hasNextPage && (
        <button onClick={() => fetchNextPage()} disabled={isFetchingNextPage}>
          {isFetchingNextPage ? 'Loading...' : 'Load more'}
        </button>
      )}
    </div>
  )
}

Prefetching on Hover

TypeScript components/UserLink.tsx 
import { useQueryClient } from '@tanstack/react-query'

function UserLink({ userId, children }: { userId: string; children: React.ReactNode }) {
  const queryClient = useQueryClient()

  return (
    <a
      href={`/users/${userId}`}
      onMouseEnter={() =>
        queryClient.prefetchQuery({
          queryKey: ['users', userId],
          queryFn: () => fetchUser(userId),
          staleTime: 10_000, // skip if cached within 10s
        })
      }
    >
      {children}
    </a>
  )
}

AI Era — Query Key Factories

As AI-assisted development generates more useQuery calls, query key consistency becomes critical. Use a query key factory pattern to prevent key drift across a large codebase:

TypeScript lib/queryKeys.ts 
// Centralize all query keys — AI tools always reference this file
export const queryKeys = {
  users: {
    all: ['users'] as const,
    lists: () => [...queryKeys.users.all, 'list'] as const,
    list: (params: UsersParams) => [...queryKeys.users.lists(), params] as const,
    details: () => [...queryKeys.users.all, 'detail'] as const,
    detail: (id: string) => [...queryKeys.users.details(), id] as const,
  },
  posts: {
    all: ['posts'] as const,
    list: (params: PostsParams) => ['posts', 'list', params] as const,
    detail: (id: string) => ['posts', 'detail', id] as const,
  },
} as const

// Usage:
useQuery({ queryKey: queryKeys.users.detail(userId), queryFn: () => fetchUser(userId) })

// Invalidate all user queries:
queryClient.invalidateQueries({ queryKey: queryKeys.users.all })

6 SWR — Vercel's Alternative

I helped ship SWR at Vercel. It's a brilliant, minimal library that pioneered the stale-while-revalidate caching strategy for React. The name comes directly from the HTTP Cache-Control RFC.

$ pnpm add swr
TypeScript hooks/useUser.ts 
import useSWR from 'swr'

const fetcher = (url: string) => fetch(url).then((r) => r.json())

interface User { id: string; name: string; email: string }

function useUser(id: string) {
  const { data, error, isLoading, mutate } = useSWR<User>(`/api/users/${id}`, fetcher, {
    revalidateOnFocus: true,
    dedupingInterval: 2000,  // deduplicate requests within 2s
  })

  return { user: data, error, isLoading, refresh: mutate }
}

SWR vs. TanStack Query

Feature SWR TanStack Query
Bundle size ~4 KB ~13 KB
Mutations Manual via mutate() useMutation with full lifecycle
Optimistic updates Supported First-class, with rollback context
Infinite query useSWRInfinite useInfiniteQuery
DevTools None (community) Official DevTools
SSR / Next.js First-class fallbackData First-class hydration
Query cancellation Manual Built-in
Best for Simple read-heavy apps, Next.js Complex data requirements
💡
My Take

SWR is excellent for read-heavy apps — especially with Next.js, where the two are designed to complement each other. The moment you need robust mutation handling, optimistic updates with rollback, or a DevTools panel for debugging, TanStack Query wins. For most non-trivial apps: go with TanStack Query.

7 Redux Toolkit — Legacy, Still Important

Redux Toolkit (RTK) is Redux done right. It was the Redux team's answer to the boilerplate criticism — and it's a substantial improvement. If you're working in an existing Redux codebase or joining a large team with existing Redux infrastructure, you'll encounter RTK.

$ pnpm add @reduxjs/toolkit react-redux

Modern Redux with TypeScript

TypeScript store/auth.slice.ts 
import { createSlice, PayloadAction } from '@reduxjs/toolkit'

interface AuthState {
  user: User | null
  token: string | null
  status: 'idle' | 'loading' | 'succeeded' | 'failed'
  error: string | null
}

const initialState: AuthState = {
  user: null, token: null, status: 'idle', error: null,
}

export const authSlice = createSlice({
  name: 'auth',
  initialState,
  reducers: {
    setCredentials: (state, action: PayloadAction<{ user: User; token: string }>) => {
      state.user = action.payload.user
      state.token = action.payload.token
      state.status = 'succeeded'
    },
    logout: (state) => {
      state.user = null
      state.token = null
      state.status = 'idle'
    },
  },
})

export const { setCredentials, logout } = authSlice.actions
export default authSlice.reducer
TypeScript store/index.ts 
import { configureStore } from '@reduxjs/toolkit'
import { TypedUseSelectorHook, useDispatch, useSelector } from 'react-redux'
import authReducer from './auth.slice'

export const store = configureStore({
  reducer: {
    auth: authReducer,
  },
})

// Typed hooks — always use these, never raw useSelector/useDispatch
export type RootState = ReturnType<typeof store.getState>
export type AppDispatch = typeof store.dispatch
export const useAppDispatch = () => useDispatch<AppDispatch>()
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector

When You Might Still Need Redux

  • 20+ engineers who need enforced conventions and code review guardrails
  • Time-travel debugging — Redux DevTools is genuinely unmatched here
  • Existing large Redux codebase — migration cost may not be justified
  • Strict audit requirements — action log gives you a complete state mutation history

Migrating from Redux to Zustand

The migration path is incremental. You can run both side-by-side during transition:

  1. Identify slices that handle server state — move those to TanStack Query first
  2. For remaining client-state slices, create equivalent Zustand stores
  3. Replace useAppSelector calls with Zustand selectors per-component
  4. Once a slice is fully migrated, delete the Redux slice
  5. Remove Redux when the last slice is gone

8 URL State

URL is the most underused state container in React apps. State in the URL is:

  • Shareable — send a link, recipient sees the same thing
  • Bookmarkable — users can save their filtered view
  • Back-button-safe — browser history handles it for free
  • SSR-compatible — server can read it without hydration

Native: useSearchParams

TypeScript components/SearchFilters.tsx 
'use client'
import { useSearchParams, useRouter, usePathname } from 'next/navigation'

function SearchFilters() {
  const searchParams = useSearchParams()
  const router = useRouter()
  const pathname = usePathname()

  const page = Number(searchParams.get('page') ?? '1')
  const search = searchParams.get('search') ?? ''

  function setParam(key: string, value: string) {
    const params = new URLSearchParams(searchParams.toString())
    params.set(key, value)
    router.push(`${pathname}?${params.toString()}`)
  }

  return (
    <div>
      <input value={search} onChange={(e) => setParam('search', e.target.value)} />
      <button onClick={() => setParam('page', String(page + 1))}>Next</button>
    </div>
  )
}

nuqs — Typed URL State

The nuqs library gives you typed, validated, serializable URL state with an API that mirrors useState. It's one of those libraries that makes you wonder how you ever lived without it.

TypeScript components/ProductList.tsx 
'use client'
import {
  useQueryState,
  useQueryStates,
  parseAsInteger,
  parseAsString,
  parseAsStringEnum,
} from 'nuqs'

function ProductList() {
  // Fully typed, validated, serialized from/to URL
  const [page, setPage] = useQueryState('page', parseAsInteger.withDefault(1))
  const [search, setSearch] = useQueryState('search', parseAsString.withDefault(''))
  const [sort, setSort] = useQueryState(
    'sort',
    parseAsStringEnum(['price_asc', 'price_desc', 'newest']).withDefault('newest')
  )

  // Batch multiple updates — single navigation event
  const [filters, setFilters] = useQueryStates({
    minPrice: parseAsInteger,
    maxPrice: parseAsInteger,
    category: parseAsString,
  })

  return (
    <div>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      {/* sort is typed as 'price_asc' | 'price_desc' | 'newest' */}
      <SortSelect value={sort} onChange={setSort} />
      <Pagination page={page} onPageChange={setPage} />
    </div>
  )
}

9 Form State

Form state deserves its own treatment because it's where many developers make state architecture mistakes. The core principle: form state is local state.

🚫
Anti-Pattern — Form State in Global Store

Putting form field values into Zustand or Redux is an extremely common anti-pattern. You'll see it in large codebases where developers incorrectly treat "state" as a synonym for "global state."

Problems: synchronization bugs when the form unmounts, unnecessary re-renders across the app on every keystroke, and improperly reset state when the form is reused. Use react-hook-form instead.

We covered react-hook-form in Chapter 16. The key points for state architecture:

  • react-hook-form uses uncontrolled components internally — no re-render per keystroke
  • The formState lives inside the library's ref, not in React state
  • On submit, extract values and hand off to a TanStack Query useMutation
  • The form's state is discarded on unmount automatically
TypeScript components/CreatePostForm.tsx 
'use client'
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'
import { useCreatePost } from '@/hooks/useCreatePost'  // useMutation wrapper

const schema = z.object({
  title: z.string().min(1).max(100),
  body: z.string().min(10),
  tags: z.array(z.string()).min(1),
})

type FormValues = z.infer<typeof schema>

export function CreatePostForm() {
  // ✅ Form state stays local via react-hook-form
  const { register, handleSubmit, reset, formState: { errors } } = useForm<FormValues>({
    resolver: zodResolver(schema),
  })

  // ✅ Server write state in TanStack Query mutation
  const createPost = useCreatePost()

  const onSubmit = (data: FormValues) => {
    createPost.mutate(data, {
      onSuccess: () => {
        reset()           // clear form
        toast.success('Post created!')
      },
    })
  }

  return <form onSubmit={handleSubmit(onSubmit)}>...</form>
}

10 State Management Patterns

State Colocation

Put state as close to where it's used as possible. This is the most violated principle in large applications.

  • Single-component state → useState in that component
  • Shared by siblings → lift to their closest common ancestor
  • Needed across many unrelated components → global store
  • Needed across route changes → URL state or persistent store

Context vs. Global State

React Context is often misused as a global state solution. It has a critical limitation: every consumer re-renders when any part of the context value changes. For rapidly-changing values (user typing, mouse position, animation), this causes serious performance issues.

Use Context for...

  • Infrequently-changing values (theme, locale)
  • Dependency injection (passing services down)
  • Component library internal state
  • Configuration that rarely changes

Use Zustand/Jotai for...

  • Frequently-changing global state
  • State with multiple independent consumers
  • State with complex update logic
  • State that needs fine-grained subscriptions

Performance: Selectors

The most common Zustand performance bug: subscribing to the whole store instead of selecting slices.

TypeScript Selector patterns 
// ❌ Re-renders on every store change
const everything = useStore()

// ✅ Re-renders only when `user.name` changes
const userName = useStore((s) => s.user?.name)

// ✅ Re-renders only when the specific cart item changes
const itemQty = useStore((s) => s.cart.items.find(i => i.id === itemId)?.qty)

// ✅ Memoized derived value — stable reference
const totalItems = useStore(
  useShallow((s) => s.cart.items.reduce((sum, i) => sum + i.qty, 0))
)
