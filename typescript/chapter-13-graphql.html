1. What is GraphQL?

I joined Facebook's infrastructure team in 2012. The mobile apps were in trouble. The existing REST APIs were designed for the web — they returned enormous JSON blobs that made Android and iOS engineers furious. Every new feature required a new endpoint, a new team meeting, and at least two weeks of back-and-forth on what the response shape should be. The real-time News Feed alone had dozens of overlapping endpoints that nobody fully understood.

Lee Byron, Nick Schrock, and Dan Schafer set out to fix this. They built a query language that let clients ask for exactly the data they needed — no more, no less. Internally it shipped in 2012. By 2015 it was open-sourced under the name GraphQL.

ℹ️ The GraphQL Specification

GraphQL is a specification, not an implementation. The spec defines the type system, query language, and execution model. Any language can implement it. The spec lives at spec.graphql.org and is governed by the GraphQL Foundation (Linux Foundation).

The Problem with REST

REST APIs suffer from two structural problems:

  • Over-fetching: GET /users/42 returns 40 fields. You only need name and avatar. The rest is wasted bandwidth and parsing.
  • Under-fetching (N+1 at the HTTP layer): You fetch a user, then fetch their posts, then fetch each post's comments. Three waterfall round trips for data that is logically connected.

GraphQL solves both with a single mechanism: the client declares a query.

GraphQL A single GraphQL query vs three REST calls 
# Instead of GET /users/42 + GET /users/42/posts + GET /posts/1/comments
query GetUserWithContent {
  user(id: "42") {
    name
    avatar
    posts(limit: 5) {
      title
      publishedAt
      comments(limit: 3) {
        body
        author { name }
      }
    }
  }
}

The Query Language

GraphQL has three operation types:

  • Query — read-only data fetching. Analogous to GET.
  • Mutation — data writes and side effects. Analogous to POST/PUT/DELETE.
  • Subscription — long-lived connection for real-time data. Typically WebSocket-backed.
◈ GraphQL Concept: Schema-First vs Code-First

Schema-first: You write SDL (.graphql files), then generate types and wire up resolvers. Tools like graphql-codegen generate TypeScript from your SDL.

Code-first: You write TypeScript/JavaScript that produces the schema at runtime. Tools like Pothos and Nexus do this. The SDL is a derived artifact.

Both approaches produce an identical runtime schema. The choice is about developer workflow. This chapter covers both — Pothos for code-first (recommended for TypeScript), codegen for schema-first.

REST vs GraphQL: When to Use Which

Criterion REST GraphQL
Multiple client types (web, mobile, IoT) Painful — different payload needs Excellent — each client queries what it needs
Simple CRUD API Simple, well-understood Overhead not worth it
Public/third-party API HTTP caching, CDN, familiarity POST-based, harder to cache publicly
Complex, graph-shaped data Waterfall requests First-class traversal
Real-time needs SSE/WebSocket bolted on Native subscriptions
File uploads Multipart, battle-tested Requires separate spec (graphql-multipart-request-spec)
Rapid iteration, product teams Versioning friction Add fields, deprecate old — no versions
Microservices / federation API gateway complexity Apollo Federation, schema stitching

2. GraphQL Concepts

Schema Definition Language (SDL)

The SDL is the lingua franca of GraphQL. Even if you use a code-first approach, understanding SDL is essential for reading documentation, debugging, and communicating with other teams.

GraphQL SDL schema.graphql — a blog API 
# Scalars: Int, Float, String, Boolean, ID (built-in)
# Custom scalar
scalar DateTime

enum PostStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!
  createdAt: DateTime!
}

type Post {
  id: ID!
  title: String!
  body: String!
  status: PostStatus!
  author: User!
  tags: [String!]!
  publishedAt: DateTime
}

# Input type — used in mutations
input CreatePostInput {
  title: String!
  body: String!
  tags: [String!]
}

# Root Query type — all read operations
type Query {
  me: User
  user(id: ID!): User
  posts(status: PostStatus, limit: Int = 10): [Post!]!
  post(id: ID!): Post
}

# Root Mutation type
type Mutation {
  createPost(input: CreatePostInput!): Post!
  publishPost(id: ID!): Post!
  deletePost(id: ID!): Boolean!
}

# Real-time
type Subscription {
  postPublished: Post!
}

Resolvers

A resolver is a function that returns the data for a single field. Every field in a GraphQL schema can have a resolver. If it doesn't, GraphQL falls back to a default resolver that reads the property with the same name from the parent object.

◈ GraphQL Concept: The Resolver Chain

GraphQL executes a query by walking the selection set depth-first. For a query like user { posts { author { name } } }, it calls:

  1. Query.user resolver → returns a User object
  2. User.posts resolver (parent = User) → returns Post[]
  3. Post.author resolver (parent = Post) → returns User
  4. User.name → default resolver reads parent.name

Each resolver receives: (parent, args, context, info).

Context

Context is a plain object created once per request and passed to every resolver. It is the correct place for: authenticated user, database connections, DataLoader instances, and request-scoped caches. Never put mutable global state in context.

DataLoaders — Preview

DataLoader batches and caches calls to data sources within a single request. It is the primary solution to the N+1 resolver problem. Full coverage in Section 8.

3. Building a GraphQL Server with Pothos

Pothos is the library I reach for first when building a new GraphQL server in TypeScript. It is code-first, requires zero code generation, and achieves full end-to-end type safety using TypeScript's type system alone. Your schema definition is the type definition.

✅ Why Pothos over SDL + codegen for new projects

With code generation, your types are always one pnpm codegen away from being stale. With Pothos, the TypeScript compiler enforces correctness at every keystroke. Refactoring a field name is a compile error, not a silent mismatch between SDL and resolver.

Installation and SchemaBuilder Setup

shell 
pnpm add @pothos/core graphql graphql-yoga
pnpm add -D @types/node typescript
TypeScript src/schema/builder.ts 
import SchemaBuilder from '@pothos/core';

// The generic parameter defines types available throughout the schema:
// - Context: the per-request context object shape
// - Objects: a map from object type name to its backing TypeScript type
interface SchemaTypes {
  Context: {
    userId: string | null;
    db: PrismaClient;
  };
  Objects: {
    User: User;
    Post: Post;
  };
  Scalars: {
    DateTime: { Input: Date; Output: Date };
  };
}

export const builder = new SchemaBuilder<SchemaTypes>({});

Defining Object Types, Queries, and Mutations

TypeScript src/schema/user.ts 
import { builder } from './builder';

// Register the User object type.
// Pothos links this to the `User` backing type from SchemaTypes.Objects.
builder.objectType('User', {
  description: 'A registered user in the system',
  fields: (t) => ({
    id: t.exposeID('id'),
    name: t.exposeString('name'),
    email: t.exposeString('email'),
    // Computed field — not on the DB model
    displayName: t.string({
      resolve: (user) => `${user.name} (${user.email})`,
    }),
    // Nested type with its own resolver
    posts: t.field({
      type: ['Post'],
      resolve: async (user, _args, ctx) => {
        return ctx.db.post.findMany({
          where: { authorId: user.id },
        });
      },
    }),
  }),
});

// Root-level Query fields for User
builder.queryFields((t) => ({
  me: t.field({
    type: 'User',
    nullable: true,
    resolve: (_root, _args, ctx) => {
      if (!ctx.userId) return null;
      return ctx.db.user.findUnique({ where: { id: ctx.userId } });
    },
  }),

  user: t.field({
    type: 'User',
    nullable: true,
    args: { id: t.arg.id({ required: true }) },
    resolve: (_root, args, ctx) =>
      ctx.db.user.findUnique({ where: { id: args.id } }),
  }),
}));
TypeScript src/schema/post.ts — mutations with input types 
import { builder } from './builder';
import { GraphQLError } from 'graphql';

// Input type — reusable in multiple mutations
const CreatePostInput = builder.inputType('CreatePostInput', {
  fields: (t) => ({
    title: t.string({ required: true }),
    body: t.string({ required: true }),
    tags: t.stringList({ required: false }),
  }),
});

builder.objectType('Post', {
  fields: (t) => ({
    id: t.exposeID('id'),
    title: t.exposeString('title'),
    body: t.exposeString('body'),
    publishedAt: t.expose('publishedAt', { type: 'DateTime', nullable: true }),
    author: t.field({
      type: 'User',
      resolve: (post, _args, ctx) =>
        ctx.db.user.findUniqueOrThrow({ where: { id: post.authorId } }),
    }),
  }),
});

builder.mutationFields((t) => ({
  createPost: t.field({
    type: 'Post',
    args: { input: t.arg({ type: CreatePostInput, required: true }) },
    resolve: async (_root, { input }, ctx) => {
      if (!ctx.userId) {
        throw new GraphQLError('Not authenticated', {
          extensions: { code: 'UNAUTHENTICATED' },
        });
      }
      return ctx.db.post.create({
        data: {
          title: input.title,
          body: input.body,
          tags: input.tags ?? [],
          authorId: ctx.userId,
        },
      });
    },
  }),

  publishPost: t.field({
    type: 'Post',
    args: { id: t.arg.id({ required: true }) },
    resolve: async (_root, { id }, ctx) => {
      if (!ctx.userId) throw new GraphQLError('Not authenticated');
      const post = await ctx.db.post.findUnique({ where: { id } });
      if (!post || post.authorId !== ctx.userId) {
        throw new GraphQLError('Not found or not authorized', {
          extensions: { code: 'FORBIDDEN' },
        });
      }
      return ctx.db.post.update({
        where: { id },
        data: { publishedAt: new Date() },
      });
    },
  }),
}));
TypeScript src/server.ts — wiring with graphql-yoga 
import { createYoga } from 'graphql-yoga';
import { createServer } from 'http';
import { builder } from './schema/builder';
import './schema/user';  // side-effect: registers types on builder
import './schema/post';

// Build the schema — Pothos emits a GraphQLSchema object

const yoga = createYoga({

  context: async ({ request }) => {
    // Parse JWT from Authorization header

    const userId = token ? verifyJwt(token) : null;
    return { userId, db: prisma };

});

If your team is already invested in SDL-first workflows, or you're working with an existing schema maintained by a different team, the code generation approach is the right tool.

TypeScript src/resolvers/user.ts — using generated types 
// Generated by graphql-codegen — DO NOT EDIT
import type { Resolvers } from '../generated/types';

// The `Resolvers` type is fully typed against your SDL.
// TypeScript will error if you return the wrong shape.
export const userResolvers: Resolvers = {
  Query: {
    me: (_root, _args, ctx) => {
      if (!ctx.userId) return null;
      return ctx.db.user.findUnique({ where: { id: ctx.userId } });
    },
    user: (_root, { id }, ctx) =>
      ctx.db.user.findUnique({ where: { id } }),
  },

  User: {
    posts: (user, _args, ctx) =>
      ctx.db.post.findMany({ where: { authorId: user.id } }),
  },

  Mutation: {
    createPost: (_root, { input }, ctx) => {
      if (!ctx.userId) throw new Error('Unauthenticated');
      return ctx.db.post.create({
        data: { ...input, authorId: ctx.userId },
      });
    },
  },
};
ℹ️ When codegen beats Pothos

Use SDL + codegen when: (1) your schema is maintained by a dedicated platform team and shared via a schema registry, (2) you're generating client types from the same schema, (3) your team uses multiple languages and SDL is the shared contract, or (4) you're working with Apollo Federation where the SDL is the federation boundary.

6. Resolvers Deep Dive

Resolver Signature and Types

Every resolver has the same four-argument signature:

TypeScript 
// The canonical resolver type
type Resolver<Parent, Args, Context, Return> = (
  parent: Parent,    // Return value of the parent resolver
  args: Args,        // Arguments passed to this field in the query
  context: Context,  // Per-request shared object (auth user, DB, etc.)
  info: GraphQLResolveInfo  // Field metadata, AST, path — rarely needed
) => Return | Promise<Return>;

// Example: typed resolver for Query.user
const userResolver: Resolver<{}, { id: string }, AppContext, User | null> =
  (_parent, { id }, ctx) => ctx.db.user.findUnique({ where: { id } });

// Field-level resolver — parent IS the User object
const postsResolver: Resolver<User, { limit?: number }, AppContext, Post[]> =
  (user, { limit = 10 }, ctx) =>
    ctx.db.post.findMany({
      where: { authorId: user.id },
      take: limit,
      orderBy: { createdAt: 'desc' },
    });

Async Resolvers and Parallel Execution

◈ GraphQL Concept: Parallel vs Serial Execution

By default, GraphQL executes sibling fields in a query in parallel. If your query asks for posts and followers on a User, both resolvers run concurrently via Promise.all semantics.

Exception: The fields of the root Mutation type execute serially, in document order, to ensure safe state mutation. This is mandated by the GraphQL spec.

Error Handling in Resolvers

TypeScript Structured errors with GraphQLError 
import { GraphQLError } from 'graphql';

// GraphQLError lets you attach machine-readable error codes
// and additional extensions visible to the client
function assertAuthenticated(ctx: AppContext): asserts ctx is AuthContext {
  if (!ctx.userId) {
    throw new GraphQLError('You must be signed in to do that.', {
      extensions: {
        code: 'UNAUTHENTICATED',
        http: { status: 401 },
      },
    });
  }
}

function assertOwner(post: Post, ctx: AuthContext): void {
  if (post.authorId !== ctx.userId) {
    throw new GraphQLError('You do not have permission to modify this post.', {
      extensions: {
        code: 'FORBIDDEN',
        http: { status: 403 },
      },
    });
  }
}

// Usage in a resolver
const deletePost: MutationResolvers['deletePost'] = async (_root, { id }, ctx) => {
  assertAuthenticated(ctx);
  const post = await ctx.db.post.findUnique({ where: { id } });
  if (!post) throw new GraphQLError('Post not found', { extensions: { code: 'NOT_FOUND' } });
  assertOwner(post, ctx);
  await ctx.db.post.delete({ where: { id } });
  return true;
};
⚠️ Error Masking in Production

Apollo Server and graphql-yoga both mask unexpected errors in production — they replace the message with "Internal server error" and log the original. Only GraphQLError instances propagate their message to clients. Unhandled Error throws are masked. This is the correct behavior — never expose stack traces to clients.

Apollo Client — Full-Featured

Apollo Client is the industry workhorse. Its normalized cache is powerful for apps with complex, interconnected data. The tradeoff is size (~38kB gzipped) and a steeper learning curve for cache management.

TypeScript Apollo Client setup 
import { ApolloClient, InMemoryCache, ApolloProvider, gql, useQuery } from '@apollo/client';

const client = new ApolloClient({
  uri: '/graphql',
  cache: new InMemoryCache({
    typePolicies: {
      // Teach Apollo how to identify Post objects for normalized caching

          posts: {
            keyArgs: false,
            merge(existing = [], incoming) {
              return [...existing, ...incoming];
            },
          },
        },
      },
    },
  }),
  // Include credentials for cookie-based auth
  credentials: 'include',
});
🐍 Coming from Python + requests/httpx

In Python you'd make a GraphQL request as a plain POST:

requests.post("/graphql", json={"query": "{ me { name } }"})

In TypeScript, clients like urql and Apollo add: automatic caching, deduplication of identical in-flight queries, normalized cache updates after mutations, and React hooks. You can still use fetch directly — GraphQL is just HTTP+JSON — but the clients handle a lot of production concerns for you.

8. DataLoader: Solving N+1

The N+1 problem is the most common performance pitfall in GraphQL. It occurs when a list resolver returns N items, and a field resolver on each item makes an individual database call — resulting in 1 (list) + N (field) = N+1 database queries.

The N+1 Problem — Without DataLoader

TypeScript src/loaders/userLoader.ts 
import DataLoader from 'dataloader';
import type { PrismaClient } from '@prisma/client';
import type { User } from '@prisma/client';

// DataLoader<Key, Value>
// Key: the type of IDs we pass to .load()
// Value: what we get back for each key
export function createUserLoader(db: PrismaClient): DataLoader<string, User | null> {
  return new DataLoader<string, User | null>(
    async (ids) => {
      // DataLoader calls this function once per tick with all queued IDs
      const users = await db.user.findMany({
        where: { id: { in: [...ids] } },
      });

      // CRITICAL: Return values in the SAME ORDER as input keys.
      // DataLoader maps results by position, not by value.
      const userMap = new Map(users.map((u) => [u.id, u]));
      return ids.map((id) => userMap.get(id) ?? null);
    },
    {
      // Cache within a single request — avoids re-fetching the same user
      // DataLoader creates a new instance per request, so cache is request-scoped
      cache: true,
      // Batch within the same tick of the event loop
      batchScheduleFn: (callback) => setTimeout(callback, 0),
    },
  );
}

// Create loaders per-request in context:
// context: () => ({ db: prisma, loaders: { user: createUserLoader(prisma) } })
TypeScript Using the loader in a resolver 
// Without DataLoader: Post.author fires N queries for N posts
// With DataLoader: all author IDs are batched into one query

const postResolvers: Resolvers = {
  Post: {
    // ctx.loaders.user.load() returns a Promise.
    // DataLoader batches all .load() calls made in the same tick.
    author: (post, _args, ctx) => ctx.loaders.user.load(post.authorId),
  },
};
⚠️ Always Create DataLoaders Per-Request

DataLoader caches by key. If you create a single DataLoader instance at startup (module level), it will cache stale data across requests. Always instantiate DataLoaders inside your context factory — one fresh instance per incoming request.

9. Subscriptions with WebSockets

GraphQL subscriptions push data to clients over a persistent connection. The most common transport is WebSocket via the graphql-ws protocol (newer) or the legacy subscriptions-transport-ws.

shell 
pnpm add graphql-ws ws
TypeScript src/subscriptions.ts — server-side with graphql-ws 
import { useServer } from 'graphql-ws/lib/use/ws';
import { WebSocketServer } from 'ws';
import { PubSub } from 'graphql-subscriptions';
import { schema } from './schema';

export const pubsub = new PubSub();

// Subscription resolver
const subscriptionResolvers = {
  Subscription: {
    postPublished: {
      // subscribe returns an AsyncIterator — GraphQL polls it
      subscribe: () => pubsub.asyncIterator(['POST_PUBLISHED']),
      resolve: (payload: { postPublished: Post }) => payload.postPublished,
    },
  },
};

// After HTTP server is created:
const wss = new WebSocketServer({ server: httpServer, path: '/graphql' });
useServer(
  {
    schema,
    context: async (ctx) => ({
      // ctx.connectionParams contains initial WS handshake params (e.g., auth token)
      userId: verifyToken(ctx.connectionParams?.token as string | undefined),
      db: prisma,
    }),
  },
  wss,
);

ℹ️ Server-Sent Events as an Alternative

graphql-yoga supports subscriptions over Server-Sent Events (SSE) out of the box, with no WebSocket server needed. SSE works over standard HTTP, passes through proxies and load balancers more reliably, and is simpler to scale. The tradeoff: SSE is server-to-client only (no client-to-server messages over the same connection). For most subscription use cases — feed updates, notifications — SSE is the better default.

10. tRPC — The TypeScript-Only Alternative

tRPC is not GraphQL. It does not use SDL, resolvers, or a query language. Instead, it exposes TypeScript functions directly as API endpoints, inferring types end-to-end without any code generation step. If your clients are all TypeScript (Next.js, React Native), tRPC can eliminate an entire layer of abstraction.

shell 
pnpm add @trpc/server @trpc/client @trpc/react-query @tanstack/react-query zod
TypeScript server/trpc/router.ts — server definition 
import { initTRPC, TRPCError } from '@trpc/server';
import { z } from 'zod';

interface Context {
  userId: string | null;
  db: PrismaClient;
}

const t = initTRPC.context<Context>().create();

// Reusable middleware
const isAuthenticated = t.middleware(({ ctx, next }) => {
  if (!ctx.userId) throw new TRPCError({ code: 'UNAUTHORIZED' });
  return next({ ctx: { ...ctx, userId: ctx.userId } });
});

const protectedProcedure = t.procedure.use(isAuthenticated);

export const appRouter = t.router({
  user: t.router({
    me: protectedProcedure.query(({ ctx }) =>
      ctx.db.user.findUnique({ where: { id: ctx.userId } })
    ),

    byId: t.procedure
      .input(z.object({ id: z.string().cuid() }))
      .query(({ input, ctx }) =>
        ctx.db.user.findUnique({ where: { id: input.id } })
      ),
  }),

  post: t.router({
    list: t.procedure
      .input(z.object({ limit: z.number().min(1).max(100).default(10) }))
      .query(({ input, ctx }) =>
        ctx.db.post.findMany({
          where: { publishedAt: { not: null } },
          take: input.limit,
          orderBy: { publishedAt: 'desc' },
        })
      ),

    create: protectedProcedure
      .input(z.object({
        title: z.string().min(1).max(200),
        body: z.string().min(1),
        tags: z.array(z.string()).optional(),
      }))
      .mutation(({ input, ctx }) =>
        ctx.db.post.create({
          data: { ...input, authorId: ctx.userId },
        })
      ),
  }),
});

// Export the router TYPE — this is what the client imports
export type AppRouter = typeof appRouter;
TypeScript client/src/trpc.ts — client-side, zero codegen 
import { createTRPCReact } from '@trpc/react-query';
import type { AppRouter } from '../../server/trpc/router'; // ← just a type import

// The client is fully typed against the server router.
// No codegen. No schema files. Just TypeScript.
export const trpc = createTRPCReact<AppRouter>();

// In a component:
function PostList() {
  // TypeScript knows: data is { id: string; title: string; body: string; ... }[]
  const { data, isLoading } = trpc.post.list.useQuery({ limit: 20 });

  const createPost = trpc.post.create.useMutation({
    onSuccess: () => trpc.useContext().post.list.invalidate(),
  });

  return (
    <button onClick={() => createPost.mutate({ title: 'Hello', body: 'World' })}>
      Create Post
    </button>
  );
}
✦ AI Era: tRPC + AI Agents

tRPC is increasingly used as the internal API layer for AI agent backends. Because every procedure is a typed TypeScript function, you can automatically generate tool definitions for function-calling LLMs from your router using zod-to-json-schema on the procedure inputs. The same input validation that protects your API from bad user input also validates LLM outputs before they hit your database.

11. REST vs GraphQL vs tRPC Decision Guide

GraphQL Query Lifecycle

Criterion REST GraphQL tRPC
Client flexibility (mobile, web, etc.) Needs versioning or BFF First-class — query what you need TypeScript clients only
End-to-end type safety Manual or codegen required With Pothos or codegen Automatic — no codegen step
Public API / third-party consumers Universally understood With good schema docs TypeScript only — not viable
HTTP caching (CDN, ETags) Native, works out of the box POST-based; persisted queries help POST-based; limited
Real-time (subscriptions) Bolt-on (SSE, WebSocket) Native subscriptions Via .subscription(), experimental
Learning curve Low — widely known Moderate — resolvers, N+1, schema Low for TS devs
Tooling maturity Decades of tooling Apollo Studio, Playground, codegen Growing rapidly, newer
Federated / multi-service graph API gateway complexity Apollo Federation, schema stitching Not designed for this
Team size Any size Large teams — clear contract Small–medium TS teams
File uploads Standard multipart Requires extra spec Via separate endpoint
Migration path — REST → GQL: wrap REST resolvers Can coexist alongside REST

The Decision Flowchart

  • Multiple non-TypeScript client types? GraphQL wins. The schema is your contract regardless of client language.
  • Internal TypeScript monorepo, Next.js app router? tRPC is likely the fastest path to production with the least overhead.
  • Public API consumed by third-party developers? REST — familiar, cacheable, universally tooled.
  • Complex graph-shaped data with many relationships? GraphQL — the traversal model is purpose-built for this.
  • Real-time is a core feature, not an afterthought? GraphQL subscriptions or a dedicated WebSocket layer.
  • Enterprise, multiple teams, federated microservices? Apollo Federation with GraphQL.
✦ AI Era: GraphQL as an Agent Interface

LLM agents need structured, discoverable APIs. GraphQL's introspection makes your API self-describing — an agent can query __schema to understand all available types and operations, then construct valid queries dynamically. This is harder to do reliably with REST (OpenAPI helps) and impossible with tRPC (no runtime reflection). For AI-powered backends where agents interact with your data, GraphQL's introspection is a genuine advantage.

✅ My Recommendation as of 2026

New full-stack TypeScript product: Start with tRPC. Add GraphQL if you need multiple client types or expose a public API.

API consumed by mobile apps + web: Pothos + graphql-yoga. Deploy to a Node.js runtime or Cloudflare Workers.

Large enterprise with multiple teams: Apollo Federation. The schema registry and schema checks are worth the operational cost at scale.

Legacy REST migration: Don't rewrite — wrap existing REST endpoints as GraphQL resolvers. Ship incrementally.
