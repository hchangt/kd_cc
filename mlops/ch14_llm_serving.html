1. LLM Inference Challenges

Serving large language models is fundamentally different from serving classical ML models. A ResNet-50 image classifier takes a fixed-size tensor, runs a deterministic forward pass, and returns a probability vector in ~5 ms. An LLM generating 512 tokens requires 512 sequential forward passes, each attending over all previously generated tokens, while managing gigabytes of cached intermediate states. The operational requirements are categorically different.

1.1 Why LLM Serving is Different

  • Variable output length: You cannot pre-allocate a fixed output buffer. A user asking for a haiku and another asking for a legal contract both hit the same endpoint but consume wildly different compute.
  • Sequential token generation: Each token depends on all previous tokens — true data dependency that blocks parallelism across the generation dimension.
  • KV Cache memory pressure: Attention keys and values for every token in every layer must be kept in GPU VRAM across the entire generation lifecycle.
  • Batching is non-trivial: Requests finish at different times. Static batching wastes GPU cycles waiting for the slowest request. You need continuous (dynamic) batching.
  • Memory bandwidth bound, not compute bound: During decoding, you move model weights from HBM to SRAM for every single generated token, even when generating just one token per step. Arithmetic intensity is ~1 FLOP per byte — far below the ridge point of modern GPUs.

1.3 Autoregressive Generation: The Sequential Bottleneck

LLMs generate tokens autoregressively: token t+1 cannot be computed until token t is fully computed, because it attends to token t's key-value pairs. This creates two fundamentally different phases:

  • Prefill: All input tokens are processed in one forward pass. GPU is compute-bound. Fast, uses tensor parallelism efficiently. Contributes to TTFT.
  • Decode: One token generated per step. GPU is memory-bandwidth-bound — weights are loaded for each single-token forward pass. Each step contributes to ITL.

2. Key Optimization Concepts

2.1 KV Cache

Without KV caching, each decode step would recompute attention keys and values for all previous tokens — O(N²) total compute for N tokens. KV caching stores these tensors in GPU VRAM, reducing decode compute to O(N) at the cost of O(N × layers × heads × head_dim) memory. It is the single most important optimization in LLM inference, non-negotiable for any production deployment.

KV Cache is the bottleneck for long contexts: A 128K context window with Llama-3-70B in FP16 requires ~342 GB of KV cache for a single request. This is why context length directly drives GPU cluster sizing in production.

2.2 Continuous Batching vs Static Batching

gantt title Static vs Continuous Batching dateFormat X axisFormat %s section Static Batch (4 requests) Req A (short) :done, 0, 3 Req B (medium) :done, 0, 6 Req C (long) :done, 0, 10 Req D (medium) :done, 0, 6 Wait (A idle) :crit, 3, 10 Wait (B,D idle) :crit, 6, 10 section Continuous Batch Req A :active, 0, 3 Req E (new) :active, 3, 8 Req B :active, 0, 6 Req F (new) :active, 6, 9 Req C :active, 0, 10 Req D :active, 0, 6

With static batching, the server waits until a batch is full, runs all requests together, and only returns results when every request in the batch finishes. Short requests sit idle waiting for long ones. GPU utilization collapses.

With continuous batching (iteration-level scheduling), as soon as a request finishes generating its last token, it is evicted from the batch and a new waiting request is immediately inserted at the very next decode step. GPU utilization stays near 100%. vLLM, TGI, and all serious serving frameworks implement this.

2.3 PagedAttention: vLLM's Core Innovation

Traditional KV cache management pre-allocates a contiguous VRAM block for the maximum possible sequence length, causing internal fragmentation and inability to serve many concurrent requests. PagedAttention (Kwon et al., 2023) manages KV cache like virtual memory in an OS — KV cache is divided into fixed-size pages. Each sequence maps to a list of pages, which need not be contiguous. A block table maps logical block numbers to physical GPU memory addresses.

  • Near-zero internal memory fragmentation (only the last page may be partially filled)
  • Memory sharing: requests with the same prefix share physical pages (prefix caching)
  • Copy-on-write for beam search: forked sequences share pages until divergence
  • 3-4x throughput improvement over Hugging Face Transformers baseline

2.4 Flash Attention

Standard attention materializes the full N×N attention matrix in HBM — O(N²) memory and IO. Flash Attention (Dao et al., 2022) tiles Q, K, V and computes attention in SRAM, making multiple passes in smaller chunks. The full attention matrix is never materialized. Flash Attention 2 improves work partitioning; Flash Attention 3 exploits H100 async WGMMA and TMA instructions. Results: O(N) memory, 2-4× speedup for long sequences, numerically exact.

2.5 Speculative Decoding

Speculative decoding uses a small draft model to propose K tokens in roughly the same time a large target model verifies them in one parallel forward pass. If draft tokens match the target distribution, all K tokens are accepted — K× speedup. If they diverge, the first divergent token is corrected and decoding continues. Typical speedup: 2-3× with well-matched draft models.

3. vLLM — The Standard for LLM Serving

vLLM (UC Berkeley, 2023) is the de facto standard for GPU-accelerated LLM serving. It implements PagedAttention, continuous batching, Flash Attention, and provides an OpenAI-compatible REST API supporting virtually all popular open-weight models and quantization formats.

5. SGLang

SGLang (Structured Generation Language) is a serving framework from the LMSYS team that co-optimizes the runtime and programming interface. Its RadixAttention provides automatic KV cache reuse via radix trees, and it has native support for structured generation (JSON, regex), often exceeding vLLM throughput for prompt-reuse-heavy workloads.

5.1 SGLang Server and Client

# Install SGLang
pip install "sglang[all]"

# Start SGLang server (OpenAI-compatible)
python -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --host 0.0.0.0 --port 30000 \
    --tp 1 --mem-fraction-static 0.85 \
    --enable-torch-compile
import sglang as sgl

@sgl.function
def multi_turn_qa(s, q1, q2):
    s += sgl.system("You are a concise technical assistant.")
    s += sgl.user(q1)
    s += sgl.assistant(sgl.gen("answer1", max_tokens=200))
    s += sgl.user(q2)
    s += sgl.assistant(sgl.gen("answer2", max_tokens=200))

sgl.set_default_backend(sgl.RuntimeEndpoint("http://localhost:30000"))

state = multi_turn_qa.run(
    q1="What is attention in transformers?",
    q2="How does multi-head attention extend this?",
)
print(state["answer1"])
print(state["answer2"])

import sglang as sgl
import json

sgl.set_default_backend(sgl.RuntimeEndpoint("http://localhost:30000"))

PERSON_SCHEMA = """{
  "type": "object",
  "properties": {
    "name": {"type": "string"},

7. Speculative Decoding

Speculative decoding is one of the highest-impact inference optimizations for latency-sensitive workloads. The core insight: the memory-bandwidth bottleneck during decode means the GPU is idle much of the time between loading weights and computing the single next token. We can exploit this slack by proposing multiple future tokens cheaply, then verifying them in one parallel step.

7.1 Algorithm: Draft Model + Verification

sequenceDiagram participant User participant Draft as Draft Model (small) participant Target as Target Model (large) User->>Draft: Generate K draft tokens speculatively Draft->>Draft: t1=argmax(p_draft(·|context)) Draft->>Draft: t2=argmax(p_draft(·|context,t1)) Draft->>Draft: t3=argmax(p_draft(·|context,t1,t2)) Draft->>Target: Verify [t1,t2,t3] in ONE forward pass Target->>Target: Compute p_target(·|context) for all K+1 positions Note over Target: Accept t1 if p_target(t1)/p_draft(t1) >= U[0,1] Note over Target: Accept t2 if t1 accepted AND p_target(t2)/p_draft(t2) >= U[0,1] Note over Target: On rejection: resample from corrected distribution Target->>User: Return accepted tokens (1 to K+1 tokens per step)

The acceptance rate α depends on distribution overlap between draft and target. If α is high (draft closely approximates target), you get near-K× speedup. The corrected sampling ensures the output distribution is exactly the target distribution — no quality loss at any acceptance rate.

7.2 Speculative Decoding Setup in vLLM

8. Quantization Deep Dive

Quantization is often the first optimization applied in production: it reduces model size, VRAM requirements, and increases effective memory bandwidth — all without requiring any model architecture changes. For LLMs, weight-only quantization (W4A16: 4-bit weights, 16-bit activations) is the most common approach, offering good quality-speed trade-offs.

8.1 GPTQ (Post-Training Quantization)

GPTQ (Frantar et al., 2022) quantizes each weight layer individually by minimizing the reconstruction error using second-order information from a small calibration dataset (~128 samples). It applies an optimal quantization order within each row to minimize the cumulative error. GPTQ is the most widely used post-training quantization method for LLMs and is supported by vLLM, TGI, and llama.cpp.

from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig
from transformers import AutoTokenizer
import torch

# Define quantization configuration

    bits=4,                    # 4-bit quantization

    sym=True,                  # Symmetric quantization

    "meta-llama/Llama-3.1-8B-Instruct",
    quantize_config=quantize_config,

)

    tokenizer("The theory of relativity was proposed by Einstein in 1905.", return_tensors="pt").input_ids,

8.2 AWQ (Activation-Aware Weight Quantization)

AWQ (Lin et al., 2023) addresses GPTQ's weakness: not all weights are equally important. Weights corresponding to high-magnitude activation channels cause more error when quantized. AWQ identifies these salient channels by analyzing activation statistics and scales them up (making them more resistant to quantization error) before quantizing. Result: consistently 0.3-0.5 perplexity better than GPTQ at the same bit width.

10. Scaling LLM Serving

10.1 Multi-GPU Serving Strategies

Three complementary parallelism strategies exist for scaling LLM serving beyond single-GPU capacity:

Tensor Parallelism (TP)

Split individual weight matrices across GPUs. Requires all-reduce every layer. Best for minimizing latency. Use within a single node (NVLink bandwidth critical). TP=4 on 4x H100 NVLink is typical for 70B models.

Pipeline Parallelism (PP)

Split model layers across GPUs/nodes. Each GPU processes full activations for its assigned layers. Lower communication bandwidth requirement — works across nodes. Best for very large models that don't fit with TP alone. Introduces pipeline bubbles.

Data Parallelism (DP)

Replicate the full model on multiple GPUs/nodes. Each replica handles different requests. Best for maximizing throughput. Requires a load balancer. KV cache is not shared between replicas — use prefix caching within each replica.

10.3 Prefill/Decode Disaggregation

Prefill and decode phases have very different compute characteristics. Prefill is compute-bound (benefits from high-FLOP GPUs) and decode is memory-bandwidth-bound (benefits from high-bandwidth memory). Disaggregating them allows each phase to be scheduled on hardware optimized for that phase:

  • Prefill cluster: Use fewer, higher-FLOP GPUs (H100 SXM). Can handle long prompts efficiently. KV cache is computed and must be transferred to decode cluster.
  • Decode cluster: Use more GPUs optimized for bandwidth. Handle many ongoing decode requests with small per-step compute.
  • KV cache transfer between clusters is the main overhead — requires high-bandwidth interconnect (InfiniBand or NVLink-C2C).
  • Implemented in DistServe (2024) and Mooncake (Kimi AI, 2024). Expected to become standard for large-scale deployments.

10.4 Router Design for Multi-Instance Serving

import asyncio
import aiohttp
from typing import List
import hashlib

class LLMRouter:
    """Simple consistent-hash router for LLM serving.
    Routes requests with the same system prompt to the same replica
    to maximize prefix cache hit rates.
    """

    def __init__(self, endpoints: List[str]):
        self.endpoints = endpoints
        self.n = len(endpoints)
        self._request_counts = [0] * self.n

    def _hash_route(self, system_prompt: str) -> int:
        """Route based on system prompt hash — maximizes prefix cache hits."""
        h = int(hashlib.md5(system_prompt.encode()).hexdigest(), 16)
        return h % self.n

    def _least_loaded(self) -> int:
        return self._request_counts.index(min(self._request_counts))

    def route(self, system_prompt: str = "", use_prefix_routing: bool = True) -> str:
        if use_prefix_routing and system_prompt:
            idx = self._hash_route(system_prompt)
        else:
            idx = self._least_loaded()
        self._request_counts[idx] += 1
        return self.endpoints[idx]

    async def forward(self, payload: dict) -> dict:
        system_prompt = ""
        for msg in payload.get("messages", []):
            if msg.get("role") == "system":
                system_prompt = msg["content"]
                break
        endpoint = self.route(system_prompt=system_prompt)
        async with aiohttp.ClientSession() as session:
            async with session.post(
                f"{endpoint}/v1/chat/completions", json=payload
            ) as resp:
                return await resp.json()

router = LLMRouter([

    fn_args = json.loads(tool_call.function.arguments)
    print(f"Tool call: {fn_name}({fn_args})")

    # Execute the function (in real code, call your actual function)
    tool_result = {"temperature": 22, "condition": "Sunny", "humidity": 65}

    # Add tool result to conversation
    messages.append(message)
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": json.dumps(tool_result),
    })

    # Second call: model formulates natural language response
    final_response = client.chat.completions.create(
        model="llama-3.1-8b",
        messages=messages,
        max_tokens=256,
    )
    print(final_response.choices[0].message.content)




13. Structured Output and Constrained Generation


Constrained generation ensures LLM output conforms to a specified schema, grammar, or regex pattern at the token generation level — not via post-processing. This is crucial for production use cases like data extraction, API response generation, and function calling where malformed JSON breaks downstream systems.

13.2 Grammar-Based Constraints with Outlines


import outlines
import outlines.generate as generate

model = outlines.models.transformers("meta-llama/Llama-3.1-8B-Instruct", device="cuda")

# Regex constraint — match a specific pattern
phone_generator = generate.regex(model, r"\+?[1-9]\d{1,14}")
phone = phone_generator("What is a US phone number? ")
print(f"Phone: {phone}")

# Choice constraint — force selection from a fixed set
classifier = generate.choice(model, ["positive", "negative", "neutral"])
sentiment = classifier(
    "Classify the sentiment: 'This product exceeded all my expectations!'"
)
print(f"Sentiment: {sentiment}")  # Always one of the three choices

# Context-free grammar — generate valid arithmetic expressions
arithmetic_grammar = """
    ?start: expr
    ?expr: term ("+" term | "-" term)*
    ?term: factor ("*" factor | "/" factor)*
    ?factor: NUMBER | "(" expr ")"
    NUMBER: /[0-9]+/
    %ignore " "
"""
expr_generator = generate.cfg(model, arithmetic_grammar)
expression = expr_generator("Generate a math expression: ")
print(f"Expression: {expression}")  # Always a valid arithmetic expression

14.2 Benchmarking Script


import asyncio
import time
import statistics
from dataclasses import dataclass, field
from typing import List
import aiohttp
import json

@dataclass
class BenchmarkResult:
    request_rate: float
    total_requests: int
    successful_requests: int
    failed_requests: int
    total_time: float
    # Latency metrics (seconds)
    ttft_mean: float
    ttft_p50: float
    ttft_p95: float
    ttft_p99: float
    # Throughput
    tokens_per_second: float
    requests_per_second: float
    # Token counts
    total_input_tokens: int
    total_output_tokens: int

async def single_request(
    session: aiohttp.ClientSession,
    endpoint: str,
    model: str,
    prompt: str,
    max_tokens: int = 128,
) -> dict:
    start = time.monotonic()
    first_token_time = None
    total_tokens = 0

    payload = {
        "model": model,
        "messages": [{"role": "user", "content": prompt}],
        "max_tokens": max_tokens,
        "stream": True,
        "temperature": 0.0,
    }

    try:
        async with session.post(f"{endpoint}/v1/chat/completions", json=payload) as resp:
            async for line in resp.content:
                line = line.decode("utf-8").strip()
                if line.startswith("data: ") and line != "data: [DONE]":
                    chunk = json.loads(line[6:])
                    delta = chunk["choices"][0]["delta"].get("content", "")
                    if delta and first_token_time is None:
                        first_token_time = time.monotonic()
                    if delta:
                        total_tokens += 1

        end = time.monotonic()
        return {
            "success": True,
            "ttft": first_token_time - start if first_token_time else None,
            "total_time": end - start,
            "output_tokens": total_tokens,
        }
    except Exception as e:
        return {"success": False, "error": str(e)}

async def run_benchmark(
    endpoint: str,
    model: str,
    prompts: List[str],
    request_rate: float,  # requests per second
) -> BenchmarkResult:
    results = []
    start_time = time.monotonic()

    async with aiohttp.ClientSession() as session:
        tasks = []
        for i, prompt in enumerate(prompts):
            # Schedule requests at given rate
            target_time = start_time + i / request_rate
            delay = max(0, target_time - time.monotonic())
            if delay > 0:
                await asyncio.sleep(delay)

            task = asyncio.create_task(
                single_request(session, endpoint, model, prompt)
            )
            tasks.append(task)

        results = await asyncio.gather(*tasks)

    total_time = time.monotonic() - start_time
    successful = [r for r in results if r.get("success")]
    ttfts = [r["ttft"] for r in successful if r.get("ttft")]
    total_output = sum(r.get("output_tokens", 0) for r in successful)

    return BenchmarkResult(
        request_rate=request_rate,
        total_requests=len(results),
        successful_requests=len(successful),
        failed_requests=len(results) - len(successful),
        total_time=total_time,
        ttft_mean=statistics.mean(ttfts) if ttfts else 0,
        ttft_p50=statistics.median(ttfts) if ttfts else 0,
        ttft_p95=sorted(ttfts)[int(len(ttfts) * 0.95)] if ttfts else 0,
        ttft_p99=sorted(ttfts)[int(len(ttfts) * 0.99)] if ttfts else 0,
        tokens_per_second=total_output / total_time,
        requests_per_second=len(successful) / total_time,
        total_input_tokens=sum(len(p.split()) * 1.3 for p in prompts[:len(successful)]),
        total_output_tokens=total_output,
    )

# Run benchmark at different request rates
async def sweep():
    prompts = ["Explain transformer attention in detail."] * 200
    endpoint = "http://localhost:8000"
    model = "llama-3.1-8b"

    for rate in [1, 5, 10, 20, 50]:
        result = await run_benchmark(endpoint, model, prompts[:50], rate)
        print(f"Rate={rate:.0f} req/s | Throughput={result.tokens_per_second:.0f} tok/s | "
              f"TTFT p50={result.ttft_p50*1000:.0f}ms | p99={result.ttft_p99*1000:.0f}ms | "
              f"Success={result.successful_requests}/{result.total_requests}")

asyncio.run(sweep())

Key Takeaways

  

    

      
Core Concepts

      
    
        
  • KV Cache: The single most important optimization — enables O(N) decode cost instead of O(N²). Must be managed efficiently (PagedAttention).
    • 
        
  • Continuous Batching: Non-negotiable for production. Static batching wastes 30-60% GPU utilization.
    • 
        
  • Memory Bandwidth is the bottleneck: LLM decode is bandwidth-bound, not compute-bound. Quantization and KV cache efficiency matter more than raw FLOPS.
    • 
        
  • TTFT vs Throughput: Fundamentally at odds — tune for your SLO using batch size and scheduling strategy.
    • 
      

    

    

      
Tool Selection

      
    
        
  • vLLM: Default choice for most production deployments. Best compatibility, active development, OpenAI API-compatible.
    • 
        
  • TGI: Strong for HF Endpoints integration, Docker-first deployments, and existing HF infrastructure.
    • 
        
  • SGLang: When you have heavy prefix reuse or need first-class structured output — RadixAttention is genuinely better.
    • 
        
  • TRT-LLM: 20-40% throughput uplift on H100 — worth the complexity for high-traffic, stable production loads.
    • 
        
  • Ollama: Local development, CI testing, Apple Silicon. Not for production GPU serving.
    • 
      

    

    

      
Optimization Hierarchy

      
    
        
  1. Continuous batching (switch from static) — biggest impact, free

  2. PagedAttention — already in vLLM/TGI, use them

  3. AWQ/GPTQ 4-bit quantization — 2× VRAM reduction, minimal quality loss

  4. Prefix caching — big wins for shared system prompts
