Containers for ML

The Reproducibility Crisis in ML

Before containers, "it works on my machine" was the defining problem of ML engineering. A model trained on Python 3.9 + CUDA 11.3 + PyTorch 1.10 would silently produce different results — or simply crash — on a colleague's machine running Python 3.11 + CUDA 12.1 + PyTorch 2.1. This is not a minor inconvenience: it is the difference between a reproducible research result and a published paper that nobody can replicate.

Containers solve this by packaging not just your code, but the entire userspace: Python interpreter, system libraries, CUDA runtime, cuDNN, and your model weights. The environment is immutable and portable across every machine that runs a compatible container runtime.

From the Borg team: Google has run virtually every production workload inside containers since ~2013. ML training jobs are first-class citizens of this system. The Borg scheduler that inspired Kubernetes treats each job as a containerized unit of work — guaranteed resource isolation, repeatable execution, and portable artifacts.

Docker Fundamentals

Docker is the dominant container runtime for development. Understanding its core primitives is essential before moving to Kubernetes.

  • Image: A read-only, layered filesystem snapshot. Built from a Dockerfile.
  • Container: A running instance of an image with an isolated PID/net/mount namespace.
  • Registry: A content-addressable store for images (Docker Hub, ECR, GCR, Artifact Registry).
  • Layer: Each RUN/COPY/ADD instruction creates a new layer. Layers are cached and shared.
  • Build context: The directory sent to the Docker daemon on docker build. Keep it small.

Dockerfile Best Practices for ML

The following Dockerfile embeds every best practice you need for production ML images:

Dockerfile — Optimized PyTorch + CUDA image
# ─── STAGE 1: build dependencies ────────────────────────────────────────────
# Use an official CUDA base — never build CUDA from scratch
FROM nvcr.io/nvidia/pytorch:24.01-py3 AS builder

# Avoid interactive prompts in apt
ENV DEBIAN_FRONTEND=noninteractive

# System deps — pin versions, clean up in the same layer to keep it small
RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential=12.9ubuntu3 \
        git=1:2.39.2-1ubuntu1 \
        libgl1=1.6.0-1 \
    && rm -rf /var/lib/apt/lists/*

# Create a virtual env so we can copy it to the runtime stage cleanly
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# Pin ALL Python deps — never use loose version ranges in production
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir --upgrade pip==24.0 \
    && pip install --no-cache-dir -r /tmp/requirements.txt

# ─── STAGE 2: runtime image ──────────────────────────────────────────────────
# Reuse the same CUDA base so driver compatibility is guaranteed
FROM nvcr.io/nvidia/pytorch:24.01-py3 AS runtime

ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"

# Copy only the venv from the build stage — not the build tools
COPY --from=builder /opt/venv /opt/venv

# Non-root user: critical for security in shared clusters
RUN groupadd --gid 1001 mluser \
    && useradd --uid 1001 --gid mluser --shell /bin/bash --create-home mluser

WORKDIR /app

# Copy application code — put this LAST to maximise layer cache reuse
COPY --chown=mluser:mluser src/ /app/src/
COPY --chown=mluser:mluser config/ /app/config/

USER mluser

# Health check for Kubernetes readiness probe
HEALTHCHECK --interval=30s --timeout=10s --start-period=60s --retries=3 \
    CMD python -c "import torch; assert torch.cuda.is_available()" || exit 1

ENTRYPOINT ["python", "-m", "src.train"]
CMD ["--config", "/app/config/default.yaml"]
Warning — Build context size: Always create a .dockerignore file. Without it, Docker sends your entire working directory — including model checkpoints, datasets, and .git — to the daemon on every build. A 50 GB dataset directory will make every build take minutes before a single instruction runs.

Dockerfile Anti-patterns vs Best Practices

Anti-patternProblemBest Practice
pip install torch Unpinned; breaks on next release pip install torch==2.2.1+cu121 with exact hash in requirements.txt
FROM ubuntu:latest "latest" changes; non-reproducible builds FROM ubuntu:22.04 with explicit digest
Running as root Container escape = full host access Create a non-root user; USER mluser
COPY . . early in Dockerfile Invalidates all downstream cache layers on any code change Copy requirements first, install deps, then copy source code last
Multiple RUN apt-get layers Bloated image; old package lists in cache layers Single chained RUN with && rm -rf /var/lib/apt/lists/*
Storing secrets in ENV or ARG Visible in docker history and registry manifests Inject at runtime via K8s Secrets or Vault agent sidecar
Single-stage builds for ML Build tools (gcc, cmake) end up in the final 10 GB image Multi-stage: builder stage compiles, runtime stage copies artifacts
No .dockerignore Sends entire repo (datasets, checkpoints) to Docker daemon Always include a comprehensive .dockerignore

GPU Docker Setup

NVIDIA Container Toolkit

The NVIDIA Container Toolkit (formerly nvidia-docker2) allows Docker containers to access the host's GPU hardware without bundling the kernel driver inside the image. The architecture is: the host installs the NVIDIA driver once; the toolkit injects the driver userspace libraries into each container at runtime via a container device interface (CDI) hook.

bash — Install NVIDIA Container Toolkit on Ubuntu 22.04
# Add the NVIDIA GPG key and repository
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
    | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
    | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
    | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit

# Configure the Docker runtime to use the NVIDIA CDI
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# Verify — should print your GPU info
docker run --rm --gpus all nvidia/cuda:12.3.2-base-ubuntu22.04 nvidia-smi

CUDA Version Compatibility Matrix

Critical rule: The CUDA version in your Docker image must be less than or equal to the CUDA version supported by the host driver. You cannot run a CUDA 12.4 container on a host with a driver that only supports CUDA 11.8. This is the single most common cause of GPU container failures.
NVIDIA Driver Version Max CUDA Runtime Typical GPU Generation Notes
≥ 570.xCUDA 12.8H200, B200Latest; required for Blackwell
≥ 550.xCUDA 12.4H100, L40SRecommended for production H100 clusters
≥ 535.xCUDA 12.2A100, A10GCommon in AWS p4d/p4de, p3
≥ 525.xCUDA 12.0A100, V100EKS AMI default for older node groups
≥ 510.xCUDA 11.6V100, T4Legacy; avoid for new workloads
≥ 450.xCUDA 11.0V100, T4EOL — upgrade immediately

Dockerfile.gpu — Production GPU training image
# NVIDIA provides optimized PyTorch containers at nvcr.io/nvidia/pytorch
# Always prefer these over building from scratch — they include:
#   cuBLAS, cuDNN, NCCL, Apex, TransformerEngine, and flash-attention
ARG BASE_IMAGE=nvcr.io/nvidia/pytorch:24.01-py3
FROM ${BASE_IMAGE}

LABEL maintainer="ml-platform@company.com" \
      cuda.version="12.3" \
      pytorch.version="2.2.0" \
      description="Production GPU training container"

ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    # Needed for NCCL multi-GPU communication
    NCCL_DEBUG=INFO \
    NCCL_SOCKET_IFNAME=eth0 \
    # Optimise for A100 Tensor Cores
    TORCH_CUDA_ARCH_LIST="8.0;8.6;9.0" \
    CUDA_DEVICE_ORDER=PCI_BUS_ID

# Install additional system libraries for distributed training
RUN apt-get update && apt-get install -y --no-install-recommends \
        libopenmpi-dev \
        openmpi-bin \
        libibverbs-dev \
        librdmacm-dev \
    && rm -rf /var/lib/apt/lists/*

# Install Python packages on top of the NGC base
COPY requirements-gpu.txt /tmp/
RUN pip install --no-cache-dir -r /tmp/requirements-gpu.txt

# Non-root user
RUN groupadd -g 1001 trainer && useradd -u 1001 -g trainer -m trainer
WORKDIR /workspace
COPY --chown=trainer:trainer . /workspace/

USER trainer

# Verify GPU is accessible at build time (optional, useful for CI)
# RUN python -c "import torch; assert torch.cuda.is_available(), 'No CUDA!'"

ENTRYPOINT ["torchrun", "--standalone"]
CMD ["--nproc_per_node=auto", "src/train_distributed.py"]

Testing GPU in Containers

bash — Validate GPU access
# Quick GPU sanity check
docker run --rm --gpus all nvcr.io/nvidia/pytorch:24.01-py3 python -c "
import torch
print(f'PyTorch: {torch.__version__}')
print(f'CUDA available: {torch.cuda.is_available()}')
print(f'GPU count: {torch.cuda.device_count()}')
for i in range(torch.cuda.device_count()):
    print(f'  GPU {i}: {torch.cuda.get_device_name(i)}')
    props = torch.cuda.get_device_properties(i)
    print(f'    VRAM: {props.total_memory / 1e9:.1f} GB')
    print(f'    SM count: {props.multi_processor_count}')
"

# Run with specific GPU(s)
docker run --rm --gpus '"device=0,1"' my-training-image:latest

# Run with all GPUs
docker run --rm --gpus all my-training-image:latest

# Check NCCL multi-GPU communication
docker run --rm --gpus all --ipc=host \
    nvcr.io/nvidia/pytorch:24.01-py3 \
    python -m torch.distributed.launch \
    --nproc_per_node=2 \
    -c "import torch.distributed as dist; dist.init_process_group('nccl'); print('NCCL OK')"
Pro tip — --ipc=host: For multi-GPU workloads using shared memory (PyTorch DataLoader with num_workers>0), always pass --ipc=host or set --shm-size=8g. The default Docker shared memory of 64 MB causes mysterious worker crashes that are very hard to debug.

Section 4

Kubernetes for ML Workloads

Why Kubernetes for ML?

  • GPU scheduling: K8s tracks available GPU capacity cluster-wide and places workloads optimally
  • Resource isolation: Each job gets guaranteed CPU/memory/GPU — no noisy neighbors
  • Fault tolerance: Failed pods are automatically restarted; Jobs retry to completion
  • Multi-tenancy: Namespaces + ResourceQuotas enforce per-team budgets
  • Portability: Same YAML works on EKS, GKE, AKS, or on-prem
  • Ecosystem: Kubeflow, MLflow, Argo Workflows, Volcano all run natively on K8s

Resource Requests and Limits

GPU limits == GPU requests: Unlike CPU (which can be throttled), GPUs are non-divisible resources. For GPUs, requests must equal limits. K8s will reject pods where they differ.
k8s/gpu-training-job.yaml — Complete GPU pod spec
apiVersion: batch/v1
kind: Job
metadata:
  name: gpt2-finetuning-run-042
  namespace: ml-training
  labels:
    experiment: gpt2-finetune
    run-id: "042"
    team: nlp
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 2           # Retry up to 2 times on failure
  ttlSecondsAfterFinished: 86400   # Clean up after 24h
  template:
    metadata:
      labels:
        experiment: gpt2-finetune
        run-id: "042"
    spec:
      restartPolicy: OnFailure

      # ── Node selection: schedule ONLY on GPU nodes ───────────────────────
      nodeSelector:
        nvidia.com/gpu.present: "true"
        node.kubernetes.io/instance-type: p4d.24xlarge

      # ── Toleration: GPU nodes are tainted to prevent CPU pods landing there
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
        - key: dedicated
          value: gpu-training
          effect: NoSchedule

      # ── Priority: don't let low-priority experiments starve prod serving ──
      priorityClassName: training-priority

      # ── Init container: stage data from S3 before training starts ─────────
      initContainers:
        - name: data-sync
          image: amazon/aws-cli:2.15.0
          command:
            - aws
            - s3
            - sync
            - s3://my-ml-data/datasets/openwebtext/
            - /data/openwebtext/
            - --no-progress
          env:
            - name: AWS_DEFAULT_REGION
              value: us-east-1
          volumeMounts:
            - name: training-data
              mountPath: /data

      containers:
        - name: trainer
          image: 123456789.dkr.ecr.us-east-1.amazonaws.com/gpt2-trainer:1.0.0
          command: ["torchrun"]
          args:
            - "--nproc_per_node=8"
            - "--nnodes=1"
            - "src/train.py"
            - "--config=/config/training.yaml"
            - "--output_dir=/checkpoints/run-042"

          # ── GPU resource request ───────────────────────────────────────────
          resources:
            requests:
              cpu: "32"
              memory: "128Gi"
              nvidia.com/gpu: "8"       # Request 8 GPUs (full p4d.24xlarge)
            limits:
              cpu: "64"
              memory: "256Gi"
              nvidia.com/gpu: "8"       # Must match requests for GPU

          # ── Environment ───────────────────────────────────────────────────
          env:
            - name: NCCL_DEBUG
              value: "WARN"
            - name: NCCL_SOCKET_IFNAME
              value: "eth0"
            - name: OMP_NUM_THREADS
              value: "8"
            - name: WANDB_API_KEY
              valueFrom:
                secretKeyRef:
                  name: wandb-credentials
                  key: api_key
            - name: HF_HOME
              value: /cache/huggingface

          # ── Volume mounts ─────────────────────────────────────────────────
          volumeMounts:
            - name: training-data
              mountPath: /data
              readOnly: true
            - name: checkpoints
              mountPath: /checkpoints
            - name: hf-cache
              mountPath: /cache/huggingface
            - name: training-config
              mountPath: /config
            - name: dshm                # Shared memory for DataLoader workers
              mountPath: /dev/shm

          # ── Liveness probe (training stall detection) ─────────────────────
          livenessProbe:
            exec:
              command:
                - python
                - -c
                - "import os, time; assert time.time() - os.path.getmtime('/checkpoints/run-042/.heartbeat') < 600"
            initialDelaySeconds: 300
            periodSeconds: 120
            failureThreshold: 3

      volumes:
        - name: training-data
          persistentVolumeClaim:
            claimName: openwebtext-dataset-pvc
        - name: checkpoints
          persistentVolumeClaim:
            claimName: training-checkpoints-pvc
        - name: hf-cache
          emptyDir: {}
        - name: training-config
          configMap:
            name: gpt2-training-config
        - name: dshm
          emptyDir:
            medium: Memory
            sizeLimit: 32Gi

EKS Deep Dive (AWS)

EKS Architecture

Amazon EKS is a managed Kubernetes service where AWS runs and manages the control plane (API server, etcd, scheduler) across three Availability Zones. You pay $0.10/hour for the control plane and standard EC2 pricing for worker nodes. The control plane is not visible or accessible to you directly — only the API endpoint is.

Karpenter — The Right Autoscaler for ML

Cluster Autoscaler works with static node groups and can take 2-5 minutes to add a node. Karpenter directly calls EC2 APIs, provisions heterogeneous instance types, and can have a GPU node running in under 60 seconds. For ML, where a training queue can have 100 pending pods waiting for GPUs, this difference is enormous.

The default Kubernetes scheduler is designed for long-running services, not ML batch jobs. Volcano adds gang scheduling (all pods start or none do), queue management, fair-share policies, and job priorities. It is the scheduler of choice for production ML training platforms.

KEDA for Async Inference Scaling

HPA scales on CPU/memory. KEDA (Kubernetes Event-Driven Autoscaler) scales on external metrics — SQS queue depth, Kafka lag, Prometheus metrics. For async inference (requests queued in SQS), KEDA ensures the right number of GPU workers are running.

k8s/keda-scaled-object.yaml — Scale inference on SQS queue depth
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: inference-worker-scaler
  namespace: ml-serving
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: inference-worker
  minReplicaCount: 0          # Scale to zero when queue is empty!
  maxReplicaCount: 50
  pollingInterval: 15         # Check queue every 15 seconds
  cooldownPeriod: 300         # Wait 5 min before scaling down
  advanced:
    restoreToOriginalReplicaCount: false
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0   # Scale up immediately
          policies:
            - type: Percent
              value: 100
              periodSeconds: 15
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
            - type: Pods
              value: 5
              periodSeconds: 60
  triggers:
    - type: aws-sqs-queue

        name: keda-aws-credentials

Cluster Networking for Distributed Training

RDMA: InfiniBand vs EFA

Multi-node distributed training is bottlenecked by inter-node bandwidth during AllReduce gradient synchronization. Standard Ethernet (even 100 GbE) adds kernel overhead that makes large-scale training inefficient. RDMA (Remote Direct Memory Access) bypasses the kernel and transfers data directly between GPU memory on different nodes.

InfiniBand HDR200 Gbps/port<1 µsOn-prem / OCISR-IOV device pluginGold standard; used by HPC clusters
InfiniBand NDR400 Gbps/port<1 µsOn-premSR-IOV device pluginH100 DGX systems
AWS EFA400 Gbps (p4d)~10 µsAWSEFA device pluginCloud-friendly RDMA; no special switch
AWS EFA v23200 Gbps (p5)~10 µsAWSEFA device pluginH100 instances; enormous bandwidth

Pod Affinity and Anti-Affinity

k8s/affinity-rules.yaml
apiVersion: v1
kind: Pod
metadata:
  name: distributed-trainer
  namespace: ml-training
spec:
  affinity:
    # ── Node affinity: prefer p4d nodes with EFA ─────────────────────────────
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: node.kubernetes.io/instance-type
                operator: In
                values: ["p4d.24xlarge", "p4de.24xlarge", "p5.48xlarge"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["us-east-1a"]    # Keep all pods in same AZ = lower latency

    # ── Pod affinity: co-locate workers in same placement group ──────────────
    podAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          podAffinityTerm:
            labelSelector:
              matchLabels:
                job-name: distributed-trainer
            topologyKey: topology.kubernetes.io/zone

    # ── Pod anti-affinity: spread inference pods across nodes ────────────────
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: model-server
          topologyKey: kubernetes.io/hostname   # 1 server pod per physical node

  containers:
    - name: trainer
      image: my-trainer:latest
      resources:
        limits:
          nvidia.com/gpu: "8"
          # Request EFA network device for RDMA
          vpc.amazonaws.com/efa: "1"
      env:
        - name: FI_PROVIDER
          value: efa
        - name: FI_EFA_USE_DEVICE_RDMA
          value: "1"
        - name: NCCL_ALGO
          value: Ring

Key Takeaways

Containers

  • ✓ Always use multi-stage builds to keep ML images under 10 GB
  • ✓ Pin all dependencies; never use floating versions in production
  • ✓ Run as non-root; always provide a .dockerignore
  • ✓ Use nvcr.io NGC base images for GPU workloads — they include cuDNN, NCCL, and flash-attention
  • ✓ CUDA in image must be ≤ max CUDA supported by host driver

Kubernetes

  • ✓ GPU limits must equal GPU requests — they are non-divisible
  • ✓ Use tolerations + nodeSelectors to isolate GPU nodes from CPU workloads
  • ✓ Volcano is the right batch scheduler for gang-scheduled training jobs
  • ✓ Karpenter dramatically outperforms Cluster Autoscaler for GPU provisioning
  • ✓ KEDA enables scale-to-zero for async inference — critical for cost control

GPU Management

  • ✓ Deploy GPU Operator — it automates driver, device plugin, and DCGM setup
  • ✓ MIG partitions A100/H100 for multi-tenant GPU sharing with true isolation
  • ✓ Monitor DCGM_FI_DEV_GPU_UTIL; alert if util < 60% during training runs
  • ✓ EFA (AWS) or InfiniBand is mandatory for efficient multi-node training

Platform

  • ✓ Use Helm to package ML services — enables versioned, reproducible deploys
  • ✓ EKS + Karpenter on AWS; GKE Standard for TPU; both are excellent choices
  • ✓ Use IRSA (AWS) or Workload Identity (GCP) — never mount static credentials
  • ✓ Prometheus + Grafana + DCGM Exporter is the required observability stack
