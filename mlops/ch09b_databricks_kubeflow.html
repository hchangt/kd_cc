Databricks, Kubeflow & Platform Selection

Deep dives into Databricks (Delta Lake + MLflow + Unity Catalog), Kubeflow as a Kubernetes-native ML platform, MLflow as a full platform, and a rigorous framework for choosing — or building — the right ML platform for your organization.

Section 1: Databricks for ML

Architecture Overview

Databricks is a Lakehouse platform: it unifies data warehousing and ML on a single runtime. The three foundational layers are Delta Lake (ACID-transactional storage on cloud object stores), Apache Spark (distributed compute), and managed MLflow (experiment tracking + model registry). Unity Catalog adds a governance layer across all assets.

Unity Catalog for Data and Model Governance

Unity Catalog (UC) provides a three-level namespace: catalog.schema.table and catalog.schema.model. It enforces column-level access control, captures data lineage automatically, and applies the same permissions to Delta tables, feature store tables, and registered models. This makes it the single source of truth for compliance auditing in regulated industries.

Key UC concepts: Metastore (one per region), Catalogs (environments), Schemas (domains), Tables/Volumes/Models. Unity Catalog replaces the legacy Hive Metastore and workspace-level model registry.

Databricks AutoML

AutoML generates a best-of-breed notebook for classification, regression, or forecasting by running a FLAML/HyperOpt sweep over scikit-learn and XGBoost baselines. Every trial is logged to MLflow. You get transparent, editable Python code — not a black-box API. This is its key differentiator versus SageMaker Autopilot.

Feature Store on Databricks

The Databricks Feature Store persists feature tables as Delta tables, enforces point-in-time lookups to prevent leakage, and packages features into models so that online serving automatically retrieves them from an online store (DynamoDB, Cosmos DB, or Bigtable). The FeatureEngineeringClient API links training data to model lineage.

Code: Databricks ML Pipeline (Notebook Style)

# Databricks notebook — cells separated by # COMMAND ----------
import mlflow
import mlflow.sklearn
from databricks.feature_engineering import FeatureEngineeringClient
from pyspark.sql import functions as F
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import roc_auc_score
import pandas as pd

# COMMAND ----------
# 1. Load features from Feature Store
fe = FeatureEngineeringClient()
training_set = fe.create_training_set(
    df=spark.table("ml_catalog.churn.labels"),
    feature_lookups=[
        fe.FeatureLookup(
            table_name="ml_catalog.churn.customer_features",
            feature_names=["tenure_days", "monthly_spend", "support_tickets"],
            lookup_key="customer_id",
        )
    ],
    label="churned",
    exclude_columns=["customer_id"],
)
df = training_set.load_df().toPandas()

# COMMAND ----------
# 2. Train with MLflow autolog
mlflow.sklearn.autolog(log_input_examples=True)
X, y = df.drop("churned", axis=1), df["churned"]
X_train, X_test = X[:8000], X[8000:]
y_train, y_test = y[:8000], y[8000:]

with mlflow.start_run(run_name="gbm_churn_v1") as run:
    model = GradientBoostingClassifier(n_estimators=200, max_depth=5)
    model.fit(X_train, y_train)
    auc = roc_auc_score(y_test, model.predict_proba(X_test)[:,1])
    mlflow.log_metric("test_auc", auc)
    # Log model WITH feature store metadata for online serving
    fe.log_model(
        model=model,
        artifact_path="model",
        flavor=mlflow.sklearn,
        training_set=training_set,
    )
    print(f"AUC: {auc:.4f}  Run: {run.info.run_id}")

# COMMAND ----------
# 3. Register in Unity Catalog Model Registry
mlflow.set_registry_uri("databricks-uc")
model_uri = f"runs:/{run.info.run_id}/model"
mv = mlflow.register_model(model_uri, "ml_catalog.churn.gbm_churn")
client = mlflow.tracking.MlflowClient()
client.set_registered_model_alias("ml_catalog.churn.gbm_churn", "champion", mv.version)
print(f"Registered version {mv.version} as @champion")

Section 2: Kubeflow

Kubernetes-Native ML Platform

Kubeflow is a collection of Kubernetes-native tools for ML workflows. Unlike managed platforms, Kubeflow gives you complete control: any cloud, any hardware, no vendor lock-in. The trade-off is operational complexity — you own the Kubernetes cluster and all its components.

Core Components

  • Kubeflow Pipelines (KFP v2): DAG-based ML pipelines compiled to Argo Workflows. Python SDK for defining components and pipelines as reusable, containerized steps.
  • Training Operator: Custom Resources (TFJob, PyTorchJob, MXNetJob, XGBoostJob) for distributed training across multiple pods with synchronized parameter updates.
  • Katib: Kubernetes-native HPO supporting grid search, random search, Bayesian optimization (using Optuna), and neural architecture search.
  • KServe: Kubernetes-native model serving with canary rollout, traffic splitting, pre/post-processing transformers, and explainers. Formerly KFServing.
  • Notebooks: JupyterHub-based multi-user notebook environment with GPU quota management per namespace.

Code: Kubeflow Pipeline (KFP v2 SDK)

from kfp import dsl, compiler
from kfp.dsl import Dataset, Model, Metrics, Input, Output

@dsl.component(base_image="python:3.11-slim",
               packages_to_install=["scikit-learn==1.4.0", "pandas", "joblib"])
def train_model(
    dataset: Input[Dataset],
    model: Output[Model],
    metrics: Output[Metrics],
    n_estimators: int = 100,
    max_depth: int = 6,
):
    import pandas as pd
    from sklearn.ensemble import RandomForestClassifier
    from sklearn.metrics import roc_auc_score
    import joblib, json

    df = pd.read_parquet(dataset.path)
    X, y = df.drop("label", axis=1), df["label"]
    split = int(len(df) * 0.8)
    clf = RandomForestClassifier(n_estimators=n_estimators, max_depth=max_depth)
    clf.fit(X[:split], y[:split])
    auc = roc_auc_score(y[split:], clf.predict_proba(X[split:])[:,1])
    joblib.dump(clf, model.path + "/model.joblib")
    metrics.log_metric("auc", auc)
    metrics.log_metric("n_estimators", n_estimators)


@dsl.component(base_image="python:3.11-slim",
               packages_to_install=["mlflow", "joblib"])
def register_model(
    model: Input[Model],
    metrics: Input[Metrics],
    model_name: str,
    mlflow_uri: str,
):
    import mlflow, joblib
    mlflow.set_tracking_uri(mlflow_uri)
    auc = metrics.metadata["auc"]
    with mlflow.start_run():
        import sklearn
        clf = joblib.load(model.path + "/model.joblib")
        mlflow.sklearn.log_model(clf, "model",
                                 registered_model_name=model_name)
        mlflow.log_metric("auc", auc)


@dsl.pipeline(name="rf-training-pipeline", description="Random Forest training + registration")
def ml_pipeline(
    data_gcs_path: str = "gs://my-bucket/data/train.parquet",
    model_name: str = "rf-classifier",
    mlflow_uri: str = "http://mlflow-server:5000",
    n_estimators: int = 200,
    max_depth: int = 8,
):
    # Step 1: load data (in real pipeline, use a data loading component)
    train_op = train_model(
        dataset=dsl.importer(artifact_uri=data_gcs_path,
                             artifact_class=Dataset).output,
        n_estimators=n_estimators,
        max_depth=max_depth,
    )
    train_op.set_cpu_request("2").set_memory_request("4Gi")

    # Step 2: register only if AUC > threshold
    with dsl.If(train_op.outputs["metrics"].metadata["auc"] > 0.75):
        reg_op = register_model(
            model=train_op.outputs["model"],
            metrics=train_op.outputs["metrics"],
            model_name=model_name,
            mlflow_uri=mlflow_uri,
        )
        reg_op.set_cpu_request("1").set_memory_request("2Gi")


if __name__ == "__main__":
    compiler.Compiler().compile(ml_pipeline, "ml_pipeline.yaml")
    print("Pipeline compiled to ml_pipeline.yaml")

Section 3: MLflow as a Full Platform

Beyond Experiment Tracking

Most teams use MLflow only for mlflow.log_metric(), but the full platform spans five components: Tracking (experiments/runs), Projects (reproducible code packaging), Models (model flavor abstraction), Registry (lifecycle management), and Serving (REST inference endpoints). Together they form a complete, cloud-agnostic ML platform at zero cost.

MLflow Tracking + Projects + Models + Registry

  • Tracking: Logs params, metrics, artifacts, tags. Stores to local FS, S3/GCS/ADLS, or MLflow server backed by PostgreSQL/MySQL.
  • Projects: MLproject YAML + conda/Docker env = reproducible entry points. Run with mlflow run git://github.com/org/repo.
  • Models: Framework-agnostic model format. A model directory contains MLmodel YAML, the serialized artifact, conda env, and requirements.txt. Supports 30+ flavors.
  • Registry: Versioned models with stages (Staging, Production, Archived). UC-backed registry uses three-level namespaces.

Section 4: Platform Selection Framework

Make vs Buy Decision Framework

The decision to build or buy an ML platform hinges on three axes: differentiation (does this capability create competitive advantage?), operational burden (who runs it at 3am?), and total cost of ownership over three years including engineering time.

The hidden cost of "free" open-source: A self-hosted Kubeflow cluster requires 0.5–1.0 FTE of platform engineering to maintain at production quality. Factor this into any "free" calculation.

Section 5: Building an Internal ML Platform

The Internal Developer Platform Concept

An Internal ML Platform (IMLP) is a product your platform team builds for internal ML engineers. The goal is a self-service "paved road": sensible defaults for infra, observability, and deployment that let ML engineers focus on model logic rather than K8s YAML. Think of it as a thin opinionated layer over Kubeflow, Databricks, or your cloud of choice.

Developer Experience Metrics

Measure platform quality with time-based DX metrics tracked as P50/P95 across ML team runs:

  • Time-to-first-experiment: New engineer runs first tracked experiment. Target P50 < 30 min.
  • Time-to-staging: Model goes from notebook to staging endpoint. Target P50 < 4 hrs, P95 < 1 day.
  • Time-to-production: Full deployment including approval. Target P50 < 3 days, P95 < 2 weeks.
  • Retraining cycle time: Data update to new model in production. Target P50 < 6 hrs.
  • Incident recovery time: Model degradation to rollback complete. Target P95 < 30 min.

Platform Team Structure (3-Tier)

  • Tier 1 — Infra: K8s cluster management, networking, GPU drivers, storage (PVC, object store). SRE-adjacent. Owns uptime SLAs.
  • Tier 2 — Platform: Kubeflow/Databricks configuration, MLflow server, CI/CD templates, cost tooling. The "paved road" builders.
  • Tier 3 — ML Enablement: Embedded in ML teams. Templates, SDKs, onboarding. The "inner loop" advocates who translate platform capabilities into ML workflows.

Code: Platform API Design (Internal ML Gateway)

"""
Internal ML Gateway — provides a unified Python SDK over
multiple backends (Databricks, Kubeflow, local).
Pattern: Adapter over heterogeneous infrastructure.
"""
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import Optional
import os

@dataclass
class TrainRequest:
    experiment_name: str
    git_ref: str              # commit SHA or branch
    entry_point: str          # e.g. "train"
    parameters: dict

Section 6: Migration Strategies

Migrating from Jupyter Scripts to Pipelines

The most common migration path is monolithic notebook → modular pipeline steps. The key insight: don't refactor and migrate simultaneously. First wrap the notebook as a single pipeline step (no logic changes), then iteratively decompose it into steps as you gain confidence in the pipeline framework.

  1. Phase 0 — Baseline: Add MLflow logging to existing notebooks. Establish metric baselines before touching code structure.
  2. Phase 1 — Containerize: Wrap notebook in a Docker image, run via papermill. Notebook still works locally unchanged.
  3. Phase 2 — Single-step pipeline: Submit the container as one pipeline step. CI/CD now owns execution.
  4. Phase 3 — Decompose: Split into data loading, preprocessing, training, evaluation, registration steps. Each step has typed inputs/outputs.
  5. Phase 4 — Parameterize: Remove hardcoded paths and hyperparameters. Enable triggered retraining.

Migrating Between Orchestrators

Moving from Airflow to Kubeflow Pipelines, or from Kubeflow to Databricks Workflows, follows a pattern: the business logic (training code) is portable; only the orchestration glue (DAG definitions, I/O passing) needs rewriting. Factor your pipeline so operators are thin wrappers over shared library functions.

Portability pattern: Define pipeline steps as Python functions that accept paths as strings and write outputs to paths. This makes each step runnable standalone (unit testable), in any orchestrator, or locally — with zero changes to the function body.

Risk Mitigation During Migration

  • Shadow mode first: Run new pipeline in parallel with old system, compare outputs. Only cut over when P99 latency and metric parity are confirmed.
  • Feature flags: Use a simple config flag to switch traffic between old and new inference path. Roll back in <5 minutes without a code deploy.
  • Data contract testing: Write Great Expectations or Pydantic validators at every pipeline input boundary before migrating. Data schema bugs are the #1 cause of silent model degradation post-migration.
  • Metric continuity: Ensure business metrics (revenue, CTR, CSAT) are tracked across the migration boundary, not just model AUC. A migration that improves AUC but breaks upstream feature logic will regress silently.
  • Rollback checkpoints: Keep the previous pipeline version operational for 30 days post-cutover. Migration is complete only when you've seen a full retraining cycle succeed end-to-end.

Summary & Key Takeaways

Chapters 9 and 9B together cover the five dominant ML platform approaches. The right choice is context-dependent — there is no universal winner. Here are the principles that survive across all contexts:

1. Match platform to data architecture

If your data lives in Delta Lake and your teams run Spark, Databricks is the natural fit. If your data is in BigQuery, Vertex AI's integration will save weeks. Platform selection should follow data gravity.

2. Kubeflow is powerful but operationally demanding

Start with standalone KFP, not the full Kubeflow manifest. Add components incrementally as your team builds K8s expertise. Full Kubeflow is a 0.75 FTE commitment minimum.

3. MLflow is the universal connector

Even if you run Vertex AI or SageMaker, keeping MLflow as your experiment tracking layer gives you platform portability. Migrate the orchestrator; your experiment history travels with you.

4. Lock-in is real but manageable

Separate your model training code from the platform's orchestration API. If your training functions accept file paths as inputs and write to file paths as outputs, you can swap orchestrators in weeks, not months.

5. Internal platforms need a product owner

Without a PM mindset — user research, DX metrics, roadmap prioritization — internal ML platforms degrade into a collection of half-integrated tools. Treat internal users as customers.

6. Migrate incrementally, validate continuously

Shadow mode, feature flags, and data contract tests are the migration trilogy. Never cut over without a tested rollback path. The business cost of a broken migration exceeds the cost of running both systems in parallel for 30 days.
