LLM Training and Adaptation Overview

The foundation model paradigm fundamentally changed how we build AI systems. Instead of training task-specific models from scratch, practitioners now start from a large pretrained model and adapt it. The pretrained model has already consumed trillions of tokens of internet text, code, and scientific literature — compressing world knowledge into billions of parameters. The job of LLM Ops is to unlock that knowledge for specific use cases while maintaining reliability, safety, and cost efficiency in production.

This chapter is written from the perspective of someone who has run RLHF pipelines at scale. The decisions that look obvious in retrospect — how much SFT data you need before RL, why KL penalties matter, how to detect reward hacking before it destroys your model — are the things that trip up every team the first time. We will cover all of it.

1.1 The Foundation Model Paradigm

Foundation models are trained via self-supervised learning on massive corpora. The dominant objective is next-token prediction (autoregressive language modeling). At sufficiently large scale, emergent capabilities appear: in-context learning, chain-of-thought reasoning, instruction following, and tool use. These capabilities do not need to be explicitly trained — they emerge from scale.

The Scaling Hypothesis

Kaplan et al. (2020) showed that loss scales as a power law with compute, data, and parameters. Chinchilla (Hoffmann et al., 2022) refined this: for a given compute budget, you should train a smaller model on more tokens. Chinchilla-optimal models train ~20 tokens per parameter. LLaMA-3 and Mistral took this further, overtrained small models to produce highly capable, inference-efficient checkpoints.

Supervised Fine-Tuning (SFT)

Supervised Fine-Tuning transforms a raw pretrained model — which knows how to continue text — into a model that follows instructions. The key insight is that pretrained models already contain the knowledge required for most tasks; SFT teaches them the format and the disposition to be helpful. This is why even small SFT datasets (1K–10K high-quality examples) can produce dramatic improvements.

2.1 SFT Dataset Preparation

SFT data consists of instruction-response pairs. Quality dominates quantity: a dataset of 1,000 carefully curated examples written by skilled annotators typically outperforms 100,000 examples scraped from the web. The LIMA paper (Zhou et al., 2023) demonstrated this with 1,000 examples achieving near-GPT-4 instruction following.

Two dominant data formats exist: ChatML (used by OpenAI, adopted widely) and Alpaca (Stanford, simpler for single-turn tasks).

2.2 SFT with Hugging Face TRL

TRL (Transformer Reinforcement Learning) is the de-facto library for LLM fine-tuning. Its SFTTrainer handles dataset formatting, gradient checkpointing, packing, and wandb logging out of the box.

SFT Hyperparameter Guidance

  • Learning rate: 1e-5 to 5e-5 for 7B models. Lower (1e-5) for larger models or smaller datasets to avoid catastrophic forgetting.
  • Epochs: 1–3 epochs. More than 3 often causes overfitting on small datasets.
  • Warmup: 3–5% warmup ratio. LLMs are sensitive to the first few steps.
  • Batch size: Effective batch of 64–128 sequences is a good default. Use gradient accumulation.
  • Packing: Enable sequence packing to improve GPU utilization by 30–60%. Disable if samples have different instruction types that shouldn't cross-contaminate.

import torch
from transformers import DataCollatorForSeq2Seq

def mask_user_tokens(example: dict, tokenizer) -> dict:
    """
    Set labels = -100 for all tokens except the assistant's response.
    This ensures we only backprop through the model's own outputs.
    """
    input_ids = example["input_ids"]
    labels = list(input_ids)

    # Find assistant response start by locating the last occurrence of
    # the assistant header tokens in the sequence.
    # (Model-specific — adjust token IDs accordingly)
    assistant_start = None
    for i in range(len(input_ids) - 1, -1, -1):
        if input_ids[i] == tokenizer.convert_tokens_to_ids("<|start_header_id|>"):
            assistant_start = i
            break

    if assistant_start is not None:
        for i in range(assistant_start):
            labels[i] = -100   # mask system + user tokens

    return {"input_ids": input_ids, "labels": labels}

Parameter-Efficient Fine-Tuning (PEFT)

Full fine-tuning a 7B model requires ~56GB of GPU memory in bfloat16 (model weights + optimizer states + gradients). PEFT methods reduce this by 10–100× while achieving 95–99% of full fine-tuning performance on most tasks. The key insight: most of the model's parameters don't need to change — only a small, low-rank perturbation is required to teach new behaviors.

3.1 LoRA: Low-Rank Adaptation

LoRA (Hu et al., 2021) decomposes the weight update matrix ΔW into two low-rank matrices: ΔW = BA, where B ∈ ℝd×r and A ∈ ℝr×k, and r ≪ min(d, k). Instead of updating W directly, LoRA freezes W and trains only B and A. At inference, the adapter is merged: W' = W + (α/r) · BA.

For a 7B model with r=16 applied to Q,K,V,O projections, LoRA adds roughly 20M trainable parameters versus 7B — less than 0.3% of the total. Memory savings are dramatic because optimizer states only track the adapter parameters.

python — lora_config.py
# ── LoRA Configuration with PEFT ─────────────────────────────────────────────
from peft import LoraConfig, get_peft_model, TaskType
from transformers import AutoModelForCausalLM
import torch

def create_lora_model(
    base_model_name: str,
    lora_r: int = 16,
    lora_alpha: int = 32,
    lora_dropout: float = 0.05,
    target_modules: list[str] | None = None,
):
    """
    r:           rank of the decomposition (8–64 typical; 16 is a good default)
    alpha:       scaling factor; effective lr scale = alpha / r
                 set alpha = 2*r for a neutral scale (many practitioners do alpha=r)
    dropout:     regularization; 0.05–0.1 for small datasets
    target_modules: which weight matrices to adapt
    """
    if target_modules is None:
        # LLaMA / Mistral attention projections + MLP gates
        target_modules = ["q_proj", "k_proj", "v_proj", "o_proj",
                          "gate_proj", "up_proj", "down_proj"]

    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=lora_r,
        lora_alpha=lora_alpha,
        lora_dropout=lora_dropout,
        target_modules=target_modules,
        bias="none",           # don't train biases
        inference_mode=False,
    )

    model = AutoModelForCausalLM.from_pretrained(
        base_model_name,
        torch_dtype=torch.bfloat16,
        device_map="auto",
    )
    model = get_peft_model(model, lora_config)
    model.print_trainable_parameters()
    # Output: trainable params: 20,185,088 || all params: 8,030,261,248
    #         trainable%: 0.2513%
    return model

# ── Merging LoRA back into base weights after training ───────────────────────
def merge_lora_adapter(peft_model_path: str, output_path: str):
    from peft import AutoPeftModelForCausalLM
    model = AutoPeftModelForCausalLM.from_pretrained(
        peft_model_path,
        torch_dtype=torch.bfloat16,
        device_map="auto",
    )
    merged = model.merge_and_unload()   # fuses LoRA into base weights
    merged.save_pretrained(output_path)
    print(f"Merged model saved to {output_path}")

3.2 QLoRA: 4-bit Quantized LoRA

QLoRA (Dettmers et al., 2023) quantizes the frozen base model to 4-bit NormalFloat (NF4) and trains LoRA adapters in bfloat16. A 65B model fits on a single 48GB A6000. The key innovations are NF4 quantization (optimal for normally-distributed weights), double quantization (quantizing the quantization constants), and paged optimizers (using CPU RAM as overflow for GPU OOM situations).

DoRA vs LoRA: When to Switch

DoRA (Liu et al., 2024) decomposes weight updates into magnitude and direction components, training direction with LoRA and magnitude separately. It consistently outperforms LoRA by 1–3 points on benchmarks with the same parameter budget. If you're already using LoRA and want a free upgrade, just set use_dora=True in your LoraConfig.

RLHF — Reinforcement Learning from Human Feedback

RLHF is the alignment technique that turned raw language models into assistants. The core idea is to capture human preferences in a reward model, then optimize the language model's policy against that reward signal using reinforcement learning. First described for summarization by Stiennon et al. (2020), it became the backbone of InstructGPT, ChatGPT, Claude, and every aligned assistant since.

RLHF is Genuinely Hard

I've run RLHF at scale. The reward model will be exploited. The policy will find pathological behaviors you didn't anticipate. KL divergence needs to be tuned carefully. If the KL is too low, the model drifts to reward hacking. If too high, you barely move from SFT. Plan for 3–5 iteration cycles before convergence. DPO avoids some of this complexity — read Section 4.4 before committing to PPO.

4.2 Reward Model Training

The reward model takes a (prompt, response) pair and outputs a scalar score. It is trained on human preference data: pairs of responses to the same prompt where humans indicated which they preferred. The training objective is the Bradley-Terry model: maximize the probability that the chosen response scores higher than the rejected one.

python — reward_model_training.py

4.3 PPO Training

Proximal Policy Optimization is the standard RL algorithm for RLHF. The reward for each generated response combines the reward model score with a KL divergence penalty against the SFT reference model. This prevents the policy from drifting to degenerate outputs that fool the reward model.

The combined reward: r(x,y) = r_RM(x,y) − β · KL[π_θ(y|x) || π_ref(y|x)]

from transformers import AutoTokenizer, pipeline
from datasets import load_dataset
import torch

# ── Models needed for PPO ─────────────────────────────────────────────────────
# 1. Policy model (trainable) — initialized from SFT checkpoint
# 2. Reference model (frozen) — same SFT checkpoint, used for KL
# 3. Reward model — trained separately (Section 4.2)
# 4. Value model — head on top of policy, estimates expected return

SFT_CHECKPOINT = "./sft-llama3-8b"

reward_pipe = pipeline(
    "text-classification",
    model=RM_CHECKPOINT,
    tokenizer=RM_CHECKPOINT,
    device_map="auto",
    torch_dtype=torch.bfloat16,
)

# ── PPO Config ────────────────────────────────────────────────────────────────
ppo_config = PPOConfig(
    model_name=SFT_CHECKPOINT,
    learning_rate=1.4e-5,
    batch_size=64,
    mini_batch_size=8,
    gradient_accumulation_steps=1,
    optimize_cuda_cache=True,
    early_stopping=False,
    target_kl=6.0,          # target KL divergence from reference policy
    kl_penalty="kl",        # "kl" or "abs" or "mse" — affects stability
    init_kl_coef=0.2,       # β in the KL penalty term
    adap_kl_ctrl=True,      # adaptively adjust β to hit target_kl
    horizon=10_000,
    gamma=1.0,
    lam=0.95,
    cliprange=0.2,
    cliprange_value=0.2,
    vf_coef=0.1,
    log_with="wandb",
)

trainer = PPOTrainer(
    config=ppo_config,
    model=model,
    tokenizer=tokenizer,
)

# ── Training loop ─────────────────────────────────────────────────────────────
prompts_dataset = load_dataset("HuggingFaceH4/ultrafeedback_binarized", split="train_prefs")

for epoch in range(1):
    for batch in trainer.dataloader:
        # Generate responses from current policy
        query_tensors = [tokenizer.encode(p, return_tensors="pt").squeeze() for p in batch["prompt"]]
        response_tensors = trainer.generate(
            query_tensors,
            max_new_tokens=256,
            do_sample=True,
            temperature=0.7,
            top_p=0.9,
        )

        # Score responses with reward model
        texts = [tokenizer.decode(r, skip_special_tokens=True) for r in response_tensors]
        rewards = [torch.tensor(r["score"]) for r in reward_pipe(texts)]

        # PPO step — computes advantage, runs multiple epochs of clipped policy gradient
        stats = trainer.step(query_tensors, response_tensors, rewards)
        trainer.log_stats(stats, batch, rewards)

trainer.save_pretrained("./ppo-llama3-8b")

4.4 DPO: Direct Preference Optimization

DPO (Rafailov et al., 2023) eliminates the separate reward model and RL loop entirely. It directly optimizes the policy on preference data using a reparameterization of the RLHF objective. The insight is that the optimal policy under the RLHF objective can be expressed in closed form, allowing training with a simple binary cross-entropy loss.

DPO loss: L = -E[log σ(β · log π_θ(y_w|x)/π_ref(y_w|x) − β · log π_θ(y_l|x)/π_ref(y_l|x))] where y_w is the preferred (chosen) response and y_l is the dispreferred (rejected) response.

Constitutional AI and RLAIF

Constitutional AI (CAI) was developed at Anthropic as a solution to a fundamental scaling problem: human preference labeling is expensive and slow. CAI replaces human labelers with a powerful AI model operating under a set of explicit principles — a "constitution." This enables RLHF at scale without proportionally increasing human annotation costs.

5.2 RLAIF Implementation

RLAIF (Lee et al., 2023) showed that AI-generated preference labels can match human labels in quality for alignment tasks. The key is careful prompt design for the judge model.

python — rlaif_pipeline.py
# ── RLAIF: LLM-as-Preference-Labeler ─────────────────────────────────────────
from anthropic import Anthropic
from datasets import Dataset
import json

client = Anthropic()

CONSTITUTION_PRINCIPLES = [
    "Choose the response that is most helpful while being honest and harmless.",
    "Prefer responses that are accurate and acknowledge uncertainty when appropriate.",
    "Choose the response that better respects human autonomy and avoids paternalism.",
    "Prefer responses that are more concise and direct without being unhelpful.",
]

def generate_ai_preference_label(
    prompt: str,
    response_a: str,
    response_b: str,
    principle: str,
    judge_model: str = "claude-opus-4-5",
) -> dict:
    """
    Use a powerful LLM to generate preference labels for RLAIF.
    Returns: {"preferred": "A" or "B", "reasoning": str, "confidence": float}
    """
    judge_prompt = f"""You are evaluating two AI assistant responses.

Evaluation principle: {principle}

Human prompt:
{prompt}

Response A:
{response_a}

Response B:
{response_b}

Which response better adheres to the principle? Reply with a JSON object:
{{"preferred": "A" or "B", "reasoning": "...", "confidence": 0.0-1.0}}"""

    message = client.messages.create(
        model=judge_model,
        max_tokens=512,
        messages=[{"role": "user", "content": judge_prompt}],
    )
    result = json.loads(message.content[0].text)
    return result

def build_rlaif_dataset(
    prompts: list[str],
    policy_model_fn,      # function(prompt) -> response
    n_responses: int = 2,
) -> Dataset:
    """Build a preference dataset using AI feedback."""
    examples = []
    for prompt in prompts:
        # Generate multiple responses from current policy
        responses = [policy_model_fn(prompt) for _ in range(n_responses)]
        # Use AI judge to rank them
        principle = CONSTITUTION_PRINCIPLES[0]  # rotate principles in production
        label = generate_ai_preference_label(
            prompt, responses[0], responses[1], principle
        )
        if label["confidence"] > 0.7:   # only keep high-confidence labels
            chosen  = responses[0] if label["preferred"] == "A" else responses[1]
            rejected = responses[1] if label["preferred"] == "A" else responses[0]
            examples.append({
                "prompt": prompt,
                "chosen": chosen,
                "rejected": rejected,
                "confidence": label["confidence"],
            })
    return Dataset.from_list(examples)

def run_llm_judge_evaluation(
    eval_dataset: list[dict],
    model_a_generate_fn,
    model_b_generate_fn,
    n_samples: int = 100,
) -> dict:
    """
    Compare two models on a question dataset.
    Returns win rates and average scores.
    """
    results = {"wins_a": 0, "wins_b": 0, "ties": 0, "scores_a": [], "scores_b": []}

    for example in eval_dataset[:n_samples]:
        question = example["question"]
        response_a = model_a_generate_fn(question)
        response_b = model_b_generate_fn(question)

        # Randomize order to reduce position bias
        import random
        if random.random() > 0.5:
            result = judge_responses(question, response_a, response_b)
        else:
            result = judge_responses(question, response_b, response_a)
            # Flip winner back
            result.winner = "B" if result.winner == "A" else ("A" if result.winner == "B" else "tie")

        if result.winner == "A":
            results["wins_a"] += 1
        elif result.winner == "B":
            results["wins_b"] += 1
        else:
            results["ties"] += 1
        results["scores_a"].append(result.score_a)
        results["scores_b"].append(result.score_b)

    n = len(eval_dataset[:n_samples])
    return {
        "win_rate_a": results["wins_a"] / n,
        "win_rate_b": results["wins_b"] / n,
        "tie_rate":   results["ties"] / n,
        "avg_score_a": sum(results["scores_a"]) / n,
        "avg_score_b": sum(results["scores_b"]) / n,
    }

    gen = pipeline("text-generation", model=model_path, device_map="auto",
                   torch_dtype="auto", max_new_tokens=256)

    results = {"passed": 0, "failed": 0, "cases": []}
    for case in GOLDEN_EVALS:
        output = gen(case.prompt)[0]["generated_text"]
        passed = True
        failures = []

        if case.expected_contains:
            for substr in case.expected_contains:
                if substr.lower() not in output.lower():
                    passed = False
                    failures.append(f"missing: '{substr}'")

        if case.expected_not_contains:
            for substr in case.expected_not_contains:
                if substr.lower() in output.lower():
                    passed = False
                    failures.append(f"found forbidden: '{substr}'")

        results["cases"].append({
            "id": case.id, "passed": passed,
            "output": output[:200], "failures": failures,
        })
        if passed:
            results["passed"] += 1
        else:
            results["failed"] += 1

    return results

import yaml
from pathlib import Path
from typing import Any

class PromptTemplate:
    """Versioned, testable prompt template."""
    def __init__(self, path: str):
        self._path = Path(path)
        data = yaml.safe_load(self._path.read_text())
        self.name: str    = data["name"]
        self.version: str = data["version"]
        self.system: str  = data.get("system", "")
        self.user: str    = data["user"]
        self.examples: list = data.get("examples", [])
        self.model: str   = data.get("model", "claude-sonnet-4-6")
        self.params: dict = data.get("params", {})

    def render(self, **kwargs: Any) -> list[dict]:
        """Render template with variables → messages list."""
        messages = []
        for ex in self.examples:
            messages.append({"role": "user",      "content": ex["user"]})
            messages.append({"role": "assistant",  "content": ex["assistant"]})
        messages.append({
            "role": "user",
            "content": Template(self.user).safe_substitute(**kwargs),
        })
        return messages

    def run(self, **kwargs: Any) -> str:
        messages = self.render(**kwargs)
        system = Template(self.system).safe_substitute(**kwargs) if self.system else None
        response = client.messages.create(
            model=self.model,
            max_tokens=self.params.get("max_tokens", 1024),
            system=system,
            messages=messages,
        )
        return response.content[0].text

Prompt Injection Defense

Prompt injection is the LLM equivalent of SQL injection — untrusted user input overrides system instructions. Defenses: (1) Structural separation: put system instructions in the system field, never concatenate with user input. (2) Input sanitization: strip or escape characters like "Ignore previous instructions". (3) Canary tokens: embed a secret token in the system prompt and alert if it appears in the output. (4) Output validation: check responses for signs of instruction override before returning to users.

# ── 1. Indexing: chunk and embed documents ────────────────────────────────────
def chunk_text(text: str, chunk_size: int = 800, overlap: int = 100) -> list[str]:
    """Sliding window chunking with overlap for context continuity."""
    words = text.split()
    chunks, i = [], 0
    while i < len(words):
        chunk = " ".join(words[i:i + chunk_size])
        chunks.append(chunk)
        i += chunk_size - overlap
    return chunks

def index_documents(doc_paths: list[str]):
    """Index a list of text files into ChromaDB."""
    ids, documents, metadatas = [], [], []
    for path in doc_paths:
        text = Path(path).read_text()
        chunks = chunk_text(text)
        for j, chunk in enumerate(chunks):
            ids.append(f"{path}::{j}")
            documents.append(chunk)
            metadatas.append({"source": path, "chunk": j})
    collection.add(ids=ids, documents=documents, metadatas=metadatas)
    print(f"Indexed {len(ids)} chunks from {len(doc_paths)} documents.")

# ── 2. Retrieval ──────────────────────────────────────────────────────────────
def retrieve(query: str, top_k: int = 5) -> list[dict]:
    results = collection.query(
        query_texts=[query],
        n_results=top_k,
        include=["documents", "metadatas", "distances"],
    )
    return [
        {"text": doc, "source": meta["source"], "score": 1 - dist}
        for doc, meta, dist in zip(
            results["documents"][0],
            results["metadatas"][0],
            results["distances"][0],
        )
    ]

# ── 3. Generation with retrieved context ──────────────────────────────────────
RAG_SYSTEM = """You are a helpful assistant that answers questions based on the provided context.
If the context does not contain enough information to answer, say so honestly.
Always cite the source document when using specific information."""

def rag_query(question: str, top_k: int = 5) -> dict:
    chunks = retrieve(question, top_k=top_k)
    context = "\n\n".join(
        f"[Source: {c['source']}]\n{c['text']}" for c in chunks
    )
    messages = [
        {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
    ]
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        system=RAG_SYSTEM,
        messages=messages,
    )
    return {
        "answer": response.content[0].text,
        "sources": [c["source"] for c in chunks],
        "chunks_used": len(chunks),
    }

def traced_llm_call(tags: dict | None = None):
    """Decorator that adds telemetry to any Anthropic API call."""
    def decorator(fn):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            trace_id = str(uuid.uuid4())
            start = time.monotonic()
            error = None
            response = None
            try:
                response = fn(*args, **kwargs)
                return response
            except Exception as e:
                error = str(e)
                raise
            finally:
                latency_ms = (time.monotonic() - start) * 1000
                if response and hasattr(response, "usage"):
                    in_tok  = response.usage.input_tokens
                    out_tok = response.usage.output_tokens
                    model   = response.model
                    trace = LLMTrace(
                        trace_id=trace_id,
                        session_id=kwargs.get("session_id", "unknown"),
                        timestamp=datetime.now(timezone.utc).isoformat(),
                        model=model,
                        prompt_tokens=in_tok,
                        completion_tokens=out_tok,
                        total_tokens=in_tok + out_tok,
                        latency_ms=round(latency_ms, 2),
                        cost_usd=calculate_cost(model, in_tok, out_tok),
                        prompt_preview=str(kwargs.get("messages", ""))[:200],
                        response_preview=response.content[0].text[:200] if not error else "",
                        tags=tags or {},
                        error=error,
                    )
                    # Emit to your observability backend (Langfuse, Datadog, etc.)
                    emit_trace(trace)
        return wrapper
    return decorator

Model Merging

Model merging combines the weights of multiple fine-tuned models into a single model that inherits capabilities from all of them — without any additional training. It is one of the most underrated techniques in open-source LLM development. Many top-ranked models on the Open LLM Leaderboard are merges, not directly trained models.

# ── Programmatic model merging with mergekit ──────────────────────────────────
# For SLERP interpolation between two models (simple, effective for 2-model blend)

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

def slerp_merge(
    model_a_path: str,
    model_b_path: str,
    alpha: float = 0.5,    # 0 = all model A, 1 = all model B
    output_path: str = "./merged-model",
):
    """
    SLERP (Spherical Linear Interpolation) merge.
    Better than linear interpolation for preserving model capabilities.
    """
    print(f"Loading models...")
    model_a = AutoModelForCausalLM.from_pretrained(model_a_path, torch_dtype=torch.float32)
    model_b = AutoModelForCausalLM.from_pretrained(model_b_path, torch_dtype=torch.float32)

    merged_state = {}
    for key in model_a.state_dict().keys():
        w_a = model_a.state_dict()[key].float()
        w_b = model_b.state_dict()[key].float()

        # SLERP: interpolate along the unit sphere
        dot = torch.sum(w_a * w_b) / (torch.norm(w_a) * torch.norm(w_b) + 1e-8)
        dot = dot.clamp(-1, 1)
        theta = torch.acos(dot)

        if theta.abs() < 1e-4:
            # Nearly parallel — use linear interpolation
            merged_state[key] = (1 - alpha) * w_a + alpha * w_b
        else:
            merged_state[key] = (
                torch.sin((1 - alpha) * theta) / torch.sin(theta) * w_a +
                torch.sin(alpha * theta)        / torch.sin(theta) * w_b
            )
        merged_state[key] = merged_state[key].to(torch.bfloat16)

    model_a.load_state_dict(merged_state)
    model_a.save_pretrained(output_path)

    tokenizer = AutoTokenizer.from_pretrained(model_a_path)
    tokenizer.save_pretrained(output_path)
    print(f"Merged model saved to {output_path}")

When Merging Beats Fine-tuning

Model merging is compelling when: (1) you have two specialized models and want both capabilities without training from scratch; (2) you want to combine instruction-following quality from one model with domain knowledge from another; (3) compute budget is limited. Merging is free at inference time after the one-time merge cost. The failure mode is capability seesaw — pushing one axis down while merging another up. Always run your full eval suite after a merge.

Key Takeaways

1. Start with prompting, earn fine-tuning

90% of use cases can be solved with better prompting or RAG. Fine-tuning makes sense when you have >1K high-quality examples and a task that requires consistent style, format, or domain knowledge not in the base model. Compute and iteration time are real costs — spend them wisely.

2. QLoRA + DPO is the practical default for alignment

For most teams, the recipe is: SFT with QLoRA on a high-quality 10K instruction dataset, then DPO with a 20K–50K preference pair dataset. This produces aligned models with near-PPO quality at a fraction of the complexity. Reserve PPO for cases requiring online, verifiable reward signals (math, code).

3. Evaluations are the only ground truth you have

Vibes are not a signal. Every training decision should be validated against a held-out eval suite that measures your actual production requirements. Build your evals before you start training. Run them on every checkpoint. Gate production deployments on eval pass rates. Your eval suite is the spec for your model.

4. Safety evaluation is not optional

Deploy only after running your full safety suite: jailbreak resistance, toxicity, bias, hallucination rate, prompt injection. The cost of a production safety incident — reputational, legal, and human — far exceeds the cost of thorough pre-launch evaluation. Plan for continuous monitoring post-deployment.

5. The observability stack is as important as the model stack

You cannot improve what you cannot measure. Instrument every LLM call with trace IDs, token counts, latency, and cost from day one. Log prompt and response previews. Track quality metrics over time. Langfuse, LangSmith, or a custom solution — pick one and use it. Without observability, you are guessing.

The LLM Ops Mental Model

Think of LLM development as a tight feedback loop between three systems:

Training Loop
SFT → PEFT → RLHF → merge → evaluate → retrain
Evaluation Loop
benchmarks → LLM-judge → human eval → safety → CI gates
Production Loop
trace → monitor → score → detect drift → trigger retraining

These loops are not sequential — they run in parallel and feed each other. A model that looks great on benchmarks may fail in production. Production feedback should drive your next eval cases. Your eval cases should drive your next training run. Close the loop.
