GPU Hardware Deep Dive

GPU Architecture Fundamentals

A modern NVIDIA GPU is not a monolithic processor — it is a hierarchy of compute units, each optimized for different levels of parallelism. Understanding this hierarchy is prerequisite to reasoning about performance.

  • Streaming Multiprocessors (SMs): The primary compute unit. An H100 SX has 132 SMs. Each SM contains CUDA cores (FP32 scalar), Tensor Cores (matrix), L1 cache/shared memory, warp schedulers, and register files.
  • CUDA Cores: Execute scalar FP32/INT32 operations. Used for elementwise ops, activation functions, reductions. H100 has 16,896 CUDA cores.
  • Tensor Cores (3rd/4th gen): Dedicated matrix-multiply-accumulate (MMA) units. Support FP16, BF16, FP8, TF32, INT8, INT4. These are what deliver the headline TFLOPS numbers you see in marketing. H100 4th-gen Tensor Cores support FP8 (transformer engine).
  • HBM (High Bandwidth Memory): Stacked DRAM on the same interposer as the die. Provides 3–5× the bandwidth of GDDR6 at lower power. H100 SXM5 has 80GB HBM3 at 3.35 TB/s.
  • L2 Cache: Shared across all SMs. H100 has 50MB L2. Critical for reuse of weight matrices in attention layers.
  • NVLink: High-bandwidth die-to-die interconnect for multi-GPU communication within a node.

Hardware Tip: FP8 with Transformer Engine

H100 and above support FP8 via the Transformer Engine (TE). TE automatically casts attention and MLP layers to FP8 while maintaining BF16 residuals. In practice you get ~1.5–2× throughput improvement over BF16 with no accuracy degradation on LLM training. Enable with transformer_engine.pytorch. This is not the same as static post-training quantization.

Gotcha: ROCm Software Maturity

AMD ROCm has closed the gap significantly but many custom CUDA kernels (FlashAttention, Triton ops, custom NCCL) require porting. If your stack depends on proprietary CUDA extensions (e.g., xFormers, custom attention), budget 2–4 weeks for porting before committing to MI300X at scale. Microsoft Azure and Meta have both deployed MI300X at scale and contribute patches upstream.

Google TPUs — When to Use Instead of GPUs

TPUs are Google's custom ASICs for matrix algebra. They are not general-purpose; they excel at large-batch training of transformer models when the compute-to-memory ratio is high. TPU v4 and v5p are available on GCP via TPU VMs.

Interconnect Technologies

In distributed training, interconnect bandwidth is often the limiting factor — not raw FLOPS. An AllReduce over 8 GPUs on slow PCIe can waste 40–60% of your compute budget waiting for gradients. Understanding the interconnect stack is non-negotiable.

NVSwitch Architecture

NVSwitch is a dedicated switch ASIC that provides all-to-all NVLink connectivity between all GPUs in a node without going through CPU or PCIe. An 8-GPU DGX H100 has 4 NVSwitch chips. Each GPU connects to all 4 NVSwitches, providing 900 GB/s total bandwidth per GPU with full bisection bandwidth — any GPU can talk to any other GPU at full link speed simultaneously. This is what enables efficient AllReduce, AllGather, and ReduceScatter at the node level.

Key Insight: Network Bandwidth vs. FLOPS Ratio

For a 70B model with 32 tensor-parallel GPUs and BF16 gradients, AllReduce transfers ~140GB per step. At 400Gbps IB NDR, this takes ~2.8 seconds. At H100 compute speed (~1000 TFLOPS effective), a forward+backward pass is ~0.3 seconds. You are 9× network-bound without careful overlap. This is why topology-aware scheduling and gradient compression matter enormously at scale.

Topology-Aware Communication Strategies

Modern training frameworks (Megatron-LM, DeepSpeed) are topology-aware: they prefer intra-node NVLink for tensor parallelism (high-BW, low-latency required) and inter-node InfiniBand for data parallelism (lower-BW, AllReduce of gradients). Pipeline parallelism sends activations point-to-point, so it only uses a single link at a time and is more tolerant of high-latency networks. The 3D parallelism section covers this assignment in detail.

Storage Hierarchy for Training

Data flows through a multi-tier storage hierarchy optimized for access latency, bandwidth, and cost. The key design principle: pre-stage hot data to fast local storage before jobs start.

  • Tier 1 — Local NVMe SSD: ~10–30 GB/s per node. Used for per-step random-access dataset shards, checkpoints. 3.84TB–7.68TB typical per node.
  • Tier 2 — Lustre / GPFS (Parallel FS): 100s of GB/s aggregate across cluster. Shared across all nodes. Checkpoints, tokenized datasets. AWS FSx for Lustre gives ~1.2 TB/s at 4.8TB/s stripe width.
  • Tier 3 — S3 / GCS (Object Storage): Unlimited capacity. Raw datasets (Common Crawl, books, code). Low cost ($0.02/GB/mo). Latency too high for random access during training — always stage to faster tiers.

SLURM for ML Workloads

SLURM Architecture

SLURM (Simple Linux Utility for Resource Management) has three key daemons: slurmctld (controller, runs on head node), slurmd (worker daemon on each compute node), and slurmdbd (database daemon for accounting). Jobs are submitted via sbatch and run on reserved node sets called allocations.

SLURM Batch Script for Distributed LLM Training

#!/bin/bash
#SBATCH --job-name=llama3-70b-pretrain
#SBATCH --partition=gpu-h100           # partition with H100 nodes
#SBATCH --nodes=16                     # 16 nodes × 8 GPUs = 128 GPUs
#SBATCH --ntasks-per-node=8            # one task per GPU
#SBATCH --gres=gpu:h100:8             # 8 H100s per node
#SBATCH --cpus-per-task=12             # 12 CPU threads per GPU worker
#SBATCH --mem=480G                     # ~60GB RAM per GPU process
#SBATCH --time=72:00:00               # 72-hour wall time
#SBATCH --exclusive                    # exclusive node access (no sharing)
#SBATCH --output=/lustre/logs/%x_%j.out
#SBATCH --error=/lustre/logs/%x_%j.err
#SBATCH --signal=USR1@120             # send USR1 120s before timeout for graceful checkpoint
#SBATCH --requeue                      # auto-requeue on preemption

# --- Environment Setup ---
module load cuda/12.3 nccl/2.20 openmpi/4.1
source /opt/conda/envs/training/bin/activate

# NCCL settings for H100 + NDR IB
export NCCL_IB_DISABLE=0
export NCCL_IB_HCA=mlx5_0
export NCCL_IB_GID_INDEX=3
export NCCL_ALGO=Ring
export NCCL_PROTO=LL128
export NCCL_NET_GDR_LEVEL=5
export NCCL_TIMEOUT=1800
export NCCL_ASYNC_ERROR_HANDLING=1

# PyTorch distributed settings
export MASTER_ADDR=$(scontrol show hostnames $SLURM_JOB_NODELIST | head -n 1)
export MASTER_PORT=29500
export WORLD_SIZE=$((SLURM_NNODES * SLURM_NTASKS_PER_NODE))

echo "Job ID: $SLURM_JOB_ID"
echo "Nodes: $SLURM_JOB_NODELIST"
echo "World size: $WORLD_SIZE"
echo "Master: $MASTER_ADDR:$MASTER_PORT"

# Signal handler for graceful checkpoint on SIGTERM
cleanup() {
    echo "Received signal — saving emergency checkpoint..."
    # Training loop should handle SIGUSR1 to trigger checkpoint
    kill -USR1 $TRAIN_PID 2>/dev/null
    sleep 30
    exit 0
}
trap cleanup USR1 TERM

# Launch with srun (preferred over torchrun for multi-node SLURM)
srun --kill-on-bad-exit=1 \
  python -u /workspace/train.py \
    --model-name llama3-70b \
    --tensor-parallel-size 8 \
    --pipeline-parallel-size 4 \
    --data-parallel-size 4 \
    --global-batch-size 1024 \
    --micro-batch-size 2 \
    --lr 3e-4 \
    --max-steps 250000 \
    --checkpoint-dir /lustre/checkpoints/llama3-70b/$SLURM_JOB_ID \
    --resume-from-checkpoint auto \
  &
TRAIN_PID=$!
wait $TRAIN_PID

Section 5

Optimal GPU Utilization

GPU Utilization vs. MFU (Model FLOP Utilization)

nvidia-smi's "GPU utilization" measures the fraction of time the GPU has any kernel running — a kernel dispatching one multiply still shows 100% utilization. MFU (Model FLOP Utilization) is the real metric: actual useful FLOPs performed divided by theoretical peak FLOPS.

MFU = (achieved_throughput × model_flops_per_token) / (peak_TFLOPS × 10¹²)

GPT-3 achieves ~46% MFU on A100. Megatron-LM on H100 targets >55% MFU. Anything below 30% indicates a bottleneck that needs diagnosis.

Common Causes of Low GPU Utilization

  • Data loading bottleneck: DataLoader workers too few, no prefetch, slow disk. GPU starves waiting for batches. Fix: increase workers, use persistent_workers=True, pin_memory=True, prefetch_factor=4.
  • CPU preprocessing: Image decode, tokenization, augmentation on CPU blocks the training loop. Fix: DALI for image pipelines, pre-tokenize text datasets offline.
  • I/O bound (checkpoint/log writes): Writing large checkpoints synchronously stalls training. Fix: async checkpoint writing to NVMe, only write every N steps.
  • Pipeline parallelism bubbles: In pipeline parallelism with p stages, there is an unavoidable bubble fraction of (p-1)/p in the naive schedule. 1F1B scheduling reduces this to ~(p-1)/m where m is micro-batch count. Always use 1F1B or interleaved 1F1B.
  • CPU-GPU synchronization: Excessive .item() calls, loss logging every step, or synchronous CUDA operations stall the compute stream. Use async logging and reduce sync points.
  • Kernel launch overhead: Too many small operations — use torch.compile() to fuse kernels and reduce launch overhead.

Section 6

Multi-GPU Training Fundamentals

Parallelism Strategies

Large model training requires splitting work across hundreds or thousands of GPUs. There are three fundamental axes of parallelism that can be composed:

  • Data Parallelism (DP): Each GPU holds a full model copy and processes a different mini-batch. Gradients are AllReduced across replicas. Scales efficiently to many GPUs as long as the model fits in one GPU's memory. DDP in PyTorch implements this with a gradient bucket AllReduce overlapped with the backward pass.
  • Tensor Parallelism (TP): Split individual layer weight matrices across GPUs. For a Linear(H, 4H) FFN layer, each of 8 GPUs holds 1/8 of the weight rows. Requires AllReduce after each layer — must use NVLink within a node. Megatron-LM pioneered this. Scales to 8–16 GPUs per node (NVLink domain).
  • Pipeline Parallelism (PP): Assign consecutive transformer layers to different GPU groups (stages). Activations flow forward through stages, gradients flow backward. Reduces per-GPU memory (fewer layers) but introduces pipeline bubbles. Megatron's 1F1B schedule minimizes bubbles.
  • Sequence Parallelism: Extension to TP that splits the sequence dimension in LayerNorm and Dropout, reducing activation memory further (Megatron-LM paper, 2022).

PyTorch DDP — Minimal Setup

import os
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data.distributed import DistributedSampler

def setup_ddp():
    """Initialize DDP process group. Called once per process."""
    dist.init_process_group(
        backend="nccl",          # nccl for GPU, gloo for CPU fallback
        init_method="env://",    # uses MASTER_ADDR, MASTER_PORT, RANK, WORLD_SIZE
    )
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    return local_rank

def cleanup_ddp():
    dist.destroy_process_group()

def main():
    local_rank = setup_ddp()
    device = torch.device(f"cuda:{local_rank}")

    # Create model and wrap with DDP
    model = MyTransformerModel().to(device)
    model = DDP(
        model,
        device_ids=[local_rank],
        output_device=local_rank,
        find_unused_parameters=False,   # set True only if needed — adds overhead
        gradient_as_bucket_view=True,   # reduces memory copies during AllReduce
        static_graph=True,              # enable if model graph doesn't change
    )

    # Distributed sampler ensures each rank gets different data
    dataset = MyDataset(...)
    sampler = DistributedSampler(
        dataset,
        num_replicas=dist.get_world_size(),
        rank=dist.get_rank(),
        shuffle=True,
    )
    loader = torch.utils.data.DataLoader(
        dataset, batch_size=32, sampler=sampler,
        num_workers=8, pin_memory=True, persistent_workers=True,
    )

    optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.1)
    scaler = torch.cuda.amp.GradScaler()  # for mixed precision

    for epoch in range(num_epochs):
        sampler.set_epoch(epoch)  # reshuffle each epoch
        for batch in loader:
            inputs = batch["input_ids"].to(device, non_blocking=True)
            labels = batch["labels"].to(device, non_blocking=True)

            with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
                loss = model(inputs, labels=labels).loss

            optimizer.zero_grad(set_to_none=True)
            scaler.scale(loss).backward()
            scaler.unscale_(optimizer)
            torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
            scaler.step(optimizer)
            scaler.update()

    cleanup_ddp()

Data Loading Bottleneck Analysis

The data pipeline must keep GPUs fed with batches faster than the GPU can consume them. For a typical LLM training run (2048 sequence length, BF16, global batch 2048), you need ~8GB/s of token throughput to fully saturate 128× H100 GPUs. Standard PyTorch DataLoader with default settings can barely deliver 1–2 GB/s — a 4–8× bottleneck.

WebDataset Pipeline for Efficient Loading

import webdataset as wds
import torch
from torch.utils.data import DataLoader

# WebDataset stores data as .tar shards — ideal for object storage
# Each shard is ~1GB, streamed sequentially (maximizes throughput)

def make_training_pipeline(
    urls: list[str],      # e.g., ["s3://bucket/shard-{000000..001999}.tar"]
    batch_size: int = 64,
    num_workers: int = 16,
):
    dataset = (
        wds.WebDataset(
            urls,
            shardshuffle=True,        # shuffle shard order each epoch
            resampled=True,           # infinite loop with random resampling
            handler=wds.warn_and_continue,  # skip corrupted shards
            nodesplitter=wds.split_by_node, # distribute shards across ranks
        )
        .shuffle(buffer_size=10000)   # buffer-based shuffle within shard
        .decode("pil")                # auto-decode images
        .to_tuple("jpg", "cls")       # extract fields: image, class label
        .map_tuple(                   # apply transforms
            train_image_transform,
            lambda x: torch.tensor(x, dtype=torch.long),
        )
        .batched(batch_size, partial=False)
        .with_length(num_samples // batch_size)
    )

    loader = wds.WebLoader(
        dataset,
        batch_size=None,         # already batched above
        num_workers=num_workers,
        pin_memory=True,
        prefetch_factor=4,       # prefetch 4 batches per worker
        persistent_workers=True,
    )
    return loader

# For text datasets (LLM pretraining), use pre-tokenized .tar shards:
def make_text_pipeline(urls, seq_len=2048, batch_size=8):
    return (
        wds.WebDataset(urls, nodesplitter=wds.split_by_node, resampled=True)
        .decode()
        .to_tuple("input_ids.npy", "attention_mask.npy")
        .map(lambda ids, mask: {
            "input_ids": torch.from_numpy(ids[:seq_len]).long(),
            "attention_mask": torch.from_numpy(mask[:seq_len]).long(),
            "labels": torch.from_numpy(ids[:seq_len]).long(),
        })
        .batched(batch_size)
    )

Efficient Checkpoint Saving and Loading

import torch
import torch.distributed as dist
import os
from pathlib import Path

def save_checkpoint_async(
    model, optimizer, scheduler, step, loss, checkpoint_dir, rank
):
    """
    Save checkpoint with rank-0 metadata + distributed state dicts.
    Uses torch.save with async I/O via background thread.
    """
    import threading

    checkpoint_dir = Path(checkpoint_dir) / f"step_{step:08d}"
    checkpoint_dir.mkdir(parents=True, exist_ok=True)

    # Each rank saves its own model shard (for ZeRO-3 / FSDP)
    model_path = checkpoint_dir / f"model_rank{rank:04d}.pt"
    optim_path = checkpoint_dir / f"optim_rank{rank:04d}.pt"

    # Collect state on CPU to free GPU memory
    model_state = {
        k: v.cpu() for k, v in model.state_dict().items()
    }
    optim_state = optimizer.state_dict()

    def _save():
        torch.save(model_state, model_path)
        torch.save(optim_state, optim_path)
        if rank == 0:
            meta = {
                "step": step,
                "loss": loss,
                "scheduler_state": scheduler.state_dict(),
                "world_size": dist.get_world_size(),
            }
            torch.save(meta, checkpoint_dir / "meta.pt")

    # Non-blocking: save in background thread while training continues
    thread = threading.Thread(target=_save, daemon=True)
    thread.start()
    return thread  # caller should .join() before next checkpoint

def load_checkpoint(model, optimizer, scheduler, checkpoint_dir, rank):
    """Resume training from latest checkpoint."""
    checkpoint_dir = Path(checkpoint_dir)

    # Find latest checkpoint step
    steps = sorted([
        int(d.name.split("_")[1])
        for d in checkpoint_dir.iterdir()
        if d.is_dir() and d.name.startswith("step_")
    ])
    if not steps:
        return 0  # no checkpoint, start from scratch

    latest = steps[-1]
    ckpt_path = checkpoint_dir / f"step_{latest:08d}"

    model.load_state_dict(torch.load(
        ckpt_path / f"model_rank{rank:04d}.pt",
        map_location=f"cuda:{rank % 8}",
    ))
    optimizer.load_state_dict(torch.load(
        ckpt_path / f"optim_rank{rank:04d}.pt",
        map_location=f"cuda:{rank % 8}",
    ))
    if rank == 0:
        meta = torch.load(ckpt_path / "meta.pt")
        scheduler.load_state_dict(meta["scheduler_state"])

    dist.barrier()  # ensure all ranks finish loading before continuing
    return latest

Thermal Management and Power

Power Usage Effectiveness (PUE)

PUE = Total Facility Power / IT Equipment Power. A PUE of 1.0 is theoretical ideal (all power goes to compute). Hyperscalers achieve 1.1–1.2. Traditional data centers are 1.4–1.6. For a 1,000× H100 cluster at 700W/GPU = 700 kW IT power, a PUE of 1.2 means 840 kW total, costing ~$750K/yr at $0.10/kWh.

Thermal Throttling and Monitoring

H100 has a junction temperature limit of 83°C (SXM). Above this, the GPU begins thermal throttling — reducing SM clocks and memory clocks to reduce power dissipation. At 700W TDP, liquid cooling is effectively mandatory for dense deployments. Air-cooled DGX H100 relies on 4× 200CFM fans and a carefully engineered airflow path. GB200 NVL72 racks require direct liquid cooling (DLC) infrastructure — no air cooling option.

Monitor thermal performance: nvidia-smi --query-gpu=temperature.gpu,clocks.throttle_reasons.active --format=csv. Key throttle reason codes: clocks_throttle_reasons_hw_slowdown (hardware thermal), clocks_throttle_reasons_sw_thermal_slowdown (software limit). Any throttling during production training is a cluster configuration problem.

Critical: Power Infrastructure for GB200

GB200 NVL72 racks require 3-phase 480V at 200–400A per rack, plus 60 LPM coolant flow for direct liquid cooling. This is not achievable in most existing data centers without significant infrastructure upgrades. Budget 12–18 months for DLC infrastructure buildout before planning a GB200 deployment.

Section 11

Reliability and Fault Tolerance

GPU Failure Rates and MTBF

At scale, hardware failures are not edge cases — they are scheduled events. NVIDIA H100 SXM5 MTBF is approximately 40,000 hours (~4.5 years) per GPU. In a cluster of 1,000 H100s, the expected mean time between any GPU failure is 40,000 / 1,000 = 40 hours. A 72-hour training job has a ~84% chance of experiencing at least one GPU failure. This is why fault-tolerant training is not optional at scale — it is the baseline.

Fault-Tolerant Training Loop with Auto-Resume

import os
import sys
import signal
import logging
import torch
import torch.distributed as dist
from pathlib import Path
from datetime import datetime

logger = logging.getLogger(__name__)

CHECKPOINT_DIR = Path(os.environ.get("CHECKPOINT_DIR", "/lustre/checkpoints"))
CHECKPOINT_INTERVAL = int(os.environ.get("CHECKPOINT_INTERVAL_STEPS", "500"))

class FaultTolerantTrainer:
    """
    Training loop designed to survive GPU failures, preemptions, and NCCL errors.
    Implements: periodic checkpointing, SIGTERM handler, NCCL error recovery.
    """

    def __init__(self, model, optimizer, scheduler, train_loader, config):
        self.model = model
        self.optimizer = optimizer
        self.scheduler = scheduler
        self.train_loader = train_loader
        self.config = config
        self.rank = dist.get_rank()
        self.local_rank = int(os.environ["LOCAL_RANK"])
        self._checkpoint_thread = None
        self._should_stop = False

        # Register signal handlers for graceful shutdown
        signal.signal(signal.SIGUSR1, self._handle_sigusr1)  # SLURM timeout signal
        signal.signal(signal.SIGTERM, self._handle_sigterm)  # Kubernetes preemption

    def _handle_sigusr1(self, signum, frame):
        """SLURM sends SIGUSR1 120s before wall time — save checkpoint and exit."""
        logger.warning(f"[Rank {self.rank}] Received SIGUSR1 (approaching wall time)")
        self._should_stop = True

    def _handle_sigterm(self, signum, frame):
        """Kubernetes sends SIGTERM on pod preemption."""
        logger.warning(f"[Rank {self.rank}] Received SIGTERM (preemption/shutdown)")
        self._should_stop = True

    def save_checkpoint(self, step: int, loss: float):
        """Atomic checkpoint save: write to temp dir, then rename."""
        if self._checkpoint_thread is not None:
            self._checkpoint_thread.join()  # wait for previous save to complete

        ckpt_dir = CHECKPOINT_DIR / f"step_{step:08d}"
        tmp_dir = CHECKPOINT_DIR / f"step_{step:08d}.tmp"
        tmp_dir.mkdir(parents=True, exist_ok=True)

        # Save distributed state — each rank saves its shard
        torch.save(self.model.state_dict(),
                   tmp_dir / f"model_rank{self.rank:04d}.pt")
        torch.save(self.optimizer.state_dict(),
                   tmp_dir / f"optim_rank{self.rank:04d}.pt")

        if self.rank == 0:
            torch.save({
                "step": step, "loss": loss,
                "scheduler": self.scheduler.state_dict(),
                "config": self.config,
                "timestamp": datetime.utcnow().isoformat(),
            }, tmp_dir / "meta.pt")

        # Barrier: ensure ALL ranks have written before renaming
        dist.barrier()
        if self.rank == 0:
            tmp_dir.rename(ckpt_dir)
            # Clean up old checkpoints (keep last 3)
            all_ckpts = sorted(CHECKPOINT_DIR.glob("step_*"))
            for old in all_ckpts[:-3]:
                import shutil
                shutil.rmtree(old, ignore_errors=True)
            logger.info(f"Checkpoint saved: step {step}")
        dist.barrier()

    def train(self, num_steps: int):
        """Main training loop with fault tolerance."""
        start_step = self._resume_or_start()

        self.model.train()
        data_iter = iter(self.train_loader)

        for step in range(start_step, num_steps):
            if self._should_stop:
                logger.info(f"[Rank {self.rank}] Stopping training at step {step}")
                self.save_checkpoint(step, float("inf"))
                sys.exit(0)  # SLURM will requeue if --requeue is set

            # Fetch batch with retry on dataloader failure
            try:
                batch = next(data_iter)
            except StopIteration:
                data_iter = iter(self.train_loader)
                batch = next(data_iter)

            # Forward + backward with NCCL error handling
            try:
                loss = self._train_step(batch)
            except RuntimeError as e:
                if "NCCL" in str(e) or "CUDA error" in str(e):
                    logger.error(f"[Rank {self.rank}] Fatal collective error at step {step}: {e}")
                    # Save what we can and exit — SLURM will requeue
                    self.save_checkpoint(step, float("inf"))
                    dist.destroy_process_group()
                    sys.exit(1)
                raise

            # Periodic checkpoint
            if step % CHECKPOINT_INTERVAL == 0 and step > start_step:
                self.save_checkpoint(step, loss.item())

            if self.rank == 0 and step % 100 == 0:
                logger.info(f"step={step} loss={loss.item():.4f}")

    def _train_step(self, batch):
        inputs = batch["input_ids"].to(self.local_rank, non_blocking=True)
        labels = batch["labels"].to(self.local_rank, non_blocking=True)

        with torch.autocast("cuda", dtype=torch.bfloat16):
            output = self.model(inputs, labels=labels)
            loss = output.loss / self.config["gradient_accumulation_steps"]

        loss.backward()
        if (self._step + 1) % self.config["gradient_accumulation_steps"] == 0:
            torch.nn.utils.clip_grad_norm_(self.model.parameters(), 1.0)
            self.optimizer.step()
            self.scheduler.step()
            self.optimizer.zero_grad(set_to_none=True)
        return loss

    def _resume_or_start(self):
        checkpoints = sorted(CHECKPOINT_DIR.glob("step_[0-9]*"))
        if not checkpoints:
            logger.info("No checkpoint found — starting from scratch")
            return 0
        latest = checkpoints[-1]
        step = int(latest.name.split("_")[1])
        self.model.load_state_dict(torch.load(
            latest / f"model_rank{self.rank:04d}.pt",
            map_location=f"cuda:{self.local_rank}"
        ))
        self.optimizer.load_state_dict(torch.load(
            latest / f"optim_rank{self.rank:04d}.pt",
            map_location=f"cuda:{self.local_rank}"
        ))
        if self.rank == 0:
            meta = torch.load(latest / "meta.pt")
            self.scheduler.load_state_dict(meta["scheduler"])
            logger.info(f"Resumed from step {step}, loss was {meta['loss']:.4f}")
        dist.barrier()
        return step

  • • FSx Lustre (AWS) or Weka (on-prem) for active training data
  • • Always size storage at 10× the bottleneck bandwidth you think you need

Operational Excellence

  • • Checkpoint every 500 steps minimum; async I/O, never synchronous
  • • Deploy DCGM + Prometheus + Grafana on every node before first job
  • • Track MFU, not nvidia-smi utilization — anything below 35% needs diagnosis
  • • Budget 1 GPU failure per 40 hours in a 1,000-GPU cluster

Cost Optimization

  • • 3-yr reserved instances break even vs on-prem at ~62% utilization
  • • Spot/preemptible saves 70–90% for fault-tolerant research jobs
  • • Power is 30–40% of 5-year TCO on-prem — low-cost power is a superpower
  • • GB200 requires DLC infrastructure investment — plan 12–18 months ahead
