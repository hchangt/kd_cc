1. Data Engineering for ML — Overview

Why data pipelines are the foundation of every production ML system

The uncomfortable truth about production machine learning: model code is typically under 5% of the total codebase. The remaining 95% is data infrastructure — pipelines, validation, storage, versioning, serving, and monitoring. Andrew Ng's framing of "data-centric AI" names this directly: improving data quality and consistency produces better model outcomes than architecture search or hyperparameter tuning, especially once you're past research-quality baselines.

At Meta, the ranking models serving billions of feed impressions per day consumed hundreds of thousands of features. The bottleneck was never the model — it was reliably computing, storing, and serving fresh features at low latency. That operational reality shapes everything in this chapter.

Why Data Is the Hardest Part

Data Quality

Missing values, schema drift, upstream outages, distribution shift — all invisible until your model degrades silently in production.

Labeling Cost

Human annotation is expensive, slow, and inconsistent. Label errors are the primary source of irreducible error in many supervised systems.

Versioning & Lineage

Models trained on different data slices are fundamentally different artifacts. Without data versioning, reproducibility is impossible.

Data-Centric AI in Practice

Fix the data, not the model. At Meta, the ranking team saw larger gains from improving feature freshness (minutes vs. hours staleness) than from comparable model architecture changes. Invest in systematic label quality audits, consistent preprocessing, and fast iteration loops on data slices before reaching for a bigger model.

2. Data Ingestion Patterns

Batch, streaming, and CDC — choosing the right ingestion strategy

Batch ingestion processes data in chunks on a schedule (hourly, daily). It is simpler to build, easier to backfill, and cheaper to operate. Streaming ingestion processes records as they arrive, enabling sub-minute feature freshness — critical for fraud detection and real-time personalization. Most production systems use both: streaming for latency-sensitive features, batch for complex aggregations where exactness matters more than speed.

ETL vs ELT

Traditional ETL (Extract → Transform → Load) transforms data before storage. Modern ELT (Extract → Load → Transform) loads raw data into the warehouse first and transforms in-place. ELT won because cloud warehouses (Snowflake, BigQuery, Redshift) have compute collocated with storage — the raw data is always available for reprocessing and schema-on-read avoids upfront decisions.

Change Data Capture (CDC)

CDC reads database write-ahead logs (WAL) to capture inserts, updates, and deletes in real time without polling. Debezium is the dominant open-source CDC tool. It publishes change events to Kafka, which downstream ML pipelines consume. This is the canonical pattern for keeping feature stores synchronized with operational databases.

Code: Kafka Consumer for Streaming ML Features

kafka_ml_consumer.py
"""
Kafka consumer: processes user activity events and writes
real-time features to Redis for online feature serving.
"""
import json
import logging
from dataclasses import dataclass
from typing import Dict, Any, Optional
from confluent_kafka import Consumer, KafkaError, KafkaException
import redis

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


@dataclass
class UserActivityEvent:
    user_id: str
    event_type: str       # "click", "purchase", "view", "search"
    item_id: Optional[str]
    session_id: str
    timestamp: float
    metadata: Dict[str, Any]


class StreamingFeatureProcessor:
    def __init__(self, kafka_config: Dict, redis_host: str = "localhost"):
        self.consumer = Consumer({
            **kafka_config,
            "group.id": "ml-feature-processor",
            "auto.offset.reset": "earliest",
            "enable.auto.commit": False,   # manual commit for exactly-once semantics
            "max.poll.interval.ms": 300_000,
        })
        self.redis = redis.Redis(host=redis_host, port=6379, decode_responses=True)
        self.feature_ttl = 3600  # 1-hour rolling window TTL

    def parse_event(self, raw: bytes) -> Optional[UserActivityEvent]:
        try:
            d = json.loads(raw)
            return UserActivityEvent(
                user_id=d["user_id"], event_type=d["event_type"],
                item_id=d.get("item_id"), session_id=d["session_id"],
                timestamp=d["timestamp"], metadata=d.get("metadata", {}),
            )
        except (KeyError, json.JSONDecodeError) as e:
            logger.warning(f"Parse error: {e}")
            return None

    def update_features(self, event: UserActivityEvent) -> None:
        """
        Maintain sliding-window feature counts in Redis sorted sets.
        Key pattern: feat:user:{uid}:{feature_name}
        Value: sorted set of (timestamp, event_id) pairs.
        """
        uid = event.user_id
        ts  = event.timestamp
        cutoff_1h = ts - 3600

        pipe = self.redis.pipeline(transaction=True)

        # --- clicks_1h: rolling 1-hour click count ---
        click_key = f"feat:user:{uid}:clicks_1h"
        pipe.zadd(click_key, {f"{ts}:{event.item_id or ''}": ts})
        pipe.zremrangebyscore(click_key, 0, cutoff_1h)
        pipe.expire(click_key, self.feature_ttl * 2)

        # --- purchases_1h ---
        if event.event_type == "purchase":
            pkey = f"feat:user:{uid}:purchases_1h"
            pipe.zadd(pkey, {str(ts): ts})
            pipe.zremrangebyscore(pkey, 0, cutoff_1h)
            pipe.expire(pkey, self.feature_ttl * 2)

        # --- last seen category ---
        if category := event.metadata.get("category"):
            pipe.set(f"feat:user:{uid}:last_category", category, ex=86400)

        # --- last event timestamp ---
        pipe.set(f"feat:user:{uid}:last_event_ts", ts, ex=86400)

        pipe.execute()

    def run(self, topics: list):
        self.consumer.subscribe(topics)
        logger.info(f"Subscribed to: {topics}")
        processed = 0
        try:
            while True:
                msg = self.consumer.poll(timeout=1.0)
                if msg is None:
                    continue
                if msg.error():
                    if msg.error().code() == KafkaError._PARTITION_EOF:
                        continue
                    raise KafkaException(msg.error())

                event = self.parse_event(msg.value())
                if event:
                    self.update_features(event)
                    processed += 1
                    if processed % 1000 == 0:
                        logger.info(f"Processed {processed:,} events")

                # Commit only after successful write to Redis
                self.consumer.commit(message=msg)
        except KeyboardInterrupt:
            logger.info("Shutting down...")
        finally:
            self.consumer.close()

from pyspark.sql.types import TimestampType
from delta.tables import DeltaTable
from delta import configure_spark_with_delta_pip
import logging

logger = logging.getLogger(__name__)

def build_spark() -> SparkSession:
    builder = (
        SparkSession.builder.appName("batch-ingestion")
        .config("spark.sql.extensions",
                "io.delta.sql.DeltaSparkSessionExtension")
        .config("spark.sql.catalog.spark_catalog",
                "org.apache.spark.sql.delta.catalog.DeltaCatalog")
        .config("spark.sql.adaptive.enabled", "true")
        .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
        .config("spark.hadoop.fs.s3a.impl",

                "com.amazonaws.auth.InstanceProfileCredentialsProvider")
    )
    return configure_spark_with_delta_pip(builder).getOrCreate()


def get_watermark(spark: SparkSession, path: str, col: str) -> datetime:
    """Return max(col) from existing Delta table, or epoch if table absent."""
    try:
        df = spark.read.format("delta").load(path)
        val = df.agg(F.max(col)).collect()[0][0]
        return val or datetime(2020, 1, 1)
    except Exception:
        return datetime(2020, 1, 1)


def ingest_table(
    spark: SparkSession,
    jdbc_url: str,
    jdbc_props: dict,
    source_table: str,
    select_cols: str,
    partition_id_col: str,
    target_path: str,
    merge_key: str,
    watermark_col: str = "updated_at",
    run_date: datetime = None,
) -> None:
    run_date = run_date or datetime.utcnow()
    wm = get_watermark(spark, target_path, watermark_col)
    logger.info(f"[{source_table}] Loading rows after {wm}")

    df = (
        spark.read.format("jdbc")
        .option("url", jdbc_url)
        .option("dbtable", f"""
            (SELECT {select_cols}
               FROM {source_table}
              WHERE {watermark_col} > '{wm.isoformat()}'
                AND {watermark_col} <= '{run_date.isoformat()}'
            ) AS inc
        """)
        .option("numPartitions", 20)
        .option("partitionColumn", partition_id_col)
        .option("lowerBound", "0")
        .option("upperBound", "2000000000")
        .options(**jdbc_props)
        .load()
        .withColumn(watermark_col, F.col(watermark_col).cast(TimestampType()))
        .withColumn("ingested_at", F.lit(run_date).cast(TimestampType()))
        .withColumn("_year",  F.year(watermark_col))
        .withColumn("_month", F.month(watermark_col))
    )

    n = df.count()
    logger.info(f"[{source_table}] Loaded {n:,} incremental rows")
    if n == 0:
        return

    if DeltaTable.isDeltaTable(spark, target_path):
        tgt = DeltaTable.forPath(spark, target_path)
        (
            tgt.alias("t")
            .merge(df.alias("s"), f"t.{merge_key} = s.{merge_key}")
            .whenMatchedUpdateAll()
            .whenNotMatchedInsertAll()
            .execute()
        )
    else:
        (
            df.write.format("delta")
            .partitionBy("_year", "_month")
            .mode("overwrite")
            .option("overwriteSchema", "true")
            .save(target_path)
        )
    logger.info(f"[{source_table}] Done -> {target_path}")

"""
PySpark feature engineering pipeline.
Input:  raw user events + user profiles (Delta Lake)
Output: feature table for model training (Delta Lake, partitioned by country)
"""
from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F
from pyspark.sql.types import FloatType
import logging

logger = logging.getLogger(__name__)
DATA_LAKE = "s3a://ml-data-lake"


def build_spark() -> SparkSession:
    return (
        SparkSession.builder.appName("feature-engineering")
        .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
        .config("spark.sql.catalog.spark_catalog",
                "org.apache.spark.sql.delta.catalog.DeltaCatalog")
        .config("spark.sql.adaptive.enabled", "true")
        .config("spark.sql.shuffle.partitions", "400")
        .getOrCreate()
    )


def compute_activity_features(events):
    """7-day and 30-day aggregations per user."""
    ref_ts = events.agg(F.max("event_ts")).collect()[0][0]
    recent = events.withColumn(
        "days_ago",
        F.datediff(F.lit(ref_ts), F.col("event_ts").cast("date"))
    )

    feats_7d = (
        recent.filter(F.col("days_ago") <= 7)
        .groupBy("user_id")
        .agg(
            F.count("*").alias("events_7d"),
            F.countDistinct("session_id").alias("sessions_7d"),
            F.countDistinct("item_id").alias("unique_items_7d"),
            F.sum(F.when(F.col("event_type") == "purchase", 1).otherwise(0)).alias("purchases_7d"),
            F.sum(F.when(F.col("event_type") == "click",    1).otherwise(0)).alias("clicks_7d"),
            F.mean("dwell_seconds").alias("avg_dwell_7d"),
        )
    )
    feats_30d = (
        recent.filter(F.col("days_ago") <= 30)
        .groupBy("user_id")
        .agg(
            F.count("*").alias("events_30d"),
            F.sum(F.when(F.col("event_type") == "purchase", 1).otherwise(0)).alias("purchases_30d"),
            F.sum("purchase_amount").alias("total_spend_30d"),
            F.countDistinct("category").alias("category_diversity_30d"),
        )
    )

    # Top category last 30 days
    w = Window.partitionBy("user_id").orderBy(F.desc("cat_cnt"))
    top_cat = (
        recent.filter(F.col("days_ago") <= 30)
        .groupBy("user_id", "category").agg(F.count("*").alias("cat_cnt"))
        .withColumn("rnk", F.rank().over(w)).filter(F.col("rnk") == 1)
        .select("user_id", F.col("category").alias("top_category_30d"))
    )

    return feats_7d.join(feats_30d, "user_id", "outer").join(top_cat, "user_id", "left")


def compute_purchase_rate(events):
    """Click-to-purchase rate with Laplace smoothing (avoids zero division)."""
    return (
        events.filter(F.col("event_type").isin("click", "purchase"))
        .groupBy("user_id")
        .agg(
            F.sum(F.when(F.col("event_type") == "click",    1).otherwise(0)).alias("clicks"),
            F.sum(F.when(F.col("event_type") == "purchase", 1).otherwise(0)).alias("purchases"),
        )
        .withColumn("purchase_rate",
                    (F.col("purchases") + 1.0) / (F.col("clicks") + 2.0))
        .select("user_id", "purchase_rate")
    )


def run():
    spark = build_spark()
    users  = spark.read.format("delta").load(f"{DATA_LAKE}/curated/users")
    events = spark.read.format("delta").load(f"{DATA_LAKE}/curated/events")

    activity = compute_activity_features(events)
    purchase_rate = compute_purchase_rate(events)

    feature_df = (
        users.select("user_id", "country_code", "age_bucket",
                     "subscription_tier", "account_age_days")
        .join(activity,      "user_id", "left")
        .join(purchase_rate, "user_id", "left")
        .fillna({
            "events_7d": 0, "sessions_7d": 0, "purchases_7d": 0, "clicks_7d": 0,
            "avg_dwell_7d": 0.0, "events_30d": 0, "purchases_30d": 0,
            "total_spend_30d": 0.0, "purchase_rate": 0.5,
        })
    )

    output = f"{DATA_LAKE}/features/user_features"
    (
        feature_df.write.format("delta")
        .mode("overwrite").option("overwriteSchema", "true")
        .partitionBy("country_code")
        .save(output)
    )
    logger.info(f"Wrote {feature_df.count():,} feature rows to {output}")
    spark.stop()


if __name__ == "__main__":
    run()

"""
Dask preprocessing pipeline — Python-native, pandas-compatible.
Best when: data fits in cluster RAM, you want sklearn compatibility,
or you need iterative exploration without JVM overhead.
"""
import dask.dataframe as dd
import pandas as pd
from dask.distributed import Client, progress
from typing import List, Tuple


def start_cluster(n_workers: int = 8) -> Client:
    client = Client(n_workers=n_workers, threads_per_worker=2, memory_limit="16GB")
    print(f"Dask dashboard: {client.dashboard_link}")
    return client


def preprocess(
    path: str,
    cat_cols: List[str],
    num_cols: List[str],
    label_col: str,
) -> Tuple[dd.DataFrame, dd.Series]:
    ddf = dd.read_parquet(path, engine="pyarrow", columns=cat_cols + num_cols + [label_col])

    # Impute
    ddf[num_cols] = ddf[num_cols].fillna(ddf[num_cols].mean())
    ddf[cat_cols] = ddf[cat_cols].fillna("__unknown__")

    # Z-score normalization — compute stats once, broadcast
    stats = ddf[num_cols].describe().compute()
    for col in num_cols:
        mu, sigma = stats[col]["mean"], max(stats[col]["std"], 1e-9)
        ddf[col] = (ddf[col] - mu) / sigma

    # Cap low-frequency categories
    for col in cat_cols:
        freq = ddf[col].value_counts().compute()
        rare  = set(freq[freq < 100].index.tolist())
        ddf[col] = ddf[col].where(~ddf[col].isin(rare), "__rare__")

    # Integer-encode categoricals
    for col in cat_cols:
        uniq = sorted(ddf[col].unique().compute().tolist())
        enc  = {v: i for i, v in enumerate(uniq)}
        ddf[col] = ddf[col].map(enc, meta=(col, "int32"))

    return ddf[cat_cols + num_cols], ddf[label_col]


def rolling_window_features(
    ddf: dd.DataFrame,
    group_col: str,
    value_cols: List[str],
    windows: List[int] = [7, 30],
) -> dd.DataFrame:
    """Rolling stats within each partition group (intra-partition windows)."""
    def _apply(pdf: pd.DataFrame) -> pd.DataFrame:
        pdf = pdf.sort_values(group_col)
        for col in value_cols:
            for w in windows:
                grp = pdf.groupby(group_col)[col]
                pdf[f"{col}_mean_{w}d"] = grp.transform(lambda x: x.rolling(w, min_periods=1).mean())
                pdf[f"{col}_sum_{w}d"]  = grp.transform(lambda x: x.rolling(w, min_periods=1).sum())
                pdf[f"{col}_std_{w}d"]  = grp.transform(lambda x: x.rolling(w, min_periods=1).std().fillna(0))
        return pdf

    meta = ddf._meta.copy()
    for col in value_cols:
        for w in windows:
            for agg in ["mean", "sum", "std"]:
                meta[f"{col}_{agg}_{w}d"] = pd.Series(dtype="float64")

    return ddf.map_partitions(_apply, meta=meta)

4. Data Storage Formats for ML

Parquet, Delta Lake, Iceberg, and Hudi — the open table format landscape

Raw object storage (S3, GCS) is cheap and durable, but offers no ACID guarantees, no schema enforcement, and no efficient time travel. Open table formats bolt these capabilities on top of Parquet files, making data lakes practical for production ML systems that require reproducible training data and point-in-time correctness.

Parquet: The Foundation

Apache Parquet is a columnar binary format. For ML, columnar storage means reading only the feature columns you need, skipping others entirely. Parquet stores column-level min/max statistics and bloom filters in row group footers, enabling predicate pushdown — entire row groups are skipped without I/O. Snappy compression achieves 3–5x on typical tabular data. Every open table format in this section stores actual data as Parquet files, layering metadata on top.

6. Feature Engineering

Transforming raw data into predictive signals — correctly

Feature engineering is the process of transforming raw data into numerical representations that models can learn from. It is simultaneously the highest-leverage and most error-prone part of the ML pipeline. The most dangerous mistake — data leakage — occurs when information from the future leaks into the training set, producing optimistic offline metrics that collapse in production.

Point-in-Time Correctness — The #1 Source of Leakage

When creating training data, each example must only use features that were available at the time of the label event. If you compute a 7-day purchase count for user U on label_date D using events from D+1 to D+7, you have leaked future information. Feature stores solve this with point-in-time joins: for each (entity, timestamp) pair in your label set, they retrieve the feature values that were active at exactly that timestamp.

Feature Types

Numerical

  • Z-score normalization, min-max scaling
  • Log transform for heavy-tailed distributions
  • Bucketization / quantile binning
  • Interaction terms (col_a * col_b)

Categorical

  • One-hot encoding (low cardinality)
  • Target / mean encoding (high cardinality)
  • Embedding lookup (learned, e.g. entity embeddings)
  • Frequency encoding

Temporal

  • Lag features (value at t-1, t-7, t-30)
  • Rolling window stats (mean, std, min, max)
  • Cyclic encoding (sin/cos for hour-of-day)
  • Time since last event (recency)

Embeddings / Dense

  • Item2Vec / Word2Vec embeddings
  • BERT / sentence embeddings for text
  • User behavior sequence embeddings
  • Graph embeddings (Node2Vec)

Code: Rolling Window Features with PySpark

rolling_window_features.py
"""
Rolling window feature computation with PySpark.
Handles multiple window sizes (1d, 7d, 30d) in a single pass.
Uses Spark window functions — avoids expensive joins.

NOTE: All aggregations use events UP TO (not including) the label_ts
to guarantee point-in-time correctness.
"""
from pyspark.sql import SparkSession, Window
from pyspark.sql import functions as F
from pyspark.sql.types import LongType
from datetime import timedelta

spark = (
    SparkSession.builder.appName("rolling-features")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog",
            "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

# ── Load data ────────────────────────────────────────────────────────
events = spark.read.format("delta").load("s3a://ml-data-lake/curated/events")
labels = spark.read.format("delta").load("s3a://ml-data-lake/curated/labels")

# Convert event_ts to epoch seconds for window arithmetic
events = events.withColumn("ts_sec", F.unix_timestamp("event_ts"))

WINDOWS = {
    "1d":  86_400,
    "7d":  86_400 * 7,
    "30d": 86_400 * 30,
}

# ── Point-in-time rolling aggregations via range windows ─────────────
# Range window: rows where ts_sec is within [current_ts - N, current_ts - 1]
# The -1 ensures we exclude the current event (strict past-only view).
feature_dfs = []
for name, seconds in WINDOWS.items():
    w = (
        Window.partitionBy("user_id")
              .orderBy("ts_sec")
              .rangeBetween(-seconds, -1)
    )
    feat = (
        events.select("user_id", "ts_sec", "event_type", "purchase_amount", "category")
        .withColumn(f"clicks_{name}",
                    F.sum(F.when(F.col("event_type") == "click", 1).otherwise(0)).over(w))
        .withColumn(f"purchases_{name}",
                    F.sum(F.when(F.col("event_type") == "purchase", 1).otherwise(0)).over(w))
        .withColumn(f"spend_{name}",
                    F.sum(F.coalesce("purchase_amount", F.lit(0.0))).over(w))
        .withColumn(f"unique_categories_{name}",
                    F.approx_count_distinct("category").over(w))
    )
    feature_dfs.append(feat.select(
        "user_id", "ts_sec",
        f"clicks_{name}", f"purchases_{name}", f"spend_{name}", f"unique_categories_{name}"
    ))

# ── Combine all window features ───────────────────────────────────────
from functools import reduce
from pyspark.sql import DataFrame

all_feats = reduce(
    lambda a, b: a.join(b, ["user_id", "ts_sec"], "inner"),
    feature_dfs
)

# ── Lag features (value at t-1 period) ───────────────────────────────
user_window = Window.partitionBy("user_id").orderBy("ts_sec")
all_feats = (
    all_feats
    .withColumn("clicks_7d_lag_7d",   F.lag("clicks_7d",   7).over(user_window))
    .withColumn("spend_30d_lag_30d",  F.lag("spend_30d",  30).over(user_window))
    .withColumn("purchases_trend",    # positive if purchases increased vs prior week
                F.col("purchases_7d") - F.lag("purchases_7d", 7).over(user_window))
)

# ── Recency feature ───────────────────────────────────────────────────
last_event_window = Window.partitionBy("user_id").orderBy(F.desc("ts_sec"))
recency = (
    events.withColumn("rnk", F.rank().over(last_event_window))
          .filter(F.col("rnk") == 1)
          .select("user_id", F.col("ts_sec").alias("last_event_ts"))
)

# ── Point-in-time join with labels ───────────────────────────────────
# For each label (user_id, label_ts), get the feature snapshot
# at exactly label_ts — no future leakage.
label_events = (
    labels
    .withColumn("label_sec", F.unix_timestamp("label_ts"))
    .join(all_feats.alias("f"),
          (F.col("labels.user_id") == F.col("f.user_id")) &
          (F.col("labels.label_sec") == F.col("f.ts_sec")),
          "left")
    .drop("f.user_id", "ts_sec")
)

# ── Save training dataset ─────────────────────────────────────────────
(
    label_events.fillna(0.0)
    .write.format("delta")
    .mode("overwrite").option("overwriteSchema","true")
    .save("s3a://ml-data-lake/features/training_dataset_v2")
)
print("Training dataset written.")
spark.stop()

7. Feature Stores — Concepts

The infrastructure layer that connects data engineering and model serving

A feature store is a centralized system for creating, storing, sharing, and serving features. It exists to solve three problems that appear once you have more than a handful of models in production:

  1. Training-serving skew: Features computed offline (for training) differ from features computed online (for inference) due to different code paths. Feature stores enforce a single feature definition used in both contexts.
  2. Feature duplication: Without a registry, every team reimplements the same features (user activity counts, item popularity) independently, inconsistently, and expensively.
  3. Point-in-time correctness: Constructing training datasets requires joining labels to feature snapshots at the exact label timestamp — not current values. Feature stores make this a first-class operation.

Training-Serving Skew: A Silent Killer

At Airbnb, training-serving skew was the single most common cause of model performance degradation in production. It arises when: (1) training uses a different feature computation than serving, (2) null/missing values are handled differently, (3) categorical encodings differ. A feature store enforces a single Python/SQL definition that is executed at both training and serving time, making skew impossible by construction.

9. Tecton — Enterprise Feature Store

Managed feature pipelines for large-scale production ML

Tecton is a fully managed enterprise feature store founded by engineers from Uber (where they built Michelangelo). Unlike Feast, Tecton manages the compute infrastructure for feature pipelines — you define transformations in Python, Tecton executes and schedules them on Spark/Flink automatically. Feast requires more operational ownership; Tecton trades that for cost and lock-in.

11. Data Quality and Validation

Great Expectations, dbt, and Pandera — catching bad data before it reaches your model

Data quality failures are the most common cause of silent model degradation. Schema changes upstream, null values where none were expected, or distribution shifts in a key feature can all cause model behavior to degrade without raising any explicit error. Data quality tools create automated checks that catch these issues at the pipeline level, before bad data reaches training or serving.

Code: Great Expectations Suite

gx_validation_suite.py
"""
Great Expectations v1.x: define, save, and run a validation suite
on a Delta Lake table. Fails the pipeline if expectations are violated.
"""
import great_expectations as gx
from great_expectations.checkpoint import Checkpoint
import pandas as pd

context = gx.get_context(mode="file", project_root_dir="gx_project/")

# ── 1. Define a data source ───────────────────────────────────────────
datasource = context.sources.add_spark(name="delta_lake_source")
asset = datasource.add_dataframe_asset(name="user_features_asset")
batch_request = asset.build_batch_request(dataframe=pd.read_parquet(
    "s3://ml-data-lake/features/user_features/"
))

# ── 2. Build expectation suite ────────────────────────────────────────
suite = context.add_or_update_expectation_suite("user_features_suite")

validator = context.get_validator(
    batch_request=batch_request,
    expectation_suite_name="user_features_suite",
)

# Schema checks
validator.expect_column_to_exist("user_id")
validator.expect_column_to_exist("clicks_7d")
validator.expect_column_to_exist("total_spend_30d")
validator.expect_column_to_exist("purchase_rate")
validator.expect_column_to_exist("top_category_30d")

# Null checks — critical features must never be null
validator.expect_column_values_to_not_be_null("user_id")
validator.expect_column_values_to_not_be_null("clicks_7d")

# Type checks
validator.expect_column_values_to_be_of_type("user_id", "StringType")
validator.expect_column_values_to_be_of_type("clicks_7d", "LongType")
validator.expect_column_values_to_be_of_type("purchase_rate", "DoubleType")

# Range checks — catch data pipeline bugs
validator.expect_column_values_to_be_between("clicks_7d", min_value=0, max_value=10_000)
validator.expect_column_values_to_be_between("total_spend_30d", min_value=0.0)
validator.expect_column_values_to_be_between("purchase_rate", min_value=0.0, max_value=1.0)

# Uniqueness
validator.expect_column_values_to_be_unique("user_id")

# Set membership — validate categorical values
VALID_TIERS = ["free", "basic", "premium", "enterprise"]
validator.expect_column_values_to_be_in_set("subscription_tier", VALID_TIERS)

# Statistical distribution checks (catch sudden upstream changes)
# These thresholds come from baseline statistics computed on training data
validator.expect_column_mean_to_be_between("clicks_7d", min_value=5.0, max_value=80.0)
validator.expect_column_quantile_values_to_be_between(
    "total_spend_30d",
    quantile_ranges={"quantiles": [0.5, 0.95], "value_ranges": [[0, 500], [0, 5000]]},
)

# Row count (catch truncated pipelines)
validator.expect_table_row_count_to_be_between(min_value=100_000, max_value=50_000_000)

# Freshness: feature_timestamp must be within last 48 hours
validator.expect_column_max_to_be_between(
    "feature_timestamp",
    min_value="2024-07-14T00:00:00",  # parametrize this dynamically in production
    max_value="2024-07-16T00:00:00",
)

validator.save_expectation_suite(discard_failed_expectations=False)
print("Expectation suite saved.")

# ── 3. Run validation via Checkpoint ─────────────────────────────────
checkpoint = Checkpoint(
    name="user_features_checkpoint",
    data_context=context,
    validations=[{
        "batch_request": batch_request,
        "expectation_suite_name": "user_features_suite",
    }],
    action_list=[
        {
            "name": "store_validation_result",
            "action": {"class_name": "StoreValidationResultAction"},
        },
        {
            "name": "update_data_docs",
            "action": {"class_name": "UpdateDataDocsAction"},
        },
        {
            "name": "alert_on_failure",
            "action": {
                "class_name": "SlackNotificationAction",
                "slack_webhook": "https://hooks.slack.com/services/xxx",
                "notify_on": "failure",
            },
        },
    ],
)
context.add_or_update_checkpoint(checkpoint=checkpoint)
result = context.run_checkpoint(checkpoint_name="user_features_checkpoint")

if not result.success:
    failed = [
        r.expectation_config.expectation_type
        for r in result.run_results.values()
        for r in r["validation_result"]["results"]
        if not r.success
    ]
    raise ValueError(f"Data quality check FAILED. Violations: {failed}")

print("All data quality checks passed.")

WITH events AS (
    SELECT *
    FROM {{ ref('stg_events') }}
    WHERE event_ts >= DATEADD(day, -30, CURRENT_TIMESTAMP())
    {% if is_incremental() %}
      AND event_ts > (SELECT MAX(feature_timestamp) FROM {{ this }})
    {% endif %}
),

activity_7d AS (
    SELECT
        user_id,
        COUNT(*)                                                    AS events_7d,
        COUNT_IF(event_type = 'click')                              AS clicks_7d,
        COUNT_IF(event_type = 'purchase')                           AS purchases_7d,
        SUM(COALESCE(purchase_amount, 0))                           AS spend_7d,
        COUNT(DISTINCT session_id)                                  AS sessions_7d,
        AVG(COALESCE(dwell_seconds, 0))                             AS avg_dwell_7d
    FROM events
    WHERE event_ts >= DATEADD(day, -7, CURRENT_TIMESTAMP())
    GROUP BY 1
),

activity_30d AS (
    SELECT
        user_id,
        COUNT(*)                               AS events_30d,
        COUNT_IF(event_type = 'purchase')      AS purchases_30d,
        SUM(COALESCE(purchase_amount, 0))      AS total_spend_30d,
        COUNT(DISTINCT category)               AS category_diversity_30d
    FROM events
    GROUP BY 1
),

purchase_rate AS (
    SELECT
        user_id,
        -- Laplace-smoothed click-to-purchase rate
        (COUNT_IF(event_type = 'purchase') + 1.0)
            / NULLIFZERO(COUNT_IF(event_type = 'click') + 2.0) AS purchase_rate
    FROM events
    GROUP BY 1
)

SELECT
    u.user_id,
    u.country_code,
    u.subscription_tier,
    u.account_age_days,

    COALESCE(a7.purchases_7d, 0) AS purchases_7d,
    COALESCE(a7.spend_7d,   0.0) AS spend_7d,
    COALESCE(a7.sessions_7d,  0) AS sessions_7d,
    COALESCE(a7.avg_dwell_7d,0.0)AS avg_dwell_7d,

    COALESCE(pr.purchase_rate, 0.5)  AS purchase_rate,
    CURRENT_TIMESTAMP() AS feature_timestamp
FROM {{ ref('stg_users') }} u

12. Data Versioning with DVC

Git for data and ML pipelines

DVC (Data Version Control) extends Git to track large files and ML pipelines. It stores data content in remote storage (S3, GCS, Azure Blob) and commits lightweight pointer files (.dvc) to Git. This gives you full reproducibility: git checkout v1.2 followed by dvc pull restores the exact data snapshot used to train that model version.

13. Data Labeling and Annotation

Scaling human judgment for supervised learning

Supervised ML is fundamentally bottlenecked by labeled data quality and quantity. Labeling is often the largest cost in a practical ML project — not compute, not engineering. Understanding the tradeoffs between labeling strategies is essential for shipping models on time and budget.

Labeling Strategies

Crowdsourcing

Platforms: Mechanical Turk, Scale AI, Labelbox, Surge AI. Fast and cheap for high-volume general tasks (image classification, text sentiment). Requires consensus mechanisms (majority vote, inter-annotator agreement) to manage quality.

Best for: image/text classification, NLU tasks with clear guidelines

Expert Labeling

Medical imaging, legal document classification, financial fraud — require domain experts. 10–100x more expensive than crowdsourcing but essential for nuanced decisions where guidelines cannot be written simply.

Best for: medical, legal, scientific, specialized fraud detection

Programmatic / Synthetic

Snorkel (weak supervision via labeling functions), LLM-generated labels, heuristic rules, or simulation. No human annotation required but introduces label noise that must be explicitly modeled.

Best for: bootstrapping, low-budget, LLM-assisted annotation

Active Learning to Reduce Labeling Cost

Active learning selects the most informative unlabeled examples for annotation, rather than randomly sampling. Common strategies: uncertainty sampling (label examples the model is least confident about), query by committee (label examples where an ensemble disagrees most), and core-set selection (label geometrically representative samples). In practice, active learning can reduce labeling cost by 60–80% for the same model performance, at the cost of implementation complexity.

With LLMs, labeling takes a new form: Reinforcement Learning from Human Feedback (RLHF) and Constitutional AI require preference annotation (which response is better?) rather than ground-truth labeling. Tools like Argilla and Scale's RLHF platform are purpose-built for this. The key insight is that relative preference judgments are faster and more consistent than absolute quality ratings — a human can reliably say "response A is better than B" even when they can't articulate an absolute score for either.

Summary & Key Takeaways

Data Infrastructure

  • ✓Data pipelines are 95% of production ML. Invest in them proportionally.
  • ✓Use streaming ingestion (Kafka + Debezium) for latency-sensitive features; batch (Spark) for complex aggregations.
  • ✓Delta Lake or Iceberg on S3 gives you ACID, time travel, and schema evolution at object storage cost.
  • ✓Organize your data lake into raw → staged → curated → features zones with clear ownership and access controls.

Feature Stores

  • ✓Point-in-time correctness is non-negotiable. Feature stores enforce it by construction.
  • ✓Training-serving skew is the most common silent failure mode. A shared feature definition eliminates it.
  • ✓Feast for self-hosted open-source; Tecton for managed streaming; SageMaker/Vertex for cloud-native.
  • ✓Online store (Redis) serves <5ms p99; offline store (Delta Lake) serves historical training data.

Data Quality & Versioning

  • ✓Great Expectations for batch validation; dbt tests for warehouse transforms; Pandera for in-code DataFrame schemas.
  • ✓DVC + Git gives complete data reproducibility. Every model version can be re-traced to its exact data.
  • ✓Define statistical distribution expectations (not just null checks) to catch upstream drift early.

Feature Engineering

  • ✓Rolling window features (7d, 30d) via Spark range windows are the backbone of behavioral ML.
  • ✓Data leakage kills production models. Every feature in training must have been available at the label timestamp.
  • ✓Laplace smoothing on rate features avoids zero-division and reduces variance on sparse users.

From the Field: What Actually Matters

After building feature stores at Meta serving 500k features to ranking models at 2M QPS, the lessons that matter most: (1) Feature freshness has a direct ROI — measure it and invest in streaming pipelines for your highest-value features. (2) The feature registry is the most valuable component — when 200 models share features, discoverability and ownership metadata prevent duplication and data debt. (3) Monitoring the offline-to-online sync lag is as important as monitoring your models — a stale online store is invisible until your model metrics drop. (4) Start simple: a well-organized Delta Lake plus pandas offline joins will take you far before you need a full feature store.
